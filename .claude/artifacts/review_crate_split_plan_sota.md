## 3 — GitHub Actions specifics (C-016/C-017)

a. **`ready_for_review` must be in `types:`.** Confirmed per the plan's own research citation (GitHub docs: default `pull_request` types are `opened, synchronize, reopened` only). C-016 includes it. Correct.
b. **Job-level `continue-on-error: true` reports the job `success` to `needs:`/required-check logic** while still showing a red step badge. Confirmed (research cites Ken Muse + community #15452). **Implication for branch protection**: if `satellite-verify` is ever added as a *required* check while this flag is `true`, the required check becomes a no-op gate — always green regardless of the mirror build's real state. Not a current problem (today's ruleset names no required checks), but WP-05/WP-39 should carry a one-line guard note against ever marking it required pre-flip. Not currently named anywhere. **Low**, advisory.
c. **`github.event.pull_request` is absent (not `false`) on `merge_group`.** C-016's guard (`event_name != 'pull_request' || …draft == false`) short-circuits correctly on event name first. Correct.
d. **Concurrency key across `pull_request` + `merge_group`.** Checked the live file: `verify-deep.yml` uses `group: verify-deep-${{ github.ref }}`, `cancel-in-progress: ${{ github.ref != 'refs/heads/main' }}`. `github.ref` (unlike `github.head_ref`, which the research warns against) **is** populated on `merge_group` (`refs/heads/gh-readonly-queue/...`, unique per queue entry), so the single-slot-lock failure mode the research names does not apply verbatim here. But `cancel-in-progress` evaluates `true` for every `merge_group` ref (≠ `refs/heads/main`) — no explicit carve-out against cancelling an in-flight merge-queue run, which GitHub's own merge-queue docs (cited in research) warn can stall/corrupt the queue. **Medium** — the plan's C-016 asserts the group "is valid" without adopting the defensive `cancel-in-progress: false` for `gh-readonly-queue/*` the research spelled out. Fix: add that one line when `merge_group:` lands.

## 4 — pytest/xdist specifics (C-012/C-013)

- **`--strict-markers` interplay**: verified empirically — every custom mark actually used across `test/tests/*.py` today is `divergence`, `requires_tty` (both already in `pyproject.toml`'s `markers=[...]`), and `xdist_group` (built into pytest-xdist, self-registering). No unregistered mark exists that `--strict-markers` would newly break. **Confirmed safe.**
- **`-m smoke` + `--dist loadgroup` + `xdist_group` interaction**: pytest-xdist's own docs (fetched) state ungrouped tests distribute as `--dist load`; they do not document whether a `-m`-deselected group-mate gets pulled back in. Pytest-core mark deselection runs in `pytest_collection_modifyitems` before xdist's scheduler builds its work queue from the final `session.items`, so deselected group-mates are not resurrected — consistent with this repo's own live `xdist_group("patch_global_slot")` usage in `test_patches.py`/`test_frozen.py` never needing every member marked together. **Not independently documented**, but the plan sidesteps the question entirely and correctly: C-013 puts the new `test_patch_smoke.py` in **no** `xdist_group` at all ("uses no `xdist_group` and never touches the … global patch descriptor slot"). **Low/no live risk**, given the design already avoids the scenario.

## 5 — Cargo specifics

a. **`members = ["crates/*"]` with a non-crate directory present.** Empirically reproduced in a throwaway workspace: Cargo **errors hard** — `error: failed to load manifest for workspace member '.../not_a_crate' … Caused by: failed to read '.../not_a_crate/Cargo.toml' … No such file or directory`, exit 101. It does **not** silently skip. Not a live problem today (`crates/` holds only crate dirs), but worth noting as a hard constraint: any future scratch/doc directory placed directly under `crates/` (not nested inside a crate) breaks every build. No plan text calls this out; **Low**, informational.
b. **`cargo test --doc -p <crate>` for a `compile_fail` doctest** — confirmed as the correct, and only, invocation shape (nextest doesn't run doctests per the research citation); plan uses this exact command (DEC-14, C-053, Testing strategy). Correct.
c. **`cargo metadata` needing submodules initialised** — confirmed by the research (reproduced: `--no-deps` succeeds without submodules, full metadata fails on an uninitialized `external/sigstore-rs`). C-019's step 3 uses full `cargo metadata --format-version 1` (not `--no-deps`) to get reverse-dep counts for hub detection — correctly matches the research's guidance that the *hub* half needs full metadata; the Parallelization section's worktree bootstrap (`git submodule update --init`) covers the precondition. **Correct, no gap.**
d. **`cargo tree -i <crate>` when the crate is absent from the satellite workspace (C-018).** Empirically reproduced in *this* repo: `cargo tree -i <bogus>` → `error: package ID specification 'X' did not match any packages`, exit 101 — **and**, before the submodule was initialized, the exact same command failed with the exact same exit code 101 for a completely unrelated reason (`failed to read external/sigstore-rs/Cargo.toml`). C-018's stated pass condition is "`cargo tree -i <crate>` … must match nothing" with no stated detection mechanism (stderr-text match vs. bare exit code). Because C-018 sequences `cargo build --workspace` *before* the closure check, a broken/unresolvable mirror workspace is caught earlier — this substantially reduces the blast radius. But the closure check itself, as specified, is still exit-code-shaped rather than message-shaped, which is exactly the "tolerated range of exit codes" anti-pattern this project's own `quality-core.md` names as a Block-tier verification-honesty smell. **Medium** — fix: assert on the literal stderr text `did not match any packages`, not the exit code alone.

## 7 — Ecosystem precedent for the batch shape

ruff (`ty` crate extractions, `ruff_cli` split) and uv (`uv-workspace`, `uv-test`, and "dozens of small, titled PRs across years" per the research) both land crate extractions as **independent PRs merged to `main` over time**, not as one serialized N-step chain on a single long-lived branch. This plan's 29-wave-deep critical path (WP-01 → … → WP-37 → WP-38) runs entirely on one branch (`evelynn`) before any of it lands on `main`. **Advisory only** (per task framing): the owner's long-lived-branch-per-worktree convention is fixed (CLAUDE.md worktree table; MEMORY.md's "long-living feature branch" pattern is established owner doctrine), and the practical rebase risk is lower than the general OSS case because no other agent works `evelynn` concurrently. The residual risk is calendar, not concurrency: a 29-wave chain gated behind sequential `/hex-execute` batches means `main` can drift underneath it for the plan's full duration, and the eventual `/hex-finalize` rebase is against however far `main` has moved by then — worth a rebase checkpoint between batches (e.g. B4, B8) rather than only at the end, which the plan does not currently schedule. **Low**, advisory.
