# Research: Test-tier operability and cost — cache hit rates, provenance, remote cache, migration cost

## Metadata

- **Date:** 2026-09-22
- **Domain:** testing
- **Triggered by:** hex-architect ADR on test-suite speed tiers (axis: operability & cost)
- **Expires:** 2027-03-22

## Direct Answer

Fix provenance first; don't port the suite to Rust to solve this problem.

1. **The premise is confirmed and quantified, not hypothetical.** bazel-remote's own Prometheus metrics (7-day window, MEASURED) show an Action-Cache GET hit rate of **~1.5 %** (359 hits / 22,947 misses) against a Content-Addressable-Storage hit rate of **~99.4 %** (339/341) on the same instance — the exact signature of an action key that churns every build while the underlying bytes mostly don't. A dedicated repo measurement (`plan_bazel_build_adoption.md` DX-97, MEASURED) makes the mechanism explicit for the acceptance lane specifically: an unchanged tree replays all 181 `sh_test` targets from cache in **1 s**; rebuilding `test/bin/ocx` — which happens on every commit, because `commit_timestamp`/`describe`/`GITHUB_RUN_ID` are baked into it unconditionally — re-executes **all 181** in **1421 s** (cold), an **8.9×** blowup that breached the ADR's own 50 % abort ceiling and was overruled by the owner on 2026-09-22.
2. **Placeholder provenance for the test-flavor binary (option b) is the cheap, reversible, already-half-built fix.** `crates/ocx_cli/build.rs` already gates `build_timestamp` on `CI` presence; extending the same pattern with a `__OCX_TESTING_STABLE_PROVENANCE`-style seam (project convention for test-only seams, `subsystem-tests.md`) to freeze `describe`/SHA/`commit_timestamp`/`GITHUB_*` for the binary under acceptance test would make `bin/ocx*`'s content — and therefore the Bazel action-cache key for all 181 targets — a function of source and toolchain, not of commit SHA. **Risk, found by grep, not assumed:** 5 modules (`test_config.py`, `test_config_test.py`, `test_install_libc.py`, `test_self_update.py`, `test_update_check_throttle.py`) reference version/build-provenance strings and need a carve-out or an escape hatch reading real provenance.
3. **Bazel-native stamped `rust_binary` (option c) is not free — it inherits a documented correctness trap, not just a caching one.** The repo's own prior research (`research_bazel_cache_trust_boundary.md` finding #24, already written 2026-09-21) shows that Bazel's `--workspace_status_command` volatile/stable split means a naively-stamped, remote-cacheable target can serve **commit A's embedded git SHA on a build of commit B** — silently wrong metadata, not just a slow build. This is real engineering (stable-vs-volatile key discipline, or a `--nostamp` test profile split from the stamped `dist` profile) and is not obviously cheaper than option (b) for the acceptance lane, which isn't Bazel-built today anyway (it's a plain Taskfile/cargo build Bazel treats as an opaque file input).
4. **Sharing the CI-written cache with local reads (option d) is already the deployed design**, not a proposal — `.bazelrc` gives every non-`main`-push lane (including local dev) a read-only credential against the same `bazel-cache.ocx.sh` instance the `main`-push lane writes to. The 1.5 % AC hit rate above **is that shared-cache reality**, measured, and it's bad because of provenance churn, not because of the read/write split. **One new trust-boundary fact this research adds**: the 2026-09-22 ADR amendment dropped the `local`/`external` tags from acceptance `sh_test` targets to enable caching — which means acceptance-test Action-Cache entries are now reachable through the **shared remote tier** for the first time. The existing trust-boundary research (findings #1–17) assumed acceptance tests stayed `local`-tagged and therefore out of remote-cache scope ("already safe by construction," finding #10); that assumption is now stale and the poisoning threat model (a bad main-branch CI run silently serving a wrong acceptance-test verdict to every PR reader) newly applies to this lane. Worth a short follow-up note in that research file, not a new one.
5. **Porting ~3,884 pytest cases across 181 modules to Rust `rust_test` (option: fan-out migration) is the expensive option and doesn't address the root cause on its own** — see § 3 for the (explicitly ESTIMATED) cost, and § 4 for why the existing Grafana surface can't yet prove either "faster" or "didn't leak" for a tiered gate.

## 1. Current cache effectiveness — measured

### 1a. Server-side Action Cache vs CAS hit rate (bazel-remote Prometheus metrics, MEASURED, 7-day window, queried 2026-09-22)

| kind | method | status | count (increase, 7d) |
|---|---|---|---|
| `ac` | `get` | `hit` | 359 |
| `ac` | `get` | `miss` | 22,947 |
| `cas` | `get` | `hit` | 339 |
| `cas` | `get` | `miss` | 2 |

- **AC hit rate ≈ 1.54 %** (359 / 23,306). **CAS hit rate ≈ 99.4 %** (339 / 341).
- `up{job="bazel-remote"}` = 1 for the full 7-day window (52/52 samples) — the metric feed itself is reliable for this window, not a gap artifact.
- Current server-side disk cache size: 1,291,444,224 bytes (~1.29 GB).
- This is **instance-wide** (every lane: `bazel:test:unit`, `bazel:test:accept`, `bazel:lint`, etc., every reader: CI + local dev), not scoped to the acceptance lane alone — but the AC/CAS split is exactly the signature the provenance-churn hypothesis predicts: actions rarely match a previous *recipe* (their key), but the *content* referenced by those recipes (source files, unchanged toolchain outputs) is still mostly identical.
- Query used: `sum by (method, status, kind) (increase(bazel_remote_incoming_requests_total[7d]))` against the `Prometheus` datasource (uid `prometheus`), instant query at `now` (2026-09-22).
- Source: `.bazelrc:60-63` (`--remote_cache=https://bazel-cache.ocx.sh/v1`, `--remote_upload_local_results=false` except the main-push lane), corroborated by `bazel_remote_http_cache_hits`/`_misses` raw gauges (both read 0 at instant-query time, consistent with the metric being a counter sampled between scrapes rather than contradicting the `increase()` figures above).

### 1b. Acceptance-lane cache behavior (MEASURED, `plan_bazel_build_adoption.md` DX-97 row, and `test/bazel.bzl` module docstring)

One tree, one host, one compose stack, three wall clocks measured in this order:

| Run | Wall clock | Result |
|---|---|---|
| `task test:parallel --force` (pytest-xdist baseline) | **160 s** | `3723 passed, 156 skipped, 5 xfailed in 154.46s` |
| `task bazel:test:accept`, cold | **1421 s** | `Executed 181 out of 181 tests`, 3884 cases (= `test/SUITE_FLOOR`) |
| Same task, unchanged tree | **1 s** | `Executed 0 out of 181 tests: 181 tests pass` (bazel-reported elapsed 0.272 s) |

- Cold run is **8.9×** the pytest-xdist baseline, **+788 %** against the ADR's own **+50 %** abort ceiling — the abort condition was **met and overruled** by the owner on 2026-09-22 (`adr_bazel_build_adoption.md` changelog, same date).
- **Selection granularity, also measured**: an edited module executes **5 of 181** (the module itself plus 4 sibling-sweeping modules whose own source reads every other module's source — `test_smoke_coverage`, `test_no_crate_path_assertions`, `test_patch_global_slot`, `test_doc_scripts_publish`, per `CLAUDE.md` § Bazel and `test/bazel.bzl`); a docs-only commit executes **0** (0.23 s).
- **Binary-content sensitivity, also measured**: rebuilding `test/bin/ocx` without touching any `test/**` file re-executes **all 181** (1425 s) — this is the target-count blast radius of a provenance-only content change, isolated from any real test-relevant source change. After the binary is restored to its prior bytes, `bazel test //test:all` reports `Executed 0 out of 181 tests` in **2 s** — served by `--disk_cache` (a fresh-server tier), not the local action cache, since the mutated run had just overwritten every one of that cache's 181 entries.
- **What this means for "does the acceptance lane pay the 1421 s cost in practice today"**: because `describe`/SHA are baked into `test/bin/ocx*` on *every* commit (not gated by `CI`, see § 2), and every ordinary commit changes the git SHA, **the common case for any commit that changes code is the cold 1421 s path, not the 1 s cached path.** The 1 s and 0.23 s cases are real but narrow: identical-tree reruns (flaky-test retries, CI re-dispatch of an unchanged PR) and docs-only commits.

- `verify-deep.yml` median: **3407 s** (superseding an earlier estimate of 3347 s carried in `.agents/memory/hex.md`).

### 1d. Tempo telemetry — what exists, what doesn't (MEASURED where stated)

- `service.name="ocx-tests"` (the pytest/junit2otlp feed the `ocx-test-time` dashboard, uid `ocx-test-time`, reads) is live and populated: **365,449 spans inspected** in the 7-day window queried, split by `span.ocx.source` (`ci`/`local`), `span.ocx.suite`, `span.ocx.os`, `span.ocx.ci.run_id`. This is real, usable per-test-case wall-clock telemetry, not a placeholder — the dashboard's own doc string calls `run_id="e2e"` a placeholder for the *local* case only, which the `source` variable already discriminates.
- `service.name="bazel-build"` (the BEP→OTLP push named in `adr_bazel_build_adoption.md` § A5) also exists in Tempo, but is **new and sparse**: in the 7-day window, non-empty samples appear only in roughly the last ~2 days, consistent with the "run the acceptance suite as cached Bazel targets in verify and CI" commit (`18dca451`, in this repo's recent log) landing during the window.
- **Data-quality flag, not yet root-caused**: every `bazel-build` trace sampled via `search_tempo_traces` in the last ~72 h shows `errorCount` within 1 of `spanCount` — e.g. `spanCount: 291, errorCount: 290`; `290/289`; `281/280`; `323/322`. That is ~99.7 % of spans in every sampled trace carrying an error status. This is either a real, systemic problem in every recent Bazel invocation (implausible given `task verify` phase 2 and `verify-basic.yml`'s `smoke` job are both green per the commit log) or — more likely — an instrumentation artifact in the BEP→OTLP pusher (e.g. spans defaulting to error status unless explicitly marked OK). **Unverified which; flagged as a blocker to trusting this feed for anything, including a future cache-hit/miss panel**, before it's relied on for a tiered-gate operability story.
- **No cache-hit/miss attribute was confirmed present on `bazel-build` spans** in the samples pulled (`list_tempo_attribute_names` returned empty for `scope=span` with no time range accepted by that tool, and the trace samples above only surfaced `service.name` in the truncated span attributes shown). `adr_bazel_build_adoption.md` § A5 states cache hit/miss "from the BEP→OTLP push" as part of the **Green** criterion for its own telemetry gate — it is not yet demonstrated *here* that the field is populated and query-able; this should be checked directly against the exporter's field list before the dashboard is cited as proof of hit rate.
- **No dedicated bazel-remote/BES-specific Grafana datasource** exists beyond the two already wired: `Prometheus` (default, scrapes bazel-remote's own `/metrics`, confirmed § 1a) and `Tempo`. No Loki datasource is configured, so no log-based corroboration is available.

## 2. Provenance mechanism — what actually changes per build (MEASURED from source)

`crates/ocx_cli/build.rs` (read in full):

- `commit_timestamp(true)` — **unconditional**, every build, every platform. Stable across rebuilds of the *same* commit (vergen-gix reads it from the commit, not wall-clock "now"), but changes on every new commit.
- `.describe(true, true, None)` with `.dirty(false)` — **unconditional**. Embeds git describe (tags + short SHA) with a dirty marker keyed on *tracked*-file modification only (deliberately not untracked, so the release job's `dist-manifest.json` redirect doesn't self-report dirty). Changes on every new commit.
- `build_timestamp(in_ci)` where `in_ci = std::env::var_os("CI").is_some()` — **gated**. Off locally (keeps local incremental builds stable), on in CI (embeds real "now" wall-clock — changes on *every* CI build of the *same* commit, including a re-dispatch with no new commits).
- `GITHUB_RUN_ID`, `GITHUB_SHA`, `GITHUB_REF`, `GITHUB_WORKFLOW`, `GITHUB_SERVER_URL`, `GITHUB_REPOSITORY` — passed through **unconditionally** whenever present (`pass_through_env`). `GITHUB_RUN_ID` alone guarantees every CI invocation embeds a unique value, so **no two separate CI runs of the identical commit can ever produce a byte-identical binary**, independent of `build_timestamp`.

Net effect: locally, two builds of the same untouched commit *can* be byte-identical (only `describe`/`commit_timestamp` apply, both stable per-commit). In CI, no two builds — even of the same commit re-run — are ever byte-identical, because of `build_timestamp(true)` and `GITHUB_RUN_ID`. This matches § 1b's observation that the *only* cache-hit path measured was "unchanged tree, same invocation" (i.e., a single `bazel test` run reading its own just-written cache), not "second CI run of the same commit."

**This is the direct target for option (b).** A `__OCX_TESTING_STABLE_PROVENANCE`-gated branch in `build.rs` — following the repo's own established test-seam convention (`subsystem-tests.md` § Test-Only Seams, `__OCX_*` double-underscore prefix, `cfg(any(test, feature = "__testing"))`-equivalent gating for a build script) — freezing `describe`/`commit_timestamp`/the `GITHUB_*` passthroughs to fixed placeholder strings for the specific binary the acceptance suite builds and tests against, would make that binary's bytes a pure function of source + toolchain, matching the same stability the 34 Bazel-native `rust_test` targets already have (WP-12, MEASURED: "run 2 fully cached over 34 targets").

## 3. Cost model of the options

| Option | Expected AC hit-rate effect | CI-minutes effect | Operational burden |
|---|---|---|---|
| **(a) Status quo** | ~1.5 % (MEASURED, § 1a), and the acceptance lane specifically pays the cold 1421 s path on almost every code-changing commit (§ 1b) | Full 1421 s cold acceptance run on essentially every PR that touches code; only docs-only / identical-tree reruns are cheap | None — already shipped, already the ADR-accepted (overruled-abort) baseline |
| **(b) Placeholder provenance for the test-flavor binary** | High — `bin/ocx*` content stops varying with commit SHA; cross-commit and cross-CI-run AC hits become reachable for the first time, matching the 34-target unit-test lane's already-measured full-cache-hit behavior (WP-12) | Directly proportional to how often source-unrelated churn was the *only* reason for a miss — not measured here, but § 1b's "rebuild binary only, no `test/**` change → all 181 re-execute" isolates exactly this variable and shows it is the dominant one for the binary-content axis | Low: one build-script seam, following an existing project convention; **named risk**: 5 modules (`test_config.py`, `test_config_test.py`, `test_install_libc.py`, `test_self_update.py`, `test_update_check_throttle.py`, found by grep) reference version/provenance content and need either a carve-out (run with real provenance) or updated assertions |
| **(c) Bazel-native stamped `rust_binary` for `ocx`** | Same theoretical ceiling as (b), but only if workspace-status stable/volatile keys are handled correctly | Larger, unscoped change: moves `ocx_cli` compilation itself onto Bazel, which it is not today (today's acceptance binary is a plain Taskfile/cargo build Bazel treats as an opaque file dependency) | **Higher** — inherits a documented correctness trap (existing research finding #24: a remote-cache hit on a volatile-status-stamped target can silently serve one commit's embedded git SHA on another commit's build — wrong, not just slow) that requires deliberate stable/volatile key discipline or a `--nostamp` test profile split from the stamped `dist` release profile. Not clearly cheaper than (b) for this specific problem. |
| **(d) Share CI-written cache with local reads** | Already the measured § 1a reality (~1.5 %, instance-wide, all readers) | N/A — already deployed | **Already shipped** (`.bazelrc:60-63`, main-push-only write credential, every other lane read-only). **New finding**: the 2026-09-22 ADR amendment removed the `local`/`external` tags from acceptance `sh_test` targets specifically to enable caching, which newly exposes acceptance-test AC entries to the shared remote tier. The existing `research_bazel_cache_trust_boundary.md` (dated 2026-09-21, one day earlier) assumed acceptance tests stayed `local`-tagged and out of remote-cache scope (its finding #10: "already safe by construction"); that assumption is now stale for this one lane. The poisoning threat model in findings #4/#6/#12 (a flaky or compromised trusted CI writer silently poisoning every reader) now applies to acceptance-test verdicts, not just build outputs. Recommend a short addendum to that file rather than new research, since the mitigations it already lists (main-push-only write, generation-salted `--remote_instance_name`, PUT-outside-window alerting per `adr_bazel_build_adoption.md`'s Risks section) already cover this lane too — they just weren't scoped to include it explicitly. |

### Cost of the fan-out port-down migration (ESTIMATED — no measured data exists for this option; treat every number below as a rough planning bound, not a commitment)

- Current acceptance surface: **181 modules**, **3,884 test cases** (`test/SUITE_FLOOR`, MEASURED). The task prompt's figure of "189 modules" does not match the current repo state (181, confirmed by `ls test/tests/test_*.py | wc -l`); the taskfile's own commit history (`WP-36`) already records a prior "172" count as stale, corrected to 181 — treat any module count as needing a fresh count at execution time, not carried forward from a plan artifact.
- **Classification pass** (mechanical, sonnet-tier): scanning 181 modules to bucket them by portability (pure logic vs. fixture-heavy vs. the ~20 modules already named in `test/bazel.bzl`'s docstring as reading across a package boundary — `target/release/ocx_schema`, `crates/**`, `website/src/docs/**`, `test/doc_scripts/**`) is cheap and batchable — call it low-single-digit hours of agent wall-clock at reasonable concurrency, not a cost driver.
- **Porting pass** (the real cost, ESTIMATED): this is not a mechanical translation. The acceptance suite drives a live `docker compose` stack (zot + registry:2 + the Sigstore stack), asserts on CLI stdout/stderr/exit-code contracts, and uses pytest fixtures/parametrization idioms with no 1:1 Rust equivalent — CLAUDE.md's own model-routing table classifies "multi-subsystem, async/concurrency, OCI/wire-format or serializer work" as **non-mechanical, opus-tier**, and a fixture-heavy CLI-driving integration test fits that description directly. A rough per-module bound of 30–90 minutes of agent wall-clock (write, contract-first stub, implement, review-fix loop) is plausible for the more mechanical third of the suite and a significant underestimate for the ~20 cross-package-reading modules, which would each need their own dependency-closure design work first. At **181 modules ÷ 3–4 concurrent workers** (the plan's own stated cap, driven by `cargo jobs=12`/RAM and the single-acceptance-suite `flock`), even the low end (30 min/module) totals **~45–90 hours of wall-clock agent time**, before counting cross-model review passes, flakiness triage against a live compose stack under concurrent Rust test execution (a new failure mode this suite has never had to handle), or the fact that `--local_test_jobs=1`/`exclusive` exists today specifically because *one* compose stack cannot serve concurrent callers — a Rust-native reimplementation inherits that same constraint unless the fixtures are also redesigned for per-test port allocation, which `test/bazel.bzl`'s docstring explicitly calls "a test-suite redesign outside this ADR."
- **Ongoing cost after migration, not just during it (ESTIMATED, but the mechanism is certain)**: a partial port leaves **two test languages and two fixture stacks** live simultaneously for however long the migration takes, and every acceptance-relevant feature change during that window needs both suites updated — a maintenance tax with a real end date only if the migration is driven to full cutover and the Python suite is deleted. A stalled or abandoned partial migration is strictly worse than either endpoint (paying both the Python-suite cost from option (a)/(b) *and* a partial, less-trusted Rust suite).

**Conclusion on cost**: the migration's per-unit cost (tens of hours, non-mechanical) is far larger than option (b)'s (one build-script seam, a handful of hours including the 5-module carve-out), and it does not address the root cause identified in § 1–2 on its own — a ported Rust test suite built with the same unstable provenance would have exactly the same cache-key churn problem, just in a different build system. The migration is only justified if (b) is tried and measured, and the residual miss rate after (b) is still dominated by something *other* than provenance (e.g. the ~20 modules with genuine undeclared cross-package inputs, which are a `test/bazel.bzl`-documented, separate problem from binary-content churn).

## 4. Operability of a tiered gate — what the existing telemetry can and cannot prove

**Can show today (MEASURED, § 1d):** per-test-case wall-clock time, split by `source` (ci/local), `suite`, `os`, and `run_id`, via the `ocx-test-time` dashboard (uid `ocx-test-time`, panels 1/6/7/8/9/10/12) reading real, populated `service.name="ocx-tests"` Tempo spans. This is sufficient to show a **before/after wall-clock trend** for the inner loop, once enough post-change data accumulates (the dashboard's 7-day retention window means a change needs to run for most of a week before a trend is visible against noise, and the panel-1 caveat — "sum of each test case's own reported duration, not wall clock" — means a genuinely parallel-vs-serial comparison needs panel 9's per-run series, not panel 1's aggregate).

**Cannot show today, and would need new work:**

1. **Cache hit/miss is not confirmed queryable from Grafana at all.** The `bazel-build` Tempo feed (the one place this could live, per `adr_bazel_build_adoption.md` § A5's own Green criterion) is new, sparse, and — per § 1d's flagged anomaly — has an unverified, possibly-systemic error-status data-quality problem in every sampled trace. Bazel-remote's own Prometheus metrics (§ 1a) *do* give an instance-wide hit rate, but not a per-target or per-lane breakdown, so they can confirm "the cache is or isn't working overall" but not "the acceptance lane specifically improved after change X" without a lane-scoped label that doesn't currently exist on those metrics either.
2. **No escape-rate signal exists.** The dashboard's `suite`/`source`/`os`/`run` variables let you filter to one tier's results, but there is no shared join key (e.g. commit SHA) across a fast inner-loop run and a slower pre-merge run of the *same* commit — `ocx.ci.run_id` is a GitHub Actions run identifier, one per workflow dispatch, not a commit identifier, so two different workflows (say, a fast `bazel:test:unit`-only lane and the full `bazel:test:accept` lane) on the same commit have different, uncorrelated run IDs today. Computing "a test that passed in the fast lane and failed in the slow lane, same commit" would require either adding a commit-SHA span attribute both lanes share, or a Grafana/Tempo query that joins on it — neither exists yet.
3. **Before trusting either gap-filling addition**, the § 1d error-status anomaly on the `bazel-build` feed should be root-caused first — building an escape-rate or cache-hit panel on top of a span feed where ~99.7% of sampled spans already carry an unexplained error status is exactly the "unchecked green" failure mode (a check whose passing state is indistinguishable from a check that never ran correctly).
