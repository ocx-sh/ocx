# Research: ocx crate split — error layering & lockstep-consumer compatibility

## Metadata

**Date:** 2026-09-06
**Domain:** cli
**Triggered by:** /hex-architect crate-split-and-verify-tiers
**Expires:** 2027-03-06

## Direct Answer

Keep per-crate `thiserror` enums composed via `#[source]`/`#[from]` at boundaries — do not adopt `snafu` or a shared leaf-error crate. Ocx's existing three-layer pattern (wrapper struct + discriminant "kind" enum, `quality-rust-errors.md`) already solves the one documented failure mode that pushed GreptimeDB to `snafu` (two call sites collapsing into one source type), so the migration snafu would justify does not apply here. Move `ClassifyExitCode`/`ClassifyErrorKind` and the `try_classify` downcast ladder out of `ocx_lib::cli` into `crates/ocx_cli` — this matches both the canonical Rust CLI guidance (library stays exit-code-agnostic) and the addendum's own ruling that a reusable signing crate consumed by grimoire must not carry ocx's exit-code vocabulary; it also retires the `cli`-module-vs-`ocx_cli`-crate naming collision as a side effect. Do not add a `cargo-hakari` workspace-hack now: it is a build-time optimization only, and its own documentation flags the exact hazard ocx would create — a lockstep path/git consumer (ocx-mirror, grimoire) silently inherits whatever features the hack crate forces on, which is precisely the `preserve_order` fragility the mirror's `Cargo.toml` already hand-manages. The ecosystem-tier contract must say, as hard mechanical fact rather than convention: `[patch.crates-io]` does not travel across a path/git boundary and must be re-declared verbatim by every lockstep consumer; Cargo's feature unification for a path dependency runs inside the *consumer's* workspace graph, not the producer's, so any producer feature whose absence silently changes behavior (again, `preserve_order`) is a named contract line, not an implicit inheritance; and vendoring the full producer tree as a git submodule is a hard requirement, not a style choice, because Cargo cannot resolve a transitive path dependency across two separate git repositories.

## Key findings

1. **`thiserror`'s documented failure mode at scale is exactly the one call-site-discrimination problem, and ocx's three-layer pattern already avoids it.** GreptimeDB's own account: "you cannot define two error variants from the same source type… performing some I/O operations, you won't know whether an error is generated in the write path or the read path" ([greptime.com](https://greptime.com/blogs/2024-05-07-error-rust)). Ocx's `quality-rust-errors.md` three-layer pattern (`Error → PackageError{identifier, kind} → PackageErrorKind`) discriminates by *wrapper variant*, not by relying on `From<std::io::Error>` alone — `crates/ocx_lib/src/error.rs:29-47` shows the same discipline already: `InternalFile` vs `LayerLayout` vs `SymlinkWalk` are three distinct wrapper variants over what would otherwise collapse to one `io::Error` `From` impl, specifically to keep classification correct (comments at `error.rs:36-47` explain this in exactly GreptimeDB's terms). The ADR does not need to import snafu's mechanism; it needs to keep applying the pattern it already has as new module-local error enums are drawn into crate boundaries.
2. **`snafu`'s core mechanical advantage — context attached at the call site rather than the type — has a real cost cited in the same source**: it requires a context-selector struct per fallible call site and is justified specifically when a crate's own team decided per-crate error types were mandatory and neither `thiserror` nor `anyhow` alone met that bar ([greptime.com](https://greptime.com/blogs/2024-05-07-error-rust); corroborated by [Leapcell's comparison](https://leapcell.medium.com/rust-error-handling-compared-anyhow-vs-thiserror-vs-snafu-597383d81c25)). Ocx already has per-crate (per-module) error types as a design decision; the open question was only whether the *composition* mechanism holds up, and finding 1 shows it does for the one concrete failure mode in evidence.
3. **The canonical guidance is that exit-code classification is binary-crate code, not library code** — the Rust CLI Book's exit-code chapter frames this as "standardized exit codes defined in a dedicated module that your binary can use while keeping your library agnostic to exit codes" ([rust-cli.github.io](https://rust-cli.github.io/book/in-depth/exit-code.html)). Ocx's own `quality-rust-exit_codes.md` states the same intent ("Use free function, not trait method… keeps dep direction clean") but the *implementation* today places `ClassifyExitCode`, `ClassifyErrorKind`, and the 166-reference `try_classify` downcast ladder inside `ocx_lib::cli` (`crates/ocx_lib/src/cli/classify.rs`), the library — not `ocx_cli`, the actual CLI binary crate. This is the one place ocx's practice and its own documented intent currently disagree, and it is also the addendum's own docket item (["may a reusable crate depend on the exit-code leaf?"](#) in the discussion dossier) — both external convention and the internal grimoire constraint point the same direction.
4. **Cargo's `[patch.crates-io]` table is scoped to the resolving workspace root and does not travel across a path or git dependency boundary.** This is not a convention ocx-mirror chose; it is documented Cargo behavior, and ocx-mirror's own `Cargo.toml` comment already states the consequence in the imperative ("Patch tables only apply at the consuming workspace root — they do NOT travel with path or git dependencies — so they are re-declared here, pointing into the nested submodules of `external/ocx`"). Every future lockstep consumer (grimoire) needs the identical re-declaration, naming its own path into its own submodule checkout.
5. **Cargo feature unification for a path dependency happens inside the *consuming* workspace's own dependency graph, not the producer's** — the resolver's `feature-unification` setting "is only honored in the top-level package or workspace and is ignored in dependencies, because feature-unification is an inherently global decision" per that workspace ([Cargo Book — Dependency Resolution](https://doc.rust-lang.org/cargo/reference/resolver.html); RFC context at [3692-feature-unification](https://rust-lang.github.io/rfcs/3692-feature-unification.html)). Concretely: `ocx_lib`'s `serde_json = { features = ["preserve_order", "raw_value"] }` in the producer's own `Cargo.toml` has **zero effect** on ocx-mirror's build unless ocx-mirror's own `Cargo.toml` separately activates `preserve_order` — which is exactly why the mirror's manifest carries an 8-line comment doing precisely that (`crates/../ocx-mirror/Cargo.toml:55-61`, read directly) and warns "Inherited today only through Cargo feature unification with `ocx_lib`; declared here so it survives an upstream change." This is not defensive-but-optional; it is the only thing preventing a silent correctness regression (alphabetized index-root JSON, hash mismatch) the day that inheritance path changes.
6. **`cargo-hakari` workspace-hack crates are a build-time optimization, not a correctness mechanism, and they actively worsen ocx's exact lockstep-consumer situation if adopted carelessly.** Per hakari's own docs: "Downstream users that import your crate directly from your repository, rather than from the registry, are going to import dependencies from the checked in workspace-hack" ([docs.rs/cargo-hakari](https://docs.rs/cargo-hakari/latest/cargo_hakari/about/index.html)) — unmitigated, this forces every feature the hack crate turned on for internal build-time reasons onto ocx-mirror and grimoire too, the identical hazard class as finding 5 but self-inflicted instead of upstream-inherited. Hakari's own mitigation is a `[patch]` entry at the consumer, i.e. the same manual-declaration discipline ocx-mirror already practices for `preserve_order` — so a workspace-hack crate is adoptable later, but only under the same "every feature a lockstep consumer needs is named at the consumer" discipline, never assumed.
7. **Cargo cannot resolve a transitive path dependency across two separate git repositories on its own** — "Cargo scans the whole monorepo to find packages for resolving dependencies, but it doesn't when searching for transitive path dependencies," which breaks the moment "an external crate tries to import from the git repository" pointing only at a subdirectory ([rust-lang/cargo#14946](https://github.com/rust-lang/cargo/issues/14946); general background at the [Cargo Book — Workspaces](https://doc.rust-lang.org/book/ch14-03-cargo-workspaces.html)). This is the mechanical reason ocx-mirror vendors the *entire* ocx tree as a git submodule (`external/ocx`) rather than pointing a `git = "…"` dependency at `ocx_lib` inside the ocx repository directly — it is not a stylistic choice available to relax later; a bare git dependency into a subdirectory of a multi-crate workspace is not reliably resolvable the way a full local submodule checkout is.
8. **Two genuinely different models exist for a multi-crate producer serving external consumers, and ocx has already chosen the less common one on purpose.** rust-analyzer publishes independently versioned `ra_ap_*` crates to crates.io ([crates.io: ra_ap_ide](https://crates.io/crates/ra_ap_ide), [ra_ap_syntax](https://crates.io/crates/ra_ap_syntax/0.0.226/dependencies)) — a real interface-tier stability contract, each crate independently semver'd. Ocx's *ecosystem* tier is deliberately the other model: unversioned lockstep path-into-submodule, explicitly "not promoted to interface" by a lockstep consumer per the discussion dossier's Decisions. This is a legitimate, load-bearing choice (avoids committing to per-crate semver before the crate map has stabilized) but the ADR should record *why* it rejected the rust-analyzer alternative, not merely that it did, since a future maintainer reading only the crate map will otherwise reach for crates.io publishing as the "obvious" fix the first time lockstep coordination gets painful.
9. **`unreachable_pub` is a real compiler lint, not a clippy lint, and it directly targets the growth mode this split will create** — "a guarantee that each `pub` item will be in fact visible outside its crate" ([rustc book — allowed-by-default lints](https://doc.rust-lang.org/rustc/lints/listing/allowed-by-default.html)). Ocx's own `rust-cargo.md` already carries this as LINT-11, staged into `[workspace.lints.rust]` only once its ratchet count hits zero — the crate split is the event that will make this lint's backlog non-trivial for the first time (today one crate has one visibility boundary; the split creates dozens), so the ADR should treat LINT-11's ratchet as an active dependency of the split's sequencing, not a pre-existing, already-settled line item.
10. **Sealed traits via a private supertrait remain the only shipping mechanism to close a trait to external `impl`s; the language-level replacement is not usable yet.** wasmtime's `GcRef` states plainly it "may not be implemented for any types outside of the wasmtime crate" ([wasmtime::GcRef](https://docs.wasmtime.dev/api/wasmtime/trait.GcRef.html)) using the private-supertrait technique. RFC 3323's `impl(crate)` restriction is real and actively being tested on nightly as of 2026-08-10, explicitly "a more direct and concise way to express the same restriction" with better compiler diagnostics ([Inside Rust](https://blog.rust-lang.org/inside-rust/2026/08/10/call-for-testing-impl-and-mut-restrictions/)) — but it is nightly-gated, has open syntax questions, and carries no stabilization date. For any crate-boundary trait the ADR wants to seal (candidates per `arch-principles.md`'s Strategy row: `IndexImpl`, `OciTransport`), use the private-supertrait pattern now; do not wait on or design around RFC 3323.
11. **A large workspace has a documented, tooled failure mode where individual crates silently drop out of `[workspace.lints]` inheritance**, motivating a purpose-built checker (`cargo-workspace-lints`) precisely because "in a large codebase with many people independently adding crates, you can't guarantee that no one else will accidentally add a crate without" the `lints.workspace = true` line ([users.rust-lang.org discussion](https://users.rust-lang.org/t/avoid-specifying-lints-workspace-true-on-every-crate-in-a-workspace/103464); tool at [crates.io: cargo-workspace-lints](https://crates.io/crates/cargo-workspace-lints)). Ocx's `rust-cargo.md` LINT-01 already mandates this and gives its own verification grep, but it is currently checked against four crates; the crate split is exactly the scale at which this class of drift first becomes likely, corroborating that LINT-01's existing check needs to run in CI on every new crate as a hard gate, not a spot-check.

## Recommendation

**Error strategy (ADR decision, reaffirm as-is): per-crate `thiserror`, no snafu, no shared leaf-error crate.** The one concrete failure mode that pushes large Rust codebases off `thiserror` — losing the ability to tell two call sites of the same source-error type apart — is already handled in ocx by the existing three-layer wrapper-struct/kind-enum pattern (`error.rs`'s `InternalFile`/`LayerLayout`/`SymlinkWalk` split is a worked example already in the tree). Snafu buys nothing ocx does not already have, and it would be a second error-composition idiom running alongside the one `quality-rust-errors.md` already documents and tests enforce. Action for the ADR: state this rejection explicitly with the source-type-collision test as the falsification criterion, so a future contributor who hits the same pain GreptimeDB hit has a documented "we checked, and the existing pattern handles it — here's how" instead of re-opening the question from zero.

**Exit-code classification: move to `crates/ocx_cli`, not into any of the new library crates.** This is the one place current practice and current doctrine already disagree (Finding 3), and the crate split is the forcing function to fix it. Concretely: `ExitCode`, `ClassifyExitCode`, `ClassifyErrorKind` become a small crate (or a module in `ocx_cli` if kept minimal) with implementations for each library crate's error type living beside the CLI, per the addendum's own ruling for the grimoire-shared signing crates — extend that ruling to *every* crate in the map, not only the signing-stack ones, so the rule is uniform rather than special-cased. This also retires the `cli` (lib-internal) vs `ocx_cli` (crate) naming collision as a side effect, since the ladder's natural home is the crate already named `ocx_cli`.

**Workspace-hack: do not add now; if added later, treat every lockstep consumer's feature list as a named contract, never an inheritance.** Hakari's own documentation states the workspace-hack is purely a build-time win and specifically warns that a path/git consumer inherits whatever features it forces — exactly ocx-mirror's and grimoire's exposure. If the scoped-gate timing later justifies one, the ADR (or its follow-up) must require the same explicit-declaration discipline ocx-mirror already applies for `preserve_order`, verified per consumer, not assumed to propagate.

**Ecosystem-tier contract — three items the ADR must state as mechanical fact, not convention:**
1. `[patch.crates-io]` never travels across a path/git boundary; every lockstep consumer (ocx-mirror today, grimoire next) re-declares it verbatim, pointing at its own submodule checkout.
2. Any producer-crate feature whose *absence* silently changes behavior for a consumer (the `preserve_order` case) is listed by name in the crate map or a companion doc, not left as an implicit "it happens to unify" — because Cargo's feature unification for a path dependency is scoped to the *consumer's* workspace graph, not the producer's, so nothing about the producer's own `Cargo.toml` protects a downstream consumer at all.
3. Full-tree git-submodule vendoring is a hard requirement of the pattern, not a style choice — Cargo cannot resolve a transitive path dependency across two separate git repositories, so a future "simplify this to a git dependency" suggestion should be rejected on that basis, cited to [rust-lang/cargo#14946](https://github.com/rust-lang/cargo/issues/14946).

Record, in one sentence, why ocx rejected the rust-analyzer `ra_ap_*` alternative (independently versioned crates.io publishing) for the ecosystem tier — likely "the crate map is not yet stable enough to commit to per-crate semver" — so the choice reads as deliberate rather than accidental to a future reader.

**Public-surface growth:** enforce `unreachable_pub` via the existing LINT-11 ratchet, treating the crate split itself as the event that makes the ratchet's backlog non-trivial for the first time — sequence it into the split's own plan, not as an unrelated pre-existing lint task. For crate-boundary traits that must not be implemented downstream (`IndexImpl`, `OciTransform`/`OciTransport` per `arch-principles.md`), use the private-supertrait sealed-trait pattern now (wasmtime's `GcRef` is a working precedent); do not wait for or design around RFC 3323's `impl(crate)`, which is nightly-only with no stabilization date as of this research. Mark every crate below the *ecosystem* tier as internal via a crate-level doc comment/README line (rust-analyzer's `ra_ap_*` convention: mark the whole crate unstable, not each item) rather than auditing per-item visibility — cheaper, and matches ocx's own "internal tier: free to change" framing. Extend `rust-cargo.md` LINT-01's existing `[lints] workspace = true` check to run as a hard per-crate CI gate once the crate count grows past a handful — the drift this guards against is a documented real-world failure mode at workspace scale (`cargo-workspace-lints` exists because of it), not a hypothetical.

## Self-check

- Every claim above carries a URL, either to an external source or to a file in this repository read directly during this research.
- Sources flagged as older than ~18 months: the GreptimeDB blog (2024-05-07) and the wasmtime PR #436 (2019) — both cited only for a fact that is either still mechanically true (thiserror's `From` limitation, a language-level fact) or an established-and-unchanged baseline pattern, not as evidence of current tooling state.
- Adjacent options considered and reported on: `snafu` (rejected, with falsification criterion), `error-stack` (searched; no substantive independent coverage surfaced beyond passing mentions in comparison round-ups, so it is omitted from the recommendation rather than asserted on thin evidence — a gap, not a finding), `anyhow`-everywhere at the cargo-style single-binary extreme (reported as the established alternative ocx deliberately does not take, since ocx crates split into a real multi-consumer ecosystem tier), rust-analyzer's versioned-crates.io alternative to lockstep vendoring (reported, with a recommendation to record why ocx rejected it), and the language-level `impl(crate)` restriction as the not-yet-usable future alternative to sealed traits.
- Opinionated throughout per instructions: explicit rejections (snafu, workspace-hack now, RFC 3323 reliance) and explicit moves (exit-code classification to `ocx_cli`) are stated as recommendations, not neutral option lists.
