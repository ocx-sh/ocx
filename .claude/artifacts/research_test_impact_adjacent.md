# Research: test impact analysis and gate tiering, adjacent fields

## Metadata

**Date:** 2026-09-06
**Domain:** testing
**Triggered by:** /hex-discuss crate-split-and-verify-tiers
**Expires:** 2027-03-06

## Direct answer

Every discipline that ships one compiled artifact behind a large e2e suite converges on the same three-part answer: (1) a cheap **always-run smoke tier** picked by hand or by ownership convention, not by diff analysis; (2) an **expensive full tier** gating merge or running nightly; (3) **prediction/coverage-based selection is real and saves 50-90% of runs**, but every implementation that reports numbers also reports a documented false-negative mode from shared/hidden dependencies, and every mature one (Google, Microsoft, the drizz.dev writeup) hard-codes a "when in doubt, run everything" fallback on protected branches. Nobody in the survey narrows a black-box compiled-binary e2e suite by per-test code coverage as a first-class supported workflow — the tooling to instrument a binary and attribute coverage back to the external test that drove it exists (Confluent's Bincover for Go, Go 1.20+ native binary coverage, `cargo-llvm-cov show-env` for Rust) but nobody has packaged the "map coverage profile → which pytest test produced it" layer; each shop hand-rolled it once. Command-to-test mapping by file/directory convention (git's `t/`, Docker's `docker_cli_<cmd>_test.go`, Terraform's `TestAcc<Resource>`) is the dominant, cheapest signal precisely because it requires zero infrastructure — but none of the surveyed projects trust it alone for cross-command regressions; they backstop it with either "just run the whole (fast) suite every time" (git) or periodic/nightly full runs (Kubernetes conformance, PyTorch periodic, LLVM test-suite).

## Trends

- **Established:** predictive/ML-ranked test selection at hyperscale (Meta PTS since 2018, Google's build-graph-distance + historical-failure GBDT ranking as of an ICST Industry 2025 paper); coverage-map TIA for unit/integration tests with a same-process test runner (Microsoft VSTest, pytest-testmon); command-name-to-test-file convention for CLI projects (git, Docker legacy suite, Terraform).
- **Emerging (last ~18 months):** language-agnostic, coverage-free RL-based test prioritization explicitly motivated by "coverage maps don't scale to massive multi-language repos" (Jungwirth et al., Jan 2025); native Go binary coverage (`go build -cover` + `go tool covdata`, GA since Go 1.20) lowering the bar for CLI-binary coverage without bespoke tooling like Bincover.
- **Declining / deprecated:** Docker/Moby's per-command `integration-cli` Go-file convention is explicitly being retired in favor of undifferentiated API-client integration tests — the project is moving *away* from command-to-file mapping, not toward it.
- **Persistently unsolved:** merge-queue re-validation reruns the full suite on every batch/requeue; multiple vendors (Mergify, Aviator, Trunk.io, Earthly) sell partial fixes as of 2025-2026, none claim it solved.

## Key findings

1. **Meta's Predictive Test Selection** cuts CI test cost ~2x via ML on historical outcomes while reporting >95% of individual test failures and >99.9% of faulty changes still caught — the explicit trade-off is a bounded, published escape rate, not zero-miss. [Predictive Test Selection (Meta Research)](https://research.facebook.com/publications/predictive-test-selection/) — 2019, **>18 months old**.
2. **Google's newer speculative-testing model (TRANSPRED)** ranks targets by build-graph distance + historical failure counts + commit metadata via gradient-boosted trees, hitting 85% recall of breakages at a 25% test budget (vs. 56% for random selection at the same budget) and cutting median detection latency from 107 to 37 minutes, trained on 120B test-cycle pairs. It explicitly depends on Google's separate "culprit finding" infra to produce clean (non-flaky) training labels. [Speculative Testing at Google with Transition Prediction](https://hackthology.com/speculative-testing-at-google-with-transition-prediction.html) — Apr 2025, fresh; cites ICST Industry Track 2025.
3. **Microsoft's Test Impact Analysis** (Azure DevOps/VSTest) builds a per-test file-touch map from a baseline run, then selects impacted tests + previously-failing tests + newly-added tests; Microsoft's own guidance says it's only worth the maintenance overhead when a run takes >15 minutes. [Use Test Impact Analysis — Azure Pipelines](https://learn.microsoft.com/en-us/azure/devops/pipelines/test/test-impact-analysis?view=azure-devops) — evergreen doc.
4. **The dominant reported failure mode across every TIA-adjacent source is the same one**: a change to a shared/low-level file doesn't touch the test files that exercise it, so naive "run the changed test files" filtering misses the regression silently. Mitigation is to select by dependency *scope*, not by which test file changed, and to treat config/CI/env changes as always-run triggers. Even mature Google TIA "falls back to running full suite whenever the system isn't confident, because the cost of a missed regression outweighs the cost of a longer build." [Test Impact Analysis — drizz.dev](https://www.drizz.dev/post/test-impact-analysis) — Jun 2026, fresh.
5. **ABB's industrial regression-test-selection case study** (2 case studies, 9 component releases, C/C++) reduced the required regression-test count by ≥70% without sacrificing fault-exposure — one of the few adjacent-field numbers with a concrete percentage. [Effective Regression Test Case Selection: A Systematic Literature Review, ACM Computing Surveys 50(2)](https://dl.acm.org/doi/10.1145/3057269) — 2017 survey, **well over 18 months old**, underlying case studies older still.
6. **Coverage-guided selection for a black-box compiled CLI binary is technically solved but never packaged as a reusable "coverage → which e2e test" tool.** Confluent built Bincover from scratch in 2020 specifically because their CLI (compiled Go binary, driven by external tests) had no existing option; it works by compiling a special instrumented test binary, writing CLI args to a temp file, replacing `os.Exit()` handling, and merging per-invocation coverage profiles. Go 1.20 later added this natively (`go build -cover`, `GOCOVERDIR`, `go tool covdata merge/textfmt`), but still leaves "attribute this profile back to test X" as caller-built glue. [Measuring Go Code Coverage with Bincover](https://www.confluent.io/blog/measure-go-code-coverage-with-bincover/) — Apr 2020, old, but mechanism is the direct match for the OCX shape. [Code coverage for Go integration tests](https://go.dev/blog/integration-test-coverage) — describes the Go 1.20+ native mechanism, evergreen.
7. **The same pattern exists, unused this way, in Rust.** `cargo-llvm-cov show-env` exports `LLVM_PROFILE_FILE` and friends so that *any* subprocess invocation of an instrumented binary — including one invoked from an external pytest harness — emits a coverage profile mergeable via `llvm-profdata merge`; nothing in the surveyed prior art shows anyone closing the loop back to "which pytest test triggered which profile" for a Rust CLI. [cargo-llvm-cov README](https://github.com/taiki-e/cargo-llvm-cov/blob/main/README.md) — actively maintained, evergreen.
8. **Command-to-test-file naming is cheap and universal among CLI/VCS tools but nobody trusts it alone.** git's `t/` suite is numbered by command family (0xxx framework, 4xxx diff, 5xxx pull/export, 6xxx revision-tree, 7xxx porcelain working-tree, 8xxx forensics, 9xxx tools) with one file per command, but git's answer to "how do you catch cross-command regressions" is simply to run the *entire* (fast, in-process) suite on every change rather than select a subset. Docker's legacy `integration-cli` used one Go file per command (`docker_cli_run_test.go`, `docker_cli_build_test.go`, …) selectable via `TESTFLAGS='-test.run TestDockerCLI<X>Suite'`, but Moby is explicitly deprecating that whole suite in favor of API-client integration tests with no equivalent per-command file convention. [git/t/README](https://github.com/git/git/blob/master/t/README); [moby/docs/contributing/test.md](https://github.com/moby/moby/blob/master/docs/contributing/test.md).

## Approaches compared

| Approach | Affected signal | False-negative risk | Maintenance cost | Handles single-binary input? |
|---|---|---|---|---|
| ML-ranked prediction (Meta PTS, Google TRANSPRED) | Historical co-failure + commit metadata + build-graph distance | Bounded and published (Meta: <5% of individual failures, <0.1% of faulty changes escape at 25%/50% budget); Google: 15% missed breakages at 25% budget | High — needs a large historical outcome dataset, a retrained model, and (for Google) a separate high-accuracy culprit-finding system to produce non-flaky training labels | Yes in principle (signal is metadata/history, not source coverage) — no code-coverage dependency, so a single-binary artifact is not a blocker |
| Coverage-map TIA, same-process (pytest-testmon, MS VSTest) | Per-test line/method coverage from a baseline run, diffed against changed files | High for shared/hidden dependencies (config, env, indirect callers) unless scope-widened; near-zero for logic the test directly executes | Medium — map must be rebuilt regularly, degrades as tests are added/removed/refactored | No — assumes the coverage tool observes the same process as the test; breaks down once the code under test is a separately invoked binary |
| Coverage-map TIA, cross-process binary (Bincover, Go 1.20 native, cargo-llvm-cov) | Line/region coverage of an externally-invoked instrumented binary, profiles merged post-hoc | Same shared-dependency risk as same-process TIA, plus attribution risk (which external test produced which profile) if that mapping isn't built | High — the raw instrumentation exists as an off-the-shelf tool, but the "map profile back to driving test" layer has been hand-built by every team that wanted it (no packaged solution found) | Yes — this is the only category built specifically for a black-box compiled binary under e2e test |
| Command/feature-to-test file convention (Terraform `TestAcc`, git `t/NNNN-cmd`, Docker legacy `docker_cli_cmd_test.go`) | Filename/prefix convention tying a test file to the command it exercises | High for cross-command regressions — no project in the survey uses this signal to *skip* a full run; it's used only to let a human run a targeted subset locally | Very low — pure naming discipline, breaks silently if the convention isn't enforced (Docker is actively abandoning it) | N/A — orthogonal to the single-binary question, this is a human-navigation aid, not an automated selector |
| Ownership/label-based selection (Kubernetes `[sig-name]`, Ginkgo `--focus`/`--skip`) | Manual test tagging by owning team/feature area | High — depends entirely on humans tagging correctly; conformance is a hand-curated subset, not a diff-derived one | Medium — tags need upkeep as tests are added, but no coverage infra required | N/A — orthogonal; used for manual scoping and CI job assignment, not diff-based skip logic |
| Tiered gates by trigger point (PyTorch trunk/periodic, Kubernetes Prow presubmit/postsubmit/periodic, LLVM check-llvm/test-suite, Linux 0-day rebasable/non-rebasable trees) | Not diff-based at all — which suite runs is fixed by *when* it runs (every commit vs. every 4h vs. nightly) or by tree trust level | By design: fast tier can miss anything the slow tier alone catches, until the slow tier runs | Low to run, but requires organizational discipline to keep the fast tier's blind spots monitored | Trivially yes — sidesteps the coverage-attribution problem entirely by not trying to select tests from a diff |

## negative:

No public postmortem was found describing a specific Chromium (or other named-project) incident where an "affected tests" heuristic missed a regression from a shared-code change — searches surfaced only generic regression-testing and flaky-test content, not an incident writeup. The Google TAP primary paper and the classic Graves et al. RTS study could not be parsed by the available fetch tooling (PDF binary, no `pdftotext`/`pypdf` in this environment) and are cited from search-result snippets only — their numeric detail (if any beyond what's summarized above) is unverified. No evidence was found of a JaCoCo/Gradle plugin that performs change-based *test selection* (as opposed to coverage threshold reporting); Gradle's own incremental-build/up-to-date-checking may be the closer JVM analog but that is inference, not a sourced claim.

## leads:

- **`cargo-llvm-cov show-env` + a custom attribution layer** is the nearest off-the-shelf building block for "which pytest test exercised which part of the `ocx` binary" — nobody has published a packaged tool for the attribution step, so building one would be net-new, not adoption of prior art.
- **Bazel-diff / target-determinator** (build-graph-based affected-target diffing) is a mature, actively maintained approach not mentioned in the original brief; worth a follow-up look since it's closer to "build graph" than "coverage map" and might compose with a Rust workspace split.
- **Jungwirth et al. (Jan 2025)** is the most directly analogous recent paper to OCX's shape (motivated explicitly by "coverage maps don't scale," proposes language-agnostic metadata-only ranking) — worth a deeper read if predictive ranking (rather than static command-mapping) is ever considered.
