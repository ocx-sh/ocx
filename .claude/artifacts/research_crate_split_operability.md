# Research: operability and cost of a many-crate ocx workspace

## Metadata

**Date:** 2026-09-06
**Domain:** ci-cd
**Triggered by:** /hex-architect crate-split-and-verify-tiers
**Expires:** 2027-03-06

## Direct Answer

Splitting `ocx_lib` into several `ocx_*` crates costs almost nothing at the CI layer and a real, one-time amount at the AI-config layer — the two costs are decoupled and should be planned separately. Every workspace-wide command already in `taskfile.yml`/`.github/workflows/*.yml` (`cargo build --workspace`, `cargo clippy --workspace`, `cargo nextest run --workspace`, `cargo llvm-cov --workspace`, `cargo deny check`, `dist-workspace.toml`'s `members = ["cargo:."]`) resolves through `cargo metadata` or the lockfile, so it absorbs new workspace members automatically with zero edits; measured CI cost (`verify-deep.yml`: Linux build+unit 1054 s, acceptance 1604 s per `research_crate_split_recon.md` finding 13) is dominated by the three-OS matrix, the Docker/Sigstore stack bring-up, and the single 87k-LOC `oci` module's own compile time — not by how many crate boundaries exist inside that compile. The real, budgetable cost is the 14 AI-config rule files that hard-code `crates/ocx_lib/src/<module>/**` globs (`research_crate_split_recon.md` finding 10) and the new per-crate `CLAUDE.md` files the plan's own requirements call for — this is finite, mechanical, one-commit-per-extraction work, not a new ongoing tax. The one place genuine new engineering is needed is the scoped work-package gate itself (§Decisions: changed-crate `nextest -p` + command-mapped acceptance subset + hub-touch escalation, ≤5 min) and the pre-commit hook's TTL-mark logic that must learn to accept a "scoped" mark — nothing in the Rust or JS ecosystem ships this as an off-the-shelf tool for a one-binary-many-e2e-tests shape (confirmed independently by `research_test_impact_adjacent.md`), so it is hand-built either way, split or no split.

## Technology Landscape

### Established (proven, widely accepted)

| Tool/Pattern | Status | Notes |
|---|---|---|
| `Swatinem/rust-cache` | Standard for hosted GitHub-runner Rust CI | Workspace-aware, excludes workspace crates' own output from the cache key by default (avoids caching what should recompile), auto-detects rustc version + target triple. [Swatinem/rust-cache](https://github.com/Swatinem/rust-cache) — evergreen, actively maintained. Already in use in `verify-basic.yml`. |
| `cargo nextest` `--partition count:m/n` | Mature CI sharding primitive | Splits one test run across N machines by binary-level counted or hashed partitioning; combined with `nextest archive` lets one build feed multiple test-executor legs. [nextest partitioning docs](https://nexte.st/book/partitioning.html) — evergreen. Not currently used in ocx (single-machine `--workspace` run is still under the ≤5 min-relevant budget per-crate). |
| `cargo-hack --each-feature` | Standard feature-matrix tool for Rust CI | Runs a command once per feature (plus `--no-default-features` and default), dedups equivalent combinations; `--depth` bounds the combinatorial blowup on large workspaces. [cargo-hack](https://github.com/taiki-e/cargo-hack) — evergreen, actively maintained. Not currently relevant to ocx: the workspace has no meaningful per-crate feature matrix beyond `ocx/__testing`. |

| `cargo-llvm-cov --workspace` / `--no-report` + `report` | Standard multi-crate coverage aggregation | Runs coverage across every workspace member and merges profiles; supports `--package`/`--exclude-from-report` for per-crate slicing. [cargo-llvm-cov README](https://github.com/taiki-e/cargo-llvm-cov) — evergreen. ocx's `coverage.taskfile.yml` already uses `--workspace`; a split makes a future per-subsystem coverage breakdown a `--package` flag away, not new tooling. |
| Nested `CLAUDE.md` per subdirectory (Claude Code) | Official, current mechanism | "Claude also discovers CLAUDE.md … in subdirectories under your current working directory. This is the mechanism the plan's "one `CLAUDE.md` per crate" requirement rests on: it is on-demand (zero context cost until a crate's files are opened), not an eager multiply-by-N load. |
| rust-analyzer's root `CLAUDE.md` | Precedent for a large multi-crate Rust repo | ~80 lines; treats new `pub` items, public re-exports, and Cargo dependencies as "architectural changes, not routine implementation details"; directs contributors to keep functionality inside the crate that owns the data and to reuse `stdx` rather than add small helper crates "without strong justification." [rust-analyzer CLAUDE.md](https://github.com/rust-lang/rust-analyzer/blob/master/CLAUDE.md) — current (checked against `master`). | Per-crate `README.md` (not `CLAUDE.md`) at scale | wasmtime's actual discipline | wasmtime documents architecture centrally (`docs/contributing-architecture.md`) plus a `README.md` per crate under `crates/*/` for what that specific crate is; internal (non-public-API) crates are convention-prefixed `wasmtime-internal-*`. [wasmtime architecture](https://docs.wasmtime.dev/contributing-architecture.html), [wasmtime crate READMEs](https://github.com/bytecodealliance/wasmtime/blob/main/crates/wasmtime/README.md) — evergreen. Cheaper precedent than a `CLAUDE.md` per crate: a README any human or agent reads, one central architecture doc, no N-way AI-specific file to keep in sync. |
| nushell: 40+-crate workspace, workspace-wide CI | Confirms scale is a non-issue for tooling | Nushell's workspace holds 40+ crates with shared versioning; CI tuning (cache strategy, not crate-count reduction) took their pipeline from ~30 min to ~10 min. [nushell DeepWiki](https://deepwiki.com/nushell/nushell) — secondary source, treat as directional. |

| Tool/Pattern | Signal | Worth Watching Because |
|---|---|---|
| `cargo-rail` | New (2026) monorepo tool: runs `cargo metadata --filter-platform` per target, intersects with git-diff-derived guardrails, deterministic planner contract for "what needs to rebuild/retest" | [cargo-rail (DEV Community)](https://dev.to/loadingalias/cargo-rail-making-rust-monorepos-boring-again-3i93) — 2026, fresh but low-adoption-signal (single blog post, no crates.io download history checked). Closest off-the-shelf match to the ADR's "changed-crate detection via `cargo metadata` + git diff" primitive — worth a from-scratch feasibility check before hand-rolling the same ~50 lines, but not mature enough to depend on for the ≤5 min gate's correctness. |

### Declining

| Tool/Pattern | Signal | Avoid Because |
|---|---|---|
| Command-to-test-file convention as a *skip* signal (Docker's `integration-cli`) | Moby is explicitly retiring its per-command Go-file convention in favor of undifferentiated API-client integration tests | Already documented in `research_test_impact_adjacent.md` finding 8/source `moby/docs/contributing/test.md`. Directly relevant here: ocx's own acceptance suite already keys on command-name file conventions (`test_announce*.py`, etc.) with no formal mapping — the industry direction is *away* from trusting that convention as an automated selector, reinforcing the discussion's "no impact-analysis tooling, hand-picked table + hub-crate escalation" position rather than trying to formalize the filename convention into a selector. |
| `dorny/paths-filter`-style CI job skipping for a shared/hub module | "When you change a file in a shared package in a monorepo, CI can skip testing the services that import it… shipping breaks while CI reports everything is fine" | [Monorepo path filters risk](https://www.codewithkarani.com/blog/monorepo-github-actions-path-filters-shared-code); large-PR file-count miss also documented ([dorny/paths-filter#227](https://github.com/dorny/paths-filter/issues/227)). This is the generic version of the exact failure mode the discussion's "hub-crate touch → full" rule exists to prevent. It is independent, external confirmation that the discussion was right not to wire `paths-filter`-style job skipping into `verify-basic.yml`/`verify-deep.yml` — those workflows should keep running `--workspace` unconditionally; only the *local pre-commit* scoped gate should ever narrow to a subset, and it already has the hub-crate escalation this literature says is mandatory. |

## Design Patterns Worth Considering

- **Facade crate re-exporting the curated public surface** — already the discussion's own leaning (Open questions: "is there a facade crate? … yes — one `ocx` facade … the wasmtime / cargo pattern"). wasmtime's `wasmtime` crate is "nearly a 100% safe API… the first crate intended to be consumed by users," with everything else `wasmtime-internal-*` and unpublished-API. [wasmtime architecture](https://docs.wasmtime.dev/contributing-architecture.html). This resolves the CLAUDE.md/name-collision problem for free: satellites (ocx-mirror, grimoire) depend on one facade crate's `CLAUDE.md`/README, not N.
- **README over CLAUDE.md for per-crate "what is this" context** — wasmtime's per-crate `README.md` is read by humans, agents, and crates.io alike; a `CLAUDE.md` per crate is agent-only and needs separate upkeep discipline (the meta-ai-config.md staleness-detection hook does not currently watch `crates/*/CLAUDE.md`, only `subsystem-*.md`). Recommend: **one short `README.md` per extracted crate** (what it is, who may depend on it, stability tier) is the primary artifact; a per-crate `CLAUDE.md` is warranted only where agent-specific guidance (e.g., "do not add a `ClassifyExitCode` impl here — see `crates/ocx_cli`") would otherwise have nowhere natural to live.
- **Changed-crate detection without a new tool** — `cargo metadata --format-version 1` already emits the dependency graph; `git diff --name-only <base>...HEAD | cut -d/ -f1-2` maps changed files to touched crate directories in a handful of lines. `cargo-rail` (above) points at the same shape but is too new to depend on. The ADR's scoped-gate task should be a `taskfiles/rust.taskfile.yml` addition (`rust:verify:scoped` or similar), not a new external dependency — consistent with `subsystem-taskfiles.md`'s "Taskfile is the single source of truth" and the "Don't Own Non-Domain Code" bar (a few lines with no edge cases is explicitly YAGNI-exempt from needing a library).

## Key Findings

1. **CI cost is flat under the split.** Every `--workspace`-flavored command in `verify-basic.yml`, `verify-deep.yml`, `taskfile.yml`, `deny.toml`, and `coverage.taskfile.yml` resolves via `cargo metadata`/`Cargo.lock`, which is crate-count-agnostic by construction — confirmed by reading all six workflow files and both root/rust taskfiles. No workflow needs a new job, matrix leg, or path filter for the split itself.
2. **`dist-workspace.toml`'s `members = ["cargo:."]` and cargo-dist's per-binary-target Application model mean the release pipeline needs zero changes.** [dist workspace guide](https://axodotdev.github.io/cargo-dist/book/workspaces/) — only `ocx` (in `crates/ocx_cli`) declares a `[[bin]]`; N new lib crates add zero new dist-able Applications.
3. **`.licenserc.toml`'s `includes = ["crates/**/*.rs"]` and `deny.toml`'s workspace-wide license/ban checks already generalize** — hawkeye and cargo-deny operate on file globs and the resolved lockfile respectively, neither keyed to today's 4-crate layout.
4. **The real, bounded cost is 14 AI-config files with `crates/`-scoped `paths:` globs** (`research_crate_split_recon.md` finding 10: `arch-principles.md`, `workflow-bugfix.md`, `workflow-refactor.md`, and 11 `subsystem-*.md`/`quality-cli-help.md` files), each needing its glob re-pointed at the new crate boundary in the same commit as the extraction it tracks (per the discussion's own requirement) — mechanical, dead-glob-detected by the existing `test_ai_config.py` generic checker, not semantically validated by it.
5. **No off-the-shelf tool exists for "which pytest test exercised which part of a single compiled Rust binary."** Independently confirmed by `research_test_impact_adjacent.md` (Bincover/Go-native-coverage/`cargo-llvm-cov show-env` all solve the mechanism but nobody has published the "map profile back to driving test" attribution layer) — this finding is orthogonal to the crate split (it would be equally unsolved with 4 crates or 20) and confirms the discussion's decision to skip impact-analysis tooling entirely in favor of a hand-picked table.
6. **Nested `CLAUDE.md` in Claude Code loads on-demand, not eagerly, per the canonical docs**: "Instead of loading them at launch, they are included when Claude reads files in those subdirectories" ([Claude Code memory docs](https://code.claude.com/docs/en/memory)) — a per-crate `CLAUDE.md` costs zero context budget for crates an agent never opens in a given session, so N small per-crate files strictly dominates one large `ocx_lib`-wide rule file on the context-budget axis `meta-ai-config.md` already cares about.
7. **rust-analyzer, the closest real-world analog (large, multi-crate, Rust, actively-agent-assisted repo), keeps ONE root `CLAUDE.md` (~80 lines) plus a separate `docs/book/src/contributing/architecture.md`**, not a `CLAUDE.md` per crate — it makes new `pub` items, re-exports, and Cargo dependencies "architectural changes," and tells contributors to reuse `stdx` rather than add small helper crates "without strong justification." [rust-analyzer CLAUDE.md](https://github.com/rust-lang/rust-analyzer/blob/master/CLAUDE.md). This is evidence *against* the "one `CLAUDE.md` per crate" plan requirement being the cheapest sufficient option — a shorter root file plus per-crate `README.md` (wasmtime's pattern) may cover the same need at lower upkeep.
8. **The pre-commit hook's TTL gate (`commit-verified`, 300 s) is the one piece of ocx-owned automation that must change code, not just config**, to support a scoped mark on feature branches while still requiring a full mark for `/hex-finalize` — confirmed by reading `pre_commit_verification.py`/`hook_utils.py`; this is genuinely new logic (a scope field, not just a timestamp), independent of how many crates exist.
9. **External literature independently validates the discussion's "hub crate touch → full" rule**: monorepo path-filtering false negatives on shared code are a named, current failure mode ([codewithkarani.com](https://www.codewithkarani.com/blog/monorepo-github-actions-path-filters-shared-code)), and Moby is retiring its own command-to-file convention as a trust signal rather than doubling down on it — both point the same direction the discussion already ruled: scope the *local* gate, never scope the CI gate itself.
10. **`cargo-hack`/feature-matrix tooling and `cargo nextest` partitioning are mature but not currently load-bearing for ocx** — the workspace has no meaningful per-crate feature matrix today, and single-machine `cargo nextest run --workspace` already completes inside CI's measured 1054 s Linux build+unit budget; both are worth keeping in reserve if crate count or feature surface grows materially, not adopting now.

## Recommendation

**CI layout: change nothing.** Keep every workflow `--workspace`-scoped exactly as today; do not add `dorny/paths-filter`-style job skipping keyed to crate boundaries. The measured cost driver (OS matrix + Docker/Sigstore bring-up + one hub module's compile time, not crate count) doesn't move with the split, and the literature is unambiguous that path-filtered CI job skipping on shared/hub code is a documented false-negative source — exactly the failure mode the discussion's own "hub-touch escalates to full" rule exists to prevent. Scope narrowing belongs only in the local pre-commit gate, never in `verify-basic.yml`/`verify-deep.yml`.

**Gate implementation: hand-roll the ~50-line version, don't adopt a tool.** `cargo metadata --format-version 1` + `git diff --name-only <merge-base>...HEAD` is enough to build a changed-crate list; feed it into a small crate→command→test-glob table (already planned) plus `nextest -p` per changed crate. `cargo-rail` is the one 2026 tool aimed at this exact shape but is too new/low-adoption to depend on for a gate whose whole point is trustworthy green/red — revisit only if the hand-rolled version's maintenance cost becomes real. This keeps the work inside `subsystem-taskfiles.md`'s existing contract (Taskfile = single source of truth) instead of introducing a new external dependency for a few lines of glue — squarely inside the "Don't Own Non-Domain Code" YAGNI exemption.

**AI-config layout: prefer README-per-crate over CLAUDE.md-per-crate as the default, escalate to a crate CLAUDE.md only when needed.** rust-analyzer — the closest real analog (large, multi-crate, actively agent-assisted Rust repo) — ships one ~80-line root `CLAUDE.md` plus a separate contributor architecture doc, not one per crate; wasmtime's per-crate `README.md` discipline is the cheaper, dual-audience (human + agent) alternative. Concretely for ocx: keep today's `subsystem-*.md` re-scoping (required regardless, since those carry real domain rules, not boilerplate), give every extracted crate a short `README.md` (what it is, stability tier, who may depend on it — mirroring the discussion's own tiering), and add a per-crate `CLAUDE.md` only for a crate whose agent-specific pitfalls (e.g., "don't add `ClassifyExitCode` here") have no natural home in a `subsystem-*.md`. This is on-demand-loaded per Claude Code's documented behavior either way, so the cost delta between the two options is authoring/upkeep effort, not context budget — and README wins that comparison because it's read by more than one audience and needs no AI-specific staleness discipline layered on top.

## Addendum: basic vs. deep acceptance tiers (2026-09-06, owner request)

The owner asked for the acceptance suite itself to split into a **basic** tier (~1 minute, a small curated set, not a heuristic subset) and a **deep** tier (the full ~2,412-test suite). Read `.github/workflows/verify-basic.yml`, `.github/workflows/verify-deep.yml`, `test/taskfile.yml`, `test/pyproject.toml`, `test/conftest.py` to answer this directly against ocx's own files.

**What "Basic Verification"'s acceptance step ran on 2026-09-06, and why it was ~558s.** *(Superseded — the recommendation below shipped: basic's acceptance job is now `smoke-acceptance` running `task test:smoke`, and the full suite is `verify-deep.yml`'s `acceptance-tests` job. The measurement is left as it was taken.)* An `acceptance-tests` job in `verify-basic.yml` ran `task test:parallel -- --junit-xml=results/junit.xml`. That task (`test/taskfile.yml`) is `uv run pytest -n auto --dist loadgroup` over the **entire** `tests/**/*.py` tree — the same full 158-file/2,412-test suite `verify-deep.yml`'s acceptance job runs. There is no curated subset today: "Basic Verification" already pays for the deep suite in full. The 558s (per `research_crate_split_recon.md` finding 13) covers, in order: registry bring-up (`docker compose up -d registry mirror-registry`, polled up to 30×0.5s = 15s), a **real Sigstore stack** bring-up (`docker compose --profile sigstore up -d` then `python3 test/sigstore/wait-for-stack.py --timeout 300` — a budget of up to 5 minutes for 7 containers: rekor, trillian-log-server, trillian-log-signer, sigstore-mysql, fulcio, sigstore-ct, dex), binary/schema artifact download, `uv`/`task` install, then the full parallel pytest run. The workflow's own comment explains the Sigstore stack is a **hard prerequisite, not a skip-if-absent fixture**: `test/fixtures/sigstore_stack.py` raises rather than skips, "because a skip here is indistinguishable from a pass and these are the tests carrying the supply-chain contract" — so today, every acceptance run pays that cost even if most collected tests never touch signing. The workflow does not break out per-step timings, so the exact registry-vs-sigstore-vs-pytest split of the 558s is not separately measured here — flagged as a gap, not fabricated.

**Fixed-cost floors that bound how low "basic" can go.** In descending likely size:
1. **Sigstore stack bring-up** — the dominant, eliminable floor. 7 real services with a 300s allowance is incompatible with a ~1-minute target on its own; a true basic tier must select **zero** sign/attest/verify/cosign tests so the stack never starts, not merely run fewer tests while still starting it.
2. **Registry bring-up** (zot + `registry:2`) — bounded at 15s by the poll loop, typically a few seconds once images are warm on the runner; unavoidable for any test that touches the registry at all (i.e., almost the whole suite), but small next to the Sigstore floor.
3. **Binary + schema artifact download** — seconds; already shared via upload/download-artifact per `subsystem-ci.md` "share artifacts, don't rebuild," so this is not a lever to pull further.
4. **`uv`/`go-task` install** — a few seconds each, fixed per-job overhead.
5. **Docker image cold-pull variance** — not measured here; GitHub's layer cache mitigates but does not eliminate it.

Net: a genuine ~1-minute basic tier is reachable (artifact download + registry bring-up + tool setup + a handful of fast CLI invocations against the local registry ≈ 30–60s), but **only if it excludes the Sigstore stack entirely** — that one exclusion, not test count, is what separates "basic" from "the full suite minus a few tests."

**How comparable projects define and defend a smoke set.** The standard mechanism is a pytest marker (`@pytest.mark.smoke`, selected with `pytest -m smoke`), registered in `pyproject.toml`'s `markers` list exactly the way ocx already registers `requires_tty` and `divergence` in `test/pyproject.toml` — this is a zero-new-tooling extension of a convention the suite already uses, and a marker survives file moves/renames the way a hard-coded file-glob list does not. [Pytest markers guide](https://qaskills.sh/blog/pytest-markers-custom-skip-xfail-guide-2026), [pytest-with-eric on runtime tiers](https://pytest-with-eric.com/pytest-advanced/pytest-improve-runtime/) — both describe exactly this pattern: mark the fast/representative subset, run `-m smoke` first, run everything in the full gate. ocx's own suite already has three files with "smoke" in the name (`test_referrers_smoke.py`, `test_sigstore_stack_smoke.py`, `test_scenarios_smoke.py`) — but each is a thorough smoke test of **one mechanism**, not a cross-cutting "one happy path per command" tier; a new `smoke` marker must be named distinctly in intent from that existing convention to avoid confusion. **Anti-rot mechanism** (the owner's ask: assert the smoke set covers every CLI subcommand at least once): no external source surveyed names this exact pattern — the CLI-smoke-testing literature covers generic "smoke test = binary pass/fail on a critical path" guidance and clap's own subcommand docs, not a coverage-of-the-command-surface assertion. This appears to be a needed, ocx-specific structural test, built the same way `test_ai_config.py`'s dead-glob detector is built: enumerate the real command surface (`crates/ocx_cli/src/command.rs` currently declares ~50 command modules — top-level verbs like `install`, `exec`, `package`, `index`, `patch`, `shell`, `config`, `self`, several with nested subcommands) and assert every top-level name appears in at least one `smoke`-marked test's invoked args. This is "test the contract, not the content" (quality-core.md) applied to the test suite itself, not new infrastructure — a `test/tests/test_smoke_coverage.py` with one assertion, not a framework. The closest external analog for a hand-curated, explicitly-tagged (not diff-derived) subset remains Kubernetes' Ginkgo `--focus`/`--skip` conformance tagging, already covered in `research_test_impact_adjacent.md`.

**Relation to the scoped per-WP gate — they should be the same list.** The discussion's Decisions section already names the scoped WP gate's acceptance component as "a fixed always-run smoke set (install / exec / lock happy paths)" plus a command-mapped subset for the touched crate. That fixed smoke set and the CI "basic" tier the owner now wants are the same requirement wearing two triggers. Recommend defining it **once** as the `smoke` pytest marker and letting both consumers select `pytest -m smoke` — the local pre-commit scoped gate adds the crate-specific command-mapped subset on top; CI's `verify-basic.yml` job runs `-m smoke` alone. One list, no duplicate maintenance.

**The "hub crate touched → full" rule does not apply to the CI basic tier — it is a local-gate-only concept.** The discussion's escalation rule exists to fix a scoped *acceptance-subset selection* (crate → command → test-glob) when the touched crate is a hub with unpredictable blast radius. CI's basic tier is not scoped by crate at all — it always runs the same fixed `smoke` set regardless of what changed, on every PR, so there is nothing for it to escalate away from. The escalation logic belongs entirely to the local pre-commit gate (and stays there); `verify-basic.yml` needs no hub-crate awareness, no diffing, and no branch on what files changed.

**A second anti-rot option: a wall-clock budget assertion.** Independent of (and combinable with) the command-coverage meta-test above, the job itself can assert its own budget: a step that fails if the `smoke`-marked run's wall time exceeds a fixed ceiling (e.g. `pytest -m smoke --durations=0` parsed for total time, or simply timing the `pytest` invocation and comparing against a constant in the Taskfile step). This catches the opposite failure mode from the coverage meta-test — not "the set stopped covering every command" but "the set grew until it stopped being fast" — e.g. someone adds a slow, unmarked-as-non-smoke test to the marker by habit. Cheap (one `time`/duration comparison, no new dependency) and directly enforces the owner's "~1 minute" constraint as code rather than as a convention nobody re-checks.

**Open dependency this surfaces for the ADR, not an implementation detail.** Today `verify-basic.yml`'s acceptance job is the *only* place the full 2,412-test suite gates every push/PR — `verify-deep.yml`'s acceptance job is `workflow_call`/weekly-schedule-only (per its trigger block: `workflow_dispatch`, `workflow_call`, and a Monday-06:00 `schedule`, composed into `release-readiness.yml`). If "Basic Verification" narrows to the ~1-minute smoke tier as asked, **the full deep suite must be repointed to run on every PR/push to stay a real merge gate** — otherwise a regression outside the curated smoke set only surfaces at the next manual dispatch or the following Monday. This is a real trigger-block change to `verify-deep.yml` (or a new workflow), not something the basic-tier work can be silent about.

**Recommendation for this repo.** Marker (`@pytest.mark.smoke` in `test/pyproject.toml`), not a directory or `-k` name-pattern — it survives file moves, matches the suite's own existing marker convention, and lets a test file mix smoke and non-smoke tests where that's the natural split (e.g. one happy-path test per file, rather than duplicating whole files). Target size: one test per top-level CLI verb (`crates/ocx_cli/src/command.rs`'s ~50 command modules collapse to roughly 20–25 user-facing top-level verbs once nested subcommand groups are counted once each) plus the discussion's own named trio (install/exec/lock happy paths) if not already covered — call it **20–30 tests**, zero of them touching sign/attest/verify/cosign. Budget check: both mechanisms, not either/or — the coverage meta-test (`test_smoke_coverage.py`) guards against the set losing a command over time, and a wall-clock budget assertion in the Taskfile/CI step guards against the set growing past ~1 minute. Ship `verify-basic.yml`'s acceptance job as `pytest -m smoke` with the Sigstore-stack-startup step deleted outright, not conditionally skipped — a conditional adds a branch to maintain for a stack this tier should simply never need.
