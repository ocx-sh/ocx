# Research: Bazel shared remote cache — trust boundary, credential scope, hermeticity

Date: 2026-09-21 · Lane: security & compliance · Model: sonnet · For: `.claude/artifacts/adr_bazel_build_adoption.md`
Expires: 2027-03-21

## Findings

### 1. Remote-cache poisoning — threat model, documented incidents

1. **bazel-remote CAS is content-addressed (self-verifying); the Action Cache is not.** CAS keys are `sha256(blob)`, so a client fetching `/cas/<key>` can (and typically does, via Bazel's own remote-cache client) recompute the digest and detect a mismatch. The AC key is `sha256(action_proto)` — an *input*-addressed key with no way to verify from the key alone that the stored `ActionResult` actually resulted from executing that action honestly. Source: buchgr/bazel-remote README (fetched raw), corroborated by christianfscott.com analysis quoted below. https://github.com/buchgr/bazel-remote/blob/master/README.md
2. **bazel-remote does validate AC entries structurally, not semantically**, and this validation is togglable. `--disable_http_ac_validation`: *"Whether to disable ActionResult validation for HTTP requests. (default: false, ie enable validation)"* — i.e. by default it deserializes the uploaded bytes as an `ActionResult` proto, but this only rejects malformed protos, not wrong/malicious-but-well-formed ones. There is a parallel `--disable_grpc_ac_deps_check` for the gRPC path. Neither flag, enabled or disabled, checks that the referenced CAS blobs are the *correct* (honestly-produced) output for that action digest — that trust is entirely extrinsic (who was allowed to PUT). https://github.com/buchgr/bazel-remote/blob/master/README.md
3. **What Bazel itself verifies on download**: for CAS blobs Bazel (like any REAPI client) is expected to check the returned bytes hash to the requested digest before trusting them — this is inherent to content-addressing, not an opt-in flag. For AC lookups, Bazel accepts whatever `ActionResult` is returned for a matching action-digest key; there is no cross-check against "did this actually come from executing this action" — that's the whole cache-poisoning surface. This matches finding #1's CAS/AC asymmetry and is the load-bearing fact behind every mitigation below.
4. **Real production incident (Google, on `bazelbuild/bazel` itself).** [bazelbuild/bazel#4276](https://github.com/bazelbuild/bazel/issues/4276): a "badly performing CI instance (perhaps due to running out of disk space)" produced a malformed action result that "exit[ed] 0, but the output is malformed," and because CI was a *trusted* uploader, the wrong result got written to a shared cache and poisoned every consumer downstream — no adversarial actor required, just a flaky trusted writer. Reporter's own posture: *"We don't let the developer machines write to the cache, but this was a CI instance."* Confirms the threat model applies even to a "CI-only writes" policy if CI itself is unreliable, not only to malicious actors.
5. **Documented adversarial variant**: [bazel-discuss thread, "Security risks of a publicly available remote HTTP cache"](https://groups.google.com/g/bazel-discuss/c/0005BAB_mlI) — a maintainer-level respondent (Fredrik Medley) states the attack directly: *"a malicious client uploads a backdoored foobar-compiler-1.0 binary into your cache"* and Bazel "blindly executes it" on the next cache hit. Recommended mitigation: *"Restrict ActionCache uploads to trusted users only"* and *"prioritize remote executors with no external network access."* Explicit verdict on read access: the thread does not bless anonymous read as safe by itself — consensus quoted: *"the trust level of the Bazel cache needs to be equivalent to or greater than your production compilation environment."*
6. **christianfscott.com, "Bazel remote caching: Action caches are more secure when they're readonly"** — spells out the exact attack chain: upload a malicious file to CAS, then write/modify an AC entry to point an existing action digest at that malicious CAS blob; any consumer with a matching action digest gets the malicious output silently. Quote: *"there is no way to verify the validity of an AC entry based on its key."* Recommendation: make the AC read-only for everything except a remote-execution service, since only RE can be trusted to have "faithfully executed" the action before uploading its own result. https://christianfscott.com/bazel-readonly-action-cache/
7. **Stripe engineering blog, "Fast builds, secure builds. Choose two."** — same threat, framed with a headline-severity example: an untrusted cache writer could "replace a business-critical binary trusted to securely handle invoice billing... with a corrupted version that reroutes funds to a personal bank account." Stripe's answer was progressively stronger sandboxing of untrusted local execution (gVisor, then Firecracker/KVM) specifically so that *no locally-run, potentially-attacker-influenced action can write to the shared AC* — cache writes are restricted to a trusted remote-execution tier, never to arbitrary CI/dev machines running untrusted code. https://stripe.dev/blog/fast-secure-builds-choose-two
8. **Applicability to the ocx.sh posture**: ocx has **no remote execution** — the write path is "main-branch CI runs `bazel test` locally on a GitHub-hosted runner, then uploads with `--remote_header`." That IS the "CI is the trusted uploader" model from #4276/#5, not the RE-only model from #6/#7. The residual risk is exactly #4's: a bug or a supply-chain compromise *in what CI itself builds/runs* (not a hostile PR — PRs can't write) poisons the shared cache for every reader, including the anonymous PR lanes. This is a materially smaller attack surface than a world-writable cache, but it is not zero, and it is not "PRs are safe from cache poisoning" — it's "PRs can't be the *source* of poisoning, only a *victim* of it."

### 2. Non-hermetic actions and cache-key soundness

9. **Exact Bazel 9 tag/flag spellings and semantics — from the primary source** (`https://bazel.build/reference/be/common-definitions`, common `tags` attribute, unchanged in spirit across Bazel versions per changelog history):
   - `no-sandbox` — *"results in the action or test never being sandboxed; it can still be cached or run remotely."* Does **not** protect the cache.
   - `no-cache` — *"results in the action or test never being cached (locally or remotely)."*
   - `no-remote-cache` — *"results in the action or test never being cached remotely (but it may be cached locally; it may also be executed remotely)."* **This is the exact tag that keeps an entry out of the shared cache while still letting local (sccache-style) caching work.**
   - `no-remote-exec` — *"results in the action or test never being executed remotely (but it may be cached remotely)."*
   - `no-remote` — *"prevents the action or test from being executed remotely or cached remotely. This is equivalent to using both no-remote-cache and no-remote-exec."*
   - `local` — *"precludes the action or test from being remotely cached, remotely executed, or run inside the sandbox."* i.e. `local` = `no-remote` + `no-sandbox` combined, exactly the three-tag combo the dossier already plans to hand-write (`no-sandbox`, `requires-network`, `local` — note `local` alone already implies `no-sandbox` and no remote cache, so the dossier's three-tag list is redundant on `no-sandbox` but the redundancy is harmless).
   - `requires-network` — *"allows access to the external network from inside the sandbox"* — only meaningful when NOT combined with `no-sandbox`/`local` (both already disable the sandbox), so on an already-`local` action `requires-network` is a no-op tag, kept only for documentation clarity to a reader.
   - `external` — test-only: *"will force test to be unconditionally executed (regardless of `--cache_test_results` value)"* — forces re-run every build; does not by itself touch remote-cache upload/download.
10. **The critical answer to the dossier's central question**: `local` on the acceptance-test `sh_test`s and the cast-recording actions already implies `no-remote-cache` (via the `no-remote` component). **These two stages are already safe by construction** as planned. The stage that needs an *explicit* audit is the **website build** (tagged only `requires-network` in the plan, not `local`/`no-sandbox`) — if it stays sandboxed, it's still eligible for the shared remote cache, so its hermeticity claim ("only `website/**` + generated inputs matter") must actually hold, or a cache hit will serve a stale/wrong site to another commit. Recommend auditing whether `bun install --frozen-lockfile` + `vitepress build` reads anything outside declared inputs (network fetch, ambient `$HOME`, timestamps) before leaving it cacheable.
11. **Bazel's own sandboxing docs confirm the exact failure mode the dossier worries about** (`https://docs.bazel.build/versions/main/sandboxing.html`, "Sandboxing"): *"Without action sandboxing, Bazel will not know if a tool uses undeclared input files... When one of the undeclared input files changes, Bazel still believes that the build is up-to-date and won't rebuild the action, resulting in an incorrect incremental build."* And on shared-cache blast radius: *"A bad cache entry in a shared cache affects every developer on the project, and wiping the entire remote cache is not a feasible solution."* This is the exact mechanism by which an action tagged `no-sandbox` (but NOT also tagged `no-remote-cache`/`no-remote`/`local`) can compute a cache key from its *declared* inputs, silently consume an *undeclared* input that differs machine-to-machine (host `agg` version, ambient font path, `$HOME`-relative cache dirs, PTY/tty quirks), and upload a result that is wrong for every other machine matching that same declared-input key. **Answer to the key question: yes — `no-sandbox` alone is cache-key-unsound; the tag that must always ride shotgun with `no-sandbox` on a target destined for the shared cache is `no-remote-cache` (or the broader `no-remote`/`local`).** The dossier's own plan already does this for casts and acceptance tests via `local`; it must NOT be skipped if either stage's tag list is ever trimmed down to just `no-sandbox`/`requires-network` for any reason (e.g. someone "optimizing" cache reach later).
12. `bazelbuild/continuous-integration#1174`, *"Remote cache poisoned?"* — filed against Bazel's own CI, corroborating that this is a recurring operational failure mode in real fleets, not a theoretical one, independent of the more famous #4276.

### 3. Credential handling

13. **`--remote_header` is a plaintext CLI flag; Bazel's own README-adjacent guidance is to keep it out of shared/committed rc files.** bazel-remote's README explicitly advises: *"place this flag in a user-specific (and .gitignore'd) bazelrc file"* to avoid leaking a password into logs — this is guidance for local dev, and confirms the flag's value is treated as log-sensitive by the tooling authors themselves.
14. **`--announce_rc` / BEP disclose the *canonical, fully-expanded* command line, which includes flag values.** Bazel's own design doc ("Improved Command Line Reporting," `be.bazel.build/designs/2017/07/13/improved-command-line-reporting.html`) states one benefit of BES/BEP is *"seeing all command-line flags used without having to use `--announce_rc`... or all environment variables set"* — i.e. the structured command line (`--build_event_text_file`/`--build_event_json_file`, message `structured_command_line` with `command_line_label: "canonical"`) is a documented, designed-in transcript of every flag value passed, and Bazel has no evidence found of automatic redaction for `--remote_header` values inside that structure. **UNVERIFIED as a specific CVE/issue**: I could not find a Bazel issue confirming or denying that `--remote_header=Authorization=...` is masked in BEP JSON output — treat it as *not* masked (safer assumption) absent a found source stating otherwise. Practical consequence for ocx: if `--build_event_json_file`/BES export is ever turned on for the write-credentialed main lane (the dossier's own bespoke BEP→OTLP pusher touches this exact file), the credential value would land in that JSON unless the header is supplied via `--credential_helper` instead of `--remote_header`, or the OTLP-pushing script is made to strip `structured_command_line` before use.
15. **`--credential_helper` is Bazel's own recommended alternative, available since Bazel 5.4.0.** From the design doc (bazelbuild/proposals, 2022-06-07): a generic mechanism to "fetch credentials for authenticating against services, such as Remote Caching, Remote Execution or uploading a Build Event Stream," configured as `--credential_helper=<path>` or scoped `--credential_helper=<pattern>=<path>` (exact-match DNS name, wildcard, or default fallback), with later entries overriding earlier ones. Its structural advantage over `--remote_header` (inferred from the design doc's own framing, not stated as an explicit security comparison in the fetched text): the secret never appears as a Bazel flag value at all — it's fetched out-of-band by an external helper program at request time, so it cannot appear in `--announce_rc`, BEP structured-command-line, or shell history. https://github.com/bazelbuild/proposals/blob/main/designs/2022-06-07-bazel-credential-helpers.md
16. **GitHub Actions exposure model for a write credential on PRs — well documented by GitHub itself, not Bazel-specific.** `pull_request` (what the dossier's PR lanes use): *"For pull requests opened from a fork, the GITHUB_TOKEN is read-only and no secrets are passed to the workflow."* `pull_request_target`: *"executed with access to action secrets"* even for fork PRs, and checks out the base branch's workflow (not the PR's) unless a step explicitly checks out PR HEAD — the well-known "pwn request" vector. https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target — **Since the dossier's PR lanes read the cache anonymously (no header at all) and only `main` pushes carry `--remote_header`, this is already the safe configuration**: the write secret is never in scope for a `pull_request`-triggered workflow, so a compromised/malicious PR cannot reach it through the workflow's own secret context. The residual risk is entirely in step 14 (does the *main* lane's own tooling leak the header it legitimately holds), not in PR exposure.
17. Environment-protection-rule guidance (GitHub Changelog, Nov 2025) confirms an additional lever if ever needed: gating the write-credentialed job behind a GitHub Environment with required reviewers, scoped to `refs/heads/main` — not currently necessary given the `pull_request`-only exposure model, but worth naming as the next lever if the write path ever grows a `workflow_dispatch` or `pull_request_target` trigger.

### 4. Anonymous read as an exfiltration channel

18. **No enumeration/listing endpoint exists.** bazel-remote's HTTP API is GET/HEAD/PUT against exact keys under `/cas/<sha256>` and `/ac/<sha256>` (and an optional ignored "instance"/pool prefix) plus a `/status` endpoint (aggregate size/count/config, not per-entry) — confirmed against the live README; no directory listing was found anywhere in the docs or source references surfaced. A reader must already know (or correctly guess) a specific 64-hex-char key to fetch anything. https://github.com/buchgr/bazel-remote/blob/master/README.md
19. **Brute force of the *key space* is infeasible (2²⁵⁶ SHA-256 space)** — but that is the wrong threat model. The real exfiltration path is **prediction, not brute force**: CAS/AC keys are deterministic functions of public inputs (source tree, `BUILD.bazel` content, pinned toolchain versions, action command lines) that anyone with the same open-source checkout can *compute themselves*, then simply GET. For an already-open-source repo this mostly leaks nothing beyond "the compiled form of code you can already read" — matches the bazel-discuss thread's own characterization of exfiltration as "less critical for open-source projects" — **except** where an action's inputs (or its output) embed a value that is not meant to be public: this is exactly the `build.rs`/stamping risk in finding #23 below — if a secret or CI-internal value ever gets baked into a *cacheable* action's declared inputs or environment, anonymous read turns the shared cache into a way to recover it, because the action digest key is computable by anyone who knows (or brute-forces over a small enough space, e.g. a GITHUB_RUN_ID counter) the varying input.
20. **`--enable_endpoint_metrics` exposes only aggregate, non-content signals**: per-HTTP/gRPC-endpoint request/hit/miss counters and status/size figures via Prometheus (`go-grpc-prometheus`), not per-key or content data. Standard Prometheus operational guidance applies regardless (*"HTTP endpoints provided by Prometheus components should not be exposed to publicly accessible networks like the internet... unless you know what you are doing"*) — worth confirming this metrics/status port is not the same public listener as the anonymous-read cache port, or is itself behind auth, since it's a (minor) information-disclosure and DoS-targeting surface (cache size/hit-rate telemetry) distinct from cache-content exfiltration. UNVERIFIED whether the hetzner1 nginx config already separates these — flag as a config-review item, not a research gap.

### 5. Supply chain of the tool path (`git_override`, stamping, strict env)

21. **`git_override` has no `integrity` field; `archive_override` does.** Per `bazel.build/rules/lib/globals/module#git_override`, the function takes `module_name` plus `**kwargs` forwarded to the underlying `git_repository` repo rule (`remote`, `commit`, `patches`, etc.) — there is no cryptographic-hash parameter analogous to `archive_override`'s `integrity` (a SHA-256 of the fetched archive). https://bazel.build/rules/lib/globals/module
22. **What verification *does* exist for `git_override` comes from git's own content-addressing, not from Bazel**: pinning an exact `commit = "<sha>"` means the fetch cannot silently substitute different tree content without also changing that SHA (git's object model is itself hash-linked) — so the pin is not "no verification," it's "verification delegated entirely to git's commit hash, with no independent second attestation." What it lacks relative to a BCR release: (a) **BCR's registry-level review** — the BCR docs describe validator checks confirming e.g. archive integrity and source provenance before a module is publishable, none of which apply to an unreviewed `git_override`; (b) **a re-verifiable manifest entry** — `MODULE.bazel.lock` records hashes of "all remote files that are inputs to module resolution" for reproducibility of the *resolution algorithm*, but this is not documented as a content-integrity attestation a reviewer can check without re-fetching (UNVERIFIED: I could not confirm from primary docs whether the lockfile entry for a `git_override` is itself a tree/commit hash a reviewer can diff against, versus an opaque resolution artifact — treat the lockfile as reproducibility tooling, not a security control, until confirmed otherwise). Net effect: a force-push that rewrites history at the pinned SHA is not possible (the SHA changes), but a *compromise of the `rules_ocx` repo itself* that lands a malicious commit and then updates `MODULE.bazel`'s `commit = ` pin to point at it is exactly as trusted as whoever can push to that repo/branch — no different in kind from any other unreviewed dependency bump, but with less tooling (no `integrity` diff in a PR) to make that bump visible in review. Practical mitigation: treat every `rules_ocx` commit-pin bump the same as a `Cargo.lock`/`ocx.lock` bump — require the PR diff to show old-SHA→new-SHA and reference what changed upstream, since there's no `integrity` hash to eyeball instead.
23. **`--incompatible_strict_action_env` (on by default since Bazel 0.21) is good news for the `build.rs` open question, with one sharp edge.** It strips the *inherited* client environment (`PATH`, `LD_LIBRARY_PATH`, and by extension ambient `CI`/`GITHUB_*` vars) from actions unless explicitly re-added via `--action_env=VAR`. Rationale, confirmed from Bazel's own community docs: *"the values of environment variables are included in cache key computations. So two users with different PATH variables are not able to share cache hits."* **This means `crates/ocx_cli/build.rs` will NOT see `CI`/`GITHUB_*` at all inside a Bazel action unless the ADR explicitly whitelists them with `--action_env`** — and if it does, each such var becomes part of the action's cache key, so any var that changes every run (e.g. `GITHUB_RUN_ID`) would make that action's output permanently uncacheable (self-defeating), while a var that's merely CI-vs-local (e.g. bare `CI=true/unset`) would split the cache into two disjoint universes without ever reusing entries across them.
24. **The correct mechanism for what `build.rs`/vergen-gix wants (embed commit SHA / build metadata) is workspace-status stamping, and it has its own cache-correctness trap.** `bazel-out/stable-status.txt` (`STABLE_`-prefixed keys) *does* participate in the action cache key — a changed stable value forces a rerun. `bazel-out/volatile-status.txt` (everything else) is deliberately excluded from the cache key: *"Bazel pretends that the volatile file never changes to avoid rerunning stamped actions all the time; if the volatile status file is the only file whose contents has changed, Bazel will not invalidate actions that depend on it."* **Consequence for a target on the shared remote cache: if vergen-gix's git-SHA/build-timestamp/CI-run values are wired through the *volatile* half of workspace status (the default for `--workspace_status_command` output not prefixed `STABLE_`) on a target that's remote-cacheable, a cache hit from commit A's CI run can be served to a build of commit B, and the binary will silently carry commit A's embedded git SHA / CI metadata.** This is a correctness bug, not merely a security one, and it directly resolves the dossier's open question: the ADR must either (a) route only genuinely-invariant values through `STABLE_` keys and keep truly-volatile ones out of any cacheable target's declared output, or (b) tag any Bazel target that runs vergen-gix-style stamping with `no-remote-cache` (finding #9), or (c) build `ocx_cli` with `--nostamp` for the cached test/build path and reserve stamping for the release/dist build (which is presumably already a distinct, non-cache-critical profile per `Cargo.toml`'s existing `dist` profile). Sources: `bazel.build/docs/user-manual` (fetched via Context7) + community thread `groups.google.com/g/bazel-discuss/c/jHaj11mm6sU` (Action environments) + `bazelbuild/bazel#5573` (workspace-status changes not invalidating `ctx.version_file`-dependent artifacts — same mechanism, filed as a bug by someone surprised by exactly this behavior).
25. **`--workspace_status_command`**: an external script Bazel runs before each build; its stdout lines become the stable/volatile status files above. Failure of that command (non-zero exit) fails the whole build — relevant if the ADR's workspace-status script shells out to `git`/`gh` and that's unavailable in a given sandbox/action context.

### 6. Prior art for public-read / authenticated-write posture

26. **Bazel's own canonical guidance is minimal but points the same direction the dossier already chose**: `bazel.build/remote/caching` — *"Take care in who has the ability to write to the remote cache. You may want only your CI system to be able to write to the remote cache."* No explicit blessing or warning about anonymous *read*; the page's only related note is that "the remote cache will have your binaries and so needs to be secure" when choosing a backend, which is a private-repo framing, not written with an OSS public-read posture in mind. https://bazel.build/remote/caching
27. **bazel-remote ships a first-class, named flag for exactly ocx's target posture**: `--allow_unauthenticated_reads` (added per commit `f7f9c9d`), documented as *"If authentication is enabled (--htpasswd_file or --tls_ca_file), allow unauthenticated clients read access."* This is bazel-remote's own supported "public read / authenticated write" mode — meaning ocx's current nginx-based split (auth only on non-GET methods) is one valid way to get this, but bazel-remote v2.6.2 can do it natively without an nginx `limit_except` rule, which is a smaller trust surface (one fewer place the read/write split could be misconfigured). https://github.com/buchgr/bazel-remote/commit/f7f9c9daa2cd15c5ad9ad999852c7d7a75b303e3 — **caveat, UNVERIFIED against the pinned v2.6.2**: [buchgr/bazel-remote#468](https://github.com/buchgr/bazel-remote/issues/468) reports `.htpasswd` auth not working correctly (401 on PUT) specifically *when* `allow_unauthenticated_reads: true` is set in some version/config combination — worth a smoke test before ever migrating off the current nginx split onto bazel-remote's native flag; the nginx split the dossier already specified sidesteps this specific bug entirely and needs no change.
28. **buchgr/bazel-remote#59, "Support read-only mode"** — the original design discussion for this exact pattern, explicitly proposing *"two instances of the cache over the same data directory with one read-only for developers and another read-write for the CI server to cache the main branch"* — i.e. the ocx architecture (PR lanes = read-only consumers, main = the only writer) is the pattern this feature was built to serve, from the tool authors' own mouths.
29. **Aspect (commercial Bazel vendor) ships the same shape for its own hosted cache, confirming this is treated as industry-standard rather than exotic**: fork PRs get no `ASPECT_API_TOKEN` secret, so *"the login never runs, and `--remote` would reach the cache with no credential"* — a failed/absent credential-helper exchange is made fatal (`--remote=none` fallback) rather than silently downgrading to an insecure or broken state. Confirms the general pattern "absent secret ⇒ explicitly no write capability, never a silent degrade," which the ADR should mirror for `--remote_header` on the anonymous PR lanes (i.e. simply never pass the header flag on PR-triggered jobs, which is already the dossier's plan — no change needed, but now cited as matching commercial prior art). Source: aggregated from `docs.aspect.build` + `aspect-build` CI configuration search results (secondary source; no single canonical doc URL fetched in full — mark this one **partially UNVERIFIED**, worth a follow-up direct fetch of `docs.aspect.build/workflows/features/remote-cache/` if the ADR wants to cite it as a primary source).
30. **Stripe (finding #7) is the strongest named prior-art example of a company reasoning explicitly about this trust boundary in public**, though at RE scale rather than cache-only scale — its relevance to ocx is the *general principle* (write access = a trust tier, not a technical toggle), not its specific tooling (gVisor/Firecracker), since ocx has no remote execution and therefore no untrusted-action-write path to sandbox in the first place — the entire Stripe-style threat only exists once you add RE, which the dossier has explicitly deferred ("Remote execution: not now").

## Decisions this changes

- Tag every cast-recording and acceptance-test action `local` (already planned) — confirmed this already implies `no-remote-cache`; do not let a later "let's cache acceptance tests too" change drop the `no-remote-cache`/`local` half while keeping only `no-sandbox`.
- Add an explicit hermeticity check for the website-build Starlark rule before trusting it on the shared cache — it is currently the *only* one of the four stages tagged sandboxed (`requires-network` only), so it is the only stage where an undeclared-input bug would produce a cross-machine-wrong cache entry.
- Do not add `CI`/`GITHUB_*` to `--action_env` for any cacheable target; route build-metadata (git SHA, build timestamp) through `--workspace_status_command` and keep it in the **volatile** half unless the ADR is prepared to tag that target `no-remote-cache`, or split a `--nostamp` cached-test profile from a stamped `dist` profile.
- Prefer `--credential_helper` over a raw `--remote_header=Authorization=…` for the main-branch write credential if the BEP→OTLP telemetry script (already planned) ever turns on `--build_event_json_file`/BES on that lane — otherwise scrub `structured_command_line` from that JSON before it's read by the OTLP pusher.
- Keep the PR lanes on `pull_request` (never `pull_request_target`) with no `--remote_header` at all — confirmed as the already-correct, GitHub-documented safe configuration; no secret is ever in scope for a PR-triggered job.
- Keep the nginx-based read/write split as-is; do not migrate to bazel-remote's native `--allow_unauthenticated_reads` without first reproducing/ruling out buchgr/bazel-remote#468 against the pinned v2.6.2.
- Treat every `rules_ocx` `git_override` commit-pin bump as a reviewable supply-chain event (diff old SHA → new SHA, note upstream change) — there is no `integrity` hash to lean on instead, unlike a future BCR release.
- Confirm bazel-remote's `/status` and `--enable_endpoint_metrics` Prometheus surface is not exposed on the same public anonymous-read listener without its own access control (config-review item, not a code change).

## Stage 5 addendum (2026-09-23)

Added by `plan_test_speed_tiers.md` WP-08b (C-020), per `adr_test_speed_tiers.md` § Security.

**Finding #10's conclusion — acceptance is out of remote-cache scope — still holds, for a different reason than the one it gave.** #10 rested on the `local` tag (`no-remote` + `no-sandbox`) riding every acceptance `sh_test`. That tag is gone: the acceptance package runs with `no-sandbox` + `exclusive` and its results cached (`test/bazel.bzl` § "Result caching is ON"), so `local` no longer keeps anything off the shared cache. What does is that **no lane writes an acceptance verdict to it**:

- `.bazelrc:73` sets `build --remote_upload_local_results=false` for every command, `test` included.
- The only override is `--remote_upload_local_results=true` on the `main`-push leg of `verify-basic.yml`'s `Unit tests (Bazel)` step, which runs `task bazel:test:unit` — `//crates/...`, never `//test:all`. `.claude/tests/test_workflows.py::test_only_the_write_lane_may_upload` reds a grant anywhere else.
- `verify-deep.yml`'s acceptance job passes the read credential only (the `bazel-cache-rc` action with no `write-auth`), so it holds no write credential on any trigger.

With no writer, findings #4, #6 and #12 (a poisoned *trusted* writer) cannot reach an acceptance entry, and an acceptance result is only ever served on the machine that produced it. That bounds the one hole caching opened — an undeclared input serving a stale verdict — to a local disk cache, and C-UNCACHED closes it there: every module whose source names a path its target does not declare carries `external` (`test/bazel.bzl` `UNCACHED_MODULES`), `scripts/bazel_tag_guard.py` derives that set from the AST and reds both directions, and WP-08b declared the inputs of 22 of the 23 modules it listed. The residual is `test_windows_shim.py`, Windows-only and skipped on the Linux lane that runs the suite.

**What would reopen #10:** an `--remote_upload_local_results=true` reaching any command that tests `//test:all`, or a write credential in the acceptance job. Either makes an under-declared module's cached verdict a cross-machine one, which is the #11 mechanism with the acceptance suite as its subject. Adding an acceptance writer is a D6 precondition in `adr_test_speed_tiers.md`, not a flag flip.
