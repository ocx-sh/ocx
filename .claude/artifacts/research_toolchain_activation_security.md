# Research: Toolchain activation security — trampolines, session PATH, link trees, installer writes

## Metadata

**Date:** 2026-09-04
**Domain:** security | packaging | cli
**Triggered by:** Decision brief `toolchain_activation_decision.md` (D2 Trampolines, D4 Materialization/consent, D5 Session PATH, D6 Hook interplay) — pre-implementation threat-model pass before the ADR is written.
**Expires:** 2027-03-04 (re-verify — CVE landscape and npm/mise supply-chain tooling move fast; re-check the mise trust model and npm lifecycle-script defaults specifically, both changed materially in the last 12 months)

## Direct Answer

Every surveyed tool with a repo-selected-execution vector (rustup, mise, direnv, VS Code) gates the **ambient, automatic trigger** — `cd`, folder-open, per-prompt hook — not an **explicit user-invoked command**. D4's split (`ocx pull`/`ocx env`/`ocx exec`/trampoline execution run without consent; only the per-prompt reconciler hook is consent-gated) sits squarely inside that norm, and its "consent before parse, not merely before apply" ordering rule is the exact fix for the one CVE this class has produced (mise, CVE-2026-35533). D5's global-only session-PATH registration mirrors rustup's `~/.cargo/bin` — always user-explicit, never repo-mutable — which is the right boundary. D2 has one concrete, current gap: the `binaries`-claim name set can shadow security-sensitive tool names, and D2's own rule demotes that collision to **debug-only, never a warning** — the identical shape as the npm "bin entry harvesting" campaign discovered in the wild one month ago (August 2026). That is the one finding in this research strong enough to change a decision; everything else confirms or sharpens.

## Technology Landscape

### Established (proven, widely accepted)

| Tool/Pattern | Status | Notes |
|---|---|---|
| Content-bound trust hash (direnv `allow`) | Mature/Standard | Hash of file bytes; any edit re-arms the gate. Strictest of the surveyed tools because `.envrc` is imperative shell — the whole file is the attack surface, not a subset of directives. |
| Gate the ambient trigger, not the explicit command | Mature/Standard | direnv (cd), mise (cd via hook + paranoid mode), VS Code (folder open) all converge here; `mise install`/`mise exec`/`mise run` "automatically trust their active config" in normal mode — an explicit invocation *is* the consent. |
| Fenced, idempotent shell-profile block | Mature/Standard | rustup (`. "$HOME/.cargo/env"`), uv, Homebrew `shellenv` all use a small sourced file rather than inlining a full PATH string per rc file — reduces duplicate-entry drift, though rustup's own tracker documents real idempotency bugs from this exact pattern (see Key Findings). |
| `NO_MODIFY_PATH`-style opt-out env var | Mature/Standard | uv ships `INSTALLER_NO_MODIFY_PATH`; rustup ships the CLI-flag form `--no-modify-path` (no documented env-var equivalent). `OCX_NO_MODIFY_PATH` matches the uv spelling and precedent directly. |
| `$GITHUB_PATH` / `$GITHUB_ENV` file-based env channel | Mature/Standard | Replaced the stdout `::set-env::`/`::add-path::` commands in Oct 2020 specifically because stdout-command injection was easier to trigger than a file write; newline/delimiter injection into the file is the residual class GitHub's own hardening docs still warn about. |

### Declining (losing mindshare)

| Tool/Pattern | Signal | Avoid Because |
|---|---|---|
| Unconditional `postinstall` script execution on install | npm ships v12 with lifecycle scripts off by default in 2026, after the Shai-Hulud worm compromised 500+ packages (Sept 2025) via exactly this vector; pnpm disabled it by default earlier (v10) | A decade of supply-chain incidents traces to "install always runs arbitrary code." OCX's own stated invariant — "install executes no package code" (Decision 4's own threat framing) — is the property this entire industry trend is converging toward, not an optional hardening. |
| Silent, no-trigger toolchain auto-install on invocation | rustup 1.28 (2026) removed implicit `rust-toolchain.toml`-driven auto-install entirely — no opt-out was ever shipped, it was just deleted, "a source of confusion" | Confirms the industry direction: even a fetch-and-install with no execution is being retired in favor of requiring an explicit trigger, not just because of security but because it surprised users. Relevant precedent for anything that materializes on an implicit trigger. |
| Ungated `.tool-versions` / arbitrary plugin shell | asdf ships no trust gate at all; plugins are shell code trusted purely out-of-band ("trust the plugin author") | Named in asdf's own community docs as a known weakness. The negative example — what NOT to imitate. Pyenv's `.python-version` avoids the class entirely by construction: it is a bare version string, no executable surface, so there is nothing to gate. |

### Emerging (early but promising)

| Tool/Pattern | Signal | Worth Watching Because |
|---|---|---|
| Structural admissibility parsers with explicit "what this deliberately does not check" documentation | mise's post-CVE fix (ignore trust-control keys from any non-global project file); ocx's own `.shimref` `is_pinned_identifier` comment (`core.rs:247-281`) | Same discipline: narrow the parser to the minimum needed to route safely, defer full validation to the component with real authority (`ocx_lib::oci::PinnedIdentifier` re-parses on the receiving end). This is best practice, already present in ocx's own tree — cite it as a positive, not a gap. |

It is the strongest single finding in this research. |

## Design Patterns Worth Considering

- **Gate resolution's first code-execution moment, not every later invocation.** Used by: direnv, mise (normal mode), VS Code Workspace Trust, and — by the 2026 removal — implicitly endorsed by rustup's retreat from silent auto-install. This is the master pattern behind D4; ocx's split (consent gates the *automatic* hook, not `ocx pull`/`env`/`exec`) is this pattern applied correctly.
- **Consent-order discipline: read nothing untrusted before the trust check runs, and scope the trust-control keys themselves to a channel the untrusted payload cannot reach.** The mise CVE (below) is the canonical failure of this pattern; `adr_shell_env_overhaul.md` Decision 4 already states the fix ("the only project-supplied bytes read before consent is established are the CWD walk's `stat` calls and the `ocx.lock` parse the source-set predicate requires; `ProjectConfig` deserialization happens after"). Confirmed correct, not merely plausible — it is the identical shape as mise's actual patch.
- **Component-wise, post-canonicalization path containment — never a string prefix.** Used identically in two independent places in ocx already: `pkg_root_allowed` (`crates/ocx_shim/src/core.rs:334-355`, `Path::starts_with` after both sides canonicalized) and the `[shell.consent] paths` subtree grammar's 2026-08-31 amendment (component-wise match, not string prefix, specifically to close a sibling-typosquat/`..`-escape footgun). This is the right generic mitigation for CWE-59/CWE-61/CWE-367-class link-following and directory-escape bugs, and the fact that ocx independently reached it twice is evidence of a systemic posture, not a one-off fix.
- **Digest-addressed content as a substitute for path containment where no local path exists yet.** `.shimref`'s documented "no E3 containment defense-in-depth" residual, compensated by digest-verified fetch — same reasoning as Sigstore/in-toto's "identity of content over identity of location." Correct pattern for the deferred-pull case.
- **Global-tier-only session PATH; project-tier PATH only through an explicit or consent-gated channel.** rustup's `~/.cargo/bin` (only ever populated by an explicit `rustup toolchain install`, never by a cloned repo) is the direct precedent for D5/D8's choice to register only `$OCX_HOME/toolchain/bin` at session level, never a project's `.ocx/toolchain/bin`.

## Key Findings

1. **rustup removed implicit `rust-toolchain.toml` auto-install in 1.28 with no opt-out** — it simply stopped happening on invocation. The team's own framing was "a source of confusion," not a CVE, but the direction matches every other tool surveyed: don't let a project file trigger a fetch with no explicit trigger. [rustup 1.30 planning post](https://blog.rust-lang.org/inside-rust/2026/07/03/rustup-update-1.30/), [rustup#4216](https://github.com/rust-lang/rustup/issues/4216)
2. **mise's trust model gates code-executing config (`[env]` directives, hooks, tasks, templates), not tool-version resolution itself** — a "safe" config (plain version pins) needs no trust at all, and explicit commands (`mise install`, `mise exec`, `mise run`) "automatically trust their active config" in normal mode. Paranoid mode requires explicit, content-bound trust for every non-global config. [mise trust docs](https://mise.jdx.dev/cli/trust.html)
3. **CVE-2026-35533 / GHSA-436v-8fw5-4mj8 (mise, CVSS 7.7, published 2026-04-03, fixed in 2026.6.4):** mise loaded trust-control settings (`trusted_config_paths`) from the *untrusted* local project config before running the trust check, so a malicious `.mise.toml` could set `trusted_config_paths = ["/"]` and self-certify, then reach `[env] _.source`/hooks/tasks/templates. Fix: never honor trust-control keys (`trusted_config_paths`, `yes`, `ci`, `paranoid`) from a non-global project file. [GitHub Security Advisory](https://github.com/jdx/mise/security/advisories/GHSA-436v-8fw5-4mj8)
4. **direnv gates the entire `.envrc` load behind a content-hash `direnv allow`** — because `.envrc` is imperative shell, there is no "safe subset" to auto-trust the way mise has; any edit invalidates the hash and re-arms the gate. Its optional path/pattern whitelist directive is explicitly documented as dangerous to anyone with write access to the tree. [direnv.net](https://direnv.net/), [direnv/direnv#23](https://github.com/direnv/direnv/issues/23)
5. **asdf ships no trust gate; `.tool-versions` plugins are arbitrary shell trusted purely out-of-band.** Documented by the community as a known weakness with no first-party fix (`asdf-plugin-manager` is a third-party partial mitigation, pinning plugin git ref). [asdf-arbitrary-code-execution](https://github.com/jpluscplusm/asdf-arbitrary-code-execution), [mise's own comparison-to-asdf doc](https://mise.jdx.dev/dev-tools/comparison-to-asdf.html)
6. **npm v12 (2026) defaults lifecycle scripts (`postinstall` etc.) to off**, ending the single largest historical attack vector in the npm ecosystem — the Shai-Hulud worm alone compromised 500+ packages in September 2025 using exactly this mechanism. [Semgrep: RIP npm Postinstall Scripts](https://semgrep.dev/blog/2026/rip-npm-postinstall-scripts-npm-v12-default-change/), [Unit42: Shai-Hulud](https://unit42.paloaltonetworks.com/npm-supply-chain-attack/)
7. **"npm bin entry harvesting" (August 2026):** 21 packages squatted the `bin` field of `package.json` — a surface entirely distinct from package-name squatting — to claim executable names including ones that could shadow `node`/`npm` once linked into `node_modules/.bin` and put on `$PATH`. None of npm's existing dependency-confusion mitigations (scoped publishing, registry allowlists, lockfile pinning) cover this gap. **Direct precedent for OCX's D2**: a `binaries` claim in package metadata is the same primitive, and D2's dedup rule currently makes a name collision debug-only, never a warning. [safedep.io: npm Bin Entry Harvesting](https://safedep.io/google-dep-confusion-bin-harvesting/), [Socket.dev: npm bin script confusion](https://socket.dev/blog/npm-bin-script-confusion)
8. **CWE-426 (Untrusted Search Path) vs. CWE-427 (Uncontrolled Search Path Element):** 426 applies when the attacker controls the search-path value itself; 427 applies when the path is fixed but the attacker can write into one of its locations. A `${workspaceFolder}/.ocx/toolchain/bin` entry an IDE or devcontainer feature puts on a terminal's PATH is CWE-426-shaped and — critically — is **outside ocx's own consent model entirely**, since ocx has no visibility into IDE-managed PATH composition; D8 already names this exposure path but does not frame it as a security residual. [CWE-426](https://cwe.mitre.org/data/definitions/426.html), [CWE-427](https://cwe.mitre.org/data/definitions/427.html)
9. **CWE-59/CWE-61 (link following) and CWE-367 (TOCTOU)** are the standard classification for symlink/junction-based redirection and check-then-use races; the standard mitigation is re-validating at time of use rather than trusting a prior write-time guarantee, which is exactly what ocx's shim sidecar readers already do independently of the writer (`core.rs:127-135`, "the reader re-validates independently rather than trusting what wrote the file"). [CWE-59](https://cwe.mitre.org/data/definitions/59.html), [CWE-61](https://cwe.mitre.org/data/definitions/61.html), [CWE-367 mitigation guidance](https://dipsylala.github.io/FlawFixingGuidance/CWE-367/)
10. **Windows junctions require no admin privilege to create** (unlike NTFS symlinks), only write access to the parent directory and an empty target — this is exactly the primitive `pkg_root_allowed`'s component-wise, post-canonicalization containment check defends against; Windows 11's own RedirectionGuard mitigates the same class at the OS level via creator-identity stamping, which is a system-level version of the same idea ocx already applies at the application level. [NTFS junction abuse Q&A](https://www.securityscientist.net/blog/12-questions-and-answers-about-ntfs-junction-abuse/), [NTFS reparse point / RedirectionGuard](https://en.wikipedia.org/wiki/NTFS_reparse_point)
11. **rustup's proxy-integrity check is a heuristic (hard-link/binary comparison), not cryptographic:** cargo detects whether `rustc` on PATH is a rustup proxy by comparing it against the known rustup binary, then dispatches directly to `$RUSTUP_HOME/toolchains/$TOOLCHAIN/bin/$TOOL` if so. ocx's `.shim`/`.shimref` design (32 KiB cap, byte-exact single-line grammar, digest-addressed pinned identifiers, canonicalized containment allow-list) is meaningfully stronger than this — worth stating as a positive differentiator, not a gap to close. [Rustup Proxies concept page](https://rust-lang.github.io/rustup/concepts/proxies.html)
12. **HKCU\Environment writes require `WM_SETTINGCHANGE` broadcast** (`SendMessageTimeout(HWND_BROADCAST, ...)` with `lParam = "Environment"`) or changes are invisible until logoff/logon; any `%VAR%`-bearing value must be stored as `REG_EXPAND_SZ`, not `REG_SZ`, or it will not expand on read. Neither requirement is optional; both are implementation-correctness risks for D5, not just documentation items. [WM_SETTINGCHANGE docs](https://learn.microsoft.com/en-us/windows/win32/winmsg/wm-settingchange), [registry env var notes](https://renenyffenegger.ch/notes/Windows/registry/environment-variables)
13. **`environment.d` supports `$PATH`-relative expansion by design** (session-manager environment composition, distinct from the "avoid `$PATH`/`$HOME` in unit files" guidance that applies to systemd *service* units — a different mechanism entirely). Files should carry standard owner-only-write permissions; nothing found suggests OCX needs anything beyond routine permission hygiene here (CWE-732 class, generically).
14. **LaunchAgent plists must be `0644`** or launchd refuses to load them ("dubious permissions on file"); `launchctl setenv` scope is future-process-only within the current session, not persisted across reboot unless the agent re-runs at `RunAtLoad`. Matches D5's stated design exactly — no gap found, but worth a plan-level test item since the failure mode (silent non-load) is easy to miss. [launchd.info](https://www.launchd.info/)
15. **PATH-prepend is the standard "dangerous direction"** in the generic privilege-escalation literature (first match wins, so a prepended attacker-controlled directory silently shadows a legitimate binary) — but every version manager surveyed (rustup, mise, asdf, pyenv, nvm) prepends by design, because shadowing the system copy *is* the product. The generic guidance does not transfer to "should ocx prepend" — it transfers sharply to the *specific subset* of names that should never be silently shadowed regardless of lock/pin state (see Recommendation). [unix-ninja: the dangers of prepending PATH](https://www.unix-ninja.com/p/the_dangers_of_prepending_path)
16. **Homebrew's official-tap namespace is PR-curated**, which structurally rejects typosquats before they exist in the namespace; real-world attacks against Homebrew instead target the *install script/website* (fake `brewe.sh` mirrors), not formula names. Scoop's model is looser for third-party buckets and has had its own shim-related AV/trust confusion incidents. Neither model transfers directly to OCX (any OCI registry, no ocx-side name curation), which is why the runtime-side mitigation in Finding 7 matters more for OCX than it does for Homebrew. [Homebrew Security and Supply Chain](https://docs.brew.sh/Homebrew-Security-and-Supply-Chain), [Intego: Homebrew-mimicking malware](https://www.intego.com/mac-security-blog/intego-discovers-new-cuckoo-mac-malware-mimicking-homebrew/)

## Recommendation

**D4 — confirmed, one residual to name explicitly.** The consent/no-consent split matches the norm every surveyed tool converges on (gate the ambient trigger, not the explicit command), and the "consent before parse" ordering already defends the exact class that produced CVE-2026-35533 in mise — this should be stated in the ADR as a validated design choice, with the mise CVE cited as the concrete case it prevents. The one gap: an IDE or devcontainer feature putting `${workspaceFolder}/.ocx/toolchain/bin` on a terminal's PATH (D8 already names this path) does so **outside ocx's consent model entirely** — this is CWE-426-shaped and should move from an implicit mention into the ADR's explicit "residual risk accepted" register, because VS Code's Workspace Trust does not uniformly gate terminal-profile PATH the way it gates task execution.

**D2 — sharpen, do not block.** Keep the last-wins dedup semantics (an explicit owner decision, correctly reasoned for the ordinary case). But demote the "debug-level only, never a warning" rule for one narrow, denylisted subset of names that should never silently shadow regardless of which package claimed them first: `sudo`, `su`, `ssh`, `git`, `curl`, `wget`, `sh`, `bash`, `cmd.exe`, `powershell.exe`, plus whatever ocx itself ships (`ocx`). Surface a WARN (at render time — `ocx pull`/`ocx shell state`) when a `binaries` claim or entrypoint collides with that set. This is the direct, current-month precedent from the npm bin-entry-harvesting campaign, and it costs nothing structural — only a diagnostic-severity change.

**D5 — confirmed correct scope, add implementation-correctness test items.** Global-tier-only session PATH registration mirrors rustup's `~/.cargo/bin` boundary exactly (always user-explicit, never repo-mutable) — no change needed. Add to the plan's "per-platform verification" item: (a) `REG_EXPAND_SZ` vs `REG_SZ` correctness if any written value ever carries a `%VAR%` token; (b) `WM_SETTINGCHANGE` broadcast confirmed to reach *new* child processes of already-open shells (existing shells will not see it without a manual refresh — this is expected and matches Chocolatey's own documented `refreshenv` workaround, not a defect to fix); (c) `environment.d` and LaunchAgent plist files written with standard owner-only-write permissions, and a test that a `0644`-violating LaunchAgent plist is caught (launchd's failure mode there is a silent non-load). `OCX_NO_MODIFY_PATH` naming is confirmed against uv's `INSTALLER_NO_MODIFY_PATH` precedent — no change.

**D6 — confirmed, no change.** Heal-before-emit is the structural equivalent of the problem rustup's hard-link proxy-identity check exists to solve (a stale trampoline surviving a toolchain upgrade); no gap found.

**Not part of D2/D4/D5/D6 but worth recording as a strength:** the `.shim`/`.shimref` sidecar design (byte-capped, single-line, digest-pinned, canonicalized-and-component-wise-contained, independently re-validated on read) is stronger than every shim/proxy mechanism surveyed (scoop's `shim.exe`, rustup's proxy heuristic) — no library or pattern to adopt here, this is already best-in-class among the prior art checked.
