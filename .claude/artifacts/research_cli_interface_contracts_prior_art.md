# Research: CLI machine-interface contracts — prior art

## Metadata
- date: 2026-09-25
- method: web scan (WebSearch + WebFetch, ~20 queries across 4 axes)
- scope: contract description formats, automated breaking-change detection, JSON-Schema-to-SDK codegen, shell-out-vs-library SDK architecture

## Axis 1 — Contract description of CLI output

- **cargo metadata / cargo book**: `format_version` field (currently `1`); explicit compat rule — adding new fields and adding new enum-like values are non-breaking; version bumps only on true incompatibility. [Cargo Book](https://doc.rust-lang.org/cargo/commands/cargo-metadata.html)
- **cargo --message-format=json**: stable JSON-lines stream; Cargo's own stance is that a genuine break gets a *new flag value* (e.g. hypothetical `json-v2`), not an in-place version bump. [rustc/cargo forum thread](https://users.rust-lang.org/t/how-stable-is-cargos-message-format-json/15662), [External Tools](https://doc.rust-lang.org/cargo/reference/external-tools.html)
- **terraform show -json / terraform-json**: `format_version` (e.g. `"1.0"`) introduced formally in Terraform 1.1.0; minor bumps = backward-compatible additions, major reserved for breaks. [JSON output format](https://developer.hashicorp.com/terraform/internals/json-format)
- **Kubernetes**: version travels *inside every object* (`apiVersion: apps/v1`), not as a wrapper field; explicit deprecation policy — GA ≥12 months/3 releases, beta ≥9 months/3 releases, alpha no guarantee. Server-side conversion lets multiple versions be served at once — a pattern tied to having a long-lived server, not obviously transferable to a stateless CLI. [Deprecation policy](https://kubernetes.io/docs/reference/using-api/deprecation-guide/)
- **gh CLI**: field-allowlist model (`--json field1,field2`) rather than a versioned schema document; convention is "consumers ignore unknown fields," not a checked version number. [gh manual](https://cli.github.com/manual/gh_help_formatting)
- **PEP 691 / PyPI Simple API**: `api-version` field in the payload, clients must check it before trusting the response. [PEP 691](https://peps.python.org/pep-0691/)
- **pip install --report / pip inspect**: `version` field (currently `"1"`), changes only on backward-incompatible change — explicitly **not** a PyPA standard, governed only by pip's own process (weaker guarantee than a PEP). [Installation Report](https://pip.pypa.io/en/stable/reference/installation-report/)
- **Bazel BEP**: pure protobuf stream (`build_event_stream.proto`); schema evolution rides protobuf field-numbering rules rather than a manual version field. [Build Event Protocol](https://bazel.build/remote/bep)
- **jdx/usage (KDL usage spec)**: CLI-*grammar* spec (not output schema), exportable from clap/cobra, drives completions/docs/typed clients. Spec-file-level versioning was not confirmed (see Negative). [usage.jdx.dev](https://usage.jdx.dev/spec/)
- **clispec.dev**: JSON-Schema-validated spec document (validates against a versioned `schema/v0.3.json`); explicitly open-world — unknown properties permitted at every level, `x-` prefix convention for extensions. [clispec.dev](https://clispec.dev/)
- **Docker/Podman**: numeric API version *negotiated* at connect time (client + daemon each advertise, highest mutual version wins); `DOCKER_API_VERSION` env var pins a version for debugging. Podman runs a Docker-compat layer pinned to a fixed floor (v1.40) *and* an independently-versioned native Libpod API in parallel — two unrelated version numbers to track. [Docker Engine API](https://docs.docker.com/reference/api/engine/), [Podman REST API](https://podman.io/blogs/2020/07/01/rest-versioning.html)
- **mise**: per-subcommand `--json` flags (`ls`, `outdated`, `version`); lockfile has an explicit format version (`0` preserved rather than silently upgraded) but no found top-level output-schema version guarantee. [mise docs](https://mise.jdx.dev/cli/version.html)

## Axis 2 — Automated backward-compatibility checking

- **buf breaking (protobuf)**: four nested categories, strict→loose: `FILE > PACKAGE > WIRE_JSON > WIRE`; passing the strict tier implies passing all looser ones. Explicitly distinguishes "breaks generated source code" from "breaks wire format" — relevant because a CLI's JSON output has the same split (humans/scripts parsing text vs. SDKs binding types). [Buf breaking rules](https://buf.build/docs/breaking/rules/)
- **oasdiff (OpenAPI)**: cataloged 755 distinct breaking/non-breaking changes across 10 spec areas; `--fail-on {ERR,WARN,INFO}` for tunable CI strictness; ships a hosted PR-review workflow as the explicit human-acknowledgment mechanism for accepting a break. [oasdiff breaking changes](https://www.oasdiff.com/docs/breaking-changes)
- **Confluent Schema Registry**: BACKWARD (default) / FORWARD / FULL, plus TRANSITIVE variants (check against all history vs. just the immediate predecessor). Rules are asymmetric by design around producer vs. consumer direction. [Schema evolution](https://docs.confluent.io/platform/current/schema-registry/fundamentals/schema-evolution.html)
- **getsentry/json-schema-diff**: self-described as finding "obviously breaking changes in CI, not much more" — partial draft-07 support, `is_breaking` flag explicitly a suggestion callers are told to override via wrapper scripts. Materially less mature than buf or oasdiff. [github.com/getsentry/json-schema-diff](https://github.com/getsentry/json-schema-diff)
- **Producer/consumer asymmetry (synthesis)**: for a CLI emitting JSON, the CLI is always the producer. Adding a field or a new enum value is safe if consumers ignore unknown data (open-world/additive). Removing a field, narrowing an enum, or making optional→required is a break. cargo, terraform-json, PEP 691, and pip's report all encode this asymmetry as **prose plus a manually-bumped version field** — none of them run an automated schema differ in CI. The automated-diffing tooling (buf, oasdiff, schema-registry) belongs to the protobuf/OpenAPI/Kafka ecosystems; I found **no CLI-JSON-output tool that combines a version field with an automated CI diff gate**.

## Axis 3 — Codegen from JSON Schema into SDK languages

- **typify (Rust, Oxide)**: actively maintained, v2 rewrite in progress (May 2026). `oneOf` normalized to `exclusiveOneOf` → clean Rust enum. `anyOf` is explicitly named a weak spot — modeled as structs with optional flattened fields, not a real closed union. Has to special-case JSON Schema's native nullable (`type: [x, null]`) vs. OpenAPI's bolted-on `nullable: true`. Known gap: imperfect type-name sharing across merged schemas causes duplicated types. [typify2 WIP](https://ahl.dtrace.org/2026/05/10/typify2-wip/)
- **quicktype (multi-lang)**: documented, more severe defect — cannot process unions of *different class types* from `oneOf`/`anyOf`; silently collapses them into one class holding the union of all properties, losing discriminated-union semantics entirely.
- **datamodel-code-generator (Python/Pydantic)**: handles JSON Schema and OpenAPI input; no specific `oneOf` defect surfaced in this pass — flagged as a lead needing a hands-on check.
- **go-jsonschema (Go)**: generates structs + unmarshal-time validation, supports cross-schema `$ref` imports. Google's own `jsonschema-go` package explicitly does not validate the `format` keyword (recommends `pattern` instead) — a portability gap in that ecosystem. [go-jsonschema](https://github.com/omissis/go-jsonschema)
- Rough maturity read on `oneOf`/discriminated-union fidelity (single-pass web read, not hands-on): quicktype (documented collapse defect) worse than go-jsonschema/datamodel-code-generator (untested here) worse than typify (explicit, mostly-correct `oneOf` handling, weak only on `anyOf`).

## Axis 4 — SDK shells-out-to-binary vs. links-a-library

- **terraform-exec (HashiCorp, official)**: README states the rationale directly — shelling to the `terraform` binary via this wrapper is preferred over importing `hashicorp/terraform/command` internals, because those internals are "not intended for use outside Terraform Core." Parsing is centralized in the wrapper (terraform-json types), not left to each caller. [terraform-exec](https://github.com/hashicorp/terraform-exec)
- **Pulumi Automation API**: `LocalWorkspace`/`Stack` shell out to the installed `pulumi` binary at runtime; ships a version-compatibility check (`opts.version` validated against the installed CLI, errors on mismatch) with an explicit skip escape hatch. Pulumi is actively *moving away* from shelling out toward calling `pkg/cmd` in-process — the vendor treats shell-out as the legacy architecture, not the target state (tracked in [#7219](https://github.com/pulumi/pulumi/issues/7219), [#10000](https://github.com/pulumi/pulumi/issues/10000), [#14987](https://github.com/pulumi/pulumi/issues/14987)).
- **Docker**: `docker/cli` is itself built on the same Go SDK client library it ships publicly — shell-out and library-linking aren't fully separate paths at the vendor level. Version-skew handling is a real connect-time negotiation (client/daemon each advertise, highest mutual version auto-selected); `DOCKER_API_VERSION` pins a version for debugging. This is the most mature version-skew mechanism found in the scan. [Docker Engine API](https://docs.docker.com/reference/api/engine/)
- **Podman**: two parallel APIs at different maturities — Docker-compat layer pinned to a fixed historical floor for interop tooling, plus an independently-versioned native Libpod API exposing Podman-only features. Two unrelated version numbering spaces to track simultaneously.
- **gh CLI (go-gh)**: hybrid — go-gh is a library scoped narrowly to auth/HTTP-client plumbing, plus an `Exec()` helper that "safely shells out to gh" for anything else. Precompiled binary extensions exist specifically so extension authors need only the `gh` binary + a release convention, not the `gh` Go internals — closer to CLI-as-the-contract than to bound-library. [go-gh](https://github.com/cli/go-gh)

## Negative

- No CLI-JSON-output producer found (cargo, terraform, gh, pip, docker) runs an automated schema-differ in CI against a published baseline — all rely on hand-written prose ("adding fields is safe") plus a manually-bumped version field. The "format_version + automated diff" combination I expected to find does not appear to exist in practice; the two mechanisms live in separate ecosystems.
- Kubernetes' apiVersion-in-payload model (multiple versions served simultaneously via a conversion layer) was not observed in any *CLI* tool in this scan — it appears tied to having a long-lived server, and should not be assumed transferable to a stateless CLI without checking whether OCX's index/registry (`ocx_index`) resembles a server closely enough.
- jdx/usage's own spec-file version-checking story was not confirmed — `WebFetch` of usage.jdx.dev/spec/ returned no explicit statement about a schema-version field consumers can check before trusting an exported spec. Unresolved, not "absent."
- Terraform's "minor bump = backward compatible" claim comes from a HashiCorp docs page stating the *policy*, not a changelog cross-check confirming it was honored release-over-release. Treat as documented intent, not verified history.

## Leads

- **codegen-eval**: hands-on test of datamodel-code-generator and go-jsonschema against an OCX-shaped `oneOf`/discriminated-union schema (e.g. something `ocx.lock`-like) before picking a codegen tool — this pass only surfaced secondhand claims.
- **schema-diff-ci**: evaluate whether a lightweight producer-side CI gate (buf-breaking-style tiering, applied to `ocx_schema`'s generated JSON Schema between releases) is worth building, since no off-the-shelf tool combines CLI-style version fields with automated diffing.
- **sdk-architecture-decision**: if/when OCX grows a language SDK, terraform-exec's "shell to the supported CLI binary, never internal crate types" model matches OCX's existing internal/ecosystem/interface tier split (`adr_crate_split_workspace.md`) — worth an ADR cross-reference once an SDK is actually proposed.
- **version-negotiation-precedent**: Docker's connect-time API version negotiation is the most mature version-skew mechanism found — worth revisiting only if `ocx_index` ever needs client/server skew handling beyond `ocx.lock` versioning.
- **clispec-vs-usage adoption check**: clispec.dev and jdx/usage both target a portable CLI-grammar spec; neither had an obvious adoption-scale signal (stars/downloads) surface in this pass — needs a dedicated adoption check before treating either as "trending."
