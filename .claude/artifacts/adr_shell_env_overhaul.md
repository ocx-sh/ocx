## Context

OCX has three shell-env surfaces and a lifecycle for none of them:

- `ocx self activate` — global scope, evaluated once per shell start from the `env.*` shims, never re-evaluated. A global-toolchain change or a `self update` leaves every running shell stale.
- `ocx direnv export` — project scope, stateless, bash-only, requires direnv installed plus `direnv allow` ceremony per `.envrc` edit.
- `ocx run --` / `--ci` — one-shot, no session.

Consequences: post-`ocx update` staleness in the same shell; project switching needs a third-party tool; Windows and nushell have no project story at all; and this repository's own toolchain bootstraps through direnv, a self-hosting cycle.

**The links initiative is not a prerequisite.** The reconciler drives current env **C** toward desired env **D** regardless of whether D's strings are digest paths or link paths; element ownership is a prefix test that covers both shapes. Links buy a per-prompt no-op in the common case — an optimization. The two initiatives also solve disjoint classes: this ADR reaches shells at the next prompt (enter/leave, project switch, post-update staleness); [#189](https://github.com/ocx-sh/ocx/issues/189) reaches processes that never re-read env (a running IDE holding `JAVA_HOME`). Either may land first.

## Decision Drivers

- **D1 — never clobber a foreign write, and say exactly where "structurally" ends.** The direnv [#82](https://github.com/direnv/direnv/issues/82)/[#1249](https://github.com/direnv/direnv/issues/1249) whole-env-capture class is structurally impossible here: keys outside D ∪ L are never read or written, and list-kind vars are only ever element-added and element-removed, which commutes with any foreign edit. **Constants in D are the bounded exception, not a structural guarantee** — when a project's own `[env]` changes, its new intent overwrites the key, by design (Decision 3). The exception is bounded by the `D ≠ L` gate, by prior re-capture, and by one summary line; it is not absolute, and asserting D1 without the carve-out is what let an earlier draft ship a rule mise had already reverted.
- **D2 — convergence over atomicity.** Shell-land has no transactions. Every prompt re-converges; races self-heal.
- **D3 — the hook must never break a prompt.** Malformed state degrades, logs once at debug, exits 0. `set -u`-safe by construction.
- **D4 — per-prompt cost is a budget, not an aspiration.** The no-op path is stat-only; the number is asserted in CI.
- **D5 — no ceremony proportional to editing.** Consent is bounded to real risk, not to file mtime.
- **D6 — wire-format firewall.** Package metadata `Env`, `ocx.lock`, OCI manifests and the `OCX_ENV` forwarding contract are untouchable. All new semantics live in session-internal or machine-local state.
- **D7 — per-shell mechanism honesty.** PowerShell and nushell are first-class *and* divergent. No parity claim without a demonstrated primitive.
- **D8 — one key, one state root.** Three coexisting project-keying schemes is the defect; a fourth is not the fix.

## Decision 1 — Private state carrier: `__OCX_ENV_STATE`

One environment variable. Its value is `<envelope tag>.<encoded payload>` — encoder `1` is base64url(compact JSON), uncompressed. 16 KiB hard cap on the whole value.

### Options

| Criterion (weight) | A: N flat vars (`_OCX_OLD_PATH`, venv/conda) | B: one blob, base64(JSON) **(chosen)** | C: one blob, msgpack→zlib→base64 (mise) | D: on-disk, session-keyed |
|---|---|---|---|---|
| Threading through 10 shell grammars (×3) | poor — N reserved names × 10 emitters | good — one opaque string | good | good |
| Nested-shell inheritance correctness (×3) | ok | **correct** — inherited atomically with the env it describes | correct | **broken** — a subshell that cd's elsewhere corrupts the parent's view |
| Payload fit (×2) | n/a | good — hundreds of bytes to low KB | over-built for this payload | good |
| Debuggability (×1) | best | ok — one `base64 -d` | poor — opaque | good |
| Failure mode under corruption (×2) | silent wrong restore (conda [#12769](https://github.com/conda/conda/issues/12769)) | rebuild from truth | rebuild from truth | stale-lock wedge (pyenv [#2829](https://github.com/pyenv/pyenv/issues/2829)) |

**B.** Environment placement is *correctness*, not preference: a nested shell must inherit the applied env and the ledger describing it in one atomic act. base64url is not decoration — it removes every per-shell quoting hazard at once, including `cmd.exe`'s `%VAR%` expansion inside a JSON payload and elvish's rejection of `\$` in double-quoted strings — the same fact that governs `Shell::export_constant`'s Elvish arm, which emits exactly that rejected form today and is corrected to avoid it (A-15). **Compression is still rejected, but the reason it was rejected before was false and is withdrawn.** That reason was dependency cost. There is none: `flate2 = "1.1.9"` and `zstd = { version = "0.13", features = ["zstdmt"] }` are workspace dependencies (`Cargo.toml:147,154`) and are **already linked into `ocx_lib`** (`crates/ocx_lib/Cargo.toml:63-64`) for tar+gzip and tar+zstd OCI layers. Compressing here adds a code path, not a crate — and Choose Boring Technology argues *for* reusing an encoder already in the binary, never against it. Re-decided on what it buys and what it costs. **Buys**: the payload is dominated by repeated `$OCX_HOME/packages/<registry>/<algo>/<hex>/…` prefixes, which deflate extremely well, so it is real headroom against the 16 KiB cap. **Costs, none of them dependency cost**: base64url re-expands the compressed bytes by 4/3, eating part of the gain against a cap the expected payload already sits several times under; the value stops being one `base64 -d` from readable, which is the Debuggability row above and the difference between diagnosing a bad ledger from a bug report and asking for a repro; and a binary container is precisely what makes an in-payload version unreadable — the problem the envelope tag exists to solve. **So: encoder `1` (uncompressed) ships, and compression is admissible only as a future envelope tag — never as a flag, never as a sniff.** The trigger is named rather than left to taste: if the NFR benchmark's encoded ledger for a real project exceeds **4 KiB** (a quarter of the cap), add encoder `2` = deflate. That is a one-tag change with no migration, no new dependency, and an older binary that repairs rather than misreads.

### Contract

- **Name** `__OCX_ENV_STATE`. Already inside the `__OCX_*` namespace `is_reserved_ocx_key` gates (`env.rs:1143-1146`) and that `ocx-sdk-python` independently rejects at exit 64. No new reservation needed.
- **Envelope tag — outside the payload, and that is the whole point.** The value is `<tag>.<payload>`: one ASCII digit naming the **encoder**, a `.` separator (absent from the base64url alphabet, so the split is unambiguous and needs no length prefix), then the encoded payload. `1` = base64url(compact JSON), uncompressed — the only encoder this ADR defines. An earlier draft rested the whole upgrade story on the `v` field *inside* the JSON, which is wrong: a version inside the payload is readable only once you already know how to decode the container, and any future encoder that compresses makes that container binary, so nothing in it — `v` included — is readable before the decode step. **Two versions, two jobs**: the **envelope tag** selects the decoder and is bumped by a change in *encoding* (compression, a different container, a different transfer alphabet); the **schema `v` inside the decoded payload** describes the field layout and is bumped by a change in *shape* (a new scope slot, a renamed field, a new `priors` variant). A change that is both bumps both. **An unrecognised tag, a missing `.`, or a payload that does not decode ⇒ treat as absent**, the same degradation path as a corrupt ledger below — which is exactly what lets a future ocx introduce encoder `2` with no migration and no dual-read window: an older binary sees `2.…`, does not know the tag, and repairs instead of misreading.
- **Shape** `{ v: 1, fp: <watch-set fingerprint>, verdict?: "inert" | "noproject", scopes: { global?: Applied, project?: { key, dir, applied, priors } } }`, where `priors` records `Unset | Value(String)` per constant-kind key and `verdict` is the negative cache (Decision 5): `"inert"` for a consent-refused project, `"noproject"` for a walk that resolved none — the latter is not consent-derived, so it leaves C-007 untouched and is expired by `project_dir`'s membership in `fp`.
- **There is no reusable `Entry` serialization — the earlier claim was wrong.** `package::metadata::env::entry::Entry` derives `Debug, Clone` only (no serde at all); `ModifierKind` derives `Serialize` without `Deserialize` (`env/modifier.rs:75`); the one serialized entry shape in the tree is `ocx_cli::api::data::env::EnvEntry` (`api/data/env.rs:71`), which is `Serialize`-only, lives in the **CLI** crate `ocx_lib::shell::reconcile` cannot depend on, and renames the field `kind` → **`type`** — the spelling the nushell shim already parses (`shims.rs:212`, `$_ocx_e.type == "path"`). Concretely: add `Deserialize` to `ModifierKind` (one derive, it already carries `Serialize` + `JsonSchema`), and define `LedgerEntry { key, value, #[serde(rename = "type")] kind: ModifierKind, #[serde(skip_serializing_if = "Option::is_none")] separator: Option<String> }` in `ocx_lib::shell::reconcile` with `From<&Entry>`. **The wire field is `type`, never `kind`**, and a unit test asserts field-name parity with `EnvEntry` — that parity is what D6's "no second schema" actually buys, since the vocabulary (`ModifierKind`) is shared. Rejected alternative: hoisting `EnvEntry` down into `ocx_lib`; its `source: Option<EntrySource>` field is CLI-side patch provenance the ledger has no use for, so the move costs more than the parity test.
- **Invariant L-1 — the ledger stores fully-interpolated, literal, self-contained final values.** Every `applied` value and every `priors` value is the exact string ocx wrote or the exact string it found, byte for byte. The ledger never stores a *reference* that has to be re-interpreted at revert time — not a package digest to re-resolve, not an `ocx.toml` key to re-read, not a template to re-interpolate. **Rejected** (owner decision, recorded here so later edits stop nibbling at it): storing package-digest references and re-deriving entry values on the revert path. Two reasons, either one sufficient. (1) **Re-derivation's inputs move independently of the shell that wrote the ledger.** `ocx.toml`, `ocx.lock` and the interpolation rules all change out from under a live session; a shell must be able to revert exactly what it applied an hour ago even though the project file has changed twice since. A re-derived revert undoes a value that was never applied — the same class of defect as direnv's byte-snapshot restore, arrived at from the opposite direction. (2) **Re-derivation puts store I/O on the per-prompt path** (D4, whose no-op is stat-only) **and stops working outright once the package is GC'd**, which is an ordinary event this repo ships a command for, not an edge case. The invariant in one line: **anything the revert path needs must already be in the ledger as a literal string.** It is also what makes the 16 KiB cap the right shape of backstop — the payload is deliberately the largest it can be, because nothing in it is a pointer.
- **Invariant L-2 — the ledger stores raw, unescaped values; escaping happens only at emit time, per shell arm.** The payload holds keys, values and kinds. It never holds shell text. This is what makes **cross-shell inheritance** correct rather than accidental: `bash -c` under zsh, `exec fish` from bash, a `pwsh` launched from either — each inherits the carrier verbatim and each reconciler emits **its own** syntax from the same raw values, through that arm's escaper (Component Contracts: `escape::posix_single_quoted` for bash/zsh and the strict-POSIX trio, `escape::single_quoted_doubled` for PowerShell/elvish, `escape::fish_double_quoted` for fish, `escape::nushell_plain_string` for nushell — all in `shell/escape.rs`) — this map governs the **element-match / `export_path`** emit path specifically; `export_constant` used one shared double-quoting escaper on *every* arm before A-15, a discrepancy A-15 corrects so each arm's constant emit matches that arm's own escaper (`shell.rs:762-782`). Any reconciler can therefore interpret a ledger any other reconciler wrote. A pre-escaped value leaking in would be **double-escaped** by the inheriting shell and single-escaped correctly by none, precisely because the escapers differ per arm — the failure would be silent and per-value. The invariant also keeps L's stored value directly comparable to C for the `C == L.applied` exit guard, which reads the shell's own *unescaped* value. The inverse direction is already closed by the env-carrier choice itself (the options table above): a subshell that `cd`s elsewhere rewrites the carrier **in its own environment only**, leaving the parent's view intact — which is why B beats the on-disk option D, and why raw values cost nothing here.
- **Over cap ⇒ marker-only ledger.** One rule, no ladder: if the encoded value exceeds 16 KiB, `Ledger::encode` emits a **marker-only ledger** — `{ v, fp, verdict, over_cap: [scopes] }`, both scope payloads dropped, roughly 60 bytes — and the variable is **omitted entirely** only if even that fails to encode (unreachable in practice); every scope named in `over_cap` operates in repair mode, with one summary line emitted per transition into that state, not per prompt. Omitting the variable outright, as an earlier draft did, destroys the fingerprint along with the payload — `fp` lives *inside* the ledger (below) — so the next prompt sees no recorded `fp`, recomposes, re-overflows, omits again, and prints again, every prompt, for the life of the shell; that is a worse outcome than the reporting gap it was meant to avoid, and it breaks the stat-only no-op budget this design otherwise guarantees (A-01). The superseded ADR's three-rung degradation ladder is still **dropped**, and its two lossy rungs are still why: dropping `priors` first discards the one datum nothing else can reconstruct (Decision 3's prefix test repairs lists; nothing repairs a prior), and dropping `applied` list-element records makes arbitrary — i.e. project `[env]` — PATH elements structurally unremovable for the rest of the session, on the project's own authority and with no forgery required. Decision 1's own measurement ("hundreds of bytes to low KB") is the same argument that rejects compression: a cap plus a recoverable marker is the whole mechanism; add a ladder if the cap is ever actually hit.
- **On the cap number, honestly**: 16 KiB against Windows XP/2003's 32767-char *whole-block* limit is a factor of **two**, not an order of magnitude, and it is two against a budget shared with every other variable in the block. Linux's 128 KiB `MAX_ARG_STRLEN` is the non-binding limit. The cap is a backstop against a pathological monorepo, not a working budget — the expected payload is two orders of magnitude under it. (The predecessor set 8 KiB on the same reasoning; the doubling is deliberate here only because the ladder that used to soften an overflow is gone.)
- **Degradation rule** — truncated, non-decoding, or `v` unrecognised ⇒ treat as **absent**: rebuild D from truth, repair lists **by the retirement rule** — *remove every prefix-owned element that is not in D*, which is subtractive and not the additive "ensure D's elements are present" (Decision 3, Retirement) — and leave constants in place (never guess-unset `JAVA_HOME`). **A genuinely absent ledger and a corrupt one take the same *code* path but are not the same situation, and the distinction is normative**: the first prompt of a shell has an absent ledger with nothing applied, so it is an apply-without-revert and there is nothing to repair; a corrupt ledger means a scope *was* applied and its record is gone, so the prefix repair actually runs. Both end at "rebuild D from truth"; only the second can leave arbitrary (non-`$OCX_HOME`) elements stranded, and only the second emits a line. Log at **debug**, never warn: an absent ledger is the normal first-prompt case, and this repository's doctrine forbids warning on common benign states. Never direnv's hard refuse — a reconciler that can brick a prompt on a bit flip is worse than a stale prompt.
- **The repair gesture is `unset __OCX_ENV_STATE`, and there is no command for it.** Clearing the variable makes the next prompt see an **absent** ledger — a path this decision already specifies in full (rebuild D from truth, repair lists by the retirement rule, leave constants in place). Because the fingerprint lives *inside* the ledger, clearing it also forces the fingerprint to be recomputed, so one gesture covers both failure modes a user can actually hit: *"detection went stale"* (the mtime+size ceiling in Decision 3 hid a write) and *"the ledger is wrong"* (a corrupt or hand-mangled carrier). No new command, no new code path, nothing to test that the degradation rule does not already test. **Its cost, stated honestly rather than buried:** `priors` are destroyed with the ledger, so constants can no longer be restored when the scope is later left — after this gesture `JAVA_HOME` keeps pointing at the project's value for the rest of that shell's life, because nothing records what it was before. A **new shell** is therefore the clean floor and the better advice whenever one is cheap: a new shell has no priors, so it loses nothing. **The consequence accepted knowingly:** documenting the gesture makes `__OCX_ENV_STATE` a **user-facing contract** — it can no longer be renamed freely. That is acceptable and not a new constraint of substance: it already sits in the reserved `__OCX_*` namespace `is_reserved_ocx_key` gates and `ocx-sdk-python` rejects writes to, so the name was never going to move quietly. **The gesture is silent by construction**: the hook cannot distinguish a deliberately-cleared ledger from the ordinary first-prompt absence, which logs at debug by design (no WARN on a common benign state), so nothing confirms it worked at the prompt — `ocx shell state` (Decision 10) is what confirms it.
- **Forgery posture: unauthenticated, matching direnv, mise and conda — but the earlier "worst case is a wrong diff" claim is withdrawn.** It was false against this decision's own shape. Read literally, the ledger carries an attacker-chosen `kind` (forge `PATH` as `Constant` with `priors["PATH"] = Value("/attacker/bin")` and `applied["PATH"].value` set to the shell's real `PATH`; the exit rule "restore the prior only if `C == L`" then holds, because the forger authored both operands, and leaving the project sets `PATH=/attacker/bin`) and an attacker-chosen `key` (`../../..` traverses out of `$OCX_HOME/state/projects/`). Neither is a wrong diff.
- **Three normative rules replace the claim.** (a) `key` and `dir` are **advisory only** — re-derived from the CWD walk every prompt, never used to construct a path; a `dir` that does not match the walk's result means that scope has been **left**: its `applied` map becomes the revert set, executed before any newly discovered scope is applied, rather than the ledger being invalidated wholesale (A-03). (b) `kind` and `separator` are **re-derived from D** for every key present in D; L's copies are used only for the revert set, and a `priors` restore never runs for a key that D currently declares list-kind. `plan` additionally refuses `ModifierKind::Constant` for `PATH`/`PATHEXT` — compared through `EnvKey` so the refusal is case-insensitive on Windows — so a ledger entry recording either key as `Constant`, or carrying a `priors` entry for either, is discarded on decode without acting; rule (b) alone has no operand to act on when D names the key nowhere at all (A-02). (c) **An L entry may only ever undo itself.** For a constant that means restoring its own recorded `priors` under the `C == L.applied` guard; for a list, removing the elements it itself records. It never selects a value for a key it is not reverting, never overrides the kind D declares for a key D declares, and never names a path. **This corrects an earlier rule (c)** — *"an L entry whose key is in neither D nor the prefix-owned set is discarded, not acted on"* — which was a real defect, not a tightening: on `cd` out of a project, a project constant is by definition no longer in D (that is what leaving means) and is not prefix-owned either (prefix ownership covers `$OCX_HOME`-rooted list elements, not arbitrary constants), so the old rule **discarded `JAVA_HOME` instead of reverting it** and leaked the project's value into the rest of the session — breaking the primary revert case this whole decision exists for. The revert set is defined properly in Decision 3, and the forgery vector the old rule was aimed at (an L entry naming `LD_PRELOAD` that D never mentions) is bounded by the equality guard below **among equal principals only** — the guard does not hold across a privilege crossing, stated in full after the next bullet (A-06). The honest posture: *the carrier is untrusted input whose only permitted effects are to name the revert set and to supply the equality operand for the exit guard. It never names a path, never selects a kind for a key present in D, and never widens the set of keys ocx touches beyond D ∪ L.*
- **What forging it is worth, stated plainly.** Setting `__OCX_ENV_STATE` requires the ability to set an arbitrary variable in the victim's shell — which is the ability to set `PATH` directly. The carrier is therefore **not a privilege boundary** and authenticating it would buy nothing; the three rules above exist so that a *bug* in the ledger's producer cannot become a value-selection primitive, not because an authenticated carrier would stop an attacker who already has the env.
- **That posture holds only among equal principals, and the residual across a privilege crossing must be named rather than assumed closed.** Rule (c)'s constant arm restores `L.priors[k]` under the `C == L.applied` guard, and the revert set is L-scoped and deliberately not intersected with D (below) — so under `sudo -E`, where the carrier crosses into a shell of different privilege, a forged entry naming a key D never mentions is still in the revert set and the forger authors both operands of the guard: an **arbitrary-value-for-arbitrary-key** primitive (`LD_PRELOAD`, `PYTHONPATH`, `GIT_SSH_COMMAND`), not mere removal. The carrier is trusted at exactly the privilege level of the process that set it; ocx does not defend a privilege crossing, and authenticating the carrier would not change that — any key an unprivileged forger can read is no key at all. The real mitigations live outside ocx: `sudo`'s `env_reset` / `secure_path` defaults (which `-E` is a deliberate opt-out of), `unset __OCX_ENV_STATE` in the privileged shell (this decision's own repair gesture, above), and `ocx shell state` as the way to see a forged scope before it acts (A-06).
- **Spoof-channel closure (carried from the superseded ADR, and widened by this one).** `is_reserved_ocx_key` has exactly three call sites: `ocx_cli/src/options/env_override.rs:170` (`ocx run --env`), `ocx_lib/src/env.rs:1406` (the `OCX_ENV` decode) and `ocx_lib/src/project/env.rs:158` (project/group `[env]`). **None is in package metadata or the composer** — `Var.key` is a plain `String` — so package-declared env vars are entirely ungated against the `OCX_*` namespace, and a published package can declare a constant named `__OCX_ENV_STATE`.
- **This ADR turns that from a wrong-diff nuisance into a consent bypass, so closing it is a precondition, not a carry-over.** The decisions below introduce `OCX_CONSENT_PATHS`, `OCX_CONSENT_NAMESPACES` and `OCX_NO_HOOK`, and that env channel is deliberately **additive** — unioned with the config tiers. A publisher inside **one** already-consented namespace ships metadata setting `OCX_CONSENT_NAMESPACES = "*/*"`; it composes into the user's shell at the next prompt, is inherited by every child process, and silently converts the whitelist into allow-all. `OCX_NO_HOOK=1` is the denial variant of the same primitive. **The env channel stays** — the owner requires it for devcontainer pre-whitelisting — which is exactly why the read-path gate has to be unconditional.
- **The gate belongs at the application seam, not the emitter.** Skip reserved keys in `Env::apply_entries` / the resolver — **not** in `conventions.rs::emit_lines`. `ocx run`, `ocx exec` and `ocx launcher exec` reach the child environment through `apply_entries` and never touch the shell emitter, so an emitter-side gate would leave the hole open on every non-interactive path (the paths automation actually uses). Equivalent alternative: widen `Env::apply_ocx_config` from its enumerated key list to a whole-namespace strip, which states the rule once for both directions. Write path unchanged: `ocx package create` hard-rejects `OCX_*`/`__OCX_*` env keys; the read path **skips with a warning**, because already-published artifacts must keep resolving. Every ledger-derived value emitted into a script passes the same per-arm escaper as a composed entry (Component Contracts).

### `OCX_ENV` is not renamed and not repurposed

The superseded ADR's Decision 8 (`OCX_ENV → __OCX_ENV`, with a one-release dual-read) is **withdrawn**. `OCX_ENV` is a live forwarding contract with real consumers: `ocx-sdk-python` documents it as opaque pass-through, aborts startup on a malformed value, rejects `OCX_*`/`__OCX_*` keys at exit 64, and **snapshots ocx's reserved-key help sentence verbatim in seven golden fixtures**; `rules_ocx` deliberately omits `OCX_ENV` from `_OCX_NEUTRALIZED_ENV` because ocx strips an inherited one on every compose (`env.rs:498-502`). Renaming it, rewording its help, or changing the stripping buys nothing this ADR needs and breaks three downstream things mechanically. The session carrier is a **separate, new variable**; the two never interact. (`find_ocx`'s `__OCX_PIN_VERSION` and friends are CMake variables, not environment variables — a spelling collision to leave alone.)

`Env::apply_ocx_config` does **not** strip `__OCX_ENV_STATE` from a child env: `ocx run -- bash` must hand the nested shell a consistent ledger.

## Decision 2 — One project key, one per-project state root

**Key**: `ReferenceManager::name_for_path(canonicalized_project_dir)` — first 16 hex of SHA-256, unchanged, already shared by `refs/symlinks/` and the projects ledger (`reference_manager.rs:59-63`, `project/registry.rs:325`). **Key derivation, stated precisely**: `name_for_path(dunce::canonicalize(canonicalize(<resolved project file>).parent()))` — the alias-collapsing canonicalization is on the **file**, at `project/registry.rs:196-198` (`tokio::fs::canonicalize`), whose `.parent()` yields the directory; the directory-level `dunce::canonicalize` at `:310` is a no-op re-canonicalization of an already-canonical directory, not the load-bearing call. Both calls are load-bearing and their order fixes the Windows form; VS Code's symlink-fork bug is what skipping the file-level canonicalization costs (A-30).

**Root**: `$OCX_HOME/state/projects/<key>/<feature>` — a new *project-scoped* branch of `StateStore`, alongside the existing *subsystem-scoped* `state/<subsystem>/<key>` branch. Those two are genuinely different axes and stay separate.

### Options

| Criterion (weight) | A: `state/activation-consent/<key>` | B: promote `projects/<hash>` to a directory (research rec.) | C: `state/projects/<key>/` **(chosen)** | D: stamp inside the project (`.ocx/`) |
|---|---|---|---|---|
| Collapses the key schemes (×3) | no — a third scheme | yes | yes | yes |
| GC (×3) | none *as written* — but see the note below the table: this row does not discriminate A from C | inherits ledger GC | sweep on each stamp's own `project_dir`, one call site in `clean.rs` | dies with the project dir |
| Risk to the hardened liveness path (×3) | none | **high** — `probe_live_target` returns `Dead` for a non-symlink (`registry.rs:117-118`), so every pre-existing ledger entry reads dead on first run after upgrade → live GC roots dropped → **pinned packages collected**. Requires reading both shapes indefinitely (a data-loss failure mode, not a cosmetic one), and turns the prune from `symlink::remove` into `remove_dir_all` inside the module carrying the SEC-1 and TOCTOU guards | **none** — ledger untouched | none |
| Security (×3) | ok | ok | ok | **fatal** — a project-writable consent stamp is GHSA-436v-8fw5-4mj8 by construction |
| Absent-state default (×2) | inert | inert | **inert** — no directory means no consent, which is the correct fail-safe | inert |

**C.** The research is right that three schemes must become one; it under-weighted what `projects/<hash>` *is*. That entry is not a container, it is a liveness oracle whose semantics were hardened across two adversarial findings (SEC-1 three-state probe, CODEX-BLOCK-1 TOCTOU re-probe, CODEX-BLOCK-2 atomic staging). Option C gets the identical outcome — one key derivation, one project-scoped state root, GC off the existing ledger — without editing that oracle, and without a dual-shape read path whose failure mode is silent package collection. `state/`'s documented contract ("safe to delete at any time without integrity loss") also fits a consent stamp exactly: deleting one makes a project inert until the next explicit ocx command. Fail-safe by construction.

**Two of the table's ×3 rows do not discriminate A from C, and the verdict does not rest on them.** Once Decision 2's first line fixes one key derivation, `state/activation-consent/<key>` and `state/projects/<key>/consent.json` use the *same* key — the remaining difference is subsystem-first versus project-first nesting, i.e. layout, so scoring A as "a third scheme" imports the brief's pre-decision framing. And `state/` is GC-walked for **neither** option today (`subsystem-file-structure.md`: "**not walked** by `ocx clean`"); C gets GC only because this ADR writes a sweep, and the identical sweep over `state/activation-consent/` would be the same call site. What actually decides the table is B's dual-shape read path (real, and its failure mode is silent package collection) and D's project-writable stamp (real, and fatal). C over A is a layout preference: project-first nesting keeps everything about one project in one directory, which is what makes the `project_dir`-based sweep above a single readdir. **Decision 2 also amends `state/`'s "not walked by `ocx clean`" bullet** — say so in `subsystem-file-structure.md`, do not leave the contract quoted selectively.

### Contract

```rust
// crates/ocx_lib/src/file_structure/state_store.rs
impl StateStore {
    /// `{root}/projects/<key>/` — project-scoped state, keyed by
    /// `ReferenceManager::name_for_path(canonical_project_dir)`.
    pub fn project_state_dir(&self, key: &str) -> PathBuf;
    /// `{root}/projects/<key>/consent.json`
    pub fn consent_stamp_file(&self, key: &str) -> PathBuf;
    /// `{root}/projects/` — the sweep root for `ocx clean`.
    pub fn project_state_root(&self) -> PathBuf;
}
```

- **GC — the stamp is its own liveness oracle; the ledger is not consulted.** `ocx clean` removes `state/projects/<key>/` iff the stamp's own `project_dir` no longer exists on disk. **Not** `{ name_for_path(dir) | dir ∈ live_projects() }`, which was the earlier rule and was wrong twice over. (1) It re-derives a key the ledger already stores *as the entry filename* (`registry.rs:325-326`) from a re-canonicalized target, and the two derivations can diverge — a changed parent symlink or a case-normalizing filesystem yields a different 16-hex for the same live project, sweeping its state while its ledger link survives. (2) The ledger's population rule is strictly narrower than the consent-writer list: registration happens only on a lock **save** or a mutation **commit** (`project/lock.rs:448`, `project/mutation.rs:373`), and `live_projects()` further requires `<target>/ocx.lock` to exist (`registry.rs:127-129`). So an `[env]`-only project — which Decision 3 makes a first-class case — can never be in the ledger, and its consent stamp would be revoked by *every* `ocx clean`, silently, forever. That is the ceremony D5 exists to abolish, reintroduced on a GC schedule. Reading the stamp's own `project_dir` costs one `symlink_metadata` per stamp, needs no ledger coupling, and is correct for lock-less and locked projects alike.
- **The sweep carries the ledger prune's guards, restated because a new call site does not inherit them**: `symlink_metadata` on `<key>` (a symlinked state directory is skipped, never followed into a `remove_dir_all`), a re-probe of `project_dir` immediately before removal (the CODEX-BLOCK-1 TOCTOU pattern, `project/registry.rs:105-133`), and a skip for `.tmp-*` staging names. An indeterminate probe retains the stamp — over-retention leaves a stale stamp for a project that still exists; under-retention makes a live project inert. **The sweep precondition is two-part, and both parts must hold to remove**: `ocx clean` removes `state/projects/<key>/` only when the stamp deserializes at a `v` this binary understands **and** the pre-removal re-probe proves `project_dir` is definitively absent; unreadable, malformed, unknown-`v` and an indeterminate probe all retain, at one line logged at debug (A-31).
- **No global-tier carve-out.** An earlier draft exempted `name_for_path($OCX_HOME)` from the sweep. **Dropped as unreachable-by-construction**: the same bullet stated that the global scope needs no consent stamp at all (`$OCX_HOME/ocx.toml` is the user's own file), so nothing ever writes that directory, the exemption never fires, and no test can tell a correct implementation from a missing one — the "green that cannot be told from never ran" class this ADR's Validation section commits to refusing. **Correction (P10, 2026-08-27): the premise was false as written, and the conclusion survives on a different basis.** "Nothing ever writes that directory" was not true — `record_activation_consent` reached `consent::record_in` with `project_dir == $OCX_HOME` on any `--global` invocation of the six consent writers, and a stamp landed. Reproduced against a release binary: `ocx --offline --global lock` wrote `state/projects/<key>/consent.json` carrying `"project_dir": "<OCX_HOME>"`, and `--global run` rewrote the same key. The carve-out deletion is still right, but it is now justified by enforcement rather than by construction: **`$OCX_HOME` is refused at the write seam itself** (`consent::record_in`, device+inode via `same_dir`, matching `register`'s ARCH-1b no-self-link guard), pinned by `a44_the_ocx_home_never_owns_a_consent_stamp` — so no stamp can exist there for a sweep to need a carve-out for. **And a stamp written by a pre-guard binary is collected**: `ocx clean`'s consent sweep classifies an ocx-root stamp as invalid by *identity* rather than by liveness, which matters because the ocx root is always `Present` and the liveness path would retain it forever (`a44_consent_sweep_collects_a_stamp_recording_the_ocx_home`). Without that second half the claim would hold only for new stamps. The exemption-with-no-defender reasoning is unaffected: the guard belongs at the write, not in the sweep's key space. If global-tier state ever lands under `state/projects/`, the carve-out returns *with* the test that reds without it.
- **Two directories named `projects`.** `$OCX_HOME/projects/` (the symlink ledger — GC truth, lifetime tied to installs) and `$OCX_HOME/state/projects/` (consent stamps — deletable at any time) share a name and a key space while having opposite lifetimes and opposite failure modes. Name the distinction in `subsystem-file-structure.md`'s state-layout row, not only here.
- **Writes** go through `write_bytes_atomic`; a stamp is replaced, never edited in place, so a future multi-writer surface here uses `lock_scoped` into `$OCX_HOME/locks`, never a sidecar (Locking Policy).
- **Pre-`Context` reachability**: `self activate` constructs `FileStructure::new()` today, which already owns `state`. No pure associated fn is needed (unlike `managed_config_snapshot_path`, whose caller is the config loader).

## Decision 3 — Reconciler: typed three-way, provenance-tagged

Per key, three values: **D** (desired, composed now), **C** (current shell env), **L** (ledger — what ocx last wrote, plus captured priors). Per prompt, per scope stack.

**Rejected**: keeping direnv (Windows and nushell stay unserved, ceremony stays); conda-style stash/restore (`OCX_PATH_BACKUP`) — byte-snapshot restore clobbers every foreign PATH edit since activation; direnv-style untyped diff — same clobbering class, and it throws away the Path/Constant/List typing OCX already has.

**List-kind vars** (PATH, `LD_LIBRARY_PATH`, any separator-joined list) — **element operations only**:
- Apply is split **per kind**, not one rule: **path-kind** (PATH itself) ensures desired elements present, in front, in order — the shipped `utility::path::move_to_front` / per-shell `Shell::export_path` pair, unchanged and byte-identical between the in-process and emitted forms; **list-kind** (`LD_LIBRARY_PATH`, `CFLAGS`, any other separator-joined non-PATH list) ensures the desired value present at the **back**, as one whole opaque contribution, via `utility::list::append_unique` / per-shell `Shell::export_list(key, value, effective_sep)`, never split into elements; **constant-kind** overwrites via `Shell::export_constant`. "In front, in order" describes path-kind only — it is false for list-kind, which is documented and tested as move-to-**back** (`env/list.rs:16-24`) precisely because its consumer resolves duplicates last-wins (A-07).
- **Apply is also gated, on the same rule constants get** ([ocx-sh/ocx#342](https://github.com/ocx-sh/ocx/issues/342), 2026-08-25). Path- and list-kind applications are idempotent, so an earlier draft re-emitted them every prompt and called that harmless. It is not: the emitted form is a `while`-loop of in-shell string surgery over the user's whole `PATH`, and re-emitting it on every prompt costs **~0.28 ms of pure shell work before ocx is even spawned** (re-measured in `bash --norc`, 500 evals per stream: 7 apply lines over a 46-segment PATH), scaling with (entries × PATH segments) — so the users it taxes hardest are the ones with the most tooling. The rule is therefore **emit nothing where applying would change nothing**, decided per key and all-or-nothing over the entries contributing to it. The operand differs from the constant rule by necessity: a constant compares against **L** (comparing against C would re-assert ocx's value over a mid-session override), a path or list key compares against **C**, by folding D into a copy of C with the same `move_to_front` / `append_unique` the emitted arms are contracted to equal byte for byte and asking whether anything moved. That makes `plan` depend on the live environment for path kinds, which is a real widening of its inputs and stated as such — it costs the lost-ledger repair nothing, because the repair path reads C directly and a key whose fold is already live needs no repair by definition. Without this rule the reconciler has **no fixed point**: D2's "every prompt re-converges" is factually "every prompt re-applies", and the summary line claims a change on every fire.
- Revert: **remove our elements**, never restore an old string. Element removal commutes with foreign prepends and appends. Delete-if-found; absence is not an error. This needs one new primitive — **`Shell::remove_list_element(key, value, separator: Option<&str>)`, not `remove_path_element`**. The earlier name and signature carried no separator and could therefore only assume the platform one, which makes every non-default-separator list var permanently unrevertible: `CFLAGS` as `{type = list, separator = " "}` or `CLASSPATH` as `{type = list, separator = ":"}` on Windows applies through `export_list` (which *does* take a separator, `shell.rs:319`) and then either removes nothing or splits on the wrong byte and corrupts the value. `None` means the platform PATH separator, mirroring `export_path`/`export_list` exactly, so PATH keeps its shipped spelling and list vars get a correct one. Per-entry separators are already settled upstream by `env::reconcile_list_separators`. **`remove_list_element` is `append_unique`'s inverse** — a flank-delimited removal of one whole opaque contribution, never a segment-level operation. `None` means the platform PATH separator **for path-kind only**; `LedgerEntry.separator` holds the *effective* separator, so a list-kind revert always passes `Some(effective)` and never relies on the `None` default (A-08).
- **Which arms are load-bearing.** `Shell` has ten variants; six get a named per-prompt mechanism (bash, zsh, fish, PowerShell, nushell, and elvish — see the elvish amendment below). The strict-POSIX trio (ash/ksh/dash) get the primitive because `export_path` already has it and asymmetry is the bug; Batch gets `None`. **The Batch `None` rationale is corrected**: `export_path` *does* work on Batch via `%VAR:search=%` substring-delete (`export_path_batch_idempotent_move_to_front:1192`), so Batch can delete an element — the reason `export_list` returns `None` there is that `cmd.exe`'s only substring-replace primitive is **case-insensitive with no case-sensitive form**, and list elements need case-sensitive matching. Batch also hosts no prompt hook at all, so nothing consumes it. Schedule the five hook arms as the implementation package; the other five ride along on the existing `export_path` template.
- **Idiom hazards, corrected and extended.** The two the earlier draft named are **already closed in shipped code and must be carried, not re-derived** (Component Contracts) — and neither has a public bug report, so cite them as this codebase's own caution, not as field-known. Three that *are* externally documented and were missing: (1) **PowerShell substring over-match** — a naive `-notlike`/substring removal that strips `C:\WINDOWS` also strips `C:\WINDOWS\system32`; matching must be segment-exact. (2) **PowerShell env-var name case** — `$env:PATH` and `$env:Path` are the *same* variable on Windows and *different* variables on Linux/macOS ([PowerShell#3571](https://github.com/PowerShell/PowerShell/issues/3571)), so the arm needs platform-conditional casing, not a scalar op. (3) **fish has no remove primitive** — the field workaround is index-based `set -e VAR[N]`, and removing 2+ elements in one call shifts every later index, so removal goes highest-index-first or re-resolves between removals ([fish-shell#7776](https://github.com/fish-shell/fish-shell/issues/7776)). (4) **`escape_value`'s `!` handling corrupts the value on every POSIX arm, interactive or not** — its `!` → `\!` replacement is not hardening but byte-corruption: the shell sets `a\!b` where `Env::apply_entries` stores `a!b` verbatim, so the `C == L.applied` exit guard can never hold for a `!`-bearing constant and the variable is treated as a foreign override forever; this codebase's own defect, not field-known (A-15). (5) **PowerShell element comparison is case-insensitive by default** — the shipped `-ne` emit is culture-and-case-insensitive, so on Linux, where `$env:Path` and `$env:PATH` are genuinely different variables ([PowerShell#3571](https://github.com/PowerShell/PowerShell/issues/3571)), it silently deletes a differently-cased sibling directory instead of leaving it alone; the comparison must be ordinal on non-Windows and ordinal-ignore-case on Windows (A-19).
- Ownership: elements under `$OCX_HOME` are self-identifying by prefix — concretely, **`Path::starts_with` against `$OCX_HOME` canonicalized once at reconcile start**, a component boundary rather than a byte prefix, so `.ocx-backup` and `.ocxevil` are correctly foreign; arbitrary elements (project `[env]` additions) are listed in L. The prefix test doubles as the repair path when L is lost, and **retirement's removal operand is the segment as it is observed in C, not as it is spelled in D**, so selection and removal share one operand and stay byte-exact even when D's spelling differs by a trailing slash or similar (A-09). If [#189](https://github.com/ocx-sh/ocx/issues/189) lands, its `.ocx/toolchain/` tree joins the prefix set additively — no change to this decision.

**Constant-kind vars** — overwrite on apply, guard on exit:
- Apply/update: **set to D only where the composed value actually changed** — i.e. where `D ≠ L`. Where `D == L`, ocx has already written this value and leaves C alone. Entering a scope records the prior state (`Unset | Value`) in L.
- Exit: restore the prior **only if C == L**; otherwise leave C. Never clobber a user's mid-session override on the way out — the single most-disliked direnv behavior.
- **Why apply is conditioned, not just exit.** An earlier draft said "set to D unconditionally", which made the mid-session-override protection one-sided: a manual `export JAVA_HOME=…` would survive *leaving* the project but be clobbered by any recompose at the next prompt — a strictly worse outcome than the exit rule exists to prevent, because it fires every prompt rather than once. mise shipped exactly that apply rule in **2026.8.0 and reversed it in 2026.8.9** ([jdx/mise#12094](https://github.com/jdx/mise/issues/12094)) after runtime overrides were being reverted on every prompt. Gating apply on `D ≠ L` costs nothing (it is the recompose fast path anyway) and makes the two sides symmetric: **ocx only ever overwrites a value it last wrote itself, or one it has never written.** The blast radius that remains — a genuine `[env]` change while the user holds an override for that same key — is the one case where the project's new intent must win, and it produces one summary line.
- Coincidence (C ≠ L but C == D): claim silently, prior = C. Note the small, accepted leak: the prior is now D, so leaving the project restores D rather than removing it. The user typed that value; restoring what they typed beats unsetting it.
- **Re-capture the prior whenever apply overwrites a value ocx did not write.** `C ≠ L.applied` at apply time ⇒ `L.prior := C`. Without this the `D ≠ L` gate is not enough: on a genuine `[env]` change the project's new intent correctly wins *inside* the project, but `L.applied` becomes D while `L.prior` still holds whatever was captured on entry — so `C == L` again, and on the way out ocx **unsets** a variable the user set by hand, which is strictly worse than direnv restoring a stale one. Re-capturing makes the exit guard's promise true rather than merely stated, and it is the difference between "the project wins while you are in it" and "the project launders your override into something ocx then deletes".
- **Two senses of "unset", which the ADR previously blurred into one line. This decision ships exactly one of them.** (1) **`priors: Unset`** — ledger-internal, meaning *"the variable did not exist before ocx set it"*, so reverting **removes** it rather than restoring a string. That is a property of `priors` in the shape above, it exists in this design already, and it needs no new type anywhere. (2) **Desired-unset** — a project asking for an *ambient* variable to be removed. **This does not exist anywhere in the product today**: `ModifierKind` is exactly `Path | Constant | List` (`package/metadata/env/modifier.rs:77-81`), project `[env]` has no unset directive, and `--env` rejects the bare `--env FOO` form outright (`options/env_override.rs:113-117`: *"passing an ambient variable through by name is not supported"*). It is [#265](https://github.com/ocx-sh/ocx/issues/265), open. **This ADR leaves #265 deferred and does not pull it in.** It is a package-metadata wire-format change — a fourth `ModifierKind` variant — plus a project-config-syntax change, and D6 keeps both out of scope on purpose; nothing in the reconciler is blocked on it. When it does land, the reconciler makes it cheap rather than the other way round: revert already handles the `Unset` prior, so desired-unset is one more apply arm over machinery that exists, and its forward-compat story is already shipped and needs nothing from here — an unknown `type` deserializes to `Modifier::Unknown { type_name }` and `ValidMetadata::try_from` refuses the package by name (`package/metadata/env/modifier.rs:23-29`), so an older ocx refuses a newer package rather than misreading its intent.
- **Which trigger dominates.** PWD events (enter / leave / switch) and fingerprint changes are the *only* two things that run apply. A same-project prompt with an unchanged fingerprint runs neither — it is the stat-only no-op path and re-asserts nothing. So a foreign write to a constant in D survives every prompt until the project's own configuration or the binary changes, at which point the rule above applies and the prior is re-captured. This is the difference between "foreign writes survive" and "foreign writes survive until the next lock bump"; the answer is the first, and it needed saying.

**Retirement — one rule, two triggers, evaluated on every recompose.** Apply and revert as stated cover a scope being *entered* and a scope being *left*. Neither covers the case that is neither: a key or an element that is in **L** drops out of **D** while the scope stays live. That is `ocx remove --global` from another shell, a branch switch that deletes a tool from `ocx.lock`, and a package digest bump. Under apply-and-revert alone the element simply persists, for the rest of the session. So state it once, as its own rule: **on every recompose, retire what ocx owns and D no longer wants.** Ownership is either **recorded** (L names the element as applied) **or structural** (the element sits under `$OCX_HOME` — plus `.ocx/toolchain/`, additively, if [#189](https://github.com/ocx-sh/ocx/issues/189) ever lands). For lists the rule is subtractive and the wording is load-bearing: **remove every prefix-owned element that is not in D** (mechanically: enumerate the segments **as they appear in C**, select the prefix-owned ones absent from D, and name each removal using that observed string verbatim, so selection and removal share one operand, A-09) — never merely "ensure D's elements are present, in front". The additive reading is what leaves both `…/packages/<old>/bin` and `…/packages/<new>/bin` on PATH after a digest change: they are *different strings*, so `move_to_front` does not dedupe them, it just reorders the new one to the front of a list that still contains the old one, and any later foreign prepend or a second recompose can put the stale one back in front. Arbitrary (non-prefix-owned) elements are retired only where L records them — the same bound as everywhere else, since nothing else identifies them as ours. Constants take the same shape: a constant in L that D no longer declares is retired by restoring its recorded prior, under the existing `C == L.applied` guard. The two triggers — **scope exit** (D for that scope becomes empty) and **recompose in place** (D changed under a live scope) — are the same code path, not two rules that happen to agree.

**Elvish hooks `$edit:before-readline`, with a narrower guard than every other arm** ([ocx-sh/ocx#341](https://github.com/ocx-sh/ocx/issues/341), 2026-08-25). An earlier draft grouped elvish with ash/ksh/dash as having "no append-safe prompt-hook point". That premise is false: elvish documents `$edit:before-readline` with the safe-append idiom `set edit:before-readline = [ $@edit:before-readline { … } ]` (https://elv.sh/ref/edit.html), and direnv ships a production hook on exactly that seam. What elvish genuinely lacks is a **clock**: 0.21's `os:stat` exposes `name`/`size`/`type`/`perm`/`special-modes`/`sys` and documents that timestamps are not exposed, and there is no `time` module, so there is no stamp and nothing to compare a watch member's mtime against in-shell. Three consequences, all deliberate:

- The guard is the two terms elvish *can* evaluate for free — an empty carrier and a changed `$pwd`. Reaching for an external `test -nt` would put one exec on every quiet prompt, which is the exact cost C-044 exists to remove, so the term is dropped rather than bought.
- **The missing term is compensated by the wrapper, which invalidates the recorded directory instead of calling the guard.** Every other wrapper calls the prompt hook's guarded function so a command that moved nothing costs nothing; here there is no watch term for a call to consult, so a call could only reconcile unconditionally. Clearing the recorded directory does not avoid the reconcile — it guarantees one at the very next prompt, the same single reconcile an inline guard call would have run. What it buys is *when*: the work leaves the ocx command's critical path and lands on the prompt, so `ocx version` keeps its direct cost. The next prompt is also what C-045 already names as the correctness floor.
- **Named residual, stated as the general rule rather than one example of it**: any watch-set member (Decision 3's fingerprint fold — project `ocx.toml` + `ocx.lock`, the global tier pair, the managed-config snapshot, the config-tier paths, the consent stamp, `project_dir`, the binary version) that changes without an `ocx` invocation *in this shell* and without a `cd` reconciles only at the next `cd` or the next ocx invocation in this shell, rather than at the next prompt. An `ocx.toml` edited by hand in place is one instance of this, not the whole of it — the same residual covers `ocx add --global` run in another shell, a `git checkout` that rewrites `ocx.lock`, a hand-edited `~/.ocx/config.toml` adding a grant, a managed-config snapshot refresh, and `ocx self update` run from another shell.

Three mechanical facts the arm is built on, all verified against elvish 0.21 rather than assumed. The `edit:` namespace is bound only in an interactive elvish and elvish resolves every variable in a chunk before executing any of it, so a direct reference is a **compile** error that kills the whole unit including any `try` around it — the registration therefore rides inside `eval` of a string, which turns that into a catchable exception. And a `fn` defined inside an `eval` unit does not escape it, so the wrapper goes in through `edit:add-var`. **Registration idempotency keys on the shell, not the process** — a corrected mechanism, not `__OCX_ENV_HOOK`, which does not exist: the marker is the registered closure's **rest-parameter name** (`{|@__ocx-prompt-hook| … }`), and the probe reads the parsed `arg-names` of each closure in `$edit:before-readline`, which is the only per-shell store an `eval` unit can both write and read, so a shell that replaces its own image with `exec elvish` still re-registers rather than reading a stale pid marker back out of an inherited environment. The text-scanning form it replaces was a **silent-suppression bug**: `to-string` renders each closure with its literal body *and* the source of the `eval` unit that defined it, so a user hook that merely mentioned the marker in a comment suppressed registration for that shell's whole life. A parser-produced list cannot be forged by text (A-42). `__OCX_ENV_PWD` is the one state variable that does live in the process environment, and it is a **pid-qualified composite of every term this arm's guard can evaluate without spawning a process** — `<pid> <pwd> <DIRENV_DIR> <MISE_SHELL> <__MISE_ORIG_PATH>`, space-joined, an unset sentinel contributing an empty field — not a bare `$pwd`. The pid is what keeps a nested elvish's inherited environment from reading as an already-reconciled match, so its own first prompt reconciles too; the three-sentinel tail is A-36's yield term, which rides here because elvish has no shell-local an `eval` unit can both write and read (A-43). The key's name is narrower than its contents on purpose: the value answers *"has anything the guard can see moved?"*, of which the directory is one term. The shipped spelling is `hook.rs`'s `elvish_pwd_value`, and `website/src/docs/reference/environment.md` documents it as interface.

**Keys outside D ∪ L are never read or written.** Foreign variables are structurally invisible — this is the whole-env-capture bug direnv has, removed by construction rather than by care.

**The revert set is scoped to L, never intersected with D.** Leaving a scope is precisely the case where D no longer names the key, so an intersection is the wrong operator: the revert set for scope S is exactly the keys `L.scopes[S].applied` names, each undone by the rule for its own kind — constants restore `priors` under the `C == L.applied` guard, lists remove the elements L records. L alone suffices to act, which is what the paragraph above already asserts and what Decision 1's corrected rule (c) states from the other side (*an L entry may only undo itself*). The earlier rule (c) contradicted this and lost: it discarded any L key absent from D, and on `cd` out of a project a project constant is by definition absent from D — that is what leaving means — and is not prefix-owned either, since prefix ownership covers `$OCX_HOME`-rooted list elements, not arbitrary constants. Under it `JAVA_HOME` was discarded rather than reverted and the project's value leaked into the rest of the session. **Containment is unchanged and comes from the sentence above, not from D**: the key set ocx touches is D ∪ L, and L is bounded because ocx only ever writes into it keys it itself composed from D. A forged L entry therefore buys exactly one thing — setting a variable in a shell where the forger could already set variables (Decision 1, *"What forging it is worth"*) — and buys no bug in the producer a value-selection primitive, because an entry can only ever undo the write it records.

**Scope stack — emission order, not resolved order, because conflating the two is a known bug class in this codebase.** The earlier wording (*"D = project block first, global block behind"*) named the *resulting* PATH order in language that reads as *emission* order. That is the exact inversion `composer.rs:1077-1085` already warns about for the shim slot: *"Consumers apply entries by prepending, so the **last** entry pushed is **first** in the resolved PATH … A reader who assumes push order equals PATH order will invert this."* Stated unambiguously in the composer's own vocabulary: **emit and apply global first, project second.** Constants — the later write wins, so project overrides global. **PATH** (path-kind) — each application prepends, so the later prepend lands earlier, and project again ends up in front. **Lists** (list-kind, e.g. `LD_LIBRARY_PATH`) — each application **appends**, not prepends (`ModifierKind::List`, `env/list.rs:16-24`); project still beats global here, but by a different mechanism: list consumers are last-wins, and applying project last makes its contribution the one that resolves (A-07). All three kinds agree on the outcome, **project beats global**, and the resolved PATH order is project → global. Resolution isolation per [`adr_global_toolchain_tier.md`](./adr_global_toolchain_tier.md) is untouched: this is shell-level concatenation, and global still never composes *into* project resolution.

**Consequence for revert: prior capture must follow global's apply.** Because global is applied first, a constant prior captured at project entry holds **global's** value for that key, not the user's original. That is correct — reverting the project restores global's value and leaves the global scope intact, which is exactly what leaving a project should mean — but it is correct **only** if capture happens after global has been applied. So the ordering is normative, not incidental: apply global → capture priors for the project's keys → apply project. Capturing before global's apply would make leaving a project silently tear down global's constants too, on the way out of a scope that never owned them. **Two cases, kept apart, because collapsing them reads as a prohibition the design does not intend.** *Scope **exit*** — leaving a project reverts the **project** section only; the global section is untouched, because the user has not left the global scope. *Recompose **in place*** — the global lock or `$OCX_HOME/ocx.toml` changed while the scope stayed active, and the retirement rule above then retires global elements and global constants **mid-session**, in the same shell, at the next prompt. `ocx remove --global foo` in another terminal is exactly this case, and it must work. So: no scope-exit rule forbids mid-session global retirement; what never happens mid-session is a *wholesale* teardown of the global section, which only the retirement rule ever touches, element by element. (Disabling the hook is not a teardown either — per "How Would We Reverse This?" level 1 it takes effect at the next shell start and reverts nothing in the running shell.)

**Why a single `project` slot is enough** — three verified facts about discovery, not an assumption. (1) `ConfigLoader::project_path` tier 3 walks up for the **nearest** `ocx.toml` and returns on the first hit (`config/loader.rs:634-694`), so a project nested inside a project does **not** layer: the inner one *replaces* the outer, and moving between them is a scope **switch** (revert A, apply B in one pass), never a push onto a stack. (2) There is **no implicit `$OCX_HOME/ocx.toml` fallback** — a CWD-walk miss is a hard `None` (`config/loader.rs:578-581`), and the global tier is reachable only through the explicit `--global` / `OCX_GLOBAL` selector per [`adr_global_toolchain_tier.md`](./adr_global_toolchain_tier.md) D1. (3) The explicit tiers (`--project`, `OCX_PROJECT`) resolve one file and return, also replacing rather than layering. Two slots, `global` and `project`, therefore span the whole space, and a ledger shaped for a deeper stack would carry a case nothing can produce.

**Fingerprint / fast path**: watch set = project `ocx.toml` + `ocx.lock`, `$OCX_HOME/ocx.toml` + `ocx.lock`, the managed-config snapshot, the ocx binary version, and the project directory. **The watch set also gains the config-tier paths recorded in the ledger at the last compose** — home `config.toml`, user `config.toml`, and the `OCX_CONFIG`/`--config` override if one was in effect, each stat'ed for presence, mtime and size — plus the project's consent stamp (`state/projects/<key>/consent.json`); `fp` additionally folds the raw values of `OCX_CONSENT_PATHS` and `OCX_CONSENT_NAMESPACES` (two `getenv`s, no I/O), so a grant added or exported mid-session expires the cached `inert` verdict at the next prompt rather than only at shell restart (A-13). `[env]` applies on its own authority independently of the lock, so watching locks alone would miss `[env]`-only edits. The no-op path is **mtime + size only**; content hashes are computed only after an mtime/size change decides recomposition is plausible. **The ceiling of that fast path, named here rather than discovered in the field, and stated granularity-free rather than as a fixed window**: the fingerprint compares the full `std::fs::Metadata::modified()` `SystemTime`, never a seconds-truncated value, so the window is exactly the filesystem's own mtime granularity and nothing coarser; a write that preserves **both** — same byte count, same `(mtime, size)` pair at that granularity — is invisible, and stays invisible until something else in the watch set moves. On ext4/NTFS/APFS that window is sub-second and correspondingly narrow; FAT/exFAT (2 s) and NFS (1 s) widen it, and Windows is a first-class host for both (A-14). The content hash cannot rescue it, because the hash is computed strictly downstream of the mtime/size verdict; that ordering is the whole point of the fast path, not an oversight in it. In practice a `git checkout` bumps mtime, so the case is narrow, but it is real and it is not detectable at this cost. direnv and mise sit on the identical ceiling for the identical reason; it is the price of a stat-only no-op, and it is accepted on those terms. The CWD upward walk to locate the project is a separate bounded per-prompt cost, and the bound is **verified rather than assumed**, because the walk-cost claim rests on it: `walk_for_project_file` probes `.git` and `ocx.toml` at each level concurrently and returns `None` as soon as `.git` is present with no hit at that level (`config/loader.rs:674-676`), so `.git` genuinely stops the walk. Two details the shorthand elided and a cost claim must not. The boundary blocks *ascending past* a level, not reading at it — an `ocx.toml` **at** the repo root still wins, since the candidate check runs before the `.git` gate. And **any** `.git` entry counts — directory, git-worktree linkfile, or symlink — with a non-`NotFound` I/O error failing closed to "boundary" (`has_git_dir`, `config/loader.rs:704-716`). `OCX_CEILING_PATH` bounds the walk the same way, checked after the current level is probed. The walk is therefore repo-depth bounded in every ordinary layout, and unbounded only outside a repository with no ceiling set — which is the case the NFR budget must be measured in, not the happy one. **A walk that returns no hit is not automatically a scope exit.** Before reverting the project scope on such a result, the reconciler runs one determinacy check: if `L.scopes.project.dir` is still an ancestor-or-self of the CWD and `symlink_metadata(dir/ocx.toml)` reports a regular file, the walk's answer is **indeterminate** — a transient `.git` I/O error or similar — and the scope is retained unchanged, with nothing emitted; only a genuine leave (CWD outside `dir`) or a genuine deletion (`NotFound`) reverts normally (A-11). An `ENAMETOOLONG`-class probe error needs no separate handling for this: `has_git_dir` already fails closed to "boundary" on any non-`NotFound` I/O error (`config/loader.rs:704-716`), which stops the ascent at that level without a new branch.

**Events**: enter (stamp check → compose → apply), leave (revert project section), project switch (revert A, apply B in one pass), `ocx update` in a live shell (fingerprint changes because the version changed → recompose at the next prompt; same-command-line freshness is the wrapper function's optimization, Decision 5 layer 3).

**Detection is file-state based, never command based.** Nothing in this design intercepts, wraps or observes an ocx invocation in order to decide that a recompose is due — the fingerprint watch set is the only trigger there is. So a `git checkout` that swaps `ocx.lock`, an `ocx.lock` copied in by a CI step or another process, an editor writing `ocx.toml`, `self update` moving the binary version, and **another shell's `ocx add --global`** are all literally the same event: something in the watch set moved, and this shell notices at its next prompt. This is worth saying plainly because every other design in this space reaches for command interception, and because it is what makes the cross-shell and cross-process cases fall out for free rather than needing their own mechanism. The wrapper function is not an exception: it re-runs the same fingerprint check, it does not report what the command it wrapped did.

## Decision 4 — Consent and the activation whitelist

**Threat**: `ocx.toml` names arbitrary OCI registries. Silent activation on `cd` into a fresh clone puts attacker-controlled binaries in front of `cmake`, `cargo`, `git`. Install executes no package code, so the risk materializes at first tool invocation — which is guaranteed.

**Activation is permitted iff any of:**
1. a valid consent stamp exists for this project **and** the current lock's **claimed** source set ⊆ the stamped source set; or
2. the **store-corroborated** source set — `refs/origins/`, the logical repository resolved, never the lock's claim (A-39) — is present, **non-empty**, and every source in it matches the namespace whitelist; or
3. the project's canonical directory is in the path whitelist.

Otherwise: **zero env change, one hint line**. A fresh clone is inert.

**Every quantifier over a source set must be non-vacuous.** Without the non-empty requirement in clause 2, an *empty* source set satisfies "every source matches" for any user, with no stamp and no whitelist entry — and the project that produces an empty source set is precisely the one this decision exists to stop. It is not hypothetical: a relative `path` value in project `[env]` resolves against the project root (`project/env.rs:17-18`), so a clone carrying `[env] PATH = { type = "path", value = "bin" }` and **no `ocx.lock` at all** would activate through clause 2 and put `<clone>/bin` PATH-front on `cd`. That defeats "a fresh clone is inert" outright. Clause 1 is unaffected: a stamp is itself the record of an explicit ocx command in this directory, so a valid stamp with an empty `sources` set is still consent — the emptiness that must never grant activation is the *unstamped* kind.

**A missing `ocx.lock` is treated exactly as an unreadable one**: no activation, one hint line. The ADR previously specified only the unreadable/unparseable case; absent, unreadable and unparseable now share one outcome, because all three leave the source-set predicate with nothing to quantify over. Clause 3 is the deliberate exception — an operator naming an exact canonical directory has consented to that directory whatever it does or does not contain.

**Project `[env]` is gated by clauses 1 and 3 only — never by clause 2.** Decision 3's "`[env]` applies on its own authority independently of the lock" is a statement about *composition and the watch set*, not about *activation*: it means an `[env]`-only edit must trigger recomposition, not that `[env]` may reach a shell that never passed consent. A consent stamp (clause 1) or a `paths` grant (clause 3) may release the `[env]` channel; a `namespaces` grant (clause 2) may not. Nothing sourced from `ocx.toml` — `[env]` included — is applied unless a clause-1-or-3 grant holds.

**Why clause 2 does not reach here.** Clause 2's evidence is the package store's own record of which logical repository this host resolved and materialized each locked digest under (`refs/origins/` — A-39 in the addendum). That record vouches for a *published package* and for nothing else, so it must never gate the one channel with no publisher at all: `[env]` needs no lock entry, no download and no registry round-trip to put an attacker-controlled directory PATH-front. The tool channel clause 2 *does* authorize has a floor that `[env]` has no equivalent of — and that floor is weaker than an earlier draft of this paragraph claimed, so it is restated here at the strength the code actually enforces.

**What an origin marker is, and is not, evidence of.** It is evidence that **this host** ran a fetching pull — anything but `pull_local` — which materialized digest-verified content and bound it to the logical repository the identifier spelled. It is **not** evidence that a registry vouched for that binding. The write gate is one predicate, `let from_registry = provided_metadata.is_none()` (`pull.rs:334`, consumed at `:451`), and `provided_metadata` is `Some` on exactly one path — `pull_local`, a local tarball. Nothing else is excluded. The two store-hit early returns the call site sits past are each conditional on `check_install_status` (`pull.rs:344`, `:381`), so a package directory that is **absent or not-OK** falls through into the fetching branch; and from there nothing requires the wire, because the layer cache short-circuits the fetch whenever `layers/{digest}/content/` is present and acquires the client lazily so an offline manager can still re-assemble (`pull.rs:908-916`), while a digest-addressed manifest read is local-first in every chain mode (`chained_index.rs:1029`). The package path is `(registry, digest)` only — `package_store.rs`'s `path_uses_only_registry_and_digest_not_repository` pins exactly that — so a pull naming **any** logical repository on a registry whose layers are already cached mints that repository's marker with no registry contact and no credential anywhere.

**The floor, at its true strength.** Reaching `PATH` through clause 2 requires that *this host* pulled the locked digest under the granted namespace. For content this host has never held, that is the publish-credential bound A-27 leans on: the bytes have to come off the wire under that name. For content the host already holds, it bounds only *local action* — one `ocx pull` naming the granted org at an already-cached digest mints the binding offline, and because the marker is a fact about the package `(registry, digest)` and not about any project, a later clone carrying nothing but a lock then satisfies clause 2 without ever having pulled anything itself. What survives intact is the comparison this decision was actually made on: the claim-based spelling was satisfiable by **text a clone's author writes** ([ocx-sh/ocx#344](https://github.com/ocx-sh/ocx/issues/344)), while the record requires an **act of pulling on this host** under that name. `[env]` clears neither bar — no publisher, no pull, not even a lock entry — so clause 2 alone must never release it. That conclusion stands unchanged on the weaker floor.

**Named residual — a code gap, stated as one, not designed away.** `record_origin` ought to be reachable only from a path that actually transferred bytes for this digest from this registry; it is reachable today from any re-assembly. Until the write gate observes wire contact, a `namespaces` grant is bounded by *"some local actor pulled under this name"*, not by *"a registry served under this name"*, and the corroboration `Reason::UncorroboratedNamespace` reports is correspondingly local. Tracked as [ocx-sh/ocx#348](https://github.com/ocx-sh/ocx/issues/348). The shape is the redirect residual A-39 already names: the marker is honest about *what this host did*, and the gap is between that and *what a registry attested*. It takes the same instrument where the difference matters — `[[trust.policy]]` plus signature verification answers "who published these bytes", which no provenance marker can.

**The hook never installs.** Compose-only, from lock plus local store; a missing tool produces one hint line. (`ocx direnv export` keeps its own install-on-miss semantics for existing direnv users — untouched, additive per [#170](https://github.com/ocx-sh/ocx/issues/170).)

**Consent stamp** (`state/projects/<key>/consent.json`): `{ v, project_dir, sources: BTreeSet<String>, stamped_at }`. Re-confirmation fires when the current lock's source set is **not a subset** of the stamped set — so a same-cardinality swap `ghcr.io/acme → ghcr.io/evil` triggers, while ordinary growth inside consented namespaces does not.

**A grant does not write a consent stamp — the two grants are drift-checked by different mechanisms, and neither ever stamps.** `paths` and `namespaces` do not bypass the stamp writers named above; they are independent activation paths that never touch `state/projects/<key>/` at all. `namespaces` is drift-sensitive by its own quantifier — clause 2 re-derives the store-corroborated source set and re-evaluates it against the whitelist on every prompt (A-39), so nothing needs to be cached. `paths` is a directory grant and is deliberately drift-blind, which the clause-3 exception above already states and which the devcontainer use case requires — the operator naming the checkout in advance cannot enumerate its sources. Revoking either grant is therefore immediately effective at the next prompt, because no stamp was ever derived from either one (A-26). Owner-confirmed shape of the two grants: **`paths` is the primary grant** (the devcontainer/checkout case); **`namespaces` is optional and acts as an auto-enabler for projects *outside* the path grants** (the fleet case); and the **global toolchain is always trusted — consent is project-scope only**, because `$OCX_HOME/ocx.toml` is the user's own file. That last point is the same fact Decision 2 uses to delete the global-tier sweep carve-out, and it is why no clause here mentions the global scope.

**A `source` is `<registry>/<first-path-segment>`, normative.** This was previously left as "the registries+namespaces the lock resolves against", which is undecidable and sets the strength of the only default-on control in the design, so it is pinned here. Derivation: for each `LockedTool.repository: Identifier` (`project/lock.rs:163-176`), take the **logical** repository coordinate the lock records, lowercase the registry host, **preserve the port** (`localhost:5000` is a distinct source from `localhost`), spell the default registry explicitly (`ocx.sh/...`, never elided), and truncate the repository path to its first segment. `ghcr.io/acme/tools/cmake:3.28` ⇒ `ghcr.io/acme`. Registry granularity alone would be nearly vacuous (consent to one GHCR org consents to all of GHCR); full-repository granularity would re-prompt on every ordinary tool addition, which is the ceremony fatigue this decision explicitly rejects. The first path segment is the org — the unit an operator controls and the unit an attacker must register. This is also the string the `namespaces` whitelist matches against, so the two surfaces share one normalization and the Validation section's "same-cardinality swap" and "`/*` boundary" tests become writable.

**The predicate is defined over the logical coordinate, and an earlier draft of this bullet claimed the opposite.** It said to take "the physical address the lock records", which does not exist: `resolve.rs:510-517` writes `identifier.without_specifiers()` and its comment records that the outer index digest is discarded; `adr_index_indirection.md` Decision C/C2 keys `ocx.lock`, storage and GC roots on **logical identity by design** and makes the physical address transport-only, re-derived per operation; and `adr_lock_records_physical_address.md` is **Rejected** precisely for proposing the change that sentence assumed had already happened. So what the predicate binds is the set of logical namespaces a project's tools are *named* in — not the registries those names currently route to. What it does not bind, stated plainly: a change in the physical registry an index routes an already-consented logical namespace to never triggers re-confirmation.

**That residual is accepted and documented, alongside Decision 8's, because it is the same seam.** For an entry already in the lock the content is digest-pinned — per-platform pull ids are reconstructed from `repository` plus each leaf digest — so an index redirect cannot silently swap bytes under a standing stamp. The exposure is at `ocx lock` / `ocx update` time, where a redirected index supplies the digest in the first place. That is a lock-changing event, which is exactly the seam Decision 8 identifies, and it takes the same instrument: an operator-tier `[[trust.policy]]` plus signature verification answers "did the expected identity publish these bytes", which is what routing changed under you actually means. Re-shaping consent around the physical address instead would pin routing — the failure the rejected ADR's own owner decision names, where a locked project stops following a legitimate registry migration — and would still not answer the publisher question.

**Write seam.** The stamp is written by any explicit project-scoped ocx command (`add`, `remove`, `lock`, `update`, `pull`, `run`) — and that is **not** the ledger's registration seam. `register_project_dir_best_effort` has exactly two call sites (`project/lock.rs:448`, `project/mutation.rs:373`); `ocx run` and `ocx pull` reach neither. The stamp therefore needs its own seam, high enough in the project-command path to cover all six, and a plan must schedule it as such rather than assuming it rides along. **Stated as a negative too, since a positive list invites a silent seventh writer**: `consent::record()` is called from **exactly these six** command paths and nowhere else — every other command, explicitly including `ocx env`, `ocx inspect`, `ocx shell state`, `ocx self activate` (with or without `--reconcile`), `ocx list`, `ocx direnv export` and `ocx completions`, MUST NOT create or modify `state/projects/<key>/` (A-29).

**`evaluate` compares `project_dir`, not just the key.** `name_for_path` is SHA-256 truncated to 8 bytes (`reference_manager.rs:59-63`) — a 64-bit name. Second preimage is out of reach, so this is not a live attack, but the stamp already carries `project_dir` and reading it costs nothing: `evaluate` rejects a stamp whose `project_dir` is not the canonical directory under evaluation. The key is a lookup index; the path is the identity.

The superseded ADR additionally bound a "first-consented tool-name set" as a project-identity guard against path reuse. **Dropped**: a `git pull` that adds a tool from an already-consented namespace would re-prompt, which is exactly the ceremony fatigue that trains users to confirm blindly. Path reuse is instead covered by the source-set predicate for the case that matters (a different repo pulling from a different namespace) and accepted otherwise — as direnv, mise and Nix all accept it.

**Sequencing (the mise CVE lesson) — consent before *parse*, not merely before *apply*.** "Zero env change" is satisfiable by compose-then-discard, which would have already deserialized the untrusted `ocx.toml`. State it as a rule instead: **the only project-supplied bytes read before consent is established are the CWD walk's `stat` calls and the `ocx.lock` parse the source-set predicate requires; `ProjectConfig` deserialization happens after.** That makes the lock-parse an explicit, bounded carve-out rather than an aside. A lock that is unreadable or unparseable means **no activation** plus one hint line. The residual is small either way — project `[env]` is literal-only with no interpolation (`project/env.rs:27`) — but the mise CVE is a lesson about ordering, and ordering is cheap to state once. This is structurally safe here in a way it was not for mise, because the whitelist can only come from `config.toml`.

### Whitelist location and grammar

```toml
# config.toml (user tier; may ship in the managed tier — Decision 7)
[shell]
hook        = true
completions = true                           # same ladder as `hook` (Decision 5)

[shell.consent]
paths      = ["/workspaces/acme-monorepo"]   # exact canonical directory; add /* for that directory's
                                             # subtree — corrected 2026-08-31, see the amendment below
namespaces = "ocx.sh/acme-corp"              # one ScopeSpec, org grant; "ocx.sh/acme-corp/*" is the
                                             # same set — a source is exactly two components (A-27)
# or the object form, which a bare string cannot spell — carve-outs are at SOURCE granularity, so a
# carve-out withdraws one org another tier's `include` already covers, never a repository from an org
# (there is no whole-registry spelling to carve out of — see the amendment below):
# namespaces = { include = ["ocx.sh/acme", "ocx.sh/acme-compromised"], exclude = ["ocx.sh/acme-compromised"] }
```

- **Never `ocx.toml` — and this needs a guard, not a citation.** Today a `[shell]` block in `ocx.toml` is a hard parse error, because `ProjectConfig` and `RawProjectConfig` both carry `#[serde(deny_unknown_fields)]` (`project/config.rs:122,259`). But that attribute's own docstring (`:113-115`) states its purpose as *"schema drift in consumer `ocx.toml` files surfaces as a parse error rather than silent ignore"* — it is a **typo detector**, load-bearing for a security property in a different file, with nothing recording the coupling and no test pinning it. Three sibling config structs already omit it citing fleet forward-compat (`config/managed.rs:23`, `config/patch.rs:21`, `config/registry.rs:19`), and the Component Contracts row below mandates exactly that doctrine for `Config`. The first person to apply this ADR's own forward-compat argument to `ocx.toml` reopens GHSA-436v-8fw5-4mj8 without ever opening this ADR. Worse, `ConfigLoader::load_with_local_view` **already resolves a project tier into the pipeline that carries `Config`** and parks it: `let _project_path = Self::project_path(…)` (`config/loader.rs:145`), commented *"consumed in later phases once the project-config schema lands"*. The untrusted tier is pre-wired one commit from being read, and `Config` has no `deny_unknown_fields` anywhere in its tree. **So: convert the prose into a guard that can go red.** When `[shell]` lands on `Config`, strip `shell` from any project-tier contribution explicitly, in `guard_managed_sigstore_trust`'s home and idiom (`config/loader.rs:431`), and ship two tests — a project-tier fold cannot contribute `[shell.consent]`, and `[shell]` in `ocx.toml` is refused. "Structurally, not by discipline" is only true once those exist; until then it *is* discipline.
- **`paths` is exact-directory, matched on the canonicalized path.** No prefix, no glob. Every tool shipping a prefix grammar carries the sibling-typosquat footgun; git ships exact-only and documents that it has no glob. The dynamic case (a checkout whose path is unknown at image-build time) is served by the env channel, which is strictly better than git's `postStartCommand` workaround. **Only the project side is canonicalized; whitelist entries are compared literally** (after separator and trailing-slash normalization). The two choices have opposite failure modes and only one can ship: canonicalizing *entries* at read time makes the grant follow a symlink an attacker may control on the parent (`/workspaces/repo → /tmp/evil` needs only write access on `/workspaces`), while comparing literally never matches a symlinked checkout and is then silently inert. Inert is the fail-safe direction, and an operator writing an exact path can write the real one. The project side is already correct — `dunce::canonicalize` at `project/registry.rs:311`, and `walk_for_project_file` rejects a symlinked `ocx.toml` at `config/loader.rs:652-657`. **Entries are compared as literal bytes, with no case folding on a case-sensitive filesystem** (amended 2026-09-01, round 3: ASCII case folds on Windows, where the filesystem folds it too — see EC-GRANT-025) — canonicalizing or case-folding the entry would widen the grant, which is the wrong failure direction here — so a case-only or separator-only near-miss between a `paths` entry and the canonical directory is `Inert`, same as any other mismatch; to pay off the resulting support cost, `ocx shell state`'s not-active reason enumeration (Decision 10) names that near-miss explicitly when it is the cause (A-28).

- **`namespaces` is one `ScopeSpec`** (`trust.rs:247`) — not a `Vec<ScopeSpec>`, and not a `Vec<String>`. A flat list carries the defect `[[trust.policy]]` already solved: a union over entries can only ever widen, so "everything under `ocx.sh/acme/*` except the one compromised namespace" is unspellable, and the exception has to be bolted on beside the list. A single `ScopeSpec` is *either* a fixed string *or* `Set { include, exclude }`, which states coverage and carve-out in one value. `ScopeSpec` already carries this exact grammar — string form `scope = "ghcr.io/acme/*"`, segment-bounded without a `*`, literal-prefix glob with one (`config/loader.rs:1523`) — already matched against canonical `registry/repository` targets, which is the same target shape a lock source has. Project rule: extend existing mechanisms, do not duplicate. **Sharing the type does not couple the policies.** `ScopeSpec` is a matching primitive, not a trust semantic: a namespace consented for shell activation is **not** thereby trusted for signature verification, and a namespace named in `[[trust.policy]]` does **not** grant activation consent. The two lists are read by different code paths answering different questions — *whose binaries may reach my PATH on `cd`* versus *whose signature satisfies a verification policy* — and neither reads the other's configuration. Two things the single-spec shape gives that a flat list cannot:
  - **`Set { include, exclude }` carve-outs.** A fleet pre-consenting to `ocx.sh/acme/*` while excluding one compromised namespace is currently unspellable; with `ScopeSpec` it is the object form, already schema'd and already refusing a table that names neither key (so a typo'd `includ` fails loudly instead of widening to catch-all — the correct failure direction for consent material).
  - **`ScopeSpec::specificity_for` (`trust.rs:419`)**, the ranking `[[trust.policy]]` already uses.
  Descendant implication is **vacuous at source granularity, and this needs saying plainly**: a source is exactly two components (`<registry>/<first-path-segment>`, above), so `ocx.sh/acme/*` and `ocx.sh/acme` match the identical set — there is no deeper namespace for `*` to reach within one source. Answering the boundary question the grammar line left open: `*` is optional-but-accepted for the org form — `ocx.sh/acme` and `ocx.sh/acme/*` name the identical set — and neither spelling licenses a third component: the grammar rejects `ocx.sh/acme/team/tool` outright, so that example is withdrawn as a repository path, not a source (A-27). There is no whole-registry spelling at all — see the amendment immediately below.
> **Amended 2026-08-25 — the whole-registry spelling is withdrawn**
> ([#344](https://github.com/ocx-sh/ocx/issues/344)). `<host>/*` and a bare `<host>` are both refused,
> as one error class, so neither is the way to spell what the other no longer says. The reason is the
> only bound clause 2 has: an attacker must get content onto this host under the granted namespace,
> which for content the host does not already hold needs that namespace's publish credential (for content
> it does hold, less — A-39's residual). A pattern spanning every organization on a host voids that bound
> wherever anyone can register on the host, and ocx cannot tell an open registry from a closed one — so
> the spelling is refused rather than documented as dangerous. An operator who genuinely trusts a whole
> private registry lists its organizations, or uses a `paths` grant. Consequence, stated: `exclude` no
> longer subtracts from a wide grant; it subtracts an organization one tier included from another tier's
> view, which is what `accumulate`'s exclusion-wins rule is for.

- **The grammar is enforced at parse, not documented — and the "no typosquat at the OCI level" rationale is withdrawn as false.** An earlier draft argued that moving from filesystem paths to OCI namespaces removes the sibling-typosquat vector because "an attacker cannot create `ocx.sh/acme-corp-evil/…` inside an operator-controlled namespace". That confuses a namespace with its siblings: on a public registry the vector is *relocated* to a primitive cheaper than creating a sibling directory — registering the org `acme-corp-evil` on `ghcr.io`, `docker.io` or the default `ocx.sh`. It would be true only for a registry where namespace creation is closed, which nothing here requires. And reusing `ScopeSpec` does **not** close it: `trust::pattern_matches` (`trust.rs:374-383`) is segment-bounded only on its *no-wildcard* branch — `Some(index) => target.starts_with(&pattern[..index])` — and its own doc comment says a bare `ghcr.io/acme*` is *"an intentional substring glob"*. So `ocx.sh/acme-corp*`, one keystroke from the intended spelling, matches `ocx.sh/acme-corp-evil/tool`. **Therefore, for `[shell.consent] namespaces` only:** (1) reject at parse/merge any pattern containing `*` anywhere other than as a final `/*`, and reject a bare `*` and the empty pattern. **Round 3's whole-list-refusal contract is withdrawn as moot, not reversed.** It existed to answer *"what happens to the surviving entries when one is malformed"* for a `Vec<ScopeSpec>`, and answering it required prohibiting a filtering deserializer this ADR never wanted. A single `ScopeSpec` has no surviving entries, so the question does not arise. **The claim that `ScopeSpec`'s deserializer already errors on a malformed form and needs no new machinery is withdrawn as false**: `visit_str` (`trust.rs:325-329`) accepts *every* string, `""` included, and the `:349-354` error covers only a table naming neither `include` nor `exclude` — neither rejects a malformed pattern. Pattern validation for `namespaces` is **new machinery**, specified as exactly two accepted spellings — `<host>[:<port>]/<org>` (no wildcard) and `<host>[:<port>]/<org>/*` (explicit descendant, equivalent to the first at source granularity) — and eight rejected classes: the empty string and a bare `*`; a `*` anywhere but the final two bytes, or more than one `*`; a trailing `/` with no `*`, and the pattern `/*` alone; any empty `/`-delimited component; any ASCII uppercase byte; three or more components after stripping an optional trailing `/*`; **exactly one component after that strip — a bare `<host>` or a `<host>/*`, the two whole-registry spellings**; and `@` anywhere, or `:` after the first `/`. There is no whole-registry spelling — see the amendment above. **Malformed ⇒ refuse, never partially parse** (A-27). Per channel, **corrected by A-40**: in a `config.toml` tier the refused `[shell.consent]` table is **stripped** — that grant contributes nothing while every other section of the file still applies, on **every** tier, exit 0 with the reason recorded and emitted — *unless* the table carries a non-empty `namespaces.exclude`, which is the one thing it can say that **withdraws** another tier's grant; dropping a withdrawal widens, so that file keeps the hard failure (**78 `ConfigError`** on home / system / `--config`; the managed snapshot goes unapplied with one WARN). On the env channel the entire `OCX_CONSENT_NAMESPACES` contribution is discarded with one warning and the config tiers stand alone, because a hard error there would break every prompt (D3). Neither channel activates on a partially-parsed spec, and neither widens. Empty tokens are not this case — they are separator artifacts, discarded before any pattern is constructed (env-channel bullet below), so only a **non-empty** malformed pattern triggers refusal. (2) Match by stripping the trailing `/*` and taking `pattern_matches`' no-wildcard branch — `target == pattern || target.starts_with(&format!("{pattern}/"))` — the safe form, already in the tree. `[[trust.policy]]` keeps its looser grammar; it is signature-gated, and this surface is not. The real reason the OCI shape is safer than a path prefix is that the boundary is enforced at the segment, not that typosquatting is impossible.
- **`[shell.consent]` is a consent-bearing table and inherits `ScopeSpec`'s deserialize discipline**, which is the one place this repo's fleet forward-compat tolerance stops. **The `trust.rs:252-257` quote establishes only the neither-key floor, not unknown-key refusal — a correction to how this was cited**: `visit_map` (`trust.rs:342-346`) explicitly drops unknown keys for forward-compat, so a blanket `#[serde(deny_unknown_fields)]` on `ShellConsent` alone does not deliver the stated property, because `ShellConsent::namespaces` deserializes through `ScopeSpec`'s own tolerant visitor underneath it. The split extends one level deeper: `namespaces` carries a `#[serde(deserialize_with = …)]` pointing at a **consent-scoped** visitor that mirrors `ScopeSpec`'s hand-written one but replaces its unknown-key arm with an error, keeps the neither-key floor, and runs the pattern validator above on every spelling before constructing `ScopeSpec::Set` — the shared `ScopeSpec` deserializer itself is untouched, since its tolerance is deliberate for `[[trust.policy]]` (A-27). An operator publishing `namespaces = ["ocx.sh/acme/*"]` plus a future *narrowing* key an older fleet host does not know must have that host **refuse** the payload, not silently drop the key and activate on the full namespace. The Component Contracts row's blanket "no `deny_unknown_fields` anywhere in the tree" therefore applies to `ShellConfig.hook` and not to `ShellConsent`.
- **Precedence: union across every `config.toml` tier, with exclusions winning inside a spec.** The earlier flat "union, never override, no precedence logic" claim is corrected here: it was true only of a list of bare prefixes, and `specificity_for` exists precisely because that claim already has a shipped counter-example in `[[trust.policy]]`. The reconciled rule is two-level and still has no tier ordering: (1) **across tiers**, the per-tier specs accumulate into one — every `include` unions with every other, every `exclude` likewise, a bare string form contributing a single `include`, and no tier overriding another, following git; (2) **within the accumulated spec**, a source is consented iff it matches at least one `include` and no `exclude` — carve-outs beat coverage regardless of which tier contributed either, and **an empty `include` is rejected at parse rather than read as a catch-all** (`ScopeSpec`'s general catch-all spelling is deliberately not inherited here, same reasoning as the grammar bullet: on this surface a widening default is the wrong failure direction). `specificity_for` ranks *which* pattern explains a decision for diagnostics; it never resolves a conflict, because exclusion already wins unconditionally. Fail-safe direction: the only thing a lower tier can do to a higher tier's grant is remove it. **Two corrections to how this rule was justified.** First, "there is no untrusted tier in the union" is **withdrawn** — `trust.rs:36-38` names *"the untrusted managed-config payload"* in as many words, and Decision 7 gating that tier concedes the point; the union is safe because exclusion wins and no tier can override another, not because every contributor is trusted. Second, `[[trust.policy]]` is a storage-append analogue **only**: `Config::merge` appends, and then `trust::resolve` masks by specificity and `apply_system_locks` exempts the system tier (`config.rs:176-193`). Say "plain union — *unlike* `[[trust.policy]]`, which masks by specificity"; the semantics chosen here are simpler and new, and citing them as an existing pattern oversells them.
- **Env channel**: `OCX_CONSENT_PATHS` (OS PATH-separator list, mirroring `MISE_TRUSTED_CONFIG_PATHS`) and `OCX_CONSENT_NAMESPACES` (**comma**-separated, each token folding into the accumulated `include` set — a registry may carry a port, `localhost:5000/acme/*`, so `:` is unusable as a separator on Unix). Both are **additive**: unioned with the config tiers, never a replacement and never higher-precedence. A hostile parent process setting them is out of scope, consistent with every surveyed tool and with OCX's existing shell-activation consent boundary. **A third channel carries the same class of threat and belongs in the same sentence**: an explicit-tier file named by `--config` / `OCX_CONFIG` can equally carry `[shell.consent]`, is not subject to Decision 7's digest-pin gate (that gate lives inside the managed-tier fold only), and is consent-bearing on the same footing as the two env vars above — a hostile parent process supplying any of the three is out of scope. **`OCX_NO_CONFIG=1` does not prune it**: that flag empties the discovered tier chain and suppresses the managed fold, but never touches the explicit-tier path — the only gesture that makes a shell wholly inert is `OCX_NO_HOOK=1` (A-33).
- **Empty tokens are discarded, never converted to a pattern — normative, both vars.** `trust::pattern_matches` returns `true` for an empty pattern and its own doc comment states *"An empty pattern is a catch-all"* (`trust.rs:373-376`), so without this rule a trailing comma, a doubled comma or the empty string would contribute one empty pattern that consents to **every** namespace: `OCX_CONSENT_NAMESPACES='ocx.sh/acme/*,'` would be indistinguishable from `'*'`, through a channel a devcontainer image writes by hand. The contract: split on the separator, trim each token, **drop every empty token before any `ScopeSpec` is constructed**; an all-empty value (`''`, `','`, `',,'`) contributes **nothing** — never a catch-all, and never an error, because an unset var and an empty one are the same situation and D3 forbids breaking a prompt over either. `OCX_CONSENT_PATHS` follows the same rule for the same reason: an empty token must never become an empty `PathBuf`, which normalizes toward a root rather than toward nothing. This is the env-channel spelling of the parse-time rule the grammar bullet already states for the config tiers — the widening direction is refused on every surface that can reach the whitelist.

**Why both lists, against the research's namespace-only recommendation** — they answer different questions and neither subsumes the other. `paths` answers *"may ocx activate in this checkout at all"* (the devcontainer case the owner stated: pre-whitelist the repo checkout, whose sources are not known to the operator publishing the image). `namespaces` answers *"whose binaries may reach my PATH"* (the fleet case). Shipping only namespaces leaves the devcontainer case unanswered; shipping only paths reproduces the footgun the research correctly identifies. Two small static grants, each independently sufficient, is less machinery than one plus the exceptions it would need. **Decided** (OQ-1): both ship, `paths` primary and `namespaces` the auto-enabler for projects outside it; the global toolchain is always trusted, so consent is project-scope only.

**How the two combine — normative, because the ambiguity here is dangerous.** They are **independent grants, OR'd**: clause 3 (a `paths` hit) and clause 2 (a `namespaces` hit) each activate on their own, and **neither constrains the other**. Requiring both would break both cases by construction — the devcontainer publisher writing `paths` does not know the checkout's sources, and the fleet operator writing `namespaces` does not know the paths. **An absent or empty grant grants nothing; it never means "everything allowed".** That is the misreading to foreclose: an unset or empty `namespaces` is **not** read as "any namespace", it simply grants nothing, and an unset `paths` likewise. What *does* activate a checkout whose sources nothing consents to is a `paths` hit — clause 3's stated exception, an operator naming an exact canonical directory whatever it contains — and that is a grant deliberately made, not a permissive default leaking out of an empty list. Fail-safe stays the default in both directions: a project matching neither grant is inert. A **strict mode** (path consented **and** every lock source inside the allowed namespaces) is a coherent product, and this ADR does not ship it: it is a separate decision, not an open question here.

**No content-hash drift re-checking on the whitelist itself.** Static list, field default. Drift belongs to the consent stamp (above), not the grammar.

## Decision 5 — Enablement, symmetric with completions

Mirror the shipped completions triad exactly (`options/completion.rs`, `activate.rs:53-61,100-103`).

```rust
// crates/ocx_cli/src/options/hook.rs  — new file, flat layout, template: options/completion.rs
#[derive(clap::Args, Clone, Debug, Default)]
pub struct Hook {
    #[clap(long = "hook",    overrides_with = "no_hook")] hook: bool,
    #[clap(long = "no-hook", overrides_with = "hook")]    no_hook: bool,
}
impl Hook {
    /// 1. `--no-hook` → false. 2. `--hook` → true. 3. `OCX_NO_HOOK` truthy → false.
    /// 4. `[shell] hook` → as set. 5. auto: `interactive`.
    pub fn enabled(&self, interactive: bool, configured: Option<bool>) -> bool;
}
```

Flattened into **both** `ocx self setup` and `ocx self activate`. `self setup --hook` / `--no-hook` writes `[shell] hook = true|false`; **flag absent writes nothing** and the default applies. **Tier and mechanism, both previously unstated and both undecidable from "the user `config.toml`"**: the target is the **home** tier, `file_structure.root().join("config.toml")` — the same file and the same accessor the shipped `self setup --managed` already writes (`setup.rs:389`), not `ConfigLoader::user_path()` (`config_dir()/ocx/config.toml`). The write is a **surgical `toml_edit` edit** (`toml_edit = "0.25"` is already a workspace dependency used by `ocx_lib`), not a whole-file rewrite — `Config` derives `Deserialize` only (`config.rs:39`), so a round-trip is not available, and a rewrite would discard comments and unknown keys the forward-compat contract exists to preserve. A missing file is created with just the one section. `--config`/`OCX_CONFIG` names a *read* override and never redirects this write; if a higher tier already sets the key, the write still lands and the CLI says which tier will win (see Decision 7). Interactivity is decided shell-side and passed explicitly, exactly as the shims already do for completions (`$-` on POSIX, `status is-interactive` on fish, `[Console]::IsInputRedirected` on pwsh) — the binary never probes a stderr the shim may have redirected.

**Boolean `OCX_NO_HOOK`, not tri-state `OCX_HOOK=0|1|auto`.** Every environment toggle in this codebase is a negative-only `OCX_NO_*` flag read through `env::flag` + `BooleanString`: `OCX_NO_COMPLETIONS`, `OCX_NO_CONFIG`, `OCX_NO_MODIFY_PATH`, `OCX_NO_PROJECT`, `OCX_NO_VERIFY`, `OCX_NO_CONFIG_REFRESH`. A tri-state would be the only one, and it buys nothing: the positive channel already exists as `--hook`, and "auto" is precisely what an unset variable means. One spelling, house style, no new vocabulary.

**`[shell] completions` — the rung completions never got, added here.** Completions ship a flag (`--completion` / `--no-completion`, `options/completion.rs`) and an env var (`OCX_NO_COMPLETIONS`), and **no config rung at all**: `Completion::enabled(interactive)` takes no `configured` parameter, so "off permanently" is only expressible as an exported variable. `[shell] hook` gets all three rungs in this decision, and shipping a second `[shell]` key with a shorter ladder would make the section's grammar unlearnable — a user who has just written `hook = false` has every reason to expect `completions = false` to exist. So `[shell] completions: Option<bool>` lands alongside `hook`, and `Completion::enabled` gains the same `configured: Option<bool>` second parameter `Hook::enabled` carries — **the identical ladder, in the identical order**: 1. `--no-completion` → off. 2. `--completion` → on. 3. `OCX_NO_COMPLETIONS` truthy → off. 4. `[shell] completions` → as set. 5. auto: `interactive`. The auto arm is unchanged from what ships: the shim passes an explicit flag from its own interactivity check where it has one, and where it does not the binary falls back to `std::io::stderr().is_terminal()` (`activate.rs`, the `load_completions` line). `ocx self setup` gains the paired `--completion` / `--no-completion` flags — it has neither today — writing `[shell] completions` exactly as `--hook` writes `[shell] hook`: home tier, surgical `toml_edit` edit, **flag absent writes nothing**. **Read at the same point as `hook`**: once per shell start by `self activate`, inside the single `ConfigLoader` pass option C already buys — never on the per-prompt path, which reads no config at all. One field, one parameter, one match arm; it closes the asymmetry instead of documenting it. Owner's call: too small to justify its own issue, it rides this ADR.

**Env names stay flat and short; no config-path mirroring.** `OCX_NO_HOOK` and `OCX_NO_COMPLETIONS` keep their shipped spellings — mechanically mirroring `[shell.*]` into the env would force `OCX_NO_COMPLETIONS` ⇒ `OCX_NO_SHELL_COMPLETIONS` for consistency, a gratuitous break of a shipped name, and renaming one but not the other is worse than renaming neither. The consent vars are `OCX_CONSENT_PATHS` / `OCX_CONSENT_NAMESPACES`: short, and out of `[[trust.policy]]`'s vocabulary, which was the whole point of the rename. **Bare `OCX_SHELL` is reserved and deliberately unused** — it must not become an alias for anything in this ADR, because mise spells the *active shell's name* `MISE_SHELL` and ocx already threads `--shell=` through every emitter, so if a shell-name variable ever appears, `OCX_SHELL` is its natural claimant.

### Where the config rung is read

| Option | Cost | Verdict |
|---|---|---|
| A: `self setup` bakes the decision into the shim body | zero read | **rejected** — shims are byte-identical across installs with no substitution, guarded by `no_shim_contains_a_substitution_placeholder` |
| B: RC block exports `OCX_NO_HOOK=1` before sourcing | zero read | **rejected** — an exported toggle leaks into every child process, the exact failure the `OCX_ACTIVATED` removal exists to prevent |
| C: `self activate` reads config once at shell start **(chosen)** | one `ConfigLoader` pass per shell start; **zero per prompt** | accepted |
| D: flags + env only, no persistence | zero | rejected — fails the owner's stated `self setup --[no-]hook` requirement |

**C** costs `self activate` a `ConfigLoader::load_with_local_view` pass — three `symlink_metadata` probes, up to three small TOML parses, one managed-snapshot read. That is a real addition to a path that today constructs only `FileStructure::new()`, and it is *bounded and once per shell*. It does **not** promote `self activate` to `Context::try_init` (no OCI client, no `OciIndex`, no `PackageManager`) — the fast-path constraint that matters is preserved. Use the existing loader, never a bespoke mini-parser: a second precedence implementation is a second source of truth.

**Per-prompt discipline is absolute**: hook presence in a session is decided once, at startup. The per-prompt path reads **no config at all** — flags, env, ledger fingerprint and watch-set stats only. Config is loaded only when the fingerprint has already decided a recomposition is needed.

**The unconsented project needs a negative cache, or the rule above is false in its most common case.** Evaluating consent reads `[shell.consent]` from `config.toml` *and* parses the lock — a full `ConfigLoader::load_with_local_view` pass on **every prompt** for a user sitting in a fresh clone, which is exactly the state the design calls normal and exactly the state the ≤5 ms budget would then have to exclude. So the ledger carries `verdict: "inert"` alongside `fp` (Decision 1): when the fingerprint is unchanged and the cached verdict is `inert`, the prompt is stat-only and reads nothing. **Only the negative verdict is cached.** An `Activate` verdict is always re-derived, never read from the carrier — caching it would make the ledger a consent input, which Decision 1's three rules forbid; caching `inert` can only ever cause ocx to do *less*, which is the fail-safe direction and matches the "narrow, never widen" posture.

**Default: on, interactive shells only.** A default-off feature requiring a config edit will not be adopted, and the consent model makes it inert for every untouched project. **Decided** (OQ-2): default-on from the first release that carries the hook, fleet blast radius accepted by the owner.

### Delivery layers (all owned by `ocx self activate`)

1. **Startup** — the existing emission order is fixed and load-bearing: completions **first** (PowerShell's `using namespace` must be the first statement `Invoke-Expression` sees), then PATH prepend, then global env. Hook and wrapper emission append **after** those.
   **Append-only, never clobbered — for every shell, not just PowerShell.** An earlier draft committed to this for pwsh's `prompt` and named the other mechanisms bare, which silently dropped a risk the superseded ADR had flagged. The same points are owned by starship, oh-my-zsh, powerlevel10k and direnv, and clobbering them is the single most common integration bug in this category. Per shell: **bash** — append to `PROMPT_COMMAND`, handling *both* the string form and the Bash 5.1+ **array** form; the array is the specific footgun ([Warp#5219](https://github.com/warpdotdev/Warp/issues/5219) — syntax errors on semicolon-terminated elements; [vscode#158090](https://github.com/microsoft/vscode/issues/158090) — exit-code `$?` clobbered by string-vs-array confusion), and the hook must preserve `$?` across itself. **zsh** — `add-zsh-hook precmd` (or `precmd_functions+=`), **never** defining `precmd()`, which is how starship avoids clobbering. **fish** — a named `--on-event fish_prompt` function, which is additive by construction. **PowerShell** — wrap the existing `prompt`, calling through to the captured previous definition. **nushell** — append to `$env.config.hooks.env_change.PWD`, never assign it.
   **The read that gates the append is governed too, and it shipped wrong twice**: every arm's "am I already registered?" probe must resolve in the namespace it asks about and no wider — a function-scoped builtin for a function (`typeset -f`, `functions -q`, `Test-Path function:`), `Test-Path variable:` for a variable, parsed `arg-names` for elvish's closure. A wider probe reads as "already registered" for something that is not ocx's registration and the shell then runs unhooked for its whole life, silently. `command -v` (which also finds `$PATH` executables, and at the wrapper's call site *runs* what it found) and elvish's `to-string` substring scan were the two instances (A-42).
2. **Per prompt** — mtime fast path first, then the reconcile script only on change.
   **The no-op path should not exec ocx at all where the shell can decide it.** `crates/ocx_cli/src/main.rs:18` is `#[tokio::main]`: every invocation execs the binary and builds a multi-thread Tokio runtime before dispatch reaches any `stat`, and that floor is ~3.8 ms on a warm 32-core Linux box — most of a 5 ms budget spent learning that nothing changed, and worse on macOS, on a 2-core runner, and above all on Windows, where process creation is an order of magnitude dearer and where this ADR calls PowerShell first-class. So the emitted hook **carries the watch-set paths** and short-circuits shell-side — bash/zsh/ksh `[[ file -nt stamp ]]` is a builtin mtime comparison with zero exec — invoking `ocx self activate --reconcile` (hidden, per the `launcher exec` precedent) only when something is newer. Shells without a builtin newer-than test fall back to the exec on every prompt and are budgeted separately (NFR Latency).
   **`--reconcile` is a cross-version contract, not plumbing.** A running shell's hook body was emitted by binary X and invokes whatever `current` points at *now* — which `self update` swaps underneath it, and which a downgrade or a rollback can make **older**. After a rollback to a pre-hook binary, every prompt in every open terminal execs a binary that has never heard of `--reconcile`. **The emitted hook resolves the binary through `current` unconditionally, and `OCX_BINARY_PIN` has no effect on that resolution**: the pin is a downstream, re-entrant mechanism — consumed by the Windows `.exe` shim, the script host's `ocx` module, and generated Unix launcher bodies, each a *child* invocation pinning back to the binary that spawned it — and the interactive shell's own top-level `--reconcile` call is upstream of that mechanism and structurally cannot consult it (A-34). Two rules make the version-skew case harmless and both are cheap: the emitted hook **discards the reconcile call's stderr and ignores its exit status** (so an unknown-flag clap error is invisible rather than printed once per prompt), and it **probe-guards the binary** — if the resolved absolute path is missing or not executable, the hook is a silent no-op. That probe guard is the mechanism the superseded ADR's amendment to `adr_idempotent_path_move_to_front.md` requires and that this ADR's Amends line promises; it lives here, with an acceptance test, not only as an NFR adjective. **On pwsh specifically, stderr-discard plus status-ignore is not enough**: under a hardened profile setting `$ErrorActionPreference = 'Stop'` (with `$PSNativeCommandUseErrorActionPreference = $true`), a native command that writes to stderr or exits non-zero raises a *terminating* error that `2>$null` does not prevent — so the pwsh arm additionally wraps the reconcile call in `try { … } catch { }`, sets `$ErrorActionPreference = 'Continue'` and `$PSNativeCommandUseErrorActionPreference = $false` in the hook's own scope with both restored in a `finally`, and captures and restores `$?` / `$global:LASTEXITCODE` around the call, the same preservation rule Decision 5 layer 1 already states for bash's `PROMPT_COMMAND` (A-22).
   **Enablement is not re-evaluated per prompt.** `--reconcile` bypasses `Hook::enabled` entirely: it runs in a fresh process with no `configured` value, and reading one would violate the zero-config rule above. Consequence, stated so it is not discovered: `OCX_NO_HOOK=1` exported mid-session takes effect at the **next shell start**, not the next prompt.
3. **Wrapper function — a latency optimization for same-command-line chaining, never the correctness floor.** A shell function named `ocx` that runs the real binary and then fingerprint-checks before returning, so `ocx update && cmake --build .` or `ocx add --global foo && foo` sees the new env **within one command line**, with no prompt in between. **The wrapper captures the real binary's exit status immediately after it returns — before running the fingerprint check or any other command — and returns exactly that captured value**; the fingerprint check runs purely for its side effect and never influences `$?`, so `ocx install nonexistent-tool; echo $?` still reports the real failure (A-35). It is the only possible host for that particular case — a child process can never mutate its parent's environment — and that case is *all* it buys.
   **The correctness floor is the next prompt, and it needs no wrapper at all.** Typing `ocx add --global foo`, pressing enter, then typing `foo` puts a prompt between the two commands; the hook fires there, the fingerprint has moved, and the env is fresh. Every way of escaping the function name therefore **degrades to next-prompt correctness rather than breaking**: an absolute-path invocation, `command ocx`, `\ocx`, a `$(which ocx)` call, and any invocation from a script, a Makefile or a subshell. None of them is a supported-vs-unsupported distinction — they are all correct one prompt later. Interactive shells only; scripts hit the real binary and use `ocx run`. (The activation stream calls ocx by absolute path *deliberately*, so the wrapper can never shadow it — see the next paragraph. That is the same mechanism seen from the other side, not a contradiction.)

**No emitted snippet may ever call bare `ocx`.** The wrapper is named `ocx` and `command -v ocx` finds functions, so a bare call inside the emitted stream would execute the wrapper inside a command substitution and capture its output into the env stream. Every ocx-emitted call site uses the resolved absolute binary path (the `$_ocx_bin` pattern the shims already use); a regression test asserts the wrapper is unreachable from the activation stream.

**All user-visible hook output is `printf … >&2` *inside the eval'd script***, not the binary's stderr — and this is narrowed to the **per-prompt `--reconcile` path only**: the startup path emits no diagnostics at all, every message being deferred to the first reconcile run. The summary line, the inert-project hint, the over-cap abandonment line, the direnv/mise yield line and Decision 7's `[shell.consent]`-strip reason are all emitted as **shell code that prints to stderr when eval'd**, via one new per-arm primitive `Shell::emit_message(text) -> Option<String>` (Batch returns `None`, since it hosts no hook); each message passes **that arm's own escaper** and rides as a `printf` **argument**, never as the format string, since a `%` in a project path would otherwise be consumed as a conversion spec. The shims discard the binary's stderr unconditionally (`2>/dev/null`, `shims.rs:63,103,105,146,239`), and that **discard stays unconditional** — it is applied at invocation time, before the exit status that would distinguish an unknown-flag clap error from a normal run is knowable, so it cannot be scoped — which is why the script body is the only reliable channel at all. `set -u` discipline is binding: every ledger read uses default expansion (`${__OCX_ENV_STATE-}` and per-shell equivalents), because the variable is unset on the first prompt by construction. **The corollary that makes deferring every diagnostic to the reconcile path reliable is itself normative: the first prompt of every shell always reconciles**, because the mtime fast path has no recorded fingerprint to compare against and "no record" counts as changed — so no diagnostic is ever silently skipped by virtue of a no-op first prompt (A-21).

## Decision 6 — Regeneration: the thin-dispatcher invariant, and exactly where lag lives

**Invariant (state it, do not revisit it).** The `env.*` shim bodies are **pure dispatchers with no ocx business logic**. Four of the five families resolve `$OCX_HOME`, find `ocx` through the `current` symlink, and `eval`/`source`/`slurp` the output of `ocx self activate` — generated fresh by the *currently running* binary at every shell start (`shims.rs:63`, `:103`, `:146`, `:239`). A change to what gets exported therefore requires **no shim rewrite** and reaches every new shell immediately.

**The invariant is currently unenforced, and the test previously cited for it does not enforce it.** `each_shim_resolves_the_binary_through_the_current_symlink` (`shims.rs:445,461-464`) asserts `body.contains("self activate") || body.contains("@('self', 'activate', '--shell=powershell')") || body.contains("--format json --global env")` — i.e. *"invokes the binary"*, not *"is a pure dispatcher"*. A shim that inlined arbitrary reconciliation logic passes it unchanged; `ENV_NU` already does, and the third `||` arm exists precisely to let it. Cite it for what it proves and add the check that would enforce the invariant: a per-family **body-size ceiling plus a denylist of business-logic tokens** (consent, trust, ledger, reconcile keywords) over the four eval-capable families, with nushell explicitly exempted by 6(b) below. Demonstrated red by inlining one such token. This is the rustup/starship/zoxide/mise-POSIX shape; the tools that got it wrong (conda's blind rc rewrite, nvm's sourced function library) pay in surprising mutation or slow startup.

**The earlier "hook logic lands one `self update` later" framing is false for this codebase.** Lag exists in exactly three places, and nowhere else:

| Lag surface | Mechanism | Size |
|---|---|---|
| (a) Shim / RC **wrapper body** changes | `refresh_shell_integration_after_swap` runs in the **old binary still in memory** (`update.rs:109-111`), so the hop that swaps in a binary carrying a new body does not heal on that hop; the heal lands on the next `self update` or a `self setup` re-run. Diff-gated (`needs_write`), best-effort, never fails the update | rare, small |
| (b) **Nushell — the whole activation body** | `env.nu` does **not** call `self activate` at all: no string `eval`, and `source` needs a parse-time-constant path, so it inlines the apply (`shims.rs:197-215`) and reads `ocx --format json --global env`. The vendor autoload at `nushell/vendor/autoload/ocx.nu` inlines the same body. For nushell, every activation-logic change **is** a body change, so it lags per (a) | **one hop, every change** |
| (c) An already-running shell | Evaluated its activation once at startup. No surveyed tool solves this; a running shell cannot un-define a function it already sourced | universal |

(b) is the one that must be budgeted by any plan: the four eval-capable families get the hook with zero rollout lag, nushell gets it one `self update` hop behind. Do **not** generalize mise's static-nushell shape to the other shells — OCX already made that call correctly.

**How nushell consumes a reconcile, since it cannot consume a `String` of shell source.** `ENV_NU` never calls `self activate`; it runs `^ocx --format json --global env | from json` and applies with `load-env` (`shims.rs:212`). So nushell takes **structured data, not emitted text**: the design is that `--reconcile --format json` returns the `Plan` (`sets` / `removes` / `restores`) and the inlined nu body applies it. **Status, stated honestly rather than as shipped fact — the `Plan` JSON channel is produced but not yet consumed.** What ships today is the *global-toolchain* half on both nu paths: the `ENV_NU` startup body and the PWD hook it appends each re-run `ocx --format json --global env` (`setup/shims.rs`), so no nu body invokes `--reconcile` at all. `emit_plan_json` (`self_group/activate.rs`) is therefore producer-only, and A-23's `v` gate has no reader yet. The shipped website page documents that state — global toolchain only, no project reconcile, no revert, no consent gate — and the decision below is the design the nu arm lands on when WP-12b's spike clears: what consumes it is the `--reconcile` call replacing those two `--global env` calls in the nu body, at which point the one-hop lag of 6(b) starts applying to reconciler changes too. That is the one place `Plan` needs a JSON wire shape — concretely, a **top-level `"v": 1`** on the same envelope discipline as the ledger, where `v` absent or unrecognised means **apply nothing this prompt and return silently** (no error, no partial apply), and unknown fields inside a recognised `v` are ignored; an additive `type` value never bumps `v`, so nushell never freezes for a hop over an additive change (A-23). It is also the reason `remove_list_element` returning `Option<String>` has no nushell consumer — nushell is not a `None` arm like Batch, it is a *different channel*. Two consequences the plan must carry: the nu apply body grows (so 6(b)'s one-hop lag applies to every reconciler change, as stated) — **and the lag is already worse than that framing suggests**: the shipped `NU_ENV_APPLY_LOOP` is a two-way branch, `if type == "path" { … } else { load-env … }`, so today's `else` arm already applies a `type: "list"` entry as a constant — overwriting a separator-joined variable instead of folding into it — which is a live defect on a kind that ships today, not only a forward-compat hazard. The applier must become a **four-way** dispatch: `path` ⇒ move-to-front prepend, `list` ⇒ an `export_list`-style fold using the entry's effective separator, `constant` ⇒ `load-env`, anything else ⇒ skip, applying nothing (A-23). And **`load-env` cannot unset** — `hide-env` is the only primitive and its scoping inside hook blocks is the known hazard the mandated spike exists to settle, so Decision 3's constant-revert (`restores: (key, None)`) is **unimplementable on nu until that spike lands**. Say that rather than claiming parity.

`rc_block.rs` already solves the harder half better than conda: its fence carries a format version and a content hash driving a `Fresh`/`Current`/`FormatUpgraded`/`Dirty` state machine, exiting 82 on user edits. Prior art to cite, not reinvent.

*Skipped:* a `# ocx-shim-schema: 1` marker in the shim body for observability. No thin-stub tool needs one. Add it if `ocx about` ever needs to flag a stale shim.

## Decision 7 — OD-2: `[shell]` in the managed tier

**`[shell]` ships from the managed tier, with one gate on the consent-granting half.**

- `[shell] hook` — merges unconditionally, **in both directions, and that is load-bearing rather than incidental**. `Config::merge` is scalar-wins-if-present with the managed tier folded *last* (`config.rs:140-145`; `fold_managed_tier` runs `accumulator.merge(parsed)` after the discovered system→user→home chain), so the managed tier beats every **discovered** tier (system → user → home) — it can force `hook = true` over a user's explicit `hook = false` in any of those three files, not only the fleet-**off** direction the "hooks off on build agents" rationale covers — while the **explicit** tiers, `--config` / `OCX_CONFIG`, still merge on top of the managed fold rather than underneath it (`config/loader.rs:180-182`), so an explicit override always wins. `ocx shell state` names the tier that actually decided the rung, never hard-codes "managed" (A-32). What makes the managed-over-discovered direction acceptable is exactly one argument, so it is stated as the load-bearing claim it is: **the toggle grants nothing, because consent (Decision 4) still gates every project independently.** An operator who already controls `[mirrors]`, `[patches]` and the default registry gains no escalation from a prompt-hook toggle. If that consent coupling ever weakens, this key stops being safe to merge unconditionally.
- `[shell.consent]` — merges **only when the `[managed] source` is digest-pinned**. Otherwise it is stripped with a WARN naming the reason. **Two things that guard needs and did not have.** (1) **A reader.** `log::warn!` goes to stderr, and Decision 5 puts this config read inside `ocx self activate`, whose stderr the shims discard (`shims.rs:63,103,105,146,239`) — so an operator shipping `[shell.consent]` from an unpinned tag would get *silence* on the exact path where the strip matters. Route the reason through the same `printf … >&2`-inside-the-eval'd-script channel the rest of the hook uses, and record it where `ocx about` can surface it. (2) **A red state.** This is the *only* thing between an unpinned managed payload and a PATH-front activation grant — where the surface cited as precedent, `[[trust.policy]]`, additionally has `system_locked` admission authority and operator-over-project tiering (`trust.rs:20-40`, `resolve` at `:747`). One guard carrying that much needs a demonstrated red+green: unpinned source ⇒ `[shell.consent]` absent from the merged config; digest-pinned source ⇒ present.

This is not a new rule; it is the existing one. `guard_managed_sigstore_trust` (`config/loader.rs:431-457`) already honours `[trust.sigstore]`'s `trusted_root_json`, `fulcio_url` and `rekor_url` only behind a digest-pinned source, because otherwise the consent material arrives over the very channel it exists to verify and whoever can move the tag can swap it. A namespace whitelist is exactly that shape of material: it decides whose binaries reach PATH. Reuse the guard's home and its warning idiom.

This resolves the inconsistency the brief names: the blanket "strip `[shell]` alongside `[managed]`" answer recommended by the superseded ADR is no longer coherent once the whitelist ships in the managed tier, and a blanket "ship everything" answer would let an unpinned tag grant PATH-front activation consent. The split is per-key and precedented.

## Decision 8 — OD-3: accept the silent digest swap, and name the real mitigation

Within a consented namespace, whoever can publish gets PATH-front code with no signal. **Accept and document** — and state the residual at its true size, because "at the victim's next prompt" overstated it. `ocx.lock` pins the **per-platform leaf digest** (`LockedTool { repository, platforms: BTreeMap<String, Digest> }`, `project/lock.rs:163-176`, with `deny_unknown_fields` across the lock tree), so a swapped publish reaches PATH only after a lock-changing event (`git pull`, `ocx update`) **and** a subsequent install. The hook itself never fetches. That seam matters, because it is exactly where the mitigation below sits.

Digest-set re-confirm was the alternative and is worse: it fires on every legitimate lock bump (`git pull`, `ocx update`), which trains users to confirm without reading — a net security regression, and the reason every surveyed default-mode whitelist is static. mise's paranoid mode is the precedent for an *opt-in* content check, not a default.

The residual has a real mitigation that already exists and must not be re-invented in a weaker form: `[[trust.policy]]` plus `ocx package verify` is the publisher-compromise control, and it is signature-based, which is the correct instrument. The consent stamp answers "do I run this project's toolchain at all"; signatures answer "did the expected identity publish this artifact". Conflating them would produce a second, weaker trust system.

**But it is a deferral, not an active control, and the earlier phrasing read as the latter.** Three facts, from `package_manager/tasks/auto_verify.rs:22-36`: with no trust policy configured, auto-verify is a **no-op**; with no *matching* policy it logs INFO and the install **proceeds** (an opt-in trust model, by design); and it is not on the hook's path at all, since the hook is compose-only. So for the victim this ADR is protecting — someone who cloned a repo and has written no operator config — the mitigation is **off**. Worse, absent an operator policy the project tier applies (`trust.rs:20-23`), so a repo-supplied `[[trust.policy]]` makes verification run and attest **the repo author's own identity**: a pass that proves nothing to the victim. The enabling step must be named as such: an **operator-tier `[[trust.policy]]` in `config.toml`**, not `ocx.toml`. (The other half is sound and stays: `trust::resolve_tiered` is operator-authoritative, so a project-tier policy cannot weaken an operator pin.) Documenting a default-off control as the residual's mitigation without saying it is default-off is the same class of error as importing another tool's benchmark as a budget.

## Decision 9 — Coexistence with other per-prompt PATH tools

Previously this existed only as a parenthetical inside an acceptance-test bullet ("detect `DIRENV_DIR`, yield with one info line"), which is not a specification — a test written against it would assert whatever the implementation happened to do. Stated properly, and widened to the tool the earlier draft missed.

**The yield signal is the other tool's live session state, never a file on disk — normative, because the cheap implementation is the wrong one.** ocx yields **only when that tool is actually managing this directory**: `DIRENV_DIR` set *and* naming the resolved project, or `MISE_SHELL` / `__MISE_ORIG_PATH` present. An `.envrc`, a `mise.toml` or a `.tool-versions` checked into a repo where the tool is **not installed, not hooked, or not active in this shell** must **not** suppress ocx activation. A config file is evidence of someone else's workflow; it is not evidence of a live hook that will set the env at this prompt. Yielding on file presence would leave the project silently managed by nobody — worse than either tool winning, and undetectable from inside ocx.

- **direnv — yield the project scope, keep the global scope.** When `DIRENV_DIR` is set and names the current project's canonical directory, ocx applies the **global** scope only, reverts any project scope it had already applied, and prints one info line naming direnv as the owner. When `DIRENV_DIR` names a *different* directory, ocx treats it as absent — direnv is active for some ancestor, not for this project — and proceeds normally. Fighting direnv is an explicit non-goal; `ocx direnv export` remains the supported path for direnv users and is untouched.
- **mise — the same class, and it was unaddressed.** mise is the other per-prompt PATH-prepending hook, and its own docs say direnv and mise should not be combined because "incompatibilities are not considered bugs" — the failure axis being PATH ordering between two hooks. OCX's mechanism is the same shape. **Symmetric yield**: `MISE_SHELL` (or `__MISE_ORIG_PATH`) present ⇒ same treatment as `DIRENV_DIR`, project scope yielded, one info line. Declaring it a non-goal instead would be defensible; leaving it unmentioned is not, because the collision is structural rather than incidental. **The two checks are independent `if`s, never an `elif` chain**: when both sentinels are set and matching, ocx yields on each one independently and prints **one info line per observed tool**; the direnv-versus-mise ordering between those two tools is their fight, and ocx is out of it either way — accepted as-is (A-37). **Hook-registration order relative to direnv's or mise's own `PROMPT_COMMAND`/`precmd`/hook entries is unspecified and accepted under D2's convergence model**: no reordering logic, no cross-tool coordination; any resulting apply-then-revert flap from a registration-order race is bounded to exactly one prompt and self-heals at the next one (A-36).
- **tmux / SSH reattach — settled, no design change.** direnv's classic stale-PATH-after-reattach complaint ([direnv#106](https://github.com/direnv/direnv/issues/106)) is a shell-*init* timing bug. This design recomputes D from truth every prompt regardless of L's staleness, so it does not transfer. Noted here to preempt it being raised as a gap.
- **IDE terminals that snapshot env once at launch** (JetBrains, and any long-lived process holding `JAVA_HOME`) are out of scope by the same boundary as Context: that is [#189](https://github.com/ocx-sh/ocx/issues/189)'s class — processes that never re-read env — not this ADR's.

## Decision 10 — `ocx shell state`: introspection, read-only, never eval-able

**The one new command surface this ADR adds.** Everything else here is a flag, a config key, a private variable or a hidden `--reconcile` arm. `ocx shell state` exists because every other decision in this ADR is designed to be *quiet*: the hook logs at debug, an absent ledger is normal, an inert project prints one hint line at most, and a yielded scope prints one info line. Quiet is right for a per-prompt path and wrong for a user asking "why is my toolchain not on PATH". Without a read-only window onto the session's own state, the answer is a `base64 -d` on an undocumented variable, and the first support question makes the ledger user-facing anyway — on worse terms than Decision 1's gesture bullet already accepts.

**What it prints**, all of it derived, none of it mutating: the decoded ledger (`__OCX_ENV_STATE` — envelope tag, schema `v`, and the payload rendered as fields, not as base64); what is currently applied **per scope**, `global` and `project` separately; fingerprint status (the watch set, each member's mtime/size, and whether the recorded `fp` still matches); whether `priors` are intact for each constant the project scope owns — the one datum nothing can reconstruct, and the thing Decision 1's repair gesture destroys; and, most importantly, **why the shell is not active when it is not**. That last part is the command's reason to exist, and the reasons are enumerable because the design enumerated them:

- no consent stamp **and** no matching grant — with the project's derived source set and the `paths` / `namespaces` grants it was tested against (Decision 4);
- consent stamp present but the current lock's source set is not a subset of it — naming the source that is new (Decision 4, clause 1);
- the hook is disabled — naming **which rung** decided it: `--no-hook`, `OCX_NO_HOOK`, or `[shell] hook = false` and the tier that set it, including the managed tier winning over a user's own file (Decision 7);
- yielded to **direnv** or **mise** — naming the live signal observed (`DIRENV_DIR` and the directory it names, `MISE_SHELL` / `__MISE_ORIG_PATH`), because Decision 9 yields on session state and a user staring at an `.envrc` will guess the wrong cause;
- the ledger was **over cap and therefore reduced to a marker-only record** — `v`, `fp` and `verdict` survive but `applied`/`priors` do not, the one degradation that loses information rather than repairing it (Decision 1, A-01);
- the ledger was absent, truncated, or carried an unrecognised envelope tag — distinguishing the *first prompt of a shell* (nothing applied, nothing to repair) from a *corrupt carrier* (a scope was applied and its record is gone), which Decision 1 already calls normatively different situations sharing one code path.

**Contract: the output is human-readable and must never be eval-able.** This is a hard rule, not a style note. `ocx self activate` and `ocx self activate --reconcile` emit shell source whose entire purpose is to be `eval`'d; this command emits diagnostics whose entire purpose is to be read. A surface where the two are confusable is one copy-paste away from executing a diagnostic dump in a live shell, and one shim bug away from `eval`ing a state report into someone's environment. So: no line of `ocx shell state` output is valid `export`/`set`/`$env.` syntax in any of the ten arms, values are rendered quoted-for-humans rather than quoted-for-a-shell, and a test asserts that the output of the two commands is never interchangeable. `--format json` is available and follows the house rule — machine-readable is a *context*, never a divergent command surface. The command is **read-only**: it never writes a stamp, never repairs a ledger, never emits a plan. Repair is the `unset` gesture or a new shell (Decision 1), and this command is how a user checks the gesture worked.

**Rejected: `ocx shell refresh`.** Considered and cut, recorded here so it is not re-proposed. The intent was "force a recompose now", and it cannot be delivered as an ordinary command: **a child process cannot mutate its parent's environment.** So it would have to be either `eval "$(ocx shell refresh)"` — which puts the eval ceremony back in the user's hands for a case the next prompt already handles, and which is exactly the shape Decision 5's wrapper exists to avoid making load-bearing — or a shell alias/function named `refresh`, which inherits every fragility the wrapper function has (an absolute-path invocation bypasses it, scripts never see it) **without** the wrapper's justification, since the wrapper buys same-command-line freshness and this would buy nothing the next prompt does not. A third variant was considered: a **request file** — `ocx shell refresh` writes a marker into `state/projects/<key>/`, and the next prompt's hook consumes it and forces a recompose. It is implementable and it was cut as complexity for no gain: it adds a write surface, a consume-and-delete race, and a third thing the fingerprint fast path must stat, to serve a case that Round A's automatic **retirement** rule (Decision 3 — every recompose retires what ocx owns and D no longer wants) and Decision 1's `unset` gesture already cover between them. What remains is diagnosis, and diagnosis is `ocx shell state`.

## Non-Functional Requirements

- **Security** — three boundaries. (1) Consent gates activation; a fresh clone is inert; consent-control keys live only in `config.toml`, and that is kept true by an explicit project-tier strip plus two tests, not by a `deny_unknown_fields` attribute in another file whose stated purpose is typo detection (Decision 4). (2) The private carrier is **untrusted input** whose only permitted effects are naming the revert set and supplying the exit guard's equality operand — never naming a path, never selecting a kind for a key in D (Decision 1). (3) Reserved-key gating at the application seam closes the metadata spoof channel (reject at `package create`, skip+warn at `apply_entries`). Residual: Decision 8, documented, and mitigated by signature verification **only for users who have written an operator-tier `[[trust.policy]]` — the control is default-off**. A `sudo -E` or an ssh `SendEnv` can likewise carry a stale `__OCX_ENV_STATE` across a host boundary, not only a privilege one; Decision 1's rule (a) — `key`/`dir` are advisory only, re-derived from the CWD walk every prompt — already handles this structurally, though the case was never named until now.
- **Latency** — the budget is **floor + work**, not a borrowed number. The floor is ocx's own exec: `main.rs:18` is `#[tokio::main]`, so every invocation builds a multi-thread Tokio runtime before dispatch, measured at **~3.8 ms** for `ocx --version` on a warm 32-core Linux box — ~77% of the 5 ms an earlier draft imported from mise's benchmark of mise's binary. On macOS, on a 2-core runner, and on Windows the exec alone exceeds it. So: (a) the emitted hook short-circuits shell-side on the no-op path where a builtin newer-than test exists (Decision 5 layer 2), making the *common* prompt cost **zero execs**; (b) the CI assert is per-platform, stated as `exec_floor + Δ`, and the floor is measured in the same job rather than assumed — **two budgets rather than one shared number, and this ADR states neither figure** — `DELTA_BUDGET_MS` (shell startup) and `RECONCILE_BUDGET_MS` (per-prompt reconcile) live in `test/bench/shell_latency.py`, each beside the measurement it was drawn through, and the reconcile pair is held 10–45% apart by that file's own `self_check` so the budget and its evidence cannot move independently (amended 2026-08-26, re-derived 2026-08-27; see the decision log and addendum A-52); (c) the assert's red state is produced by a fault-injected extra `ConfigLoader` pass, so the gate is demonstrated red as well as green — a wall-clock budget on shared runners is otherwise the canonical flaky-or-vacuous gate. Composition on change is permitted to cost more and is bounded by the existing `resolve_env` path. Shell startup gains one bounded `ConfigLoader` pass (Decision 5); measure it and record the number in the plan.
- **Operability** — one summary line per change (`ocx: +JAVA_HOME ~PATH -PYENV_ROOT (acme, lock a1b2c3)`), plus one line when a scope's ledger is abandoned over cap. **No verbosity tri-state at v1** — the earlier `silent | summary | full` appeared once, in this bullet, with no flag, no config key, no env var and no default: a knob nobody could turn. Ship the summary line; add `[shell] verbosity` if field use asks for it. A malformed ledger, a missing binary (probe guard, Decision 5 layer 2), or an unreadable lock all degrade to a no-op plus at most one line. `ocx about` remains the diagnostic entry point and is where the managed `[shell.consent]` strip is surfaced (Decision 7). **Every line named above rides the reconcile path's `Shell::emit_message` channel (Decision 5), never the startup path, which emits no diagnostics at all** (A-21).
- **Availability** — the hook is compose-only and never touches the network. `--offline` semantics are irrelevant to it by construction.
- **Cost** — no new dependency, no new service, no telemetry. The only recurring cost is developer time on the per-shell emission matrix.
- **Scalability** — per-project state is O(projects) small JSON files, swept by `ocx clean` on the stamp's own `project_dir` liveness (Decision 2). The ledger carrier is capped at 16 KiB per shell; over cap it degrades to the marker-only record (Decision 1, A-01), never full omission except in the unreachable case where even the marker fails to encode. **That 16 KiB cap bounds only the carrier's own contribution — it is not a general env-size mitigation.** The combined argv+envp size handed to any spawned child, interactive shell included, is an ordinary OS boundary; an `E2BIG` on `execve` degrades through the existing `Command::spawn()` → `std::io::Error` → `Error::Io` (exit 74) path, identical to any other spawn failure, and is deliberately not separately accounted for or warned on (A-38).

## Migration and Rollout

Pre-1.0: breaks just break. No migration prose in user docs, no dual-form parsing, no deprecation window. The changelog entry **is the commit subject** — `CHANGELOG.md` is generated by `git-cliff` and must never be edited by hand.

**What actually breaks for existing users:**

| Change | Who observes it | Carried by |
|---|---|---|
| Per-prompt hook becomes default-on for interactive shells | every user, at their next shell start after `self update` | `feat(shell)!: reconcile the toolchain environment at every prompt` |
| New `[shell]` section in `config.toml` | nobody — older binaries ignore unknown sections (no `deny_unknown_fields`), which is exactly what that contract is for | — |
| `[shell]` written into `ocx.toml` | a user who tries it: hard parse error | intentional; help text names `config.toml` |
| `package create` rejects `OCX_*`/`__OCX_*` metadata env keys | a publisher who was doing this (none known) | `feat(package)!: refuse reserved OCX_* env keys in package metadata` |
| Already-published packages carrying such keys | nobody — read path skips with a warning, keeps resolving | read-path compat, the one hard exception |

**Rollout sequence** — nushell trails by one `self update` hop (Decision 6b); every other shell is immediate at next shell start. An `OCX_INSTALL_NO_SETUP` install never gets shims and therefore never gets the hook — documented, not fixed. `setup-ocx` (CI, non-interactive) is unaffected: the shims pass explicit non-interactive flags.

**Documentation surfaces** (mandatory, enumerate in the plan): `website/src/docs/reference/environment.md` (new vars; **it currently documents the per-prompt hook as removed — rewrite, do not append**); `website/src/docs/reference/command-line.md` (`self setup`/`self activate` flags, including the new `--completion`/`--no-completion` pair on `setup`, **and the new `ocx shell state` command** — Decision 10, the ADR's only new command surface); a new shell-integration page; `website/src/docs/user-guide.md` (activation + consent); `.claude/rules/subsystem-cli.md`, `subsystem-cli-commands.md`, `subsystem-file-structure.md` (**two edits, not one**: the `state/projects/` layout row, *and* the "`state/` is not walked by `ocx clean`" bullet, which Decision 2 amends — leaving it as written makes the contract a second source of truth; also name the two `projects` directories so the collision is documented once), `arch-principles.md` (glossary + ADR index); `handshake_toolchain_cli.md` §2 + §7a; the new shell-integration page also carries Decision 9's direnv/mise coexistence rules, `ocx shell state`'s diagnostic role, and the `unset __OCX_ENV_STATE` repair gesture **with its cost** (priors destroyed; a new shell is the clean floor) — which is what makes `__OCX_ENV_STATE` user-facing contract; regenerated config JSON schema.

## Validation

**Structured by cost, because the expensive tier is where a shell suite goes to rot.** The repo already ships the right shape and this section **extends it rather than inventing one**: `test/tests/test_shell_activation.py` runs the *real* activation path per shell — `_POSIX_SHELLS = ["sh", "dash", "ash", "bash", "zsh"]` parametrized over one scenario, plus dedicated fish, nushell, elvish and pwsh tests for their divergent mechanisms — on stdlib + pytest only (no `src.runner`, no registry fixtures), with `shutil.which` skipping shells absent on the host and the whole matrix running inside the **shell-zoo Docker image**. It already owns `_script_pty_command` (papering over the util-linux/BSD `script(1)` split) and `_clean_env` (which keeps assertions non-vacuous by guaranteeing the ocx bin dir is *not* pre-present on PATH). Reconciler coverage lands in that file's idiom and beside it. The tiers below are a cost ladder, and every check is pushed as far down it as it will go.

### Tier 1 — no shell

The emitters and the planner are **pure functions returning strings**, so a golden fixture per arm is the entire test: no process, no timing, no skip-if-absent.

- **Unit** — reconciler case table (every constants row, including **prior re-capture on overwrite** and the exit guard firing against the re-captured prior; list algebra with foreign elements interleaved; ledger corruption, truncation, unknown version, over-cap ⇒ omitted; case-insensitive keys on Windows); ledger forgery rules (forged `kind`, forged `key = "../../.."`, and — corrected from an earlier "discard" rule — an L constant absent from D is **reverted**, not discarded: the forgery bound is D ∪ L, enforced by "an L entry may only undo itself" (Decision 1, rule (c)) plus the `PATH`/`PATHEXT` constant refusal (A-03, A-02)); `LedgerEntry` field-name parity with `EnvEntry` (`type`, not `kind`); `remove_list_element` per-shell matrix **with a non-default separator**; reserved-key gate (create-reject, `apply_entries`-skip); whitelist grammar — exact-path non-match on a sibling directory, `namespaces` `/*` descendant boundary, and **parse-time rejection of `acme-corp*`, a bare `*`, an empty pattern and an empty `include` — each refusing the whole `namespaces` spec, never read as catch-all** (config tier: `[shell.consent]` fails to deserialize and the refused table is then **stripped**, so the rest of that file still applies — unless it carries a non-empty `exclude`, where the file keeps failing, A-40; env channel: the whole contribution is discarded with one warning and the config tiers stand alone); **env-channel empty-token discard** — `OCX_CONSENT_NAMESPACES='ocx.sh/acme/*,'`, `'a,,b'`, `','` and `''` each yield exactly their non-empty patterns and grant nothing else, asserted by an untrusted source (`ghcr.io/evil/tool`) **not** matching, with the red state produced by feeding the same values through a parser that keeps empty tokens — that variant must make the untrusted source match, which is what proves the assertion discriminates rather than passing vacuously; same pair for `OCX_CONSENT_PATHS` (an empty token must not become a path that matches any project directory); `[shell]` in `ocx.toml` refused, and a project-tier fold unable to contribute `[shell.consent]`; consent subset predicate including the same-cardinality swap and the `<registry>/<first-segment>` normalization (port preserved, default registry spelled, **derived from the lock's logical `repository` — a source set built from a re-derived physical address is the wrong operand and must fail the test**); `evaluate` rejecting a stamp whose `project_dir` mismatches.
- **Every hostile-value and escaping case lives here, and nowhere else.** Per-arm escaper selection — governing the **element-match / `export_path`** emit path (`escape::posix_single_quoted` for bash/zsh and the strict-POSIX trio, `escape::single_quoted_doubled` for PowerShell/elvish, `escape::fish_double_quoted` for fish, `escape::nushell_plain_string` for nushell; `export_constant` is moved onto this same map by A-15, where it previously used one shared double-quoting escaper on every arm) — against values carrying `'`, `"`, a backtick, `$`, `\`, `%VAR%`, a newline, and the `/tmp/a';id;'b` element Component Contracts names as the live injection. Asserted on the emitted **string**. Escaping is the one property whose tier-2 or tier-3 failure would be a *silent* wrong value rather than a visible one, which is precisely why it is not tested there.
- **Invariant L-2 — the ledger never holds shell text.** Round-trip every fixture value through `Ledger::encode`/`decode` and assert byte equality with the raw input; assert no arm's escaper output can reach `encode`. A pre-escaped value leaking in is double-escaped by an inheriting shell and correctly escaped by none, which is a silent per-value failure.
- **`ocx shell state` is not eval-able** (Decision 10) — for every enumerated inertness reason, its output is asserted **not** to be valid `export` / `set` / `$env.` syntax in any arm, and not interchangeable with `self activate`'s stream. Two strings differing in the right way needs no shell to prove.

### Tier 2 — execute the emitted snippet, no pty

`bash -c 'eval "$(…)"; env'` and diff the environment. A real shell applies the real snippet; there is no prompt, no tty and no timing. **This is most of the matrix**, and it is where lifecycle depth lives.

- **Global lifecycle in one shell — the owner's headline acceptance criterion** ("copy the command, paste it, the next command works"): `ocx add --global <tool>` ⇒ the new binary resolves; `ocx update` ⇒ the *new version* resolves; `ocx remove --global <tool>` ⇒ the binary is **gone**, not shadowed and not still on PATH behind something else. The third is what the retirement rule (Decision 3) exists for and the one an apply-only reconciler passes vacuously.
- **Branch switch, no ocx command involved** — the same trigger class twice: a checkout that **deletes a tool** from `ocx.lock` (element retired) and one that changes **only `[env]`** (constant applied, lock untouched). Together they are the executable form of Decision 3's "detection is file-state based, never command based".
- **A digest change produces no duplicate PATH entry** — after a bump, `…/packages/<old>/bin` is **absent**, not merely behind `…/packages/<new>/bin`. They are different strings, so `move_to_front` cannot dedupe them and an additive apply passes an "is the new one in front" assertion while leaving the stale one on PATH for the rest of the session. Assert the old segment's **count is zero**.
- **Apply, retire, and idempotency under repeated application** — the same snippet eval'd N times leaves PATH byte-identical and the ledger unchanged. The shipped `_assert_activation` already asserts exactly this shape (the bin dir *exactly once* after a double source); reuse it.
- **List separators** — a non-default-separator list var (`CFLAGS` with `separator = " "`, `CLASSPATH` with `":"` on Windows) applies **and reverts**. The unrevertible-list defect Decision 3 names only surfaces once a real shell has split the value, so this is tier 2 rather than tier 1.
- **Cross-shell inheritance** — a ledger written by one shell type is interpreted correctly by a different one. **No pty needed**: spawn the child with the carrier inherited (`bash -c` under zsh, `fish -c` from bash, `pwsh -Command` from either) and assert its decode, plan and emitted result. This is Invariant L-2's end-to-end proof.
- **Subshell containment** — a subshell inherits the ledger, and a subshell that `cd`s elsewhere rewrites the carrier **in its own environment only**, leaving the parent's view intact afterwards. This is the property that makes the env carrier beat the on-disk option in Decision 1's table, and nothing else tests it.
- **Consent and yield, in full** — fresh clone inert; post-`add` active; source-swap re-prompts (the same-cardinality `ghcr.io/acme → ghcr.io/evil` swap); unreadable **and absent** lock inert; a `paths`-granted project activates on lock-source drift without ever writing a stamp, and a `namespaces`-granted project goes inert the moment a source leaves the granted set (A-26); managed `[shell.consent]` stripped under an unpinned source **and present under a pinned one**; direnv and mise yield (Decision 9), including `DIRENV_DIR` naming a *different* directory (no yield) and an `.envrc` present with direnv **not** active (no yield). Every one of these is decided before a prompt exists, so none of them needs one.
- **Degradation** — `set -u` shells; ledger absent, truncated, unknown envelope tag, and over cap ⇒ omitted; `unset __OCX_ENV_STATE` followed by a recompose (Decision 1's repair gesture — lists repaired, constants left in place, **`priors` gone**, confirmed through `ocx shell state`); **probe guard** — binary removed mid-session ⇒ silent no-op, and an older binary rejecting `--reconcile` ⇒ no output on either stream.
- **`ocx clean`** retains an `[env]`-only project's stamp and collects a stamp whose `project_dir` is gone.
- **The wrapper is unreachable from the activation stream** — no emitted snippet calls bare `ocx`. The grep on the emitted text is tier 1; the assertion kept here is that a shell with the wrapper *defined* still resolves the absolute path.
- **nushell exercises the static-data path instead**, because it has no `eval`: `--reconcile --format json` returns the `Plan` and the inlined nu body applies it (Decision 6). Same tier, different channel — and the `hide-env` spike (Decision 6b) is a tier-2 gate, not a tier-3 one. **Until that arm lands, both nu paths still call `--format json --global env`, so the nushell rows cover the global apply only** and the project-scope rows skip themselves off a probe that reads the shipped `env.nu` (Decision 6's status note).

### Tier 3 — a real pty

Only what genuinely needs a prompt. Everything above is already covered, so this tier stays **thin** and duplicates none of it — that is the point of the ladder, and it is what makes the red-and-green requirement below affordable.

- The hook **fires per prompt at all** — the failure class [nushell#14944](https://github.com/nushell/nushell/issues/14944) belongs to, where `env_change.PWD` silently did not fire on a lowercase `PWD`. No non-pty test can distinguish a hook that never ran from one that ran and decided nothing.
- **Enter and leave on `cd`**, and a **project switch** (revert A, apply B in one pass).
- **PATH does not grow across many prompts** — N prompts in one session, segment count constant.
- **Prompt-hook coexistence** — ocx's hook appended and never clobbering, under **starship**, **oh-my-zsh** and **powerlevel10k**, with `$?` preserved across it and **both** the Bash 5.1 array and string forms of `PROMPT_COMMAND`.
- **Same-command-line freshness** — `ocx update && tool` through the wrapper function, which by definition has no prompt in between and therefore cannot be tested one tier down.
- Reuse `_script_pty_command`; it already absorbs the util-linux/BSD `script(1)` split the elvish test hit.

### Matrix control

**All shells × a small core; one or two shells × full lifecycle depth.** The core is apply, retire, idempotency under double application, and cross-shell inheritance — four assertions across ten arms, cheap. Depth (global add/update/remove, branch switch, digest bump, subshell, the consent matrix) runs on **bash and pwsh** only: the two arms whose mechanisms differ most, and depth × breadth is exactly what makes a shell suite unmaintainable. This is the shipped file's own shape, not a new policy.

### Windows

**PowerShell 5.1, pwsh and cmd need a Windows runner leg** and cannot be covered from Linux. Specifically, **5.1 cannot be approximated by pwsh-on-Linux**: prompt-wrap semantics and the absent `LocationChangedEventArgs` exist only there, and `$env:PATH` versus `$env:Path` are the *same* variable on Windows and *different* variables on Linux/macOS ([PowerShell#3571](https://github.com/PowerShell/PowerShell/issues/3571)), so the platform-conditional casing arm the design requires is untestable off-platform. Tiers 1 and 2 run there unchanged; tier 3 is what needs the runner. `test_shell_activation.py` skips the whole module on `win32` today — that skip is that file's, not a precedent the new one inherits.

### Perf and parity

- **Perf** — no-op prompt benchmark asserting `exec_floor + Δ` per platform, with the floor measured in the same job (NFR Latency); red produced by a fault-injected extra `ConfigLoader` pass; shell-startup benchmark covering the new config read; a benchmark showing the shell-side short-circuit costs **zero execs** on the no-op path.
- **Parity** — emitted `export_path` output versus in-process `utility::path::move_to_front`, per arm; entry iteration order versus the emit path (shim-slot ordering).

### Red and green, and why the ladder makes it affordable

**Every check is demonstrated red as well as green** — a green that cannot be told from "never ran" is not a check, which is why Decision 2's global-tier sweep carve-out was *deleted* rather than tested. Red states are cheap at tiers 1 and 2, and that is the third reason tier 3 stays small. Fault-inject the **escaper** (route bash/zsh through `escape::fish_double_quoted` or `escape::nushell_plain_string` instead of `escape::posix_single_quoted` and watch the `'`-injection fixture red); fault-inject the **retirement rule** (make the list repair additive and watch the digest-duplicate assertion red); fault-inject the **empty-token filter** (keep empty tokens and watch `ghcr.io/evil/tool` start matching); fault-inject the **source derivation** (build the set from a re-derived physical address and watch the consent test fail). Prove the mutation actually landed before trusting the red — a harness that reports success unconditionally makes a no-op edit indistinguishable from a real one. The **nushell** work package stays gated on a red+green spike proving element removal *and* unset on a real nushell before any parity claim (`hide-env` scoping inside hook blocks is the known hazard, and the shipped nu integration is apply-only). A tier-3 wall-clock or prompt-firing check is the canonical passes-when-it-never-ran gate, so each one ships with its own named red state or does not ship.

## How Would We Reverse This?

Cheaply, at four levels — with two honesty corrections an earlier draft got wrong.

1. **Per user** — `[shell] hook = false`, or `OCX_NO_HOOK=1`, or `ocx self setup --no-hook`. Takes effect at the **next shell start**, and **nothing is reverted in the already-running shell**: Decision 5 decides hook presence once, at startup, so a running shell never observes the disable and keeps the env it applied until it exits. The earlier "the reconciler reverts what it applied on the way out" described a third shell that does not exist. That is an acceptable cost, but it is a cost, and it belongs here rather than in a surprised bug report.
2. **Per fleet** — publish `[shell] hook = false` in the managed payload (Decision 7).
3. **Flip the default** — one constant in `Hook::enabled`; reaches every new shell immediately (Decision 6 invariant), nushell one hop later.
4. **Remove entirely** — delete hook emission from `self activate`. `__OCX_ENV_STATE` evaporates with the sessions that hold it: no persisted format, no migration. `state/projects/` becomes inert data — note that once the sweep is removed with the feature, those stamps are orphans in a tree nothing walks, so removal deletes the directory once. The `[shell]` section degrades silently on any binary that no longer knows it (`ShellConfig` has no `deny_unknown_fields`; `ShellConsent` does, so a fleet still carrying `[shell.consent]` must un-publish it — see level 2). `ocx direnv export` / `direnv init` are untouched throughout and remain a complete fallback.

**Levels 1 and 2 are not independent.** Two of level 1's three levers (`[shell] hook = false`, `self setup --no-hook`) write a config key the managed tier merges *over* (Decision 7), so under a fleet policy only `OCX_NO_HOOK` survives as a per-user escape. Say so rather than presenting four orthogonal levels.

**Rollback across running shells is level 4's real cost**, and it is handled by Decision 5 layer 2's two rules: the emitted hook discards the reconcile call's stderr, ignores its exit status, and probe-guards the binary. Without those, a rollback to a pre-hook binary prints a clap usage error at every prompt in every open terminal. With them, the hook goes quiet.

The only genuinely one-way element is `package create` refusing reserved env keys in metadata — and that is a write-path narrowing whose read path stays permanently compatible.

## Open Questions

**None.** The three this ADR opened are decided by the owner and are recorded here as **decisions**, not recommendations — a recommendation left standing in an Open Questions section is an invitation to re-litigate it in review.

- **OQ-1 — whitelist shape: both grants ship.** `paths` is the **dominant, primary grant** — exact canonical directory, a list, the devcontainer/checkout case the owner stated. `namespaces` is **optional** and acts as an **auto-enabler for projects outside the path grants** — one `ScopeSpec`, the fleet case. They are independent and OR'd (Decision 4), and the **global toolchain is always trusted**: consent is **project-scope only**, because `$OCX_HOME/ocx.toml` is the user's own file. That is the same fact Decision 2 uses to delete the global-tier sweep carve-out, which is why no consent clause anywhere mentions the global scope. Neither grant removes the sibling-typosquat vector — `paths` avoids it by being exact-only, `namespaces` bounds it by enforcing a segment boundary at parse; the earlier claim that OCI namespaces are structurally immune is withdrawn as false on a public registry.
- **OQ-1a — strict AND mode considered, deliberately not shipped.** Requiring a project to be *both* path-consented **and** to have every lock source inside the allowed namespaces was evaluated and rejected on two independent grounds. It **breaks both use cases by construction**: the devcontainer publisher writing `paths` does not know the checkout's sources, and the fleet operator writing `namespaces` does not know the paths, so an AND leaves each of them unable to grant anything. And it fails **OD-3's own reasoning** (Decision 8): a control that fires on every legitimate change trains users to confirm without reading, which is a net security regression rather than a tightening. Recorded as a considered-and-cut product decision, not an open question and not a future default.
- **OQ-2 — default-on: yes.** The hook is **default-on for interactive shells, from the first release that carries it**. It reaches every existing user at their next shell start after `self update` with no opt-in step, which is the point: a default-off feature requiring a config edit is not adopted, and the consent model (Decision 4) makes it a **no-op for every project the user has not explicitly used ocx in**. The rejected alternative — default-off for one release, flip after field time — trades adoption for caution and costs a second breaking-subject commit. The blast radius is fleet-wide and the owner has taken it.
- **OQ-3 — PowerShell 5.1 is supported, via prompt-wrap.** Not "degraded" — that framing was overstated and is withdrawn. The missing `LocationChangedEventArgs` (PS 7+ only) affects exactly one case: a **programmatic `Set-Location` that never returns to a prompt**, i.e. the non-interactive scripting path this hook should not be serving in the first place. Interactively, a `cd` is always followed by a prompt, the wrapped `prompt` function fires, and fidelity is **full**. So 5.1 gets the same contract every other arm gets, and OCX keeps the 5.1 support its shim already ships (`$PSVersionTable.PSVersion.Major -ge 5` gates only completions) rather than recommending an upgrade the way mise does. What 5.1 *does* still need is its own Windows runner leg in the matrix (Validation → Windows), because prompt-wrap and the `LocationChangedEventArgs` difference exist only on Windows and cannot be approximated by pwsh-on-Linux.
