## 1. `ocx_schema` — schema generation and golden tests

**Schemas generated** (`crates/ocx_schema/src/lib.rs::schema_for`, seven kinds, one binary `ocx_schema`):

| Kind | Type | Published `$id` |
|---|---|---|
| `metadata` | `AuthoringMetadata` (authoring form, published-blob-compatible subset) | `https://ocx.sh/schemas/metadata/v1.json` |
| `config` | `Config` | `https://ocx.sh/schemas/config/v1.json` |
| `project` | `ProjectConfig` (`ocx.toml`) | `https://ocx.sh/schemas/project/v1.json` |
| `project-lock` | `ProjectLock` (`ocx.lock`) | `https://ocx.sh/schemas/project-lock/v3.json` (in lockstep with `LockVersion::V3`; carries a `$comment` flagging it machine-generated/do-not-hand-edit) |
| `patch` | `PatchDescriptor` (`ocx patch publish --descriptor`) | `https://ocx.sh/schemas/patch/v1.json` |
| `reports` | 55 `Printable` roots over one shared `$defs` bag (see §2) | `https://ocx.sh/schemas/reports/v1.json` (`REPORTS_ID` const) |
| `execution-record` | `ExecutionRecord` (pre-exec resolution record, ADR `adr_exec_resolution_record.md`) | `https://ocx.sh/schemas/execution-record/v1.json`, `schemaVersion` moves in lockstep with the URL |

**Golden tests** (`crates/ocx_schema/tests/golden_schemas.rs` + `tests/golden/*.json`): **exact byte-for-byte comparison**, not a diff/classification tool. `assert_matches_golden` regenerates via `ocx_schema::schema_for` in-process and fails on the first differing byte (with a 40-byte window printed both sides) if the generated bytes don't match the committed golden exactly — including `$defs` *key order* (schemars registers in type-discovery order, so moving a type between crates can reorder `$defs` with no field change). There is **no automated breaking-vs-additive classification** in this test; the doc comment states the convention that a golden may be regenerated **only** in a commit whose subject names the schema change (bisectability), but nothing enforces that convention mechanically beyond the byte-exact fail.

**How goldens are updated ("blessed")**: manually, by running
```sh
cargo run -p ocx_schema -- <kind> > crates/ocx_schema/tests/golden/<kind>.json
```
and committing under a subject that names the change — human-driven, no auto-approve/auto-bless tooling found.

**Correctness machinery beyond the golden**: `reports.rs`'s own unit tests (`every_printable_root_is_published`, `every_skip_serializing_if_field_carries_the_marker`, `the_two_option_shapes_are_published_differently`, `the_marker_never_reaches_the_published_document`, `manual_schema_names_are_unique_across_the_workspace`) source-scan `api::data` and the whole workspace to catch a printable type that silently didn't get a root, or an `Option`/`skip_serializing_if` field whose required/nullable rendering would lie to a parser (schemars renders "sometimes absent" and "always present, sometimes null" identically without the `x-ocx-absent-when-none` marker `normalize()` consumes).

**Publish path** (`website/schema.taskfile.yml`, task `schema:generate`): schemas are **not committed to the repo** — `website/src/public/schemas/{config,execution-record,metadata,patch,project,project-lock,reports}/` exists as empty dirs on disk today (git-ignored contents); the task runs Bazel target `//crates/ocx_schema:schemas`, verifies via `cquery --output=files` that exactly the 7 expected `<kind>/<version>.json` paths are produced, stages all 7, then renames atomically (all-or-nothing publish). Consumed by the website build; canonical published URLs are the `https://ocx.sh/schemas/...` `$id`s above.

## 2. `ocx_cli/src/api/data/*` — report-type coverage

- 45 files under `crates/ocx_cli/src/api/data/`.
- 42 of those files contain at least one `impl Printable for …`; 3 do not (`forge_report.rs`, `path_kind.rs`, `sweep.rs` — the latter's `Printable` impl is generic, `impl<R: Serialize> Printable for SweepReport<R>`, which the earlier grep for the literal string missed but `reports.rs`'s own test matches via `Printable for ` substring).
- **55 report roots** are published in `reports.json` today (`report_roots!` macro in `reports.rs`), including two instantiations of the generic `SweepReport<R>` (`SweepReport<SignatureReport>`, `SweepReport<AttestationReport>` — from `package sign`/`package attest`).
- Coverage is **test-enforced, not just documented**: `every_printable_root_is_published` (in `reports.rs`) source-scans every file under `api::data` for `impl … Printable for …` and fails the build if any printable type's name (or generic-base name) is absent from the published `reports` map. So today there is no command whose `--format json` stdout is *silently* uncovered — the enforcement mechanism is a compile-time-adjacent test, not a runtime guarantee.

## 3. Other machine-facing surfaces

- **Exit codes** (`crates/ocx_exit/src/exit_code.rs`): `ExitCode` enum, `#[repr(u8)]`, `#[non_exhaustive]`, sysexits.h-aligned (64 usage, 65 data, 69 unavailable, 74 I/O, 75 tempfail, 77 permission, 78 config) plus OCX-specific codes 79–84 (`NotFound`, `AuthError`, `PolicyBlocked`, `DirtyRcBlock`, `TransparencyLogUnavailable`/renamed from `RekorUnavailable`, `ReferrersUnsupported`). Classification is a free function walking the `anyhow` error chain (`ocx_cli`'s exit-code ladder), per `quality-rust-exit_codes.md` convention.
- **Structured JSON error envelope on stdout** (`crates/ocx_cli/src/error_envelope.rs`, ADR `adr_oci_referrers_signing_v1.md` §"C-S1-1", amended to cover **every** `--format json` command, not just sign/verify): frozen v1 shape — `schema_version`, `command`, `exit_code`, plus `error{kind,detail?,message,remediation? (reserved, never emitted),context}` on failure or `data` on success. `error.kind` is the serialized `ErrorCategory` enum (`crates/ocx_exit/src/error_category.rs`) — 14 variants, derived via an **exhaustive, wildcard-free** match from `ExitCode` (the compiler forces classification of every new exit code because `#[non_exhaustive]` only binds downstream crates, not the defining crate). Rendered on **stdout**, not stderr (confirmed both by `error_envelope.rs` doc comment and Phase-5 resolution R8: "parseable via `json.loads(result.stdout)`"). `error.detail`/`kind` values ("slugs") are a closed, frozen-per-major-version vocabulary — additive-only within v1, tracked in the ADR's `error_kind` inventory table, not in a generated schema file (the envelope shape itself is not one of the 7 `ocx_schema` kinds).
- **CLI grammar (clap)**: no generated OpenAPI-style usage spec or manpage generator found (no `clap_mangen` usage). Shell **completions do exist**: `ocx shell completion` (`crates/ocx_cli/src/command/shell_completion.rs`), driven by clap's own completion machinery — this is the one machine-consumable rendering of the argv grammar, but it targets shell completion, not a documented/versioned grammar artifact.
- **Env vars**: canonical reference is a **hand-written** Markdown doc, `website/src/docs/reference/environment.md` (1307 lines) — not generated from any schema or from the `ocx_config::env::keys` Rust source. No machine-readable env-var manifest found.
- **`ocx.toml`/`ocx.lock`/metadata schemas**: covered by the `project`, `project-lock`, and `metadata` kinds in §1 (same generation/golden/publish pipeline as `reports`).

## 4. Versioning / compatibility mechanisms

- Every schema kind carries an explicit `$id` version segment (`v1`/`v3` for project-lock only); **none has ever been bumped** in this repo's history except project-lock's pre-existing v3 (see §6 — `REPORTS_ID` has only ever been introduced, never incremented).
- `ENVELOPE_SCHEMA_VERSION = 1` (error envelope) — explicit doc comment states the freeze policy: additive fields/kind values do not bump; renames/removals do; a renamed slug bumps only if the **old** spelling ever shipped in a release (observed precedent: `rekor_unavailable` → `transparency_log_unavailable` did NOT bump because the old spelling never shipped).
- `LockVersion::V3` — `ocx.lock`'s own in-band version enum, `serde_repr`-style, rejects unknown versions.
- `deprecated.rs` / `RENAMED` (`crates/ocx_cli/src/command/deprecated.rs`): the CLI-surface (not wire-format) deprecation mechanism — old command spellings kept as hidden clap aliases, warn once on stderr, tracked in one `RENAMED: &[(&str, &str)]` table, swept by `test/lint/test_deprecated_spellings.py`. In flight per root `CLAUDE.md`: `ocx run`→`ocx exec`, `ocx package describe`→`ocx package description push`, `ocx package info`→`ocx package description pull`, `ocx package announce --package`→positional — all deprecated 0.6, removed 0.7.
- ADRs touching the output contract / JSON schema / SDK surface: `adr_oci_referrers_signing_v1.md` (defines the frozen error-envelope contract, C-S1-1 — later amended to cover all commands, not just sign/verify), `adr_exec_resolution_record.md` (execution-record schema + its in-band `schemaVersion`), `adr_index_claim_command.md` (touches `ClaimReport`, a reports root), `adr_real_sigstore_stack_and_delegation.md` (references C-S1-1's exhaustive-match discipline). `.claude/artifacts/phase5_contract_resolutions.md` is a plan-stage document (not an ADR) that resolved 8 concrete contract points (envelope `command` values, error-kind taxonomy, stdout-not-stderr emission, `SignatureReport` field naming) before Slice-1 implementation — useful as the paper trail for *why* the envelope looks the way it does.

## 5. Consumers

- **`ocx-sdk-python`** (`/home/mherwig/dev/ocx-sdk-python`, package `ocx_sdk`, PyPI dist not yet published): a CLI-wrapper SDK, explicitly **not** a schema-generated client. `src/ocx_sdk/_results.py` (3039 lines) states its own contract in its module doc: "Every `json.loads` in this SDK happens here. One command, one result struct, one hand-written parser — no serialization framework, and unknown keys are ignored." `_types.py` pins `TESTED_OCX_VERSION = "0.6.2"` and `MIN_SUPPORTED = "0.6.2"` — a **tested compatibility window**, not a schema-version pin; a compat gate raises below `MIN_SUPPORTED` and DEBUG-notes (never warns) above the tested window. Zero runtime dependencies (stdlib only), enforced by an import-walk test. Identifiers (`PackageRef`) are carried byte-for-byte, never parsed — "ocx owns the identifier grammar." Two bounded, contract-tested exceptions reimplement ocx logic client-side (the `[env]` merge algorithm and `registry_slug` canonicalization), each guarded by a fixture/diff test against the real CLI.
- **Rust-side subprocess wrapper**: no standalone `*sdk*`-named Rust crate was found anywhere under `/home/mherwig/dev` (see §"negative" below). What plays that role today is `ocx-mirror`'s own `crates/ocx_mirror_pipeline/src/ocx_cli/{push,sign,announce}.rs` — these spawn `tokio::process::Command::new(ocx_binary)` for `ocx package push --cascade --format json`, `ocx package sign …`, `ocx package announce …`, and hand-parse the JSON stdout into local structs (e.g. `PushReport` in `push.rs`, `#[derive(serde::Deserialize)]` with `#[serde(default)]` on every field so an older `ocx` binary that predates a field, or output containing only `{}`, still parses — a defensive-forward-compat pattern, not schema-pinned). This is genuinely a "shells out, doesn't link the CLI logic" boundary, but it is **not** a separate crate `ocx-mirror` depends on — it's inline in `ocx-mirror`'s own tree, alongside the same crate's *direct* linking of several ecosystem-tier `ocx_*` crates (see next point). Doc comments in this tree (`ocx_mirror_spec/src/dist.rs`) reference "`find_ocx` and the SDKs" as consumers of a separate `dist.json` release manifest (checksums/versions for install scripts), but no dedicated Rust SDK crate exists in any repo under `/home/mherwig/dev` today.
- **`ocx-mirror`'s direct linking**: `Cargo.toml` `[workspace.dependencies]` path-links `ocx_config`, `ocx_console`, `ocx_exit`, `ocx_index`, `ocx_oci`, `ocx_package`, `ocx_sign`, `ocx_util`, `ocx_python` from `external/ocx/crates/*` (the vendored submodule) — all ecosystem-tier crates per `ocx`'s stability table, consistent with `CLAUDE.md`'s "satellite linking rule" (`task satellite:verify` in `verify-deep.yml` asserts no internal-tier crate is ever resolved into this workspace). The workspace comment explicitly documents two crates that were **removed** from this list after being replaced by CLI-surface calls: `ocx_shell` (now reached via `ocx package push --ci-annotations`) and `ocx_announce` (forge vocabulary restated locally in `ocx_mirror_spec::forge`).
- **`ocx-mirror-sdk`** (`/home/mherwig/dev/ocx-mirror-sdk`): a separate, already-published Python package (`ocx_mirror_sdk` 0.3.0 wheel present) — but per its file layout (GraphQL/REST examples for GitHub/GitLab, a `url-index.v1.json` schema) it wraps the **mirror spec's URL-index format**, not the `ocx` CLI's report contract; out of scope for "binds to OCX's machine interface" beyond that it is a sibling SDK repo.

## leads:

- **Confirm the "Rust SDK" identity with the owner directly** — either it is informally `ocx-mirror`'s `ocx_cli/*` subprocess module (in which case the "does not link ocx" framing needs qualifying, since the *same* workspace also links 9 ecosystem-tier crates directly), or it is a crate that exists in a location not scanned here (e.g. a private/unpublished repo, or one not yet checked out locally).

- **No machine-readable env-var source of truth** — if an SDK or index tooling ever needs to validate `OCX_*` keys programmatically, `environment.md` cannot be parsed reliably; `ocx_config::env::keys` (Rust) is the actual source of truth today.
