In short: **only the wire-format struct definitions (`sigstore_protobuf_specs`) are consumed** — every actual network client, chain-walking, SCT check, and trust-root fetch is hand-written against those types, not against the crate's own clients/verifiers.

### `crates/ocx_lib/src/oci/verify/trust_root.rs` (520 lines) — confirmed via Bash cat -n (additional Section-1 findings, appended after §3 was already drafted — filed here rather than reordering the document)

- `TrustRoot::load_embedded` (lines 130-137) is a **hard stub**: `pub fn load_embedded() -> Result<Self, VerifyErrorKind> { Err(VerifyErrorKind::TrustRootUnavailable) }` — no embedded TUF root asset exists in the binary at all. Doc comment: "shipping a bundled TUF root is deferred to a future slice."
- `validate_der_certificate` (lines 51-106) is the structural TLV check MISSION.md refers to: hand-rolled, ~55 lines, checks only tag `0x30` (SEQUENCE), well-formed DER length encoding (short/`0x81`/`0x82` long form), non-zero content length, and `header_len + content_len == der.len()` exactly. **Its own doc comment explicitly names its successor**: "A future slice will replace this with `x509-parser` once `sigstore-rs` pulls it transitively; until then the strict equality + non-empty invariants are the load-bearing guarantees." This is a structural well-formedness gate only — it does not decode/validate any certificate *field* (no signature check, no validity-period check, no extension parsing). It runs on trust-root-loading paths only (`load_from_pem`, `load_trusted_root_json`), i.e. it validates the **trust anchors**, not the leaf/signing certificate — that's `identity.rs`'s job (below), which does real `x509_cert` parsing.
- `TrustRoot::load_from_pem` (139-180): parses all `CERTIFICATE` PEM blocks via the `pem` crate, runs each through `validate_der_certificate`, requires ≥1 valid block else `NoCertificateBlocks`. Sets `rekor_public_key_pem: None` (no key pinning — used by acceptance tests to inject the `fake_fulcio` self-signed root, per module doc).
- `TrustRoot::load_trusted_root_json` (194-270) is the `--tuf-root`/`OCX_SIGSTORE_TUF_ROOT` seam. Parses a Sigstore `TrustedRoot` JSON via **untyped `serde_json::Value`** (not a typed `sigstore_protobuf_specs::TrustedRoot` struct — confirms §2's "only wire-format structs are consumed, not for trust-root parsing" finding is even narrower than stated: trust-root JSON parsing doesn't use `sigstore_protobuf_specs` typed structs at all, just ad hoc `.get("certificateAuthorities")...` field walks). Extracts Fulcio CA certs from `certificateAuthorities[].certChain.certificates[].rawBytes` (base64 DER, each validated via `validate_der_certificate`) and the pinned Rekor public key from `tlogs[].publicKey.rawBytes`, base64-decoded then re-encoded to a `PUBLIC KEY` PEM block. Doc comment (203-205) is explicit: "does NOT perform any TUF network fetch or metadata-expiry verification — real TUF refresh is deferred." No signature over the TrustedRoot document itself is checked (no TUF root-of-trust chain, no expiry/`validFor` check) — a `--tuf-root` file is trusted purely because it was supplied locally.
- `TrustRoot::from_der_and_rekor` (182-192): reconstructs from the trust-root cache (§6/§8-adjacent `trust_cache` module) with no re-validation ("No validation beyond what the cache already round-tripped").
- `TrustRoot` struct itself (108-128): `der_certs: Vec<Vec<u8>>` + `rekor_public_key_pem: Option<String>`. An empty `der_certs` is a *valid* construction state ("no trust anchors loaded" — verify then rejects every chain).

### `crates/ocx_lib/src/oci/verify/identity.rs` (132 lines) — confirmed via Bash cat -n

- Uses **real `x509_cert` parsing**, not hand-rolled: `parse_certificate` (line 25-27) calls `x509_cert::Certificate::from_der`, mapping any failure to `CertChainInvalid`. This is a materially different, more thorough parse than trust_root.rs's structural TLV check — the leaf/signing certificate is fully ASN.1-decoded via the `x509-cert` crate (not hand-rolled), while the trust-root's own anchor certs get only the minimal TLV well-formedness check. This nuance matters for planning: replacing `validate_der_certificate` with `x509-parser`/`x509-cert` (as its own doc comment plans) is a smaller, more contained change than it might appear, since the harder real-X.509-parsing machinery is already proven in this file.
- `subject_identity` (33-42) extracts the cert's SAN (SubjectAltName, OID `2.5.29.17`), returning the first RFC822 (email) or URI general name — the two Fulcio issues for human/workload identities.
- `oidc_issuer` (48-56) extracts the Fulcio-proprietary OIDC-issuer OID extension `1.3.6.1.4.1.57264.1.1` (hardcoded const, `fulcio_oid_parses` test guards against typo), decoded as a DER UTF8String.
- `verify_policies` (67-86) is the ANY-of policy matcher: iterates `&[CompiledPolicy]`, cert passes if SAN+issuer satisfy **any one** policy (supports key/workflow rotation — old and new identities coexist). On failure, distinguishes `IssuerMismatch` (some policy's identity matched but issuer didn't) from `IdentityMismatch` (no identity matched at all) — preserves the original flag-mode error granularity even under multi-policy ANY-of matching. A cert with no usable SAN/issuer fails closed (garbage cert → `CertChainInvalid` from `parse_certificate`, or `IdentityMismatch` if it parses but SAN/issuer extraction yields `None`).

### `crates/ocx_lib/src/oci/endpoint.rs` (304 lines) — confirmed via Bash cat -n

- `sigstore_http_client()` (50-62): one process-wide `static CLIENT: OnceLock<reqwest::Client>`, `connect_timeout` 10s / `timeout` 30s (named consts `SIGSTORE_CONNECT_TIMEOUT`/`SIGSTORE_REQUEST_TIMEOUT`, lines 34/37). Two structurally separate SSRF surfaces in this codebase: (a) this one, closed; (b) the registry dial-site one, open (§1/§6).
- A known gap explicitly called out by its own test (`http_ipv4_mapped_ipv6_rejected`, line 232-239): `::ffff:127.0.0.1` (IPv4-mapped IPv6 loopback) is **deliberately rejected**, not accepted as loopback — the test comment notes the OS may route it to loopback but `std::net::Ipv6Addr::is_loopback()` returns `false` for it, and the code takes the conservative (reject) reading of that ambiguity rather than trying to special-case it.

### Both commands, shared mechanism

- Both `execute()` methods route through a `PackageManager` facade (`context.manager().sign_one(...)`/`verify_one(...)`) that assembles the pipeline (registry client, index, signer/trust material) and returns a `Result<_, PackageError>`; both then unwrap via a near-identical `{sign,verify}_error_into_anyhow` helper that re-roots the anyhow chain on the bare `SignError`/`VerifyError` node specifically so `error.context.identifier` survives — both crates carry a named regression test (`*_wrapped_in_package_error_still_populates_envelope_identifier`) guarding exactly this unwrap, with an identical rationale comment: `PackageError` omits `#[source]` on `kind`, and `Error::{Sign,Verify}` is `#[error(transparent)]`, so a naive `anyhow::Error::new(package_error)` would leave the envelope's chain-walk unable to downcast past the outer node.
- Both validate their own endpoint URL flags via the same `crate::oci::endpoint::validate_sigstore_url` function (see §1's `endpoint.rs` finding) before those URLs reach an HTTP client — this is a narrower, CLI-flag-scoped SSRF guard, distinct from the dial-site guard gap documented in §1/§6.
- Neither command's flag/env/exit-code contract has any test-only or `#[cfg(test)]`-gated variance — the CLI surface enumerated above is exactly what a production build exposes.

Confirmed via full Bash `cat -n` of `crates/ocx_lib/src/package_manager/tasks/auto_verify.rs` (236 lines, the actual hook module — MISSION.md's "`pull.rs` ~line 259" is the *call site*, not the implementation), `crates/ocx_lib/src/package_manager/tasks/pull.rs` (1469 lines, read via `sed`/`python3` line-scans), and `crates/ocx_cli/src/app/context.rs` (excerpt around line 459). Cross-checked call graph via `grep -rn` for `maybe_auto_verify`, `find_or_install`, `setup_impl`, `pull_local`.

### The hook module and its call site

- **`PackageManager::maybe_auto_verify`** (`auto_verify.rs:154-226`) is the entire implementation. Called from exactly one production site: `crates/ocx_lib/src/package_manager/tasks/pull.rs:259`, inside `setup_impl` (`pull.rs:201`) — `if let Err(kind) = mgr.maybe_auto_verify(pinned.as_identifier()).await { let shared = handle.fail(kind); return Err(...); }`. Confirmed no other call site exists in the tree (`grep -rn maybe_auto_verify` returns only the definition, this call, and one doc-comment reference in `package_manager.rs:359`).
- Runs **after manifest resolution (digest known) but before any layer download** — the module doc states this precisely: "a fail-closed abort leaves no package-store or symlink state" — only the benign, inert tag→digest pointer and manifest blobs that `resolve` already committed via write-through survive a failed covered install.
- Runs **leader-only** under the singleflight group: the auto-verify call sits after `groups.packages.try_acquire(...)` resolves to `Acquisition::Leader(handle)` (confirmed at `pull.rs:220-259` — a `Resolved` waiter returns early at line ~244, before reaching the auto-verify call). Singleflight key is the resolved digest, so concurrent diamond-dependency waiters on the same digest share one verification, not N.

### Call chain from every install surface — confirmed by tracing, not assumed

`setup_impl` is reached by exactly **two** call paths in the whole tree (`grep -rn "setup_impl("` → one call site, `pull.rs:190`, inside `setup_with_tracker`):

1. **`PackageManager::pull`** (`pull.rs:117-123`, single package) → `setup_with_tracker` (line 182-191) → `setup_impl`.
2. **`PackageManager::pull_all`** (`pull.rs:139-...`, batch) → same `setup_with_tracker` per package inside its `JoinSet` fan-out (confirmed at lines ~160-176) → `setup_impl`.

Both converge on the identical `setup_impl` choke point — there is no separate code path for batch vs. single-package pulls that could diverge on the verify gate.

`pull`/`pull_all` are themselves reached only via **`PackageManager::find_or_install`** (`find_or_install.rs:24-41`, private, single `self.pull(package, platform).await` call at line 39) and its batch sibling **`find_or_install_all`** (`find_or_install.rs:52-91`, public). | Caller | File | Purpose |
|---|---|---|

### The one confirmed bypass: `pull_local`

`PackageManager::pull_local` (`package_manager/tasks/pull_local.rs`) calls `setup_owned` **directly**, per `pull.rs`'s own doc comment on `setup_impl`'s `dest_override` parameter (lines ~196-198): "only `pull_local` supplies a value here (via `setup_owned` directly, **bypassing this function's singleflight gate**)" — and therefore bypassing `setup_impl`, and therefore bypassing `maybe_auto_verify` entirely. `pull_local` is consumed by `ocx package test --script` (`ocx_cli/command/package_test.rs`) and `patch_test.rs` — a **locally-built/locally-sourced** package under test, not a registry-fetched signed artifact, so this bypass is a scoped, load-bearing design choice (there is nothing to verify a signature *of* — a local test build has no Sigstore bundle) rather than an accidental gap in the install-surface coverage claim above. Flagging it here explicitly since the mission brief asked for exhaustive install-surface enumeration; this is the one documented exception, and it is documented as deliberate at the source (not merely absent).

### The gate itself (`maybe_auto_verify` body, `auto_verify.rs:154-226`)

Five-branch gate, matching the module doc's own numbered list exactly:

1. `self.auto_verify()` returns `None` (no `[[trust.policy]]` configured anywhere) → `Ok(())`, no-op. Checked first, before any policy resolution work.
2. `trust::resolve_tiered(operator_policies, project_policies, target)` — cross-tier ANY-of policy resolution (operator `config.toml` authoritative, project `ocx.toml` fills ungoverned scopes) using the **same** `resolve_tiered` function `package_verify.rs::resolve_policies` calls (§3) — CLI verify and auto-verify share one policy-resolution codepath, cannot silently diverge. A malformed matched policy → `TrustPolicyInvalid` → exit 78 (same taxonomy as §3's verify error table).
3. Empty resolved policy set (`policies.is_empty()`) → `crate::log::info!` ("no trust policy covers '{target}'...") and `Ok(())` — install proceeds. This is the documented **opt-in trust model**: an uncovered package installs silently (at info level) with no verification attempted at all.
4. Covered but `auto_verify.user_opted_out` (resolved `--verify`/`--no-verify` flag over `OCX_NO_VERIFY` env, flag wins — same `SignatureVerify::resolve` precedence rule as §3's `options/verify.rs` finding) → `crate::log::warn!` **exactly once per invocation** (`AtomicBool` latch `warned`, `swap(true, Ordering::Relaxed)`, shared across a whole batch install so N covered-but-opted-out packages log one warning, not N) → `Ok(())`, install proceeds.
5. Covered, not opted out → lazily resolve the trust root (memoized via `Arc<OnceCell<TrustRoot>>` — **only computed the first time a covered package is actually seen**, so an all-uncovered batch never touches the offline/trust-root machinery at all) → call `self.verify_one(resolved, &oci::Platform::any(), options)` (the **same** `verify_one` facade method `package_verify.rs` calls, §3) → any error is unwrapped to its bare `PackageErrorKind`/exit code and propagated fail-closed via `handle.fail(kind)` in the `pull.rs` call site, aborting before any layer download.

**Trust-root memoization detail not in the mission brief**: when the resolved policy's trust root is a bare Fulcio-CA PEM (`--trust-root`/`OCX_SIGSTORE_TRUST_ROOT`, no pinned Rekor key) and the manager is online, `auto_verify.rs:201-206` performs a **one-time** TOFU fetch of the Rekor public key via `crate::oci::verify::pipeline::fetch_rekor_public_key_pem`, then re-wraps it into a new `TrustRoot::from_der_and_rekor(...)` that gets memoized — so a batch of N covered packages against the same policy TOFU-fetches the Rekor key exactly once, not N times. This function name (`fetch_rekor_public_key_pem`) confirms `verify/pipeline.rs` exposes at least one function used cross-module by the auto-verify hook, not only internally by `VerifyPipeline::run` — worth noting for §6/§8 dependency-surface mapping.

**`Platform::any()` note**: verification runs against `oci::Platform::any()`, not the platform the package was resolved for — doc comment explains `resolved` is already `ResolvedChain.pinned`, the platform-selected leaf digest, so re-selecting with the concrete platform would strict-equality-fail against the leaf manifest's own advertised `any()` platform tag. This is a deliberate implementation detail, not a verification-scope weakening (the leaf digest being verified is already platform-concrete; only the *lookup* uses the wildcard).

### Config wiring — `Context::try_init` (`crates/ocx_cli/src/app/context.rs`, ~line 455-475)

- `AutoVerify` is attached to the shared `PackageManager` **exactly once**, at CLI-composition time, not per-command — comment at lines 456-459 states this explicitly: "Attach policy-gated auto-verify ONCE on the shared manager so EVERY install surface inherits it fail-closed... `install`/`pull` refine the opt-out from their `--verify`/`--no-verify` flag via `conventions::manager_with_verify_flag`" (defined in `crates/ocx_cli/src/conventions.rs:461`, not independently opened this pass — flagging **UNCONFIRMED at the source level** for that function's own body, though its existence and call sites in `package_pull.rs`/`install.rs`/`context.rs` are confirmed via grep).
- `operator_policies = config.trust_policies().to_vec()` — **only** operator-tier (`config.toml`) policies are captured at this point; auto-verify has no access to project-tier (`ocx.toml`) policies at construction (the `AutoVerify.project_policies` field exists on the struct but a full trace of what populates it beyond `config.toml` was not completed in this pass — the struct comment says "empty for OCI-tier install/pull," implying it is deliberately left empty here, distinct from `package_verify.rs`'s CLI verify command which does read project `ocx.toml` trust policies per §3).
- **Perf-motivated laziness, confirmed by comment** (lines 465-467): `auto_verify` is built as `None` when `operator_policies.is_empty()`, specifically to avoid forcing the lazy registry-client cell (`registry_client_cell`) to materialize — "an empty `operator_policies` must not pay the ~7ms TLS-store build cost `build_auto_verify` would otherwise trigger by taking `&oci::Client`." This means a build with zero trust policies configured pays zero cost for the auto-verify machinery at all, at every single command invocation, not just an amortized no-op check.
- `no_verify_env = env::flag(env::keys::OCX_NO_VERIFY, false)` resolved once here; both the auto-verify config and the CLI's own `--verify`/`--no-verify` flag refinement (`conventions::manager_with_verify_flag`) read this single resolved value — consistent with the flag-over-env precedence pattern seen throughout §3.

### `fake_sigstore.py` (`test/tests/fixtures/fake_sigstore.py`, 909 lines, fully read)

Pure-Python, no Docker. Three real HTTP servers (`http.server.HTTPServer`) on daemon threads, each bound to `127.0.0.1` on an OS-assigned free port (`_find_free_port`), **plain HTTP only — no TLS**:

- **`FakeOidcIssuer`** — mints ES256 JWTs. Fixed claims: `sub=test-signer@example.com`, `iss=https://fake-oidc.test`, `aud=sigstore`, 10-minute expiry. Serves `GET /.well-known/openid-configuration` and `GET /.well-known/jwks.json` so the sign pipeline's OIDC discovery step (§1, `fulcio.rs`) has something real to fetch.
- **`FakeFulcio`** — handles `POST /api/v2/signingCert`. Verifies the presented OIDC JWT against the fake issuer's JWKS, then mints a P-256 leaf certificate: SAN = the token's email, and the extension at the real Fulcio issuer OID `1.3.6.1.4.1.57264.1.1` (`_FULCIO_ISSUER_OID`, line ~731) is set from the token's `iss` claim. 10-minute cert validity. Returns a Fulcio v2 JSON response whose `certChain` is **self-signed by the fake's own CA with no intermediate** (`_FulcioCaMaterial._build_ca_cert`/`mint_leaf_cert`) — this is the fixture-side reason `verify_cert_chain` (`verify/pipeline.rs:441-468`, §1) only ever needs to check the leaf directly against a one-entry trust-root cert set: the fake never produces a leaf→intermediate→root chain for it to walk, so the hand-rolled single-hop verifier has never been exercised against a multi-hop chain in this repo's own test suite. Control method: `set_invalid_chain(bool)` — makes the next-minted cert chain fail validation, used by exactly one test (below).
- **`FakeRekor`** — handles `POST /api/v1/log/entries` with a `hashedrekord:0.0.1` proposal; builds a canonical payload and signs it with a fake Ed25519 key (`_RekorKeyMaterial.sign`) to produce a SET. This payload format is the fixture-side counterpart of `rekor.rs`'s custom `ocx-rekor-set-v1` payload (§1) — the two are co-designed and symmetric with each other, **not** with a real Rekor's SET wire format (real Rekor SETs are signed over a different canonicalized payload by a service-held key registered in the public Sigstore trust root, not a per-test-run ephemeral key). Also serves `GET /api/v1/log/publicKey`. Control methods: `set_tampered_set(bool)` (flips a bit in the SET after signing, so the bundle is self-consistent-looking but the signature is wrong) and `set_failure_mode(HttpStatus)` (makes the next request return an arbitrary HTTP status, e.g. 503 — used to simulate "Rekor unavailable").
- **`FakeSigstoreStack`** — composite owning all three servers plus a shared `_control` dict the two `set_*` methods mutate; exposes `fulcio_url`/`rekor_url`/`oidc_url`, `oidc_token()`/`foreign_oidc_token()` (a JWT with correct claims but signed by a key absent from the fake issuer's JWKS — models a wrong-key/foreign-issuer token, expected to produce `OidcTokenRejected`/exit 80), `trust_root_pem_path()` (fake Fulcio CA PEM, for `TrustRoot::load_from_pem`), `rekor_public_key_pem_path()`, and `trusted_root_json_path()` — writes a minimal `application/vnd.dev.sigstore.trustedroot+json;version=0.1` document carrying the fake CA cert and fake Rekor public key in exactly the shape `TrustRoot::load_trusted_root_json` (§1, `trust_root.rs:213-270`) parses via untyped `serde_json::Value`. This is the fixture that stands in for `--tuf-root`/`OCX_SIGSTORE_TUF_ROOT` in every offline/pinned-trust-root test — it is a **static, locally-written file**, matching §1's finding that this flag is a local pin, not a live TUF client.

### What breaks if `fake_sigstore.py` is replaced with a real Fulcio + Rekor

Three concrete, evidenced breakages, cross-referenced against §1's hand-rolled-crypto findings:

1. **Single-hop `verify_cert_chain` would start failing on legitimate signatures.** `verify/pipeline.rs:441-468` (§1) checks the leaf certificate directly against the trust-root DER cert set — it never parses or walks an intermediate. A real Fulcio issues leaf certs signed by an **intermediate** CA, itself signed by Fulcio's root — a 2+ hop chain. The fake's `_FulcioCaMaterial` signs the leaf directly with its "CA" key and returns a single-entry `certChain`, so the existing single-hop verifier has never had to handle an intermediate in this test suite. Against a real Fulcio, `test_sign_then_verify_happy_path` and every other currently-passing sign+verify round-trip would need `verify_cert_chain` to actually walk the chain, which it does not do today.
2. **The custom `ocx-rekor-set-v1` SET format would not validate against a real Rekor's SET.** `rekor.rs`'s `set_signing_payload` (§1) constructs a bespoke canonical payload and expects a signature over exactly that payload; `FakeRekor`'s `_RekorKeyMaterial.sign` is written to sign the identical bespoke payload, so the two are symmetric by construction. A real Rekor computes its SET over the RFC 6962-style Merkle-log-entry structure per the actual Rekor API, not this bespoke format — so `verify_rekor_set` would reject every real-Rekor response as `RekorSetInvalid` (the same exit-65 path `test_verify_detects_tampered_rekor_set` currently exercises deliberately).
3. **The failure-injection surface (`set_invalid_chain`, `set_tampered_set`, `set_failure_mode`) has no real-service equivalent.** These three control methods let a test deterministically force a bad chain, a bad SET, or an arbitrary HTTP status from Rekor on demand — 12 test call sites across `test_verify.py`, `test_sign.py`, `test_auto_verify.py`, `test_offline_verify.py` (table above) rely on this to hit their negative-path exit codes (65, 77, 78, 79, 80, 83, 84) deterministically and instantly. A real Fulcio/Rekor cannot be told "return a broken chain on the next request" or "go down for exactly one call" — those tests would need to be rewritten around network-level fault injection (e.g. a proxy) or dropped, and would become flaky/slow (real network round-trips) where they are currently fast, deterministic, in-process HTTP calls.

Additionally, since no Merkle inclusion proof is ever populated on the sign side (`bundle.rs:66`, §1) or checked on the verify side, a real Rekor's actual log-inclusion behavior (returning a real proof, requiring the client to verify it against a real signed checkpoint) is entirely unexercised by this suite regardless of which Rekor backs it — that gap is orthogonal to the fake-vs-real question and would persist even if Fulcio/Rekor were swapped for the real services, since neither side of the pipeline currently does anything with an inclusion proof.

## 6. SSRF guard

### The guard mechanism itself (`crates/ocx_lib/src/oci/ssrf.rs`, 467 lines, fully read)

Module doc (lines 4-30) states the design directly: an index root's `repository` pointer is remote-controlled data, so before OCX dereferences it into a physical fetch the resolved host must not land in a forbidden range. Two layers, both confirmed by reading their bodies:

1. **`is_forbidden_ip(ip: IpAddr) -> bool`** (lines 81-143) — the range table: IPv4 loopback/private/link-local (incl. `169.254.169.254` cloud metadata)/unspecified/CGNAT-shared (`100.64.0.0/10`, hand-rolled since `Ipv4Addr::is_shared` is unstable)/broadcast/multicast/documentation/benchmarking (`198.18.0.0/15`)/reserved (`240.0.0.0/4`); IPv6 loopback/ULA (`fc00::/7`)/link-local/unspecified/multicast/documentation (`2001:db8::/32`). An IPv4-mapped IPv6 address (`::ffff:a.b.c.d`) is unwrapped and judged as its embedded IPv4 (`is_forbidden_v6`, lines 122-135) so the mapping cannot smuggle a forbidden target past the check — this exact case has a unit test (`is_forbidden_ip_unwraps_ipv4_mapped_ipv6`, line 336).
2. **`resolve_and_validate(host, port, trusted) -> Result<Vec<SocketAddr>, SsrfError>`** (lines 234-256) — the pre-flight: resolves via `tokio::net::lookup_host`, then (unless `host_is_trusted`) rejects if any resolved address is forbidden.
3. **`GuardedResolver`** (lines 262-285) — a `reqwest::dns::Resolve` hook that re-runs `resolve_and_validate` at actual connect time, injected into a client via "the vendored `oci_client` fork's `ClientConfig::dns_resolver` seam" (doc comment, line 261). This is the mechanism that closes the resolve→connect DNS-rebinding window **for whichever client it is wired into**.
4. **`host_is_trusted`** (lines 148-159) — exact string match or CIDR membership (`parse_cidr`/`cidr_contains`, hand-rolled `/N` prefix masking) against a per-namespace `trusted_hosts` list — the documented escape hatch for a private registry.

`SsrfError` has exactly two variants (lines 40-54): `ForbiddenTarget` → `ExitCode::ConfigError` (78) — "the fix is a `trusted_hosts` config entry" — and `Resolution` → `ExitCode::Unavailable` (69). Both confirmed via the file's own `ClassifyExitCode` impl and its pinning tests (lines 450-467).

This module defines the *mechanism* only. It has no opinion on which client or call site uses it — that is decided per-caller, which is exactly where the gap in §1's suspicion lives.

### Two structurally distinct guard call sites, now confirmed from their own definitions

**`Index::guard_physical_dial`** (`crates/ocx_lib/src/oci/index.rs:378-388`, doc comment lines 344-377, fully read) — the **dial-time** guard. Doc comment states its own rationale precisely: `physical_reference` (the resolve-time lookup) "must tolerate a lookup failure" because it runs on *every* resolve, warm or cold, including ones that never fetch — so an attacker-controlled domain "only has to answer NXDOMAIN while the pre-flight asks and a loopback address when the pull dials." `guard_physical_dial` exists specifically to close that gap: it "fails closed on everything, a lookup failure included," because by the time it runs, a dial is actually imminent. Implementation (lines 378-388) is a thin wrapper: skip if `physical.registry() == logical.registry()` (non-rewrite carve-out), else `split_host_port` + `resolve_and_validate` against the *logical* registry's `trusted_hosts`.

**`ChainedIndex::guard_local_physical`** (`crates/ocx_lib/src/oci/index/chained_index.rs:397-412`, fully read) — the **resolve-time** guard, called from `local_physical_answer` on every local-index physical-pointer read. Its `match` on `resolve_and_validate`'s result (lines 401-411) is the tolerance the dial-time guard's doc comment describes: a `ForbiddenTarget` still propagates as an error, but a `Resolution` failure on a plain DNS name (`is_plain_dns_name`) is logged at `debug` and treated as `Ok(())` — "proceeding — a connection cannot succeed where the lookup failed."

The two are genuinely different functions with genuinely different fail-open/fail-closed behavior on one input class (unresolvable DNS name), and this asymmetry is confirmed — not just claimed in a comment — by `index.rs`'s own test module (lines 1531-1650, fully read): `guard_physical_dial_fails_closed_where_the_resolve_time_guard_tolerates` explicitly proves both halves against the same `physical.invalid` fixture, asserting `guard_local_physical`'s underlying call tolerates it (via a direct `resolve_and_validate` assertion) while `guard_physical_dial` refuses it.

### Every production call site, confirmed by grepping the actual `.guard_physical_dial(` invocation (not doc mentions)

There is **exactly one** production call site of `guard_physical_dial` in the entire tree: `crates/ocx_lib/src/package_manager/tasks/pull.rs:903`, inside `extract_layer_inner`'s layer-blob-fetch path (the JoinSet fan-out `pull_all`/`pull` ultimately drives per §4). The surrounding comment (lines 895-902, read in full) states the reasoning directly: "The layer is genuinely absent, so a request to the PHYSICAL location is imminent — and `client` carries no SSRF resolver of its own. This is the one point where a target the index rewrote is validated before anything dials it." The call is memoized via a `dial_guard.get_or_init(...)` cell so it runs once per pull, not once per layer.

Four other matches for `guard_physical_dial` in the codebase are all doc-comment cross-references, not calls: `chained_index.rs:385,1317,1440` and `index.rs:349,635` (`Self::guard_physical_dial` / `Index::guard_physical_dial` named in prose explaining the split between the two guards). `guard_local_physical` itself has no other callers than `local_physical_answer` (chained_index.rs:441).

### Which sign/verify transport calls bypass the dial-time guard — confirmed from the pipelines' own source, not from comments citing comments

Both `sign/pipeline.rs` and `verify/pipeline.rs` call `ctx.index.physical_reference(&resolved)` to get the physical target, then transport off that value directly — **neither ever calls `guard_physical_dial`** (`grep -c "guard_physical_dial"` on both files returns `0`). Each carries its own explicit comment at the exact point this matters:

- `sign/pipeline.rs:113-117` (fully read, immediately before the `physical_reference` call): "The SSRF floor on the returned host is enforced upstream in the shared index choke point (`ChainedIndex::guard_local_physical`), never re-checked here."
- `verify/pipeline.rs:145-151` (fully read, same position): "The SSRF floor on the returned host is enforced upstream in the shared index choke point (`ChainedIndex::guard_local_physical`)."

Both comments are literally true of `guard_local_physical` alone — that guard *does* run, once, when `ctx.index.physical_reference` resolves the pointer (it is `physical_reference`'s own internal SSRF check). What neither pipeline does is what `pull.rs:903` does: a **second, dial-time** re-validation via `guard_physical_dial` immediately before the transport call that actually dials the physical host. Concretely, every one of the following transport calls in both pipelines runs against `client.transport_reference(&physical)`/`client.transport_write_reference(&physical)` with only the resolve-time guard behind it:

- **Sign** (`sign/pipeline.rs`): `transport.pull_manifest_raw(&subject_ref, ...)` (line 138, subject-manifest fetch), `transport.push_blob(...)` (lines 183 and 192, bundle + descriptor blobs), `transport.push_referrer_manifest(...)` (line 212).
- **Verify** (`verify/pipeline.rs`): `Self::list_signature_referrers(transport, &ctx, &image, ...)` (line 176, which itself lists referrers against `image`), and `transport.pull_manifest_raw(referrer_ref, ...)` (line 586, per-referrer bundle fetch).

Practical consequence, following directly from `guard_physical_dial`'s own doc comment (§6, above): if a local index root's physical pointer for a package names a plain DNS host that is unresolvable at the moment `physical_reference` runs (e.g. transient NXDOMAIN, or a name whose resolution the attacker controls and delays), `guard_local_physical` tolerates that and returns the pointer anyway. `pull.rs`'s blob-fetch path re-validates that pointer at the moment it actually dials and would refuse a now-resolving-to-loopback answer; sign and verify's transport calls have no equivalent second check and would proceed to dial whatever the (by-then-resolved) physical host turns out to be. This is the identical TOCTOU shape the `guard_physical_dial` doc comment names as the reason it exists for the pull path — sign and verify are simply the two pipelines that do not have that second check wired in.

**Resolved — the gap is live, not defense-in-depth-only.** `oci::ClientBuilder` has an opt-in `.ssrf_guard(trusted_hosts)` method (`crates/ocx_lib/src/oci/client/builder.rs:199-210`, fully read) that wires a `GuardedResolver` into `ClientConfig::dns_resolver`. `grep -rn '\.ssrf_guard(' crates/` finds exactly **two** call sites in the whole tree, both in `crates/ocx_cli/src/app/context.rs`: `package_announce.rs:218` (a one-off client for the `ocx package announce` command) and `context.rs:805` inside `build_index_sources` (lines 760-815, read in full) — and that second one is explicitly scoped, by its own comment, to "the physical-fetch client of an index **source**" (i.e. `index::OcxIndex`'s metadata-fetch client), never the package/blob-transport client.

The shared client sign, verify, pull and auto-verify all actually transport package bytes over — `Context::registry_client_cell`, built by `build_registry_client` (`context.rs:956-968`, fully read; its own doc comment states it backs "the online `remote_client`/`oci_index` pair, and policy-gated auto-verify") — is built with `.plain_http_registries(...)`, `.mirrors(...)`, `.progress(...)` and **no `.ssrf_guard(...)` call at all**. This is the same shared client `pull.rs`'s own comment at the `guard_physical_dial` call site describes as carrying "no SSRF resolver of its own" (§6, above) — sign and verify obtain their `oci::Client` from the identical construction path, so the same statement applies to them without qualification. The gap therefore has no second line of defense: sign and verify's transport calls (`pull_manifest_raw`, `push_blob`, `push_referrer_manifest`, `list_signature_referrers`) run against a client with neither a dial-time `guard_physical_dial` re-check nor a connect-time `GuardedResolver` — only the resolve-time, DNS-failure-tolerant `guard_local_physical` stands between an index root's physical pointer and the socket sign/verify actually opens.

### Why `sigstore-rs`'s own network clients are unused — the authoritative in-tree rationale (confirms §1/§2 from a different source)

`Cargo.toml:95-99` (read in full) carries this comment directly above the `reqwest` dependency declaration: "Plain-HTTPS client for the static-file index.ocx.sh source ... and for the hand-rolled Fulcio/Rekor calls (**sigstore's own clients require an SCT + a different wire shape than the offline fake stack**)." This is the first-party, dated (issue #194) explanation for exactly the finding §1 derived independently from reading `signer.rs`/`fulcio.rs`/`rekor.rs`/`oidc_browser.rs`: it is not that sigstore-rs's clients are missing or unwired, but that they hard-require a Certificate Transparency SCT the fake Fulcio stack cannot produce, so OCX reuses only sigstore's lower-level types and hand-rolls the transport.

This is corroborated in more detail by `.claude/artifacts/research_sigstore_rs_spike.md` (dated 2026-07-09, "issue #194, Step 0" — an empirical probe of `sigstore` 0.14.0 against the real vendored crate source, fully read for its verdicts table). Its "Keyless sign (Fulcio)" verdict states plainly: `SigningSession::sign` → `sign_digest` "**mandatorily calls `verify_sct()`** against a CT-log keyring. The fake Fulcio embeds no SCT and there is no CT log → `SigningSession` rejects the fake cert. **We hand-roll the sign flow** reusing the lower-level `FulcioClient::request_cert_v2` (no SCT check at that layer) + `p256`/`x509-cert`." It also notes `SigningArtifact::to_bundle()` — sigstore-rs's own bundle builder — emits **v0.2**, not v0.3, which is a second, independent reason `bundle.rs` builds the `Bundle` struct by hand (§1) rather than calling into sigstore-rs for that step too.

### `deny.toml` — the RSA/openidconnect finding, and what it implies for a future TUF client crate

`deny.toml:14-20` (read in full) carries a documented, machine-checkable advisory ignore: `RUSTSEC-2023-0071` (the "Marvin" RSA timing-sidechannel advisory against the `rsa` crate) is ignored because `rsa` "is pulled transitively via `sigstore` → `openidconnect` for OIDC JWT (RS256) public-key verification. OCX signs and verifies with ECDSA P-256 only (`adr_oci_referrers_signing_v1.md` S1-A) and holds no RSA private key; the attack targets RSA private-key decryption timing, not the public verify path OCX exercises." Confirmed both `openidconnect` (`Cargo.lock:3779`) and `rsa` (`Cargo.lock:4512`) are in fact present in the resolved graph today, at the *current*, narrow `["bundle", "rustls-tls"]` feature selection — the spike doc's own note that "`openidconnect` is a NON-optional dep of sigstore (every feature pulls it)" is independently confirmed by `sigstore`'s own `Cargo.lock` dependency list (read in full, line ~3760 onward), which lists `openidconnect` unconditionally alongside `oci-client`, `p256`, `x509-cert`, `sigstore_protobuf_specs`, `webbrowser`, etc.

**Directly answering the TUF-client question**: `tough` — a real, general-purpose Rust TUF client crate — is **already sigstore-rs's own TUF dependency**, per the spike doc's version-facts table ("Transitively provides the crypto we need: ... `tough 0.22` (TUF), `openidconnect 4.0.1`"). It is confirmed **absent** from the current `Cargo.lock` (`grep -n '^name = "tough"' Cargo.lock` returns nothing) — meaning it sits behind a `sigstore` feature the workspace does not currently enable (the spike's probe used a broader feature list, `["sign","verify","bundle","fulcio","rekor","sigstore-trust-root","rustls-tls"]`, versus the shipped `["bundle", "rustls-tls"]`; `sigstore-trust-root` is the most likely gate on `tough`, though this pass did not open sigstore's own `Cargo.toml` to confirm the exact feature-to-dependency mapping — **UNCONFIRMED** at that level of detail). The practical implication for a future "wire up a real TUF-distributed trust root" slice (§7's `#deferred-future-work` item): it would very plausibly **not** require adding a new direct dependency or a `cargo deny` bans-list decision from scratch — it would mean turning on an already-vetted, already-in-the-dependency-tree `sigstore` feature (bringing `tough` and its own transitive tree into the lockfile for the first time), which would need a fresh `cargo deny check` pass (license + advisory) specifically for `tough`'s subtree, since nothing in the current `deny.toml` ignore list currently covers it — it has never been resolved, so it has never been checked.
