**Reviewer:** researcher (sonnet)

## Verdict

## Findings

### F-01 · Warn · Push-option value sanitization stops at control characters; the disclosed 2026 real-world RCE for this exact mechanism was a printable-character delimiter, not a control character
**Where:** C-039 (`WriteTransport::Git` push), edge-case hunt "Input" row, WP-8
**What the state of the art does:** CVE-2026-3854 (CVSS 8.7, disclosed by Wiz, patched in GitHub Enterprise Server 3.14.25/3.15.20/3.16.16/3.17.13/3.18.8/3.19.4/3.20.0) is a live, dated 2026 demonstration that this exact mechanism — a user-supplied `git push -o` value copied into an internal service's field — is a real RCE surface. GitHub's `babeld` proxy copied push-option values verbatim into a semicolon-delimited internal `X-Stat` header; a semicolon in the value (an ordinary printable character, not a control character) broke out of its field and injected new attacker-controlled fields (`rails_env`, `custom_hooks_dir`, `repo_pre_receive_hooks`), reachable with nothing more than a normal `git push -o '<value>'` from a standard client. Sources: [Wiz Blog, "GitHub RCE Vulnerability: CVE-2026-3854 Breakdown"](https://www.wiz.io/blog/github-rce-vulnerability-cve-2026-3854); [The Hacker News, April 2026](https://thehackernews.com/2026/04/researchers-discover-critical-github.html); [SOCRadar](https://socradar.io/blog/cve-2026-3854-githubs-git-push-pipeline/).
**What the plan does:** C-039: "Every rendered option value is rejected if it contains a newline, a NUL or any other control character, before it reaches the pkt-line."
**Fix:** Add one line to WP-8's mandatory edge-case hunt ("Input" row): a push-option value containing a structural/record-delimiter character the *receiving forge's own internal pipeline* might use (semicolon at minimum, since that is the disclosed exploited character) must be asserted to arrive at the merge request as literal, unsplit title/description text — not just "not a control character." This is cheap (one more fixture assertion in WP-14) and turns an untested assumption into a proven one, citing CVE-2026-3854 as the reason the class of bug is not hypothetical. Note: I could not establish that GitLab's own push-option pipeline (`PushOptionsHandlerService`) uses a similarly delimiter-fragile internal format — the already-persisted `research_plan_index_claim_gitlab_verification.md` describes it working through structured Ruby service objects, not a flat string — so this is precautionary, not a confirmed GitLab vulnerability.

### F-02 · Suggest · The CI-environment owner-confirmation fallback trusts exactly the identity signal the packaging ecosystem has been retiring
**Where:** C-048 "who confirms" ladder, unreachable-users-API branch; cross-referenced by the plan's own WP-16 "actor_id governance" row
**What the state of the art does:** crates.io (2025) and PyPI Trusted Publishing both moved first-publish/publish-authorization away from any bare actor-string toward OIDC claims cryptographically scoped to `repository owner + repository name + workflow filename (+ optional environment)`. Sources: [crates.io Trusted Publishing docs](https://crates.io/docs/trusted-publishing); [PyPI Trusted Publishers — Adding a Publisher](https://docs.pypi.org/trusted-publishers/adding-a-publisher/); [Rust RFC 3691](https://rust-lang.github.io/rfcs/3691-trusted-publishing-cratesio.html). The explicit reason both ecosystems give is that a bare actor identity (who triggered the run) is a weaker trust anchor than a claim bound to which workflow file ran.
**What the plan does:** C-048's unreachable-API, CI-derived branch accepts `GITHUB_ACTOR`+`GITHUB_ACTOR_ID` (or `GITLAB_USER_LOGIN`+`GITLAB_USER_ID`) unconfirmed, recording `owner_identity_source: "ci-environment"` rather than `"resolved"` — the plan is already transparent about the weaker trust level via that field, and the plan's own Cross-repository closeout table already lists an "`actor_id` governance" issue for `ocx-sh/index`, "naming `actor_id` explicitly — the OIDC claim carrying the triggering human's account id... materially stronger than the bare `GITHUB_ACTOR` string."
**Fix:** No plan edit needed — the plan already reaches the right conclusion and has already queued the right cross-repo issue. Cite crates.io/PyPI Trusted Publishing in that issue body as precedent when it is drafted; it strengthens the ask with a shipped, uncontroversial reference implementation of the same fix.

### F-03 · Suggest · A single 0.6→0.7 release window is short relative to comparable CLI deprecation practice (record only — the window's existence and length trace to this project's own established convention, not to this ADR)
**Where:** C-062, DV-3, "Batched-window carve-out" (CLAUDE.md)
**What the state of the art does:** Kubernetes requires flags to keep working "no less than 1 year or 2 releases (whichever is longer)" after deprecation ([Kubernetes Deprecation Policy](https://kubernetes.io/docs/reference/using-api/deprecation-policy/)); Jaeger's policy is deprecate-in-N, remove-no-earlier-than-N+2 ([jaegertracing/jaeger#2113](https://github.com/jaegertracing/jaeger/issues/2113)); Salesforce CLI commits to a 4-month minimum ([Salesforce CLI Deprecation Policy](https://developer.salesforce.com/docs/platform/salesforce-cli-reference/guide/cli_reference_deprecation.html)). All three give users more than one release cycle to see and act on a warning.
**What the plan does:** C-062: the hidden `--package` flag "warns once on stderr and never on stdout, naming 0.7 as the removal release" — one release pair, matching the project's own already-established precedent (`ocx run` → `ocx exec`, deprecated 0.6, removed 0.7, named in `CLAUDE.md`'s "Batched-window carve-out").
**Fix:** None proposed — this is the project's own settled doctrine (pre-1.0, "even interfaces break," one window per release pair by explicit policy), not something this ADR/plan invented, so it is recorded per this task's constraint rather than argued. If the owner ever revisits the batched-window carve-out doctrine itself, the citations above are the evidence base.

## Confirmed sound

- **The hand-rolled `git http-backend` CGI-bridge fixture is the correct SOTA choice, not a corner cut.** Checked how comparable tools test git push: cargo's own test harness (`cargo-test-support::git`) uses **libgit2 bindings against local `file://` repositories only** — no HTTP server, no hooks, no push options (confirmed by reading `crates/cargo-test-support/src/git.rs` on GitHub). jj's `cli/tests/test_git_push.rs` shells out to a real `git` binary but likewise only against **local file-path repositories** — no HTTP, no push-options, no server hooks, no async merge-request creation. Neither tool needs what this plan needs (server-side hook synchrony, push-option delivery, an asynchronous merge-request worker), so neither is a stronger precedent to imitate — the plan's own research already identified the one closest real analog (isomorphic-git's Node.js `git-http-mock-server`) and correctly rejected `dulwich` for the same missing capability. This SOTA pass found nothing that contradicts that conclusion.
- **The blobless-clone proof mechanism is the git-native, state-of-the-art one.** `git rev-list --objects --missing=print` is git's own documented mechanism for listing objects a partial clone is missing, and pairing it with a `GIT_TRACE_PACKET=1` capability-negotiation capture against a full-clone negative control is exactly the shape of git's own upstream regression coverage for this feature (`t/t5616-partial-clone.sh` in git.git). No better-established or more official tooling exists; DV-5's mechanism does not need strengthening.
- **The fixture's git-version anchoring is current, not stale.** The persisted git-fixture research verified header framing, hook exit-code semantics, and push-option delivery against git **2.54.0** — which is also what is actually on `PATH` in this environment (`git --version` → `git version 2.54.0`). Git 2.55 (released June 25, 2026, before this plan's own research date) added "configuration-based hooks," confirmed to be **purely additive** to the traditional `$GIT_DIR/hooks/<name>` executable-file mechanism and to have no effect on `http-backend`'s CGI wire format, chunked-body handling, or push-option delivery (per GitHub's own release write-up). No drift to correct.

## Negative findings

- Searched for a Git or GitLab release, a CVE, a clap release, or a CPython `http.server` change dated strictly **after 2026-09-04** that bears on this plan: found nothing. The closest-dated items surfaced (Git 2.55 — June 25, 2026; clap 4.6.0 — March 12, 2026; CVE-2026-3854 — disclosed March 4, 2026, patched within the same window; GitLab 19.4 — not yet released, expected ~Sept 19, 2026 with no push-option/partial-clone/job-token content found in its preview notes) all predate or postdate the ADR's 2026-09-04 cutoff by enough that they are either already stale inputs the earlier research should have (and largely did) already absorb, or not yet public. No same-day-or-later delta exists to report.
- Could not find a maintained CLI that tests smart-HTTP `git push` end-to-end against real server-side hooks and push-options (searched `gh`, `glab`, `cargo`, `jj`, `renovate`, `release-please`). `gh`/`glab` test their platform surface against a running instance or mocked API and treat `git push` itself as already-succeeded input; `cargo` and `jj` both stay at local `file://` transport. This corroborates rather than undermines the plan's fixture design (see Confirmed sound) but means there is no third-party test suite this plan could borrow from wholesale.
- Could not confirm or rule out that GitLab's push-option-to-merge-request pipeline (`PushOptionsHandlerService`) uses a delimiter-fragile internal serialization comparable to GitHub's `babeld`/`X-Stat` (the mechanism CVE-2026-3854 exploited). The already-persisted GitLab verification research describes the path as passing through structured Ruby service objects rather than a flat delimited string, which would make the exact CVE-2026-3854 shape inapplicable to GitLab — but this was not independently verified against GitLab source, only inferred from prior research. Recorded as an open question feeding F-01, not a confirmed second vulnerability.
- Searched for a "claim a namespace" or "first publish" flag grammar in winget, Homebrew, or conda-forge beyond what the ADR already surveyed, specifically hunting for a flag this plan's concrete grammar (`--repository`, repeatable `--owner`, three `--upstream-*` flags, `--transport`) might be missing. Found none: conda-forge's `recipe-maintainers:` list is the repeatable-login precedent the plan's `--owner` already matches; crates.io/PyPI Trusted Publishing's `owner + repo + workflow-file(+environment)` shape (F-02) solves a different problem (CI-authorization, not namespace governance) and is not a flag this command is missing so much as a stronger alternative *mechanism* for a question WP-16 already plans to escalate.
