# Research: index claim command — git transport tooling

## Metadata

- Date: 2026-09-04
- Expires: 2027-03-04
- Domain: cli
- Triggered by: /hex-architect index claim command (dossier .agents/discussions/index-claim-command.md)
- Author: hex-architect research lane, axis technology/tooling

## Direct Answer

Shell out to the system `git` binary via `tokio::process::Command`, following the existing `crates/ocx_lib/src/utility/child_process.rs` pattern. Do not add `git2` or `gix` as a dependency. Compute `compare_branch` from a local `git clone --filter=blob:none --no-checkout` (fetching both refs), commit via the plumbing chain (`hash-object -w` → `mktree` → `commit-tree` → `update-ref`, no worktree needed), and push with `-o merge_request.create -o merge_request.target=<base> -o merge_request.title=…` plus `--force-with-lease=<branch>:<expected-sha>` for the rebuild-on-base case. Confirm the MR via `GET /merge_requests?source_branch=` — never parse `remote:` stderr as the source of truth, only as a UX nicety. Minimum git version: **2.31** (for `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_n`/`GIT_CONFIG_VALUE_n` credential injection — the binding constraint, not push options, which arrived in 2.10).

## Trends

- The whole Rust-git-tooling ecosystem is mid-migration toward `gix` (gitoxide), but **push is still explicitly listed as partial/in-progress** as of the current `gitoxide` crate-status document (fetched 2026-09-04) — [crate-status.md](https://github.com/GitoxideLabs/gitoxide/blob/main/crate-status.md). `gix-protocol` has send-pack/receive-pack plumbing and push-options/atomic-push support at the protocol layer, but the document still lists "push … over `file://` and `ssh://`" under cross-cutting parity work still needed. This is exactly the axis this decision needs (HTTPS push with push options), so "partial" is the operative word, not "done."
- `git2`/libgit2 gained `push_options` support only in **libgit2 1.8.0** (2024) — [libgit2 git_push_options docs](https://libgit2.org/docs/reference/main/remote/git_push_options.html) note `remote_push_options` requires libgit2 ≥ 1.8.0; the v1.3.2 docs show the field did not exist yet. Current `git2` (crates.io) requires libgit2 ≥ 1.9.0, so the feature is available in principle — but see Design Patterns below for why this project still shouldn't take the dependency.
- Editors that made this exact library choice all now sit on the pure-Rust side for **read/plumbing** work: Helix uses `gix` — [DeepWiki VCS integration](https://deepwiki.com/helix-editor/helix/5.2-version-control-integration); Jujutsu's git backend "uses the gitoxide Rust library" — [jj-vcs/jj#2316](https://github.com/jj-vcs/jj/issues/2316) discussion and current jj docs. None of these need *push with push options against a specific forge's MR-create protocol*, which is the actual requirement here — they need commit-graph reads, checkout, and (for jj) fetch/push of ordinary refs, a materially smaller surface than what this decision needs.
- The two CLIs doing precisely this job today — creating a PR/MR by driving a real forge from local git state — both **shell out to the system `git` binary**: `gh` invokes `/usr/bin/git` as a subprocess for clone/fetch/checkout, and `glab mr checkout` is "the same shape" — [Git Forges Made Simple](https://julianhofer.eu/blog/2025/git-forges/). Neither embeds git2 or gix for the git-plumbing half of MR creation. `glab mr create` itself does **not** rely on push options at all — it posts through GitLab's REST API and only pushes commits separately via `--push` — [glab mr create docs](https://docs.gitlab.com/cli/mr/create/). This is independent precedent for the design's "REST is the source of truth, push options are best-effort" split (Requirements §Transport).
- `git2-rs`'s own migration pressure is one-directional: Cargo itself already moved fetch/clone negotiation onto `gix` (v0.45, multi-round pack negotiation) while keeping `git2` elsewhere, and its own tracking issue calls a full git2→gix migration "a fun research project," not a completed or near-term one — [rust-lang/cargo#12236](https://github.com/rust-lang/cargo/pull/12236), [gitoxide-in-cargo #106](https://github.com/GitoxideLabs/gitoxide/issues/106). If Cargo — gitoxide's flagship consumer — hasn't retired git2 wholesale, treating gix as push-production-ready today is premature.

## Key Findings

1. **`gix` push: partial, not GA.** `gix-protocol` has push-side plumbing (send-pack/receive-pack, push-options, atomic pushes) per crate-status.md, but the document still lists full push workflows under unfinished cross-cutting work. No worked example of `gix` doing an authenticated HTTPS push with push options against a real forge was found in current docs or examples. — [crate-status.md](https://github.com/GitoxideLabs/gitoxide/blob/main/crate-status.md) (fetched 2026-09-04).
2. **`gix` *can* avoid an OpenSSL dependency for HTTP** via `blocking-http-transport-reqwest-rust-tls` (stacks `blocking-http-transport-reqwest` + rustls), so a hypothetical future `gix` adoption would not by itself break the workspace's rustls-only invariant (`Cargo.toml:103-105`, `adr_index_indirection.md` F). This removes "TLS stack conflict" as gix's blocker — its blocker is push maturity, full stop. — [gix-transport docs](https://docs.rs/gix-transport/latest/gix_transport/), [Fedora package listing confirming the feature combination exists](https://packages.fedoraproject.org/pkgs/rust-gix/rust-gix+blocking-http-transport-reqwest-rust-tls-trust-dns-devel/index.html).
3. **`git2`/libgit2 does *not* get the same pass.** `git2-rs`'s README states: "If the `ssh` feature is enabled then this library depends on `libssh2` which depends on OpenSSL." Push-over-HTTPS in libgit2 doesn't strictly require the ssh feature, but libgit2's own HTTPS transport historically links against the platform's TLS library (OpenSSL on Linux by default, unless built against `mbedTLS`/`WinHTTP`/`Secure Transport` per-platform) — there is no first-class "libgit2 HTTPS via rustls" build the way gix has. Taking `git2` as a dependency risks a second, non-rustls TLS stack in a workspace whose `Cargo.toml` explicitly documents "the workspace is rustls-only" (`Cargo.toml:144`) as a deliberate invariant (avoiding two Sigstore/OpenSSL providers per `adr_index_indirection.md` F). — [git2-rs README](https://github.com/rust-lang/git2-rs/blob/master/README.md).
4. **Minimum git version is set by credential injection, not push options.** `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_n`/`GIT_CONFIG_VALUE_n` — the mechanism the discussion already commits to for scoping the injected credential to the index host without touching `.git/config`, argv, or the remote URL — were introduced in **git 2.31** (March 2021) per the official release notes: "Two new ways to feed configuration variable-value pairs via environment variables have been introduced." — [git 2.31.0 release notes](https://github.com/git/git/blob/master/Documentation/RelNotes/2.31.0.adoc). Push options themselves (`GIT_PUSH_OPTION_COUNT`/`_n`, `-o`/`--push-option`) are much older (git 2.10, 2016), so they are not the binding constraint. git 2.31 is old enough to be a non-issue: Debian 12 ships 2.39, Ubuntu 22.04 ships 2.34, GitHub Actions/GitLab SaaS runners ship current git — pin **git ≥ 2.31** and fail closed with a named error before any network call when the binary is absent or older (the discussion's own recommendation, §Open questions "Minimum git version").
5. **Ahead/behind/diverged is a two-command combination, already well-trodden.** `git rev-list --left-right --count <base>...<head>` yields "ahead behind" counts directly; `git merge-base --is-ancestor <a> <b>` (exit 0/1, a plumbing command meant for scripting) answers strict ancestry. Together these reproduce `BranchComparison` exactly: both counts zero → `Identical`; head-count > 0 and base-count 0 → `Ahead`; head-count 0 and base-count > 0 → `Behind`; both > 0 → `Diverged`. This requires **both refs actually fetched locally** — a `--depth 1` shallow clone lies about ahead/behind because history is truncated, which is exactly the D13 "unclassifiable compare read as Identical" failure mode the council's operability seat flagged for job-token-only reads. Use `--filter=blob:none` (blobless partial clone) instead of `--depth`: full commit/tree history (so ancestry math is exact), no blob bytes (so it's cheap) — [git-clone partial clone docs](https://git-scm.com/docs/partial-clone), [GitHub: partial clone vs shallow clone](https://github.blog/open-source/git/get-up-to-speed-with-partial-clone-and-shallow-clone/).
6. **Committing without a worktree checkout is a standard four-command plumbing chain.** `git hash-object -w <file>` writes each blob and prints its SHA; `git mktree` (fed `ls-tree`-format lines) builds the tree object and prints its SHA; `git commit-tree <tree> -p <parent> -m <msg>` creates the commit and prints its SHA; a final `git update-ref refs/heads/<branch> <new-sha> <old-sha>` (or an update via push in one step) moves the ref with an optimistic-lock check builtin (the two-SHA form fails if the ref isn't at `<old-sha>`, which is `RefUpdate::FastForward`'s CAS semantics for free, locally). No worktree, no `--no-checkout` clone step is even required for the *commit* half — only for the *read* half (getting file bytes back out to diff against, via `git cat-file` or `git show <sha>:<path>`, both of which also work against a bare/no-checkout clone). — [git mktree docs](https://commandmasters.com/commands/git-mktree-common/), [git commit-tree docs](https://docs.oracle.com/cd/E86824_01/html/E54763/git-commit-tree-1.html).
7. **Full push-option grammar and version provenance** (fetched from a GitLab docs mirror, 2026-09-04, since `docs.gitlab.com` itself returned an auth-gate redirect to `projects.gitlab.io/auth?...` for this fetcher — treat that redirect as a fetch artifact, not a real GitLab endpoint, and re-verify against the live page before the ADR ships):

   | Option | Introduced | Purpose |
   |---|---|---|
   | `merge_request.create` | — | Opens a new MR for the pushed branch |
   | `merge_request.target` / `merge_request.target_project` | `target_project`: GitLab 16.6 | Target branch / cross-project target |
   | `merge_request.title` / `.description` | — | MR title/body |
   | `merge_request.remove_source_branch` | — | Delete-source-branch-on-merge flag |
   | `merge_request.merge_when_pipeline_succeeds` (aliased `auto_merge`) | — | Auto-merge-on-green |
   | `merge_request.draft` | GitLab 15.0 | Marks the MR draft |
   | `merge_request.milestone` | GitLab 14.1 | Milestone assignment |
   | `merge_request.label` / `.unlabel` | — | Label add/remove |
   | `merge_request.assign` / `.unassign` | GitLab 15.5 (username form) | Assignee add/remove |

   All of these predate the 18.x job-token-push window, so no push-option grammar gap exists for this feature at the version floor decision 4 already sets (GitLab ≥ 18.4 for job-token push). — [push_options.md mirror](https://repository.prace-ri.eu/git/help/user/project/push_options.md).
8. **Repeated push with `merge_request.create` to a branch already carrying an open MR is a no-op, not an error.** GitLab enforces a strict one-open-MR-per-branch invariant; docs describe pushing `merge_request.target`/`merge_when_pipeline_succeeds` again to *update* the existing MR, and community reports confirm `merge_request.create` on a branch with an existing MR does not create a duplicate. This directly supports the discussion's "re-run while the claim PR is still open updates the same branch and PR" requirement — the push options themselves are naturally idempotent in this direction, independent of the REST confirmation step. — [GitLab merge_requests docs mirror](https://repository.prace-ri.eu/git/help/user/project/merge_requests/creating_merge_requests.md), [GitLab-foss MR !26752](https://gitlab.com/gitlab-org/gitlab-foss/-/merge_requests/26752).
9. **The `remote:` MR-URL line is real but explicitly not meant as an API.** GitLab's push response prints:
   ```
   remote: View merge request for my-awesome-branch:
   remote:   https://gitlab.com/<ns>/<repo>/-/merge_requests/<iid>
   ```
   sent to stderr from `gitlab-shell`. GitLab's own issue tracker records requests to *disable* or *change* this message (e.g. [gitlab-ce#21451](https://gitlab.com/gitlab-org/gitlab-ce/issues/21451)) and to fix cases where the URL is stale after a non-`.create` push ([gitlab#441944](https://gitlab.com/gitlab-org/gitlab/-/issues/441944)) — i.e., GitLab treats this text as a UX courtesy it has changed shape on before, not a contract. Confirms the discussion's own position: read the URL opportunistically for a nicer first log line, but the authoritative value comes from `GET /merge_requests?source_branch=<branch>`, which is job-token-readable per the fact-check thread already closed in the discussion.
10. **`receive.advertisePushOptions` must be `true` server-side** or the push-option payload is silently dropped before the hook ever sees it — a real GitLab instance already sets this, but the fixture's bare repo must set it explicitly (`git config receive.advertisePushOptions true` in the bare repo, or `--config` at `git init --bare`). — [git-push docs / push options overview](https://zerokspot.com/weblog/2020/09/28/git-push-options/).
11. **Pre-receive/hook rejection semantics are exact and testable:** a hook that exits non-zero causes `git push` to abort the *entire* ref update before anything is written, and the client sees the rejection text the hook wrote to stderr, prefixed `remote:` (`! [remote rejected] <branch> -> <branch> (pre-receive hook declined)`). This is the mechanism the fixture uses to simulate a version-gate rejection (job-token push disabled, allowlist miss): the fake bare repo's hook inspects an env var the test harness sets (e.g., simulate "GitLab 18.3" by rejecting) and exits 1 with a message naming the missing capability, which the ocx client then must map to the discussion's named `EX_UNAVAILABLE` error. — [git githooks docs](https://git-scm.com/docs/githooks/2.27.0).
12. **Non-fast-forward vs. stale-lease rejection text differs and both need parsing coverage.** An ordinary non-fast-forward push (someone else moved the branch) rejects with `! [rejected] <branch> -> <branch> (fetch first)`; a `--force-with-lease` whose expected value no longer matches rejects with `(stale info)` instead. The fixture needs both scenarios (concurrent announce vs. spent-branch race) to prove the client distinguishes "someone raced me, retry" from "my lease was wrong, re-read and recompute" rather than treating both as the generic `ForgeError::NonFastForward`.
13. **`GET /users?username=` requires an authenticated session and is not documented as job-token-accessible**; the GitLab users-API doc fetched for this report only states "you must be signed in," with no explicit job-token carve-out, consistent with the discussion's own decision 9 fallback: `login:id` must be accepted directly wherever "no users API is reachable (job token)." This is corroborating, not new — the discussion had already reached this conclusion from the live job-token access table. — [GitLab Users API mirror](https://microfluidics.utoronto.ca/gitlab/help/api/users.md).
14. **GitHub's users API works fine under `GITHUB_TOKEN`**, at the standard token-scoped rate limit (1,000 req/hour/repo for `GITHUB_TOKEN` in Actions, 15,000/hour/repo on GHEC) — no special carve-out needed, unlike GitLab's job token. — [GitHub REST rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api).
15. **GHES version-skew handling is a header, not a URL scheme change** beyond the already-known `/api/v3` base: GHES supports `X-GitHub-Api-Version`, defaulting to `2022-11-28` when omitted, and an unsupported explicit version 410s. Since `crates/ocx_lib/src/forge/github.rs` presumably already targets `.com`'s versioned surface, the only GHES-specific delta for `claim`'s reads (contents, users, pulls) is the base URL swap already handled by D3 (declared `--forge github` with a custom host) — no new version-negotiation logic is needed. — [GHES API Versions docs](https://docs.github.com/en/enterprise-server@3.20/rest/about-the-rest-api/api-versions).
16. **No other forge has an MR/PR-via-push-option grammar comparable to GitLab's.** GitHub: none. Gitea: none (push gives a compare-page hint link only). Forgejo: has "push-to-create" and a distinct **AGit** workflow (`git push origin HEAD:refs/for/<branch>/<topic>` with its own inline options), which is a different wire convention, not GitLab's `-o merge_request.*` grammar, and out of this decision's scope (GitHub/GitLab only per the dossier). Bitbucket Cloud/Server: no push-option PR-create mechanism found. This confirms decision to scope `--transport git` to GitLab only was correct and there's no shared abstraction worth building across forges for this. — [Forgejo AGit docs](https://forgejo.org/docs/latest/user/agit-support/), [Forgejo push-to-create docs](https://forgejo.org/docs/v15.0/user/git-cli/push-to-create/).

## Design Patterns Worth Considering

- **Shell-out-with-full-env-control, matching the existing `child_process.rs` contract.** `spawn_and_wait` already gives ocx exactly what a git subprocess needs: `env_clear()` before applying an explicit `Env`, inherited stdio (so `remote:` lines are visible for logs/debugging), `kill_on_drop`, and signal forwarding. The git-transport work should be a **third caller** of this module (`get_ref_sha`/reads stay REST; only `commit_files`/`open_or_update_pull_request`/`compare_branch` under `--transport git` spawn git), not a new subprocess abstraction. This directly satisfies "Don't Own Non-Domain Code" — git plumbing is exactly the kind of externally-solved problem the quality-core rule names, and the boundary module already exists.
- **Ephemeral clone directory, not a shared cache.** Each claim/announce invocation under `--transport git` should `git init` (or `git clone --filter=blob:none --no-checkout --origin <name>`) into a fresh `tempfile::TempDir`, fetch exactly the two needed refs (`fetch <url> <base>:refs/remotes/o/<base> <branch>:refs/remotes/o/<branch>` — as the discussion's own draft already specifies), do the commit/compare/push dance, then let RAII remove it on every exit path — matching `spawn_and_wait`'s doc comment about callers needing to run cleanup after the child exits (not `exec`, which never returns).
- **Compare via local refs, never via a server compare endpoint, under git transport.** This is the one place the "REST reads, git writes" split from the council's synthesis needs a footnote: `compare_branch` is listed in the `Forge` trait as an operation with no git-wire answer in general (`api.rs:151-163`'s contract doc), but *for the git-transport case specifically* the whole point is that the local clone has fetched both refs already — so `git rev-list --left-right --count` is not an approximation, it's the ground truth, computed identically to what the server would say, without a network round-trip. Frame this in the ADR as "git transport computes `compare_branch` locally because it already has both refs on disk," not as an exception to "no git-wire answer."
- **Push-then-confirm, not push-then-parse.** Treat the `-o merge_request.*` push options as a fire-and-hope UX nicety and the immediate follow-up `GET /merge_requests?source_branch=<branch>` (job-token-readable, per the discussion's own closed fact-check thread) as the only thing `open_or_update_pull_request`'s return value is built from. This is consistent with finding 9 above (GitLab itself doesn't treat the `remote:` text as stable) and with how `glab` itself is built (REST-first, push separate).
- **Two-hook fixture, one object graph** (per the council's D10 and open-question recommendation): extend `fake_forge.py`'s existing in-memory graph with a real `git init --bare` repo served via CGI `git http-backend` (stdlib `http.server` can run it as a CGI script per request, or shell to `git http-backend` directly with the right `PATH_INFO`/`GIT_HTTP_EXPORT_ALL` env), `receive.advertisePushOptions true`, and a `post-receive` hook (not `pre-receive`, since the MR record should only be created after the ref actually moved) that reads `GIT_PUSH_OPTION_COUNT`/`_n`, parses `merge_request.create`/`.target`/`.title`, and calls back into the same Python process's in-memory MR store the REST fake already serves (e.g., via a local socket, a shared file, or by running the hook as a small script that hits the fixture's own already-listening HTTP port with a loopback REST call) — so `GET /merge_requests` sees exactly what the push created, one graph, two protocols, as D10 requires. A **separate `pre-receive`** hook (or the post-receive itself refusing and exiting non-zero before doing anything persistent) simulates the version-gate rejection and the non-fast-forward/stale-lease cases from findings 11–12.
- **`git --version` parsing**: git's version string format is stable (`git version 2.43.0`, sometimes with a vendor suffix like `git version 2.39.5 (Apple Git-154)`) — parse with a simple regex extracting the first `\d+\.\d+(\.\d+)?` and compare numerically; do this once at the start of any `--transport git` run (per the discussion's own recommendation) so an absent or too-old binary fails before any network call, with a named error rather than a git subprocess spawn failure surfacing as a generic I/O error.
- **Author/committer identity**: inject `GIT_AUTHOR_NAME`/`GIT_AUTHOR_EMAIL`/`GIT_COMMITTER_NAME`/`GIT_COMMITTER_EMAIL` explicitly into the child's `Env` for the `commit-tree` step (do not rely on `git config user.*`, which may be absent in a CI runner's minimal image and would otherwise fail the commit outright). Since GitLab's *MR author* field on a job-token push is the **pushing user** (attached to the job token itself, per the discussion's closed "Job-token read scope" thread — "the token carries the triggering user's permissions"), not the git commit's author/committer identity, these variables only affect the commit metadata inside the repository, not who GitLab records as having opened the MR — so a reasonable default (`ocx-bot <noreply@ocx.sh>` or similar) is safe here and does not need to track `--owner`.

## Recommendation

**Shell out to `git`, minimum version 2.31, via a new thin wrapper alongside `crates/ocx_lib/src/utility/child_process.rs`.** Concrete sequence for the git-transport write path (GitLab only, per D3/decision 6):

1. `git --version` → parse, refuse < 2.31 with a named error before any network call (per the discussion's own recommendation).
2. `git init <tempdir>` then `git -C <tempdir> fetch <url> <base>:refs/remotes/o/<base> <branch>:refs/remotes/o/<branch>` with `--filter=blob:none` on the `init`/first fetch to keep it cheap while keeping full history for exact ancestry math (never `--depth`). Credential and `GIT_TERMINAL_PROMPT=0` injected via `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_n`/`GIT_CONFIG_VALUE_n` scoped to the index host, per the discussion's decision 9 — this needs git ≥ 2.31, confirmed above as the binding version floor.
3. Ancestry: `git -C <tempdir> rev-list --left-right --count o/<base>...o/<branch>` for the four-way `BranchComparison` classification; `git merge-base --is-ancestor` only if a tie-break is ever needed (it normally isn't — the two-count read already disambiguates all four states).
4. Commit: `hash-object -w` each changed file against the fetched base tree, `mktree` (starting from `git ls-tree o/<base>` for unchanged entries), `commit-tree -p o/<base>` (or `-p o/<branch>` when accumulating) with `GIT_AUTHOR_*`/`GIT_COMMITTER_*` env set to a fixed bot identity, then move a local ref to the new commit.
5. Push: `git push <url> <local-ref>:refs/heads/<branch>` with `-o merge_request.create -o merge_request.target=<base> -o merge_request.title=… [-o merge_request.description=…]`, plain (fast-forward) push for the ordinary case, `--force-with-lease=<branch>:<old-sha>` only for the `RefUpdate::Reset` spent/stale-branch rebuild case (reusing #399's carried-tags logic verbatim — it is transport-agnostic already).
6. Never parse push stderr for the MR URL as ground truth: confirm via `GET /merge_requests?source_branch=<branch>` (job-token-readable) and use the `remote:` line only as an optional log embellishment if present.
7. Map git's stderr precisely: `(fetch first)` → `ForgeError::NonFastForward` (retry via re-read-and-regenerate, same as REST today); `(stale info)` → the lease-specific variant (re-read expected sha, retry once); `hook declined` with a recognizable substring (the fixture and real GitLab both use this phrasing) → the named version/allowlist error, `EX_UNAVAILABLE` (69) per the discussion's own recommendation.

**Why not `git2`:** push-option support only arrived in libgit2 1.8.0, and its HTTPS transport has no first-class rustls build path — taking it risks a second, undocumented TLS stack in a workspace whose `Cargo.toml` treats "one rustls provider" as a load-bearing invariant (finding 3). It buys nothing shelling out doesn't already give, at a real dependency-graph and binary-size cost, violating "Choose Boring Technology" (a subprocess call to the git already required on the CI runner is more boring than vendoring libgit2+its own C build).

**Why not `gix`:** the exact feature this decision needs — authenticated HTTPS push with push options, against real forges — is stated as not fully done by the project's own crate-status document (finding 1). Nothing in this codebase or any precedent found (Cargo, Helix, jj, Zed) has shipped `gix` doing this. Revisit when a `gitoxide` release explicitly marks push GA and a precedent project (ideally `gh`/`glab`/Renovate) ships it in production — track via the "Expires" date on this artifact.

**Fixture:** extend `fake_forge.py`'s shared object graph with a real `git init --bare` repo behind `git http-backend` (`receive.advertisePushOptions=true`), a `post-receive` hook parsing `GIT_PUSH_OPTION_*` to create/update the MR record the REST handlers already serve, and a separate rejection path (`pre-receive` or an early `post-receive` exit) for the version-gate and non-fast-forward/stale-lease negative cases — one shared graph, two protocol surfaces, exactly as the council's D10 already settled.
