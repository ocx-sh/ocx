# Research: workspace granularity, test scoping, build system prior art

## Metadata

**Date:** 2026-09-06
**Domain:** cli
**Triggered by:** /hex-discuss crate-split-and-verify-tiers
**Expires:** 2027-03-06

### Direct answer

**A. Workspace crate granularity.** Splitting a large crate does help incremental compiles because Cargo only recompiles crates whose code (or a dependency's public interface) changed — the mechanism is real and comparable Rust CLI/package-manager projects use it at scale (uv: 50–90+ crates, ruff/ty: 49 crates, deno: 77 crates, wasmtime: dozens of `wasmtime-*` crates) [uv DeepWiki](https://deepwiki.com/astral-sh/uv), [Ruff DeepWiki](https://deepwiki.com/astral-sh/ruff), [Deno DeepWiki](https://deepwiki.com/denoland/deno/1.2-core-principles-and-design), [Wasmtime architecture](https://docs.wasmtime.dev/contributing-architecture.html). Against it: no source found gives a rigorous benchmark isolating "split one crate into N" (the widely-repeated "2:22→26s" and "9x faster" figures trace to *dependency replacement*, not crate-splitting, per direct inspection of the corrode.dev post — see negative:); the binary that depends on every crate anyway still pays full link cost, and Cargo's per-workspace-member **feature unification** means a feature turned on by any one workspace member is compiled into every member that depends on that crate — `cargo-hakari` exists specifically to manage the resulting drift with a generated `workspace-hack` crate [hakari docs](https://docs.rs/cargo-hakari/latest/cargo_hakari/about/index.html). The **orphan rule** is a documented structural obstacle: an active 2023 Rust RFC PR states plainly that "organizations with big workspaces that need to split types and implementations into separate crates for improved compilation speed and caching are forced to use free standing functions instead of trait implementations," calling it a chicken-and-egg problem [RFC #3482](https://github.com/rust-lang/rfcs/pull/3482) (draft, Sept 2023, still unmerged 3 years later — flag as unresolved, not adopted).

**B. Scoping acceptance/integration runs.** Two families exist: coverage/graph-based prediction (`pytest-testmon`, `cargo-difftests`, Bazel `target-determinator`, Turborepo/Nx affected-graph) and brute-force parallelization/sharding (`pytest-split`, `pytest-xdist`, `nextest` partitioning). The prediction family has a documented, named false-negative risk: Aspect (a Bazel vendor) states outright that "bazel-diff is incorrect and will sometimes miss affected targets, so they aren't delivered," and recommends an *empirical* (run-everything, cache-backed) approach over prediction for that reason [Aspect docs](https://docs.aspect.build/workflows/features/delivery/); Turborepo has an open, confirmed bug where its affected-graph filter misses dependent packages entirely [turborepo#9234](https://github.com/vercel/turborepo/issues/9234). This is the structurally relevant case for OCX: **when every acceptance test's real input is one built `ocx` binary**, a source-level diff→test mapping is describing a proxy (which Rust module changed) for the actual dependency (whether the binary's behavior changed), and every tool in this family inherits that same lossiness — none of the sources found handles "one build artifact, many black-box tests" as a distinct case with a stated accuracy number. Tiering (fast per-commit subset, full pre-merge/nightly) is the empirically well-attested pattern instead: rust-lang/rust runs a reduced check set per PR push and the *entire* suite only at bors/merge-queue time, explicitly accepting that some failures "only run under a full bors CI run" and surface "hours or days later" to a developer who saw green locally [rustc-dev-guide CI](https://rustc-dev-guide.rust-lang.org/tests/ci.html); nextest's partition feature is the mechanical primitive most CI tiers use to keep any one shard under a time budget [nextest partitioning](https://nexte.st/docs/ci-features/partitioning/).

**C. Bazel vs Cargo.** rules_rust/crate_universe is actively maintained into 2026 and now has real non-Google production adopters reporting success (Qwello: "surprisingly easy," bought them cross-language build unification; OpenAI/Codex: shipped native Bazel test sharding for their Rust suite in 2026) [Qwello](https://www.linkedin.com/pulse/bazel-adoption-qwello-surprisingly-easy-rust-projects-evgeny-petrov), [OpenAI/codex PR #18082](https://github.com/openai/codex/pull/18082). Against it: every first-hand adoption report found names the same three losses — rust-analyzer either needs Bazel-specific tooling or "chokes" on large codebases, `cargo check`/prototyping ergonomics degrade, and crates.io publishing/`cargo-expand`-style tooling stops working out of the box [mmapped.blog](https://mmapped.blog/posts/17-scaling-rust-builds-with-bazel) (2023, flagged as >18mo old), [Tweag](https://www.tweag.io/blog/2023-07-27-building-rust-workspace-with-bazel/) (2023, flagged old — also documents that Cargo.toml stays the dependency source of truth *in parallel* with Bazel files, a manual-sync burden). `crate_universe` explicitly does not resolve workspace-internal path dependencies for you — those still need manual `BUILD.bazel` targets — and per the rules_rust docs bzlmod support is described as "most features work but bugs are more likely" (an actively-moving target, not a settled baseline). No source found reports a team of this repo's exact size (four crates, ~340K LOC total) switching to Bazel; all adoption reports found are either much larger monorepos or greenfield.

### Trends (trending / established / emerging / declining)

- **Established:** many-small-crates workspaces for Rust CLIs/package managers at the scale of uv, ruff, deno — this is the median shape among comparable tools, not an outlier choice.
- **Established:** `cargo-hakari`/workspace-hack as the standard mitigation for feature-unification bleed once a workspace splits past a handful of crates.
- **Established:** CI tiering (fast subset per push, full suite at merge/nightly) as the default answer to "acceptance suite too slow to run every commit," across Rust (`rustc`), Python (pytest ecosystem), and monorepo tooling (Nx/Turborepo) alike.
- **Emerging/unresolved:** orphan-rule relaxation for same-workspace crates (RFC #3482) — proposed exactly to unblock crate-splitting, still in draft after ~3 years; treat "just split the crate" as having this known ceiling today, not as blocked-then-fixed.
- **Emerging:** Bazel-for-Rust adoption outside Google/Meta is now happening at mid-size companies (Qwello) and being talked about publicly by OpenAI (2026) — up from a 2023 landscape that was almost all first-party accounts (Tweag as consultants, mmapped.blog as a single-author report).
- **Declining:** `cargo-raze` is archived; the Bazel ecosystem has fully consolidated onto `rules_rust`'s `crate_universe` — cited directly in the project's own docs [crate_universe docs](https://bazelbuild.github.io/rules_rust/crate_universe_bzlmod.html).
- **Declining/contested:** pure coverage-based test-impact-analysis (testmon-style) as a *sole* gate for anything safety-relevant — the Aspect vendor's own guidance for their public-facing product steers customers away from prediction toward empirical/cache-based selection, specifically citing missed targets as the failure mode.

### Key findings (each with a link)

1. uv is a ~50-to-90-crate Rust workspace (source disagrees on exact count between DeepWiki pages, both >18 mo fresh as of 2026) organized in strict layers (CLI → engine → foundation crates) — the most directly comparable "package manager written in Rust" precedent for OCX. [uv architecture](https://deepwiki.com/astral-sh/uv/1.1-system-architecture)
2. ruff + ty share one 49-crate workspace split by prefix convention (`ruff_*`, `ty_*`, two thin CLI binaries) — a naming-convention-driven granularity model, not a layered one. [Ruff DeepWiki](https://deepwiki.com/astral-sh/ruff)
3. Deno's workspace has 77 member crates split into CLI / runtime library / extensions / utilities, but its CLI flag parser alone is one ~15.9K-line file inside a single crate — proof that "many crates" and "one huge file" coexist even in a well-regarded codebase; splitting is not applied uniformly. [Deno DeepWiki](https://deepwiki.com/denoland/deno/1.2-core-principles-and-design)
4. Wasmtime distinguishes public crates from `wasmtime-internal-*` crates specifically to keep internal dependencies out of the public API surface — a direct precedent for "how do we split without leaking internals," relevant to OCX's `ocx_lib` API-growth worry. [Wasmtime architecture](https://docs.wasmtime.dev/contributing-architecture.html)
5. `cargo-hakari` exists because per-workspace-member feature unification is real: it simulates a Cargo build per package/platform/feature-combination and generates a `workspace-hack` crate with the union of resolved features to stop feature bleed from silently changing what gets compiled. [hakari about](https://docs.rs/cargo-hakari/latest/cargo_hakari/about/index.html)
6. RFC #3482 (draft, Sept 2023, rust-lang/rfcs) documents the orphan-rule tax on workspace splitting in the proposers' own words: teams are "forced to use free standing functions instead of trait implementations" and call it "a chicken-and-egg situation." The relaxation is workspace-scoped only (never published to crates.io) and is still unmerged. [RFC #3482](https://github.com/rust-lang/rfcs/pull/3482)
7. Aspect (commercial Bazel vendor) explicitly recommends the *empirical* approach over prediction-based affected-target tools for their own customers, stating "bazel-diff is incorrect and will sometimes miss affected targets" and "target-determinator is slow and may hurt delivery times" — a vendor picking neither speed nor prediction, but correctness-by-execution. [Aspect docs](https://docs.aspect.build/workflows/features/delivery/)
8. Turborepo has a confirmed, open bug (`#9234`) where the affected-dependency-graph filter misses packages that depend on a changed one — a concrete, sourced false negative in a widely-used affected-graph tool, not a hypothetical. [turborepo#9234](https://github.com/vercel/turborepo/issues/9234)
9. rust-lang/rust's own CI explicitly runs a reduced test subset on every PR push and the full suite only at merge-queue (bors) time, and documents that some regressions are known to only surface at that later, full-suite stage — direct precedent for a tiered-gate design accepting some slip-through by policy. [rustc-dev-guide CI docs](https://rustc-dev-guide.rust-lang.org/tests/ci.html)
10. First-hand Bazel-for-Rust adopters (mmapped.blog, 2023; Tweag, 2023) both call the migration a success on caching/CI unification grounds but both independently report the same rust-analyzer degradation and loss of casual `cargo check`/`cargo expand` ergonomics — a repeated, not one-off, cost; more recent evidence (Qwello LinkedIn post, OpenAI/Codex 2026 Bazel PRs) shows adoption continuing despite that known cost, at companies smaller and larger respectively than the earlier reports. [mmapped.blog](https://mmapped.blog/posts/17-scaling-rust-builds-with-bazel), [Tweag](https://www.tweag.io/blog/2023-07-27-building-rust-workspace-with-bazel/), [Qwello](https://www.linkedin.com/pulse/bazel-adoption-qwello-surprisingly-easy-rust-projects-evgeny-petrov), [OpenAI/codex #18082](https://github.com/openai/codex/pull/18082)

### negative:

- The often-repeated "2:22min → 26s" and "9x faster incremental" compile-time figures (surfaced by the first search on this topic) do **not** measure crate-splitting. Direct inspection of the corrode.dev source shows "2:22→26s" is about *replacing a heavy dependency*, not splitting a crate into a workspace. **No source found in this pass gives a controlled before/after benchmark isolating "same code, split into N workspace crates" for a codebase anywhere near ocx_lib's ~280K LOC / ~6K-test scale.** Treat granularity-benefit claims as directionally true (mechanism is real, comparable tools do it) but not as quantified for a repo this size — a locally-run experiment would be needed for a real number.
- Could not source a single first-hand account of a 4-crate, ~340K-LOC-total Rust CLI workspace (OCX's actual current shape) adopting Bazel or undertaking a crate split; every adoption report found is either markedly larger (Deno-scale monorepos, OpenAI) or a from-scratch greenfield choice, not a mid-flight split of an existing single dominant crate.
- Could not find a rust-lang/rust-style "regression slipped through the fast tier and only appeared at full/nightly" postmortem with a *named, dated incident* for any Rust project — the pattern (full suite catches things the fast subset doesn't) is well-documented as a structural fact but the request for a concrete "here's the regression that got through" story came back empty for PyTorch, uv, and cargo specifically.
- Could not find measured cargo-difftests or pytest-testmon accuracy numbers (false-negative rate, precision/recall) from any source — both tools are documented mechanistically (how they decide "dirty") but neither project publishes an accuracy study, and no third-party benchmark was found either.
- The claim that Bazel adoption "bought" cross-language build unification is corroborated (Qwello explicitly says the biggest win was for Rust despite starting from a Python-first monorepo) but I could not find a *dated, disconfirming* account of a team reverting from Bazel back to Cargo for a Rust-specific project — several searches for this came back empty. Absence of evidence is not evidence of absence here; it may mean the search terms were wrong, not that it never happens.
- `crate_universe`'s exact current (2026) support maturity for `[patch.crates-io]` path patches on a *forked* dependency (OCX's `external/rust-oci-client` situation specifically) was not confirmed either way — docs describe `crate.annotation(patches=...)` for patching crates.io crates in-place, but not the "vendored fork replacing a crates.io crate wholesale via a local path" pattern OCX actually uses. This is a real open question, not a settled negative.
