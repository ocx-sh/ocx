## 4. Windows deep-job points (rules_ocx)

a. `taskfile.yml deep:windows-update-target`: added the case `run @tools//:update -- -g "a)b"` expecting exit 64 and the text
   `-g a)b failed (exit 64)`. Not run, CI only. Reasoning from `ocx/private/update.bat.tpl`: E13 refuses only `& | < > ^ % "`, so `)` passes
   the capture check; the later uses of the argument line are `set "ARG=%~1"`, `if "%ARG:~0,1%"` (quoted), `set "ARGSET_%ARG%=1"`
   and `ocx ... update --no-pull %RUNARGS%` (line 349) and `set "SHOWN=..."` / `for /f ... in ("%SHOWN%")` (quoted), all at top level
   or inside quotes, none inside a parenthesised block, so an unquoted `)` cannot close a block. The one place not provable from the text:
   the REM capture (`@for %%a in (1) do rem #%*#`) inside the `( ... )` block that writes the file; that is what the new case runs.
   Verified with D2: `ocx --project <ocx.toml> update --no-pull -g 'a)b'` exits 64 with `unknown group 'a)b'`, so the expected code is right.
b. Windows `with_runfiles`: `deep (windows-latest)` runs `task ci:deep` => `deep:examples` => `bazelisk test //...` in
   `examples/cross_platform`, whose `.bazelrc` no longer carries `startup --windows_enable_symlinks` / `common:windows --enable_runfiles`
   (removed by c4c73f0). `launcher_status(runfiles = True)` builds the tree through a per-target transition to `--enable_runfiles=yes`, so the job does
   build it (`runfiles_test` reads `tree=yes`); it is not skipped. Whether Windows can create that tree without the startup symlink flag is
   unproven: every `verify-deep` run on this branch (newest success 45828177769 at 401c9c4, all before c4c73f0) predates the flag removal.
