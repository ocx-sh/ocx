# Research: crate decomposition patterns for a large Rust library

## Metadata

**Date:** 2026-09-06
**Domain:** cli
**Triggered by:** /hex-discuss crate-split-and-verify-tiers
**Expires:** 2027-03-06

## Direct answer

Every documented large-scale Rust codebase (rust-analyzer, wasmtime, cargo, uv, deno, zed, nushell, bevy) settles on the same shape: a small number of **layered, dependency-acyclic crates** where lower layers know nothing about upper ones, plus one thin "facade" crate that is the only stable public surface — internal crates are free to break ([wasmtime contributing-architecture.md](https://github.com/bytecodealliance/wasmtime/blob/main/docs/contributing-architecture.md), [rust-analyzer architecture.md](https://github.com/rust-lang/rust-analyzer/blob/067b4a32dd267d2599f908fc556491be45af7176/docs/dev/architecture.md)). None of them frame the split as hexagonal/DDD in name, but the mechanics — traits as ports defined in the lowest crate, orphan-rule-driven adapter placement — are identical to what hexagonal-architecture-in-Rust writeups describe ([howtocodeit](https://www.howtocodeit.com/guides/master-hexagonal-architecture-in-rust), [barrage.net](https://www.barrage.net/blog/technology/how-to-apply-hexagonal-architecture-to-rust)). The strongest pushback in the ecosystem is **against splitting by feature/module count** rather than by genuine architectural need: r/rust and users.rust-lang.org threads converge on "you should not use multiple crates unless you need one of the things you can only get that way" — dead-code analysis, `cargo test -p`, trait coherence, and independent versioning all degrade once split, and modules are "much cheaper for merely organizing code" ([Modern Rust Project Layouts](https://users.rust-lang.org/t/modern-rust-project-layouts/137003)). Migration guidance is uniformly incremental (workspace first, then peel off low-dependency utility/vocabulary crates one at a time; [rustprojectprimer.com](https://rustprojectprimer.com/organization/workspace.html)), and the tooling to keep a split honest (`cargo-modules --acyclic`, `cargo-deny` bans, `guppy`/`cargo-hakari`) is real but thin — most of it is one-or-two-maintainer projects, not standardized infrastructure.

## Trends (trending / established / emerging / declining)

- **Established:** layered facade-crate pattern (wasmtime, rust-analyzer, nushell, deno) — years old, explicitly documented, stable.
- **Established:** per-crate `thiserror` + aggregation at the boundary — but multiple large projects (GreptimeDB) report `thiserror`/`anyhow` alone don't scale past a handful of crates and reach for `snafu` instead ([greptime.com](https://greptime.com/blogs/2024-05-07-error-rust)).
- **Trending / growing tooling:** `cargo-modules --acyclic` (PR #184, active in 2025), `guppy`/`cargo-hakari` for workspace-hack crates to cut duplicate-feature-unification rebuilds.
- **Emerging (language-level):** `impl(crate)` / restriction attributes proposed in RFC 3323, called for testing in [Aug 2026 Inside Rust post](https://blog.rust-lang.org/inside-rust/2026/08/10/call-for-testing-impl-and-mut-restrictions/) — would replace the sealed-trait workaround used today to keep ports crate-local.
- **Declining / contested:** "one crate per module" as a default — every first-hand account (kpreid on users.rust-lang.org, corrode.dev) frames this as a regretted overcorrection, not a goal.
- **Stagnant tooling:** `cargo-udeps` (still releasing through 2026 but nightly-only, single maintainer); `cargo-depgraph` and `cargo-workspace-analyzer` are small, single-purpose, no recent architecture-enforcement features added.

## Key findings

1. Wasmtime treats every crate except the top-level `wasmtime` facade as a private, semver-unconstrained internal dependency — "we publish crates to crates.io but put very little effort into having a 'nice' API for internal crates." [source](https://github.com/bytecodealliance/wasmtime/blob/main/docs/contributing-architecture.md)
2. rust-analyzer's layering is explicitly justified by two non-negotiable invariants, not aesthetics: incrementality ("these crates explicitly care about being incremental") and fault isolation ("rust-analyzer should be partially available even when the build is broken"); `hir` and `ide` are named "API Boundary" crates on purpose. [source](https://github.com/rust-lang/rust-analyzer/blob/067b4a32dd267d2599f908fc556491be45af7176/docs/dev/architecture.md)
3. uv organizes ~90 crates into modular layers (CLI → resolver/installer/python-manager services → shared vocabulary), explicitly separated by responsibility, not by feature team. [source](https://deepwiki.com/astral-sh/uv/1.1-system-architecture)
4. Deno's `deno_core` / `deno_runtime` split is a deliberate reuse boundary: `deno_core` is "the V8 + Tokio runtime layer that everything else builds on," and ~24 of its crates are independently published to crates.io so third parties can "put together the right crates" for their own runtime. [source](https://oida.dev/dissecting-deno/)
5. Nushell's `nu-protocol` / `nu-parser` / `nu-engine` split follows strict downward dependency flow: protocol → parser/engine → command layer → CLI, with `nu-protocol` holding only shared struct/trait definitions (a vocabulary crate). [source](https://deepwiki.com/nushell/nushell)
6. Bevy's crate boundaries are drawn on actual reuse needs, not ECS-module symmetry: `bevy_transform` was split from `bevy_hierarchy` specifically "to enable `bevy_scene` to work without bevy's transform" — a concrete consumer-driven cut, not a speculative one. [source](https://github.com/bevyengine/bevy/discussions/2187)
7. The strongest documented counter-position: "You should not use multiple crates unless you need one of the things you can only get that way" (procedural macros, platform gating, independent publishing, or measured compile-time pain) — modules are the default, crates are the escalation. [source](https://users.rust-lang.org/t/modern-rust-project-layouts/137003)
8. Splitting has real, named costs beyond compile time: cross-crate dead-code analysis stops working, and the orphan rule means an impl that used to live trivially in one module now needs a newtype wrapper or a sealed-trait/ports indirection to reach across the new crate boundary. [source](https://users.rust-lang.org/t/modern-rust-project-layouts/137003), [source](https://www.barrage.net/blog/technology/how-to-apply-hexagonal-architecture-to-rust)
9. GreptimeDB, a large multi-crate Rust workspace, found that `thiserror`'s `From`-per-variant model breaks down once several crates each need to convert the same upstream error into differently-contexted variants; they moved to `snafu` specifically to keep call-site location and context while composing errors across crate boundaries — direct evidence against "just `thiserror` per crate, `?` everywhere" as a scaling strategy. [source](https://greptime.com/blogs/2024-05-07-error-rust)
10. `cargo-modules --acyclic` (merged PR, [regexident/cargo-modules#184](https://github.com/regexident/cargo-modules/pull/184)) is the concrete, runnable tool for enforcing "no cycles" as a CI gate on module (and by extension crate) graphs; `guppy` (ex-Facebook/Diem) is the more mature library for querying workspace dependency graphs and was used in production to enforce "test-only crates never reach production builds." [source](https://github.com/facebookarchive/cargo-guppy)

## Styles compared

| Style | Rust realisation | Where impls live | Error strategy | Who uses it | Reported downside |
|---|---|---|---|---|---|
| Layered (vocabulary → infra → domain → application) | Downward-only crate deps; lowest crate has zero workspace deps | Each layer implements its own traits; no cross-layer orphan issues if traits are defined at the layer they're consumed from | `thiserror` per crate, `?`-propagated upward, `anyhow`/facade error at the top | rust-analyzer ([architecture.md](https://github.com/rust-lang/rust-analyzer/blob/067b4a32dd267d2599f908fc556491be45af7176/docs/dev/architecture.md)), nushell ([deepwiki](https://deepwiki.com/nushell/nushell)), uv ([deepwiki](https://deepwiki.com/astral-sh/uv/1.1-system-architecture)) | Still needs discipline to prevent a "leaf" crate from growing an upward dependency by accident — needs a graph-cycle check in CI, not just convention |
| Hexagonal / ports-and-adapters | Ports = traits in the core/domain crate; adapters = separate crates implementing those traits for a concrete infra (OCI, filesystem, etc.) | Adapter `impl Trait for Type` must live in a crate that owns either the trait or the type (orphan rule) — usually forces adapter crates to depend on the domain crate, never vice versa | Domain crate defines its own error enum; adapters convert their infra errors into it at the boundary | Documented as a pattern (not by name) in wasmtime's env/cranelift split, and explicitly in Rust-specific hexagonal writeups | Orphan rule friction: wrapping/newtyping foreign types just to implement a local trait is common friction ([howtocodeit](https://www.howtocodeit.com/guides/master-hexagonal-architecture-in-rust), [barrage.net](https://www.barrage.net/blog/technology/how-to-apply-hexagonal-architecture-to-rust)) |
| DDD bounded context / vertical slice (crate per capability) | One crate per business capability, each with its own types+logic+tests, minimal shared vocabulary crate | Impls stay local to the slice's own crate; cross-slice calls go through a shared facade or event, not direct type sharing | Per-slice error type, no forced aggregation (slices are meant to be independent) | uv (resolver/installer/python-mgmt as near-independent capability crates), Deno (extension crates) | No first-hand Rust-specific "vertical slice" account found beyond .NET/frontend material — this pattern is DDD-native, not yet a named Rust convention; risk of crate-count explosion and duplicated vocabulary noted generically |
| Functional core / imperative shell | Core = pure crate, no I/O deps at all; shell = separate crate holding all HTTP/DB/OS calls, thin | Shell owns all trait impls that touch effects; core has nothing to implement against externally | Core returns plain `Result<T, DomainError>`; shell wraps with I/O error variants | Advocated generically ([ricofritzsche.me](https://ricofritzsche.me/applying-functional-core-and-imperative-shell-in-practice/)), not confirmed in a named large Rust project's architecture doc | Purely advisory source material; no production-scale Rust case study found — treat as a design lens applied *within* a layer, not a workspace-wide crate-split strategy on its own |
| API crate + impl crates ("facade + private deps") | One published/stable crate re-exports a curated surface; all others are `wasmtime-internal-*` / unpublished-contract crates | Impls freely live in internal crates since they're not consumer-facing; sealed-trait or `impl(crate)` (RFC 3323, in testing as of Aug 2026) used where internal traits must not be implemented externally | Internal crates: whatever's convenient; public crate: hides internal error types behind its own enum | wasmtime ([contributing-architecture.md](https://github.com/bytecodealliance/wasmtime/blob/main/docs/contributing-architecture.md)), cargo (`cargo-util` is explicitly "not intended for external use") | Safe/unsafe and API-stability boundaries between internal crates can still blur without discipline — wasmtime's own docs flag this as an "ongoing matter of improvement" |

## negative:

- No first-hand, named Rust production case study for "functional core / imperative shell" as a *crate-boundary* strategy (only generic/advisory posts) — treat as within-layer design guidance, not validated at workspace scale.
- No Rust-specific "vertical slice architecture" writeup found (all vertical-slice sources are .NET/frontend) — the DDD-bounded-context-as-crate mapping is inferred by analogy from uv/Deno's capability crates, not confirmed by anyone naming it that way.
- Could not confirm cargo-modules' current (2026) maintenance cadence directly — GitHub page didn't surface commit dates through WebFetch; 16 open issues and an active PR suggest it isn't abandoned, but this is not dated evidence to the ~18-month freshness bar.
- No wasmtime/rust-analyzer/etc. source explicitly used the terms "hexagonal," "ports and adapters," or "DDD bounded context" — the mapping in the styles table is this researcher's structural analogy, not the projects' own framing.

## leads:

- RFC 3323 (`impl(crate)` / restrictions) is in active call-for-testing as of August 2026 — worth re-checking stabilization status before committing to sealed-trait boilerplate as the long-term port-sealing mechanism.
- `cargo-hakari` / workspace-hack crates (from the same `guppy` toolchain) directly address the "many crates → duplicate feature-unification rebuilds" cost that a large split will hit; not asked for in the brief but load-bearing if the split goes ahead.
- GreptimeDB's `snafu`-based error design is the closest real precedent to "N crates, one coherent error story" and worth a deeper read if the decomposition proceeds past the research stage.
- Zed's `foo` / `foo_ui` / `foo_settings` naming convention is a concrete, low-cost pattern for keeping a 200+-crate workspace navigable, orthogonal to which architecture style is chosen.
