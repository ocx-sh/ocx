# Diff Integrity

You loaded this because you are checking what a change did to the
project's own safety net — independently of whether the code is correct.
The reading pass over the code itself is
[reviewing-a-diff.md](reviewing-a-diff.md).

## Why This Is Separate

Every dimension in [reviewing-a-diff.md](reviewing-a-diff.md) asks "is
this code right?". This one asks a different question: **did the change
make the gate green by fixing the code, or by weakening the gate?**

The distinction matters because the second is invisible to every other
check. A suppressed lint, a relaxed assertion, and a regenerated snapshot
all produce a green build. They are the shortest path from red to green,
which is exactly why an agent under pressure finds them — not from
malice, but because "make the check pass" and "make the code correct"
are different objectives and only one of them is directly observable.

A hit here is MUST-severity regardless of how good the rest of the diff
is, and it is reported even when the change is otherwise perfect.

## The Detectors

Run all nine. Each is cheap; the class each catches is not. Every hit is
labelled with the tag the table below explains.

```bash
D="origin/main..."
git diff "$D" -- '*.rs' | rg -nE '^\+.*#!?\[allow\('                    # allow
git diff "$D" -- '*.rs' | rg -nE '^-.*assert'                           # assert
git diff "$D" -- '*.rs' | rg -nE '^\+.*#\[ignore\]'                     # ignore
git diff "$D" -- '*.rs' | rg -nE -e '^\+.*todo!' -e '^\+.*unimplemented!' # stub
git diff "$D" | rg -nE '^\+.*unsafe '                                   # unsafe
git diff "$D" | rg -nE '^\+.*\.unwrap\(\)'                              # unwrap
git diff --name-only "$D" -- '*Taskfile*' '*Justfile*' .github/workflows \
  deny.toml clippy.toml 'rust-toolchain*'                               # gate
git diff --name-only "$D" -- '*.snap'                                   # snapshot
git diff --stat "$D" -- Cargo.lock                                      # lockfile
```

Each `rg` above reads a `git diff` on stdin deliberately — that is the one
case where omitting a path operand is correct. Anywhere else it silently
searches stdin, finds nothing, and reports a clean tree.

| Tag | Catches |
|---|---|
| `allow` | A lint silenced instead of fixed. Suppression is `#[expect(lint, reason = "…")]`, which fails the build once the lint stops firing; bare `#[allow]` rots silently (LINT-08) |
| `assert` | A deleted or weakened assertion. Every removed assert needs a stated reason (TEST-12) |
| `ignore` | A failing test parked instead of fixed |
| `stub` | A body that compiles clean and panics at runtime, sailing past the fast gate (LINT-05) |
| `unsafe` | New `unsafe`, which needs a `// SAFETY:` comment stating the invariant — and usually needs to not exist (LINT-07) |
| `unwrap` | New `unwrap` on a path that returns `Result` — the fastest way past a type error (ERR-09) |
| `gate` | The gate edited in the same change the gate was blocking. An agent cannot police the gate that constrains it |
| `snapshot` | A snapshot changed. Legitimate only when regenerated by the named command and the diff was read; never hand-edited |
| `lockfile` | A dependency bumped to dodge a build error, producing a green build against different code than was reviewed |

Two further checks that need the test files themselves:

- **Red-then-green ordering.** For a bug fix, the failing test must exist
  and fail *before* the fix. If the test and the fix arrive in one
  commit, you cannot tell whether the test ever constrained anything.
- **No test-file diff in a commit that turns red tests green**, outside
  an explicitly labelled spec-correction. Otherwise the specification was
  edited to match the implementation.

## Scope Creep

Separate from weakening, and nearly as expensive: the change did more
than it claimed.

```bash
git diff --name-only origin/main... .    # against the declared file set
git diff --shortstat origin/main... .    # against the stated task size
```

An unrelated refactor bundled into a bug fix is a finding: it inflates
the diff, and a large diff gets a fraction of the real scrutiny per line
that a small one does. The correct outcome is a split, not an apology.

Formatting-only churn across untouched files (a different `rustfmt`
version, an editor's trailing-whitespace pass) is the same problem
wearing a harmless costume — it buries the real change.

## Judging a Hit

Not every hit is a violation. For each one, ask in this order:

1. **Is it justified in the diff itself?** A `#[expect(…, reason = "…")]`
   with a real reason, a deleted assertion whose behaviour moved to a
   better test, a snapshot regenerated by the documented command with the
   diff reviewed — these pass. The justification must be in the change,
   not in a chat message.
2. **Did the underlying problem get fixed?** A suppression next to a fix
   is a judgment call. A suppression *instead of* a fix is a finding.
3. **Could the gate have caught the defect this suppression hides?** If
   yes, that is the report: name the defect the suppression conceals, not
   just the suppression.

Report a justified hit as a one-line note, not a finding. Report an
unjustified one as a blocker, quoting the line.
