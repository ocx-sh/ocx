# Flags, rc Files and Versions

Owns `BZL-FLAG`: every claim about a Bazel flag, command or version, and the
files that carry them — `.bazelversion`, the launcher that reads it, `.bazelrc`
and its imports, `PROJECT.scl`, a ruleset's declared floor, and the ordered
checklist for crossing a major boundary. It does not own what a flag *means*
once it is proven to exist: BZL-CACHE owns the remote-cache and credential
flags, BZL-HERM owns the action-environment and sandbox flags, BZL-MOD owns
lockfiles and the WORKSPACE-to-`MODULE.bazel` port, and BZL-LARK owns the
explicit `load()` that the autoload removal forces. This file owns their
existence, their default per version, and where their value is allowed to live.

8.7.0, 8.8.0 and 9.2.0 binaries, with tagged source read at 9.0.0 and 9.1.0
where only a deletion date was in question. On that date the LTS table read: 9
Active (9.2.0, ends Dec 2028), 8 Maintenance (8.8.0, ends Dec 2027), 7
Maintenance (7.7.1, ends Dec 2026), 6 Deprecated. Ruleset versions this file
binds to: aspect_rules_js 3.4.1, aspect_rules_ts 3.10.1, rules_python 2.3.3, rules_rust
0.74.0, rules_cc 0.2.22, aspect_rules_lint 2.9.0, rules_shell 0.8.0, protobuf
36.1.bcr.1. **Re-check a flag on both help surfaces — `bazel help <command>
--long` *and* `bazel help startup_options` — at your own pinned version before
citing it anywhere; a default measured here is a default at 8.7.0, 8.8.0 or
9.2.0 and nothing else.** Two standing caveats apply to every check below: a
grep sees only checked-in text, so BUILD and `.bzl` content a repository rule
or module extension *generates* as a string is out of its reach; and every
sandbox or cgroup measurement was taken on one Linux host with working
unprivileged user namespaces, so those rows are Linux-only findings.

## Reading the Flag Surface

The check for this whole block runs on the pinned binary, both surfaces, once
per Bazel version in the matrix — a flag can live in only one of them, and
`bazel help all --long` is not a command:

```bash
# wrong — prints "ERROR: 'all' is not a known command", which is not a miss
bazel help all --long | grep -- '--repo_contents_cache'
```

```bash
# right — both surfaces, and a miss on both is the stop signal
# (--repo_contents_cache only matches like this because it is a path flag;
# a boolean renders as --[no]<flag> and needs the plain-name or [no] form instead)
bazel help build --long    2>&1 | grep -- '--repo_contents_cache'
bazel help startup_options 2>&1 | grep -- '--repo_contents_cache'
```

| ID | Rule | Rationale | Verification | Severity |
|---|---|---|---|---|
| BZL-FLAG-11 | Prove every flag name exists on the pinned binary's two help surfaces before writing it into an rc file, a workflow, a doc or a generated config — including a flag copied from a community always-on list — and confirm that any PR cited for a flag's addition or removal actually merged. | 6 of the 8 `--incompatible_*`/`--no*` flags named by the widely-copied 2022 always-on blog post return zero hits today; Bazel hard-fails the whole invocation with `unrecognized option`, so one stale line breaks every command in the repository. Citations fail the same way one level up: two PRs cited in circulation for two flag removals are both closed with `mergedAt: null`. | `FLAG=incompatible_strict_action_env; bazel help build --long 2>&1 \| grep -i -e "$FLAG"` **and** `bazel help startup_options 2>&1 \| grep -i -e "$FLAG"`, per matrix leg (same commands on 8.7.0 and 9.2.0) — matching the bare name, not `--$FLAG`, because both surfaces render a boolean as `--[no]<flag>` and a leading-dash match returns zero hits for every one of them (`grep -E -e "--(\[no\])?$FLAG"` is the equivalent explicit form). EMPTY on both is not yet the stop signal by itself: run the decisive existence probe, `bazel build --nobuild --$FLAG //... 2>&1 \| grep 'Unrecognized option'` — a hit means the flag is genuinely absent on that version (now the stop signal), exit 0 with no hit means it parses and exists though undocumented on both surfaces. For a cited PR: `gh pr view <n> -R bazelbuild/bazel --json state,mergedAt` — `mergedAt: null` means the claim needs another source. | MUST |

| BZL-FLAG-13 | Never write or suggest `--enable_workspace` or `--enable_bzlmod` on a pin at 9.0 or later, and never describe either as a no-op there. | Both are live flags on 8.7.0 and 8.8.0 (`--enable_workspace` default `false`, `--enable_bzlmod` default `true`) — exactly the shape pre-2026 training data remembers and will confidently offer — and absent from *both* help surfaces at 9.2.0, so passing one fails the invocation with `unrecognized option`. The 9.0.0 notes' appendix calls them "now no-ops"; the binary disagrees and the binary wins. Re-derive on any pin with this section's two help commands; zero hits on both is the 9.2.0 result. | MUST |
| BZL-FLAG-14 | Never offer a non-empty `--incompatible_autoload_externally=<symbol-list>` as a way to keep Bazel-8 autoloads alive on a Bazel-9 pin; a symbol list is an 8-only migration aid. | Measured off the binaries: on 8.7.0 and 8.8.0 the flag defaults to the full moved-symbol allowlist, on 9.2.0 to `""`. The flag exists on all three — a default change, not a removal — so an 8-era value parses cleanly, restores nothing, and reads as a hallucinated workaround. It is a different flag from `--incompatible_disable_autoloads_in_main_repo` (boolean, main-repo scope, available since 8.2.0), and the names are close enough that "disable autoloading" produces either. | `grep -rn 'incompatible_autoload_externally=' .bazelrc* .github/` on a ≥9.0 pin — a non-empty value is the finding, EMPTY = pass. Confirm the value *shape* matches the flag intended: a comma-joined list belongs to this flag, a bare boolean to the other. | SHOULD |
| BZL-FLAG-26 | Delete an explicit rc value that already equals the default on **every** Bazel version in the matrix, or give it a comment naming the future default change it defends. | It protects nothing today and reads as meaningful tuning, so a reviewer cannot tell dead configuration from a deliberate defensive pin. The premise is measured: `--incompatible_disallow_empty_glob` defaults `true` on 8.7.0, 8.8.0 and 9.2.0 alike, so a line setting it is dead on every leg of a two-major matrix — and it is one of the lines a 2022-era always-on flag list copies forward. | Read the default off the **oldest** leg, not the dev pin: `bazel help build --long 2>&1 \| grep -A2 -- '--<flag>'` per leg, plus `bazel help startup_options` for a startup flag. A value equal to the default on every leg with no adjacent comment is the finding. EMPTY (the flag appears on neither surface on some leg) is BZL-FLAG-11's stop signal, not this row's finding. | CONSIDER |
| BZL-FLAG-34 | Re-derive a `--@<module>//<package>:<flag>` build setting's label and default from the pinned module version's own tagged source, and name that module version beside every citation of it. | Such a setting is versioned by the ruleset that defines it, not by Bazel, and `bazel help` cannot see it at all. A citation naming the flag with no module version attached is the finding. The grep does not reach a setting referenced only from generated `.bzl` text. | MUST |

## The Pin and the CI Matrix

Three commands catch this whole block: `cat .bazelversion`;
`grep -n 'rolling\|last_green' <CI config>`; and
`grep -n 'USE_BAZEL_VERSION' <workflow files> .bazeliskrc`. The launcher
resolves `USE_BAZEL_VERSION` *ahead of* `.bazelversion`, so the last command
decides which of the other two is actually in force.

| ID | Rule | Rationale | Verification | Severity |
|---|---|---|---|---|
| BZL-FLAG-01 | Pin `.bazelversion` to an exact three-component LTS semver. Never `rolling`, `last_green`, `last_rc`, `latest`, `latest-N`, a bare RC string, a floating `X.x`/`X.*`, or a commit hash — outside a deliberately disposable fixture directory that states the exemption in a comment beside it. | Every one of those resolves to a value that moves independently of any code change in the repository, which is the opposite of what a pinned build file is for; the rolling channel's own announcement warns that default behaviour may change with any rolling release. All of them are real, resolvable launcher values, which is what makes the mistake easy to make confidently. | `cat .bazelversion` must match `^[0-9]+\.[0-9]+\.[0-9]+$`. A **missing** file is equally the finding — the launcher then falls through to "the latest official release", unpinned by a different route. EMPTY output (an empty file) = finding. | MUST |
| BZL-FLAG-02 | Run `rolling` and `last_green` as non-blocking CI canaries only, with the non-blocking directive on the leg itself, and never as any repository's default pin. | No patch-backport promise exists for either channel and default behaviour can change on any rolling cut, so a rolling regression that blocks merges blocks them on a version nobody chose. | `grep -n 'rolling\|last_green' <CI config>`, then read that leg's failure-handling directive (`continue-on-error:` or the platform's equivalent). A rolling or last_green leg **without** one is the finding. EMPTY (no such leg exists) = pass by absence, not by configuration. | MUST |
| BZL-FLAG-03 | Never write a literal Bazel version into a workflow's `USE_BAZEL_VERSION` or into `.bazeliskrc` — only a matrix or env reference. | The launcher resolves `USE_BAZEL_VERSION` ahead of `.bazelversion`, so a hardcoded literal silently overrides every future bump of the committed file; the pin then lives in two places that can disagree with no error anywhere. | `grep -n 'USE_BAZEL_VERSION' <workflow files> .bazeliskrc 2>/dev/null` — a literal semver rather than a matrix or env expression, alongside a differing `.bazelversion`, is the finding. EMPTY = pass, the committed file is the single source. | MUST |
| BZL-FLAG-04 | Re-derive a pinned major's LTS stage and Support-Ends date from the live release page every time either is cited, and never state a fixed month count for how long a major stays Active — state "until the next major ships", and compute a duration from two consecutive majors' tagged release dates when one is needed. | The live table shifts on the roughly two-month Active-track minor cadence, so a citation ages within one minor release. The 2020 LTS announcement's "9 months" figure measures 12.0 and 13.4 months against the last two transitions (7.0.0 2023-12-11 → 8.0.0 2024-12-09 → 9.0.0 2026-01-20); the live page has dropped the fixed-duration framing, and the announcement has never been corrected at its own URL. | Fetch [bazel.build/release](https://bazel.build/release) and diff the pinned major's row against the value being cited; an EMPTY diff is the pass. For a duration, `gh api repos/bazelbuild/bazel/releases/tags/<N>.0.0 --jq .published_at` for two consecutive majors — a 404 on the newer tag means that major has not shipped, so do not extrapolate. | SHOULD |
| BZL-FLAG-05 | **pinned** — Carry dated guidance for a Maintenance major beside the Active major's only through that major's own published Support-Ends date; past it, collapse it to a footnote naming the version and what stopped being true. For Bazel 8 that is **through Dec 2027**. An adopter may override this once, in their own copy, never per rule. | Turns "we still cover Bazel 8" from an open-ended assumption into a checkable claim with an expiry a maintainer can act on. It presumes the ruleset is re-read at least once before the date arrives. | Reading heuristic — compare any "supports Bazel N" claim against the live release row for N. Once that row reads Deprecated the claim is already stale and the content should have converted. EMPTY (no such claim anywhere in the artifact) = the artifact is silently single-major, which is its own finding. | CONSIDER |

## Crossing 8 to 9

Every row here is caught by running the ordered checklist **before** the
`.bazelversion` edit, not after it. Each step is cheap relative to the one
after it, and a step-1 failure is pre-existing debt rather than a regression.
The checklist assumes a Bzlmod-only tree; a repository still carrying a live
WORKSPACE finishes that migration first (BZL-MOD). The incoming major's own
release notes are the flag list every step below reads — for 8→9 the 19
flipped flags, the WORKSPACE deletion and the "now no-ops" appendix all live in
the [9.0.0 notes](https://github.com/bazelbuild/bazel/releases/tag/9.0.0).

| ID | Rule | Rationale | Verification | Severity |
|---|---|---|---|---|
| BZL-FLAG-15 | **pinned** — Move a pin across a major boundary in this order, stopping at the first failure: (1) `bazelisk --strict build //... test //...` green on the **current** pin; (2) `BAZELISK_INCOMPATIBLE_FLAGS=<the incoming major's exact "flipped in X.0" list> bazelisk --migrate` on the current pin, fixing everything reported; (3) `buildifier --lint=fix -r -v .`, diff-reviewed; (4) confirm the ruleset floors the autoload migration needs *and* any minimum module version the incoming major enforces from its own side (Bazel 9 enforces protobuf ≥ 33.4); (5) `find . -iname 'WORKSPACE*'` empty; (6) grep for the permanent-flip traps — no canonical-repo-name parsing, no `native.local_repository`/`native.new_local_repository`; (7) grep docs, task files and CI for commands and enum values the incoming major deleted; (8) bump `.bazelversion` and regenerate `MODULE.bazel.lock` in the same commit; (9) add the new major as a real, blocking CI leg and keep the old major's leg live until its Support-Ends date; (10) re-read the flag list from that major's own release notes before reusing this checklist. | Skipping to step 8 is the default failure: the version file changes, CI goes red on a different machine, and the diagnosis starts from an error message rather than from a list. Step 7 exists because a major deletes commands and enum values as well as flags. Step 8's lockfile regeneration is not optional inside a major either — `bazel mod deps` writes `lockFileVersion` 24 on 8.7.0 and 28 on 8.8.0 and 9.2.0, so an 8.7.0 → 8.8.0 patch bump crosses the same schema boundary as the major move (BZL-MOD owns the lockfile). | The ten steps are the check. Step 1: an empty `--strict` report = clean start. Step 2: an empty `--migrate` report = every incoming flag already compatible. Step 3: a `git diff` showing only added `load()` lines and reordering is expected; any other semantic change is investigated, never auto-accepted. Steps 5, 6 and 7: EMPTY = pass. | MUST |
| BZL-FLAG-17 | Test an incoming major's flag flips on the **outgoing** pin before touching `.bazelversion`: run `bazelisk --strict` first as the one-build pass/fail signal, and reserve `bazelisk --migrate` (scoped with `BAZELISK_INCOMPATIBLE_FLAGS`) for isolating which flag broke it. | This is upstream's own stated mechanism — the 9.0.0 notes name `bazelisk --migrate` with `BAZELISK_INCOMPATIBLE_FLAGS` as the way to test the 9.0 flips on 8.x. Running `--migrate` cold burns N+1 builds to answer what `--strict` answers in one. | `BAZELISK_INCOMPATIBLE_FLAGS=<list> bazelisk --strict build //... ; echo $?` on the outgoing pin, then `--migrate` only on a non-zero status. An empty `--strict` report = every flag already compatible = pass. EMPTY in the other sense — no such invocation anywhere in CI or a task target — means the flips are untested, and the absence is the finding. | MUST |
| BZL-FLAG-12 | `find . -iname 'WORKSPACE*'` returns nothing on any repository pinned to 9.0.0 or later. A hit is a hard build break, not a deprecation warning. | 8.0.0 disabled the mechanism by default behind a real `--enable_workspace`; 9.0.0 removed all WORKSPACE logic from Bazel outright, so there is no code left for a flag to re-enable. | `find . -path ./.git -prune -o -iname 'WORKSPACE*' -print` — EMPTY = pass. Any hit on a ≥9.0 pin must be ported to `MODULE.bazel` before the bump; BZL-MOD owns the port and BZL-HERM owns rejecting a WORKSPACE reinstatement as a "fix". | MUST |
| BZL-FLAG-16 | A `.bazelversion` bump onto or past 9.0, in any repository declaring `cc_*`/`java_*`/`py_*`/`sh_*`/`proto_library` targets, carries a non-trivial BUILD/`.bzl` diff produced by `buildifier --lint=fix -r -v .` in that same commit — never a bare version-file edit. | Autoloading defaults to the empty string at 9.0, so every such symbol needs an explicit `load()` (BZL-LARK owns writing them). A repository with such targets and an empty BUILD diff on the bump commit has not migrated, it has broken. The breakage has **two** error shapes and only one names the fix: bare `py_library`, `sh_binary` and `proto_library` fail on 9.2.0 with `name 'X' is not defined` plus a *wrong* `did you mean` suggestion, while `cc_library` hits a purpose-built removed-rule stub that names `buildifier --lint=fix` outright. | `git show --stat <bump-commit>` cross-referenced against `grep -rln 'cc_\|java_\|py_\|proto_library\|sh_' --include='BUILD*' --include='*.bzl' .` on the pre-bump tree. An EMPTY grep legitimately gives an empty BUILD diff and is the pass; hits plus an empty BUILD diff is the finding. The grep sees only checked-in text, so a generator emitting a native rule name needs a separate read of the emitting `.bzl`. | MUST |
| BZL-FLAG-31 | Treat a major bump as removing **commands and enum values**, not only flags: before and after the bump, grep the repository's own docs, task files, CI and generated help text for every spelling the incoming major deleted, and re-derive each against the pinned binary. For 8→9 that is at minimum `bazel analyze-profile` (deleted at 9.0.0), `bazel dump --skyframe=working_set` / `working_set_frontier_deps` (renamed `active_directories` / `active_directories_frontier_deps` at 9.0.0) and `bazel sync --only=` (deleted at 9.0.0; the replacement is `bazel fetch --repo=@<repo>`). | Each is still advertised by a source a reader would reasonably trust: Bazel's own frozen 9.1.0 docs snapshot still lists `analyze-profile`, the live memory page still prints `--skyframe=working_set`, and a widely-used ruleset's current docs still print `bazel sync --only=`. A checklist that greps only for `--incompatible_*` names passes a repository whose tooling is already broken, and the failure surfaces as an unknown-command error in CI rather than at review time. | `grep -rn 'analyze-profile\|skyframe=working_set\|sync --only' --include='*.md' --include='*.yml' --include='*.yaml' --include='*.bzl' --include='BUILD*' --include='Taskfile*' .` — any hit on a ≥9.0 pin is the finding, EMPTY = pass. Then re-derive each surviving spelling on the pin: `bazel help <command>` (a deleted command answers `ERROR: '<name>' is not a known command`) and `bazel help dump --long \| grep -A5 skyframe` for the enum, which prints the 8.x spelling on 8.7.0/8.8.0 and the 9.x spelling on 9.2.0. A command spelled inside generated shell or `.bzl` text is outside this grep. | MUST |
| BZL-FLAG-09 | Never write migration guidance implying a newly flipped flag can be reverted with its `--no<flag>` form without first checking that same release's "now no-ops" appendix. | Confirmed twice: `--incompatible_use_plus_in_repo_names` (8.0) and `--incompatible_disable_native_repo_rules` (9.0) each appear in both the "flipped" list and the "now no-ops" appendix of the release that flipped them — the escape hatch is stripped in the same release that makes it necessary. | `gh api repos/bazelbuild/bazel/releases/tags/<major>.0.0 --jq '.body' \| grep -A30 'now no-ops'` and look for the flag. A hit means no revert path exists on that major and the guidance must say so. EMPTY (the flag is absent from the appendix) = a revert path exists there and may be described. | MUST |

## rc Files

Read the committed `.bazelrc` top to bottom — precedence is positional — then
confirm what actually loaded with
`bazel build --announce_rc //<target> 2>&1 | grep '^INFO: Reading rc'`, which
behaves identically on 8.7.0 and 9.2.0. The five-layer precedence chain and the
three import directives, `try-import-if-bazel-version` included, are specified
at [bazel.build/run/bazelrc](https://bazel.build/run/bazelrc). Options in an
imported file beat options appearing before the import line and lose to those
after it:

```
# wrong — every later line silently defeats the personal override
try-import %workspace%/.bazelrc.user
build --keep_going
```

```
# right — the import is the last non-comment line
build --keep_going
try-import %workspace%/.bazelrc.user
```

| ID | Rule | Rationale | Verification | Severity |
|---|---|---|---|---|
| BZL-FLAG-19 | The only mechanism for a personal override is a `try-import`ed, gitignored file imported as the **last** non-comment line of the committed `.bazelrc`; and any flag whose value is *executed*, or whose value is a *secret*, lives only in a file the repository does not ship — never merely one it ignores by convention. | Import position is part of the precedence contract, so a personal-override import placed anywhere but last is silently defeated. The execute/secret clause generalises the credential-helper case BZL-CACHE owns: a helper path from a committed rc is resolved and spawned with the client environment before the sandbox, on a plain `bazel query //...` of a fresh clone, and upstream closed that report as intended behaviour under Bazel's documented threat model — so the constraint does not loosen on a future version. | `tail -1 .bazelrc` must be the `try-import` line (or the last non-comment, non-blank line if a comment trailer follows), and `git check-ignore <the imported path>` must succeed. For the second clause, `git ls-files \| grep -E '\.bazelrc' \| xargs -r grep -n credential_helper` — any hit in a tracked file is the finding. EMPTY (including no `.bazelrc` files for `xargs` to search) = pass. | MUST |
| BZL-FLAG-20 | For every filename a `try-import` names, determine and write down beside that line which of two shapes CI has: (a) CI never creates the file, so developer content is never validated by CI, or (b) CI recreates the same path at runtime with a different, non-overlapping flag set. | The two look identical in the committed `.bazelrc` — one `try-import` line — and differ entirely in what a reviewer may assume. Shape (b) is the more dangerous, because a reviewer who sees a CI job writing that filename can wrongly infer that CI reads the developer's committed intent. `try-import`'s "try" controls only whether a *missing* file fails the invocation; it says nothing about divergence when the file is present. | Bind the imported filename to a variable using a concrete example, `.bazelrc.user`: `BASENAME=.bazelrc.user; grep -rn -e "$BASENAME" <CI workflow and action directories>` — no write anywhere = shape (a); a write whose flag set is disjoint from the developer file = shape (b). Cross-check the effective result with `--announce_rc` as above. The finding is the **missing note**, not either shape: an EMPTY comment beside the `try-import` line is the finding. | MUST |
| BZL-FLAG-21 | Version-gate a flag that does not exist, or whose default differs, across the matrix's Bazel majors with a mechanism — `try-import-if-bazel-version` at file level, or a generated preset's per-flag `if_bazel_version` predicate — never with a prose comment saying "remove this after upgrading". | A comment is not enforced: a matrix spanning two majors runs the wrong flag set on one leg the moment someone forgets the comment existed. The measured cross-major set for 8.7.0 / 8.8.0 / 9.2.0 is small and concrete: `--incompatible_strict_action_env` (false/false/**true**), `--incompatible_autoload_externally` (allowlist/allowlist/**empty**), `--repo_contents_cache` (off/off/**on**), `--enable_workspace` and `--enable_bzlmod` (present/present/**absent**), `--experimental_remote_merkle_tree_cache` and `--incompatible_remote_use_new_exit_code_for_lost_inputs` (present/present/**absent**, deleted at 9.0.0 — never "never existed"), `--experimental_remote_repo_contents_cache` (**absent**/startup-only/startup-only). | Bind the flag to a variable using a concrete example from that set: `FLAG=incompatible_strict_action_env; grep -n -e "$FLAG" .bazelrc*`, for any flag in that set, or any other flag BZL-FLAG-11 shows differing across the matrix, and confirm the line sits inside a version-scoped block. A major-dependent flag found bare in the shared rc file with a multi-major matrix present is the finding. EMPTY is not automatically a pass: an 8.x leg with no `--incompatible_strict_action_env` line inherits the client `PATH` and `LD_LIBRARY_PATH` that the 9.x leg does not, which is BZL-HERM's row on that flag. | MUST |
| BZL-FLAG-22 | A numeric tuning value in an rc file — a timeout, retry count, worker or parallelism count, memory limit — carries an adjacent comment stating why that number, or a citation to the versioned source it was copied from; and any such value is re-checked against the current pin before being copied into another repository. | A bare number cannot be told apart from a typo, a stale local value, or a deliberate choice. One measured instance sits 60× tighter than the community preset's own cited CI default, duplicated in two files, with nothing anywhere stating whether that is intentional. A flag whose *name* states its behaviour (`--test_output=errors`) needs no comment. | For every rc line whose value is a bare integer, confirm a comment on the same or preceding line, or a citation naming a source repository and version. An EMPTY comment above a numeric flag is the **finding**, regardless of what the number is. | MUST (new configuration) / SHOULD (retrofit) |

## Flags That Enforce Nothing

Two greps settle this whole block for most repositories:
`find . -name PROJECT.scl -not -path './.git/*'` and
`grep -rn 'sandbox_limits\|sandbox_memory_limit' .bazelrc* <CI directories>`.
EMPTY on both means nothing in this section can be active there — that is a
pass, not a gap. Every row is a guidance-accuracy rule: the flag is real, the
default is real, and the enforcement a reader infers from it is not.

| ID | Rule | Rationale | Verification | Severity |
|---|---|---|---|---|
| BZL-FLAG-32 | Never read `--enforce_project_configs`'s default-`true` as meaning project-config enforcement is active on a build, and never write guidance implying a Bazel-9 pin newly enforces project configs: the flag is inert until the nearest `PROJECT.scl` on the *target's own package path* declares a non-empty `configs`/`buildable_units`. | Measured from tagged source at 8.7.0, 8.8.0, 9.0.0, 9.1.0 and 9.2.0: the flag defaults `true` on all of them — so it is not a 9.0 flip at all — and the flag-set function returns an empty set immediately when the resolved file declares nothing, which is what keeps the default from breaking every build sitting near an unrelated `PROJECT.scl`. "A `PROJECT.scl` with no configs" and "no `PROJECT.scl` at all" are behaviourally identical. The flag's own help text ("interactive builds may only pass `--scl_config`…") reads alarming out of context and is the sentence an agent over-applies; both it and `--scl_config` are `UNDOCUMENTED` + `EXPERIMENTAL` and appear nowhere on the generated CLI reference. | `find . -name PROJECT.scl -not -path './.git/*'` — EMPTY means nothing on this axis can be active whatever the default says, which is the pass. Where a file exists, the only user-visible signal is an `INFO: Reading project settings from …` line in build output for a target whose innermost `PROJECT.scl` is populated; its absence means no enforcement is in effect for that target. | MUST |
| BZL-FLAG-33 | Never write `--config=<name>` inside a `PROJECT.scl` buildable unit's `flags` list when `<name>` is defined in any ordinary rc file — spell the flags out directly instead. Only a config traceable to Bazel's synthetic "client" source (the literal command line) or to an invocation policy is legal there. | Config expansion inside a buildable unit admits only a *global* rc file, and Bazel defines that set as exactly `client` plus `Invocation policy`, with an empty allowlist and the source comment "No global RC files in Bazel, so no global configs." A config defined in the system rc, the workspace `.bazelrc`, the user's home rc, a `--bazelrc=` file or a `try-import`ed file therefore fails at **analysis time**: "can't set `--config=ci` because its definition depends on `<path>/.bazelrc` which isn't a global rc file." Reusing an existing `build:ci` stanza is the obvious first move for an adopter, and it is the one move that cannot work. | For each `PROJECT.scl`, `grep -n -- '--config=' PROJECT.scl`; for every hit, bind the config name to a variable using a concrete example — `ci`: `NAME=ci; grep -rn -e "^[a-z]*:$NAME" .bazelrc*` — a hit in any committed or imported rc file is the finding. EMPTY on the first grep = pass, the unit spells its flags out. | MUST (once a repository adopts `PROJECT.scl`) |
| BZL-FLAG-35 | Never read `--incompatible_use_new_cgroup_implementation`'s default-`true` on Bazel 9 as meaning sandbox resource limits are enforced: without an explicit `--experimental_sandbox_limits` or `--experimental_sandbox_memory_limit_mb` the flag creates nothing, and *with* one, a host that denies a writable cgroup degrades silently to no limits and the build still exits 0. | Measured from tagged 9.2.0 source: the cgroup factory returns a null cgroup whenever no limits are requested, so such a build never touches `/sys/fs/cgroup` on either implementation or either major. When limits *are* requested, a non-writable mount is skipped with an INFO-level line and the I/O error is swallowed the same way — nothing throws, no WARNING appears in default build output, and the action runs unlimited. Two adjacent claims are also wrong: the flag supports cgroup **v1 and v2**, not v2 only, and under v2 the *parent* must be writable, not just the leaf. | `grep -rn 'sandbox_limits\|sandbox_memory_limit' .bazelrc* <CI directories>` — EMPTY means no limit was ever requested and the flag is inert for that repository, which is a pass. Where limits are requested: `bazel build --sandbox_debug --subcommands //<target> 2>&1 \| grep -- '-C '` and read the printed `linux-sandbox` invocation; a hit proves a cgroup was created and the limit is live. **EMPTY there is one-way**: it cannot separate "flag off", "no limits requested" and "cgroup creation failed silently", and no `bazel info` line or exit code distinguishes them. Linux only. | MUST |
| BZL-FLAG-24 | Never cite `--sandbox_default_allow_network=false` as a control over a repository-rule fetch — in a rule, a doc, a comment or a commit message. | The flag is tagged `execution` and reaches sandboxed build and test *actions*; `repository_ctx.download`/`.execute()` run in the loading phase, which has never been sandboxed — the 2019 feature request asking for exactly that (bazelbuild/bazel#7764) is still open. Measured default `true` on 8.7.0, 8.8.0 and 9.2.0, and measured to genuinely block when flipped under `linux-sandbox`: the flag works, just not on the phase the mis-citation aims at. An agent pattern-matching "sandbox" + "network" + "hermeticity" onto a repo-rule problem ships a flag that does nothing for the stated goal. | `grep -rn 'sandbox_default_allow_network' --include='*.bzl' --include='*.md' .` — any hit framing it as a fetch-time or repo-rule control is the finding, EMPTY = pass. Triage question: does the problem originate in a `repository_rule` implementation (loading phase, out of scope) or in `ctx.actions.run*` (execution phase, in scope)? Setting the flag at all is BZL-HERM's row; the block was measured on Linux only. | MUST |

## Ruleset Floors and Drift

The check for this block is where you read from: a ruleset's `MODULE.bazel`
**at the release tag**, its `.bazelci/presubmit.yml`, and a full release
listing — never a rendered doc page, a badge, or `releases/latest`.

| ID | Rule | Rationale | Verification | Severity |
|---|---|---|---|---|
| BZL-FLAG-27 | Read an absent `bazel_compatibility` in a ruleset's released `MODULE.bazel` as "undocumented", never as "no floor", and name which of three mechanisms a version-support claim rests on: the module's own `bazel_compatibility`, its CI presubmit matrix, or a minimum module version the Bazel major enforces from its own side. | Measured at the release tags: aspect_rules_js 3.4.1 and aspect_rules_lint 2.9.0 declare `>=7.6.0` and protobuf 36.1.bcr.1 declares `>=8.0.0` (first declared at BCR 35.0, absent at 33.4 and 34.x), while aspect_rules_ts 3.10.1, rules_python 2.3.3, rules_rust 0.74.0 and rules_cc 0.2.22 declare nothing at their release tag — yet each has a real floor recorded elsewhere: `minimum_bazel_version "7.4.1"` exactly for rules_rust, a `[7.x, 8.x, 9.x]` CI matrix for rules_python, a `7.x` leg for rules_cc, and, for aspect_rules_ts, a `>=7.7.0` its own `main` carries and its release does not. The third mechanism differs in kind: Bazel 9 enforces protobuf ≥ 33.4 by graph resolution, not by a self-declared range, and conflating the two misattributes who is enforcing what. | `grep -n bazel_compatibility MODULE.bazel` **at the release tag** — EMPTY = undeclared, not unrestricted. Then read `.bazelci/presubmit.yml` for the version matrix or a `minimum_bazel_version` anchor, and check the target major's own release notes for an enforced minimum module version. A support claim citing none of the three is the finding. | MUST (authoring adoption or upgrade guidance) / SHOULD (spot-checking a `bazel_dep` bump) |
| BZL-FLAG-28 | Never determine a ruleset's current version from a single `releases/latest` API call, a "Latest release" badge, or a remembered version string — list all non-prerelease releases and sort by semver. | Measured live on 2026-09-05: one widely-used ruleset's `releases/latest` returned a 2.x maintenance backport published two minutes *after* the actual current-major 3.4.1 the same morning. The API's "latest" is publish-timestamp order, not semver order, so any ruleset running parallel maintenance and current tracks defeats it. | `gh api repos/<org>/<repo>/releases --jq '.[] \| select(.prerelease==false) \| .tag_name'` piped through a semver sort, compared against what `releases/latest` returned; a mismatch is the tell that parallel tracks exist. An EMPTY release list (a ruleset that publishes only tags) = fall back to `gh api .../tags` and sort those, not a conclusion that there are no releases. | MUST |
| BZL-FLAG-29 | For a pre-1.0 (`0.y.z`) ruleset, run the "how many majors behind" comparison on the **second** version component. | Semver treats `y` as the breaking-change counter below 1.0, so `0.73 → 0.74` is a major bump. rules_rust 0.74.0 and rules_cc 0.2.22 are both pre-1.0 today, and a check written against the leading digit alone never fires for either — it silently tolerates an arbitrarily stale pin. This is a check-correctness bug, not a policy preference. | Before diffing a pinned `bazel_dep` version against current, test whether the current release's leading component is `0`; if so, diff the second component under the same one-behind threshold. Two or more behind = hard finding; exactly one behind = tracked item. EMPTY (the versions are equal) = pass. | MUST |

## Gaps

- Every sandbox and cgroup measurement here is one Linux host with working
  unprivileged user namespaces; darwin and Windows behaviour is unmeasured.
- Whether a hosted CI runner or a plain container grants a writable cgroup
  subtree is unmeasured, so BZL-FLAG-35's EMPTY stays one-way.
- The exact 9.x minor that removed `--enable_workspace`/`--enable_bzlmod` from
  the help surfaces is unmeasured; both are absent at 9.2.0.
- `--enforce_project_configs` and `--scl_config` are `UNDOCUMENTED` +
  `EXPERIMENTAL`: their behaviour may change inside a minor with no notes line.
- No shipped ruleset consumes `PROJECT.scl` as of 2026-09-06, so BZL-FLAG-32/33
  are documented rather than exercised in a live dependency.

## What Agents Get Wrong Here

1. **Copying a memorised or blog-sourced flag list into a new `.bazelrc`** —
   6 of 8 flags in the canonical 2022 always-on post are gone, and Bazel
   hard-fails the invocation rather than ignoring them (BZL-FLAG-11).
2. **Running `bazel help all --long`, or checking one surface only**, then
   reporting the error or the miss as "the flag does not exist" — both invert
   the answer, and an `UNDOCUMENTED` flag is real (BZL-FLAG-11).
3. **Treating `rolling`, `last_green` or `latest` as a stable pin** because the
   name sounds current; all three are real, resolvable values (BZL-FLAG-01).
4. **Offering `--enable_workspace` as a way to bring WORKSPACE back**, or
   calling it a harmless no-op, on a Bazel-9 pin (BZL-FLAG-13).
5. **Citing `bazel analyze-profile` or `dump --skyframe=working_set` on a 9
   pin** — deleted and renamed at 9.0.0, and both still printed by sources a
   reader trusts (BZL-FLAG-31).
6. **Reading `--enforce_project_configs=true` as live enforcement or as a
   Bazel-9 change** (BZL-FLAG-32), and assuming the new cgroup implementation
   turns sandbox limits on (BZL-FLAG-35).
7. **Recommending `--sandbox_default_allow_network=false` for a non-hermetic
   repository-rule fetch** — the wrong build phase entirely (BZL-FLAG-24).
8. **Trusting `releases/latest` for a ruleset's current version**
   (BZL-FLAG-28), or reading an undeclared `bazel_compatibility` as "works on
   any Bazel" (BZL-FLAG-27).
