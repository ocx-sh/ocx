# Lazy Package Loading (Shims) — Manual Exploration

A tool composed with `--lazy-mode always` reaches `PATH` as a generated
launcher — a **shim** — and its content downloads the first time one of its
names actually runs. This document walks the full state machine from both
sides: the **consumer** (compose, run, uninstall, clean) and the
**maintainer** (what a shim tree contains, what refuses, what only warns).

Every command below was captured from a real run against the local
registry. All paths assume the repo root.

## Prerequisites

1. Start the local registry:
   ```sh
   cd test && docker compose up -d
   ```
   (Port 5000 already taken? See "Acceptance tests" in
   [`CONTRIBUTING.md`](../../CONTRIBUTING.md) — export `OCX_TEST_REGISTRY_PORT`
   and `env.sh` follows.)
2. Build the binary the rig will use:
   ```sh
   cargo build --release -p ocx
   ```
3. Point the shell at the local registry and a disposable `OCX_HOME`:
   ```sh
   source test/manual/scripts/env.sh
   ```
4. Publish the packages:
   ```sh
   test/manual/scripts/bootstrap.sh
   ```

For the ad-hoc calls below:

```sh
export OCX=./target/release/ocx
```

### One knob that is easy to miss

A generated shim re-enters ocx as `${OCX_BINARY_PIN:-ocx}`. With no pin it
resolves `ocx` **off `PATH`** — on a developer machine, usually the *released*
ocx. A released build that predates this feature answers:

```
error: unrecognized subcommand 'shim'
```

and exits 64. When testing a local build, pin it:

```sh
export OCX_BINARY_PIN="$PWD/target/release/ocx"
```

## Guided tour

```sh
test/manual/scripts/show-shims.sh
```

Runs every section below in a throwaway `OCX_HOME` and **asserts** each
contract — including the negatives ("no content directory exists yet", "no
candidate symlink was created"). A silent run is a passing run; any violated
contract exits non-zero naming the contract. Pass `--keep` to keep the
directory for poking at afterwards.

## Use-Case 1 — Names on `PATH` before any content exists

**Goal**: a tool is usable-looking immediately; nothing downloads until it runs.

```sh
$OCX package env --lazy-mode always dojo/multi-entry-toolkit:1.0.0
```

```
Key   Type  Value
PATH  path  $OCX_HOME/shims/localhost_5010/dojo/multi-entry-toolkit/sha256/5b/83863951f8184294f0b5daf6697c9e/bin
PATH  path  $OCX_HOME/packages/localhost_5010/sha256/5b/83863951f8184294f0b5daf6697c9e/content/bin
PATH  path  $OCX_HOME/packages/localhost_5010/sha256/5b/83863951f8184294f0b5daf6697c9e/entrypoints
4 binaries available (tool-a, tool-b, tool-c, ...); 4 entrypoints available (tool-a, tool-b, tool-c, ...)
```

Three `PATH` entries, and **two of them do not exist yet** — the `packages/`
directory is absent entirely at this point. That is deliberate: the shim
directory is emitted *first*, so it wins the lookup now, and the package
directories are already in place for after materialization. A nonexistent
directory on `PATH` costs nothing.

The tree ocx wrote:

```
$OCX_HOME/shims/localhost_5010/dojo/multi-entry-toolkit/sha256/5b/83863951f8184294f0b5daf6697c9e/
├── bin/
│   ├── tool-a
│   ├── tool-b
│   ├── tool-c
│   └── tool-d
├── digest
└── refs/blobs/sha256_cac262b29340bdce2182caa36ea85949
```

Note the shape, and how it differs from `packages/`:

- **The repository is in the path** (`dojo/multi-entry-toolkit`), unlike
  `packages/`, which keys on registry + digest alone for cross-repo dedup. A
  shim body names a pinned identifier and that identifier carries the
  repository.
- **Launchers nest under `bin/`**, never at the tree root — `binaries =
  ["digest", "refs"]` is a legal claim, and flat launchers would overwrite the
  CAS marker.
- `bin/` is written **last**, by one atomic rename: its presence is the
  completeness marker, so a reader never sees a half-built tree.

One launcher, in full:

```sh
cat "$OCX_HOME/shims/.../bin/tool-a"
```

```sh
#!/bin/sh
# Generated by ocx at install time. Do not edit.
exec "${OCX_BINARY_PIN:-ocx}" launcher shim 'localhost:5010/dojo/multi-entry-toolkit:1.0.0@sha256:5b83863951f8184294f0b5daf6697c9e74d2fd6b1d0c6a48a95df65a9cbb9bb6' -- "$(basename "$0")" "$@"
```

Everything the materialization needs is baked in: the **pinned digest** (so the
download is addressed by content, never by tag) and `$(basename "$0")` (so the
same body serves every name, and the invoked name selects the entry point).

## Use-Case 2 — First use materializes, second use is quiet

```sh
PATH="$OCX_HOME/shims/.../bin:$PATH" tool-a
```

```
INFO Package 'localhost:5010/dojo/multi-entry-toolkit:1.0.0@sha256:5b8386...' not found locally, pulling.
INFO Downloading layer sha256:be44389c61cd to $OCX_HOME/temp/847ff69339066405153331e90eb1841d
multi-entry-toolkit: tool-a
```

```sh
PATH="$OCX_HOME/shims/.../bin:$PATH" tool-b
```

```
multi-entry-toolkit: tool-b
```

Three things to check afterwards, each easy to assume and wrong to assume:

| Check | Result |
|---|---|
| `packages/.../content/bin` exists | yes — the content is now materialized |
| the shim tree still exists | **yes** — materialization does not consume it |
| `symlinks/` has a candidate | **no** — first use is *not* an install |

The shim surviving is what makes the next compose stable: it emits the same
slot whether or not the content happens to be cached. The absent candidate
symlink is why `ocx package uninstall` on such a tool reports `absent` and
exits 0 rather than warning — there was never anything to remove.

### Progress on that first download

The generated shim carries a `--lazy-report` value chosen at **compose** time,
resolved from `ocx.toml` (package entry ▸ group ▸ top-level `lazy-report`) then
`OCX_LAZY_REPORT`, floor `silent`. `progress` renders on the controlling
terminal and **degrades to silent** where no terminal is reachable — a
container build, a CI runner, anything detached — rather than failing. Errors
go to stderr either way.

## Use-Case 3 — A dependency closure defers as ONE tree

```sh
$OCX package env --lazy-mode always dojo/deps-app:1.0.0
ls "$OCX_HOME/shims/localhost_5010/dojo/deps-app/sha256/94/.../bin"
```

```
app  leaf-a  mid
```

`deps-app` depends on `mid` (interface) which depends on `leaf-a` (interface);
`leaf-b` is a **private** dependency. The root's shim tree carries launchers for
the whole *interface surface* — its own name plus every name that crosses to a
consumer — and `leaf-b` is absent. Dependencies get **no shim tree of their
own**: two composed roots produce exactly two trees.

This is not a parallel rule invented for shims. The name set comes from the same
surface algebra `ocx env` and `ocx package inspect --closure` use, so the shim
surface cannot disagree with the composed surface.

## Use-Case 4 — Advisories warn, they never decide

```sh
$OCX --format json package env --lazy-mode always dojo/single-layer-hello:1.0.0 | jq '.advisories'
```

```json
[
  {
    "kind": "install-path-rooted-non-path-var",
    "package": "localhost:5010/dojo/single-layer-hello:1.0.0@sha256:1d6d3051...",
    "key": "HELLO_HOME",
    "message": "'HELLO_HOME' interpolates ${installPath} in a non-path variable; its value will not resolve until the package materializes"
  }
]
```

`HELLO_HOME` points into a content directory that does not exist yet, so a
consumer reading it before first use sees a dangling path. Three kinds exist:

| Kind | Fires when |
|---|---|
| `undeclared-binaries` | the package makes no `binaries` claim at all (`None`, not `[]`) — the name set had to be inferred |
| `install-path-rooted-non-path-var` | a `constant`/`list` value interpolates `${installPath}` |
| `combined-path-value` | a `path` value concatenates a package-rooted segment with something else |

**Nothing downstream steers on an advisory.** The compose above succeeded and
the shim was written. Advisories are also computed *only* for a deferred tool:
the same package composed with `--lazy-mode never` reports none, because an
eagerly composed tool has nothing to defer.

## Use-Case 5 — What lazy loading refuses

```sh
$OCX package env --self --lazy-mode always dojo/multi-entry-toolkit:1.0.0
```

```
ERROR --self and --lazy-mode always ask for contradictory things: a shim is a
consumer-facing launcher, and --self selects the private view that bypasses
launchers
```

Exit **64**. Three more refusals, all at compose time so a broken shim is never
written:

| Refusal | Cause |
|---|---|
| names not enumerable | a node in the closure claims neither `binaries` nor entry points — there is nothing to put on `PATH` |
| name shadows `ocx` | a claimed name is literally `ocx`; its shim would re-invoke itself through the `${OCX_BINARY_PIN:-ocx}` fallback |
| invalid name | an entry-point name that is not a valid binary name |

## Use-Case 6 — add / remove / re-add

The sequence worth exercising by hand, because each step leaves a different
intermediate state:

```sh
# 1. deferred compose            → shim, no content
$OCX package env --lazy-mode always dojo/multi-entry-toolkit:1.0.0

# 2. first use                   → shim + content
PATH="$OCX_HOME/shims/.../bin:$PATH" tool-a

# 3. uninstall                   → "absent", exit 0 (no candidate ever existed)
$OCX package uninstall dojo/multi-entry-toolkit:1.0.0

# 4. clean --force               → collects blobs, layers, packages AND shims
$OCX clean --force

# 5. recompose                   → regenerated at the IDENTICAL path
$OCX package env --lazy-mode always dojo/multi-entry-toolkit:1.0.0
```

Step 4's output names the shim trees explicitly:

```
object  $OCX_HOME/packages/localhost_5010/sha256/5b/83863951f8184294f0b5daf6697c9e
object  $OCX_HOME/shims/localhost_5010/dojo/deps-app/sha256/94/b74da506c6dc1edcf797a2af571e06
object  $OCX_HOME/shims/localhost_5010/dojo/multi-entry-toolkit/sha256/5b/83863951f8184294f0b5daf6697c9e
object  $OCX_HOME/shims/localhost_5010/dojo/single-layer-hello/sha256/1d/6d30515b2fe4eedecaec75d8401903
```

A shim is GC'd like anything else — but it is rooted **directly in the lock
pins**, not reachable from a package, because a shim exists exactly when the
package directory does not. `--force` drops those roots and collects it; the
next compose regenerates it at the same path, with the same launchers, because
the tree is derived from the pinned digest rather than from any local state.

Step 5 regenerating identically is the property to check by hand: it is what
makes `ocx env` byte-stable regardless of cache state.

## Use-Case 7 — Patches and integrations under a deferred compose

The question this section answers: **does a patched package still get its
companions when it is composed as a shim?**

Set the patch rig up first (`test/manual/scripts/setup-patches.sh`, which also
installs the bases so companions are discovered), then compose the same base
both ways:

> **The patch rig writes to the registry's reserved global slot.** Its global
> descriptor matches `*`, so it attaches a companion to *every* base in that
> registry — including the ones `test/tests/test_patches.py` publishes. Running
> the acceptance suite against the same registry afterwards fails the
> `@patch_global_slot` tests with the manual rig's companion value. Recreate the
> containers (`docker compose down && docker compose up -d`) before the next
> `task test`; `teardown-patches.sh` does not clear the slot.

```sh
$OCX --format json package env --lazy-mode never  patches/base-tool:1.0.0
$OCX --format json package env --lazy-mode always patches/base-tool:1.0.0
```

| | `never` | `always` |
|---|---|---|
| env keys | `NODE_EXTRA_CA_CERTS`, `PATH`, `REQUESTS_CA_BUNDLE`, `SSL_CERT_FILE`, `TOOL_HOME` | **identical** |
| `integrations` | `com.microsoft.vscode` ← `corp-ca-bundle:1.0.0` | **identical** |
| `advisories` | `[]` | `undeclared-binaries`, `install-path-rooted-non-path-var` |

Three of those env keys (`SSL_CERT_FILE`, `NODE_EXTRA_CA_CERTS`,
`REQUESTS_CA_BUNDLE`) come from the `corp-ca-bundle` companion the global
descriptor attaches, and the `integrations` row is the companion's too. Both
cross into a deferred compose exactly as they cross into an eager one — the
companion overlay runs on the composed surface, which is the same surface
either way. Only `advisories` differ, and only because an eagerly composed tool
has nothing to defer.

The companion does **not** get a shim tree of its own, and its content is not
downloaded by the compose:

```sh
find "$OCX_HOME/shims" -name bin -type d
```

```
$OCX_HOME/shims/localhost_5010/patches/base-tool/sha256/87/1d745c36ffafc839c836ad623b0f27/bin
```

One tree, for the base. A companion contributes env vars and integrations, not
`PATH`-shaped claims — so there is nothing for it to launch.

### The asymmetry that is NOT about shims

Composing a patched base in a **cold** `OCX_HOME` (config present, nothing
installed) yields no companion contributions at all:

```
cold home, --lazy-mode never  : ['PATH', 'TOOL_HOME']  integrations: 0
cold home, --lazy-mode always : ['PATH', 'TOOL_HOME']  integrations: 0
```

Identical in both modes. Companion **discovery** is an install-time step
(`ocx package install` records the pins); `package env` composes what is
already pinned. Worth knowing before reading a thin deferred compose as a lazy-
loading bug — check whether the base was ever installed first.

The manual rig is for exploring shapes; the durable coverage lives in
