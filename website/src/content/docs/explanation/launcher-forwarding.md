This page explains how a generated launcher embeds its package root and how a running `ocx` forwards its configuration to every `ocx` it spawns.

## Launcher Embedding {#launcher-embedding}

`ocx package install` generates a launcher for each of a package's declared [entrypoints][entry-points]. Each launcher delegates to the internal `ocx launcher exec` subcommand, with the package-root path baked in at install time.

Unix (POSIX sh):

```sh
#!/bin/sh
# Generated by ocx at install time. Do not edit.
exec "${OCX_BINARY_PIN:-ocx}" launcher exec '/home/alice/.ocx/packages/ocx.sh/sha256/ab/c123…' -- "${0##*/}" "$@"
```

Windows (native `.exe` shim + `.shim` sidecar):

```text
# entrypoints/cmake.shim — one UTF-8 line, the absolute package root
C:\Users\alice\.ocx\packages\ocx.sh\sha256\ab\c123…
```

The companion `cmake.exe` is a compiled shim. It derives its entry-point name from its own filename and reads `cmake.shim` for the package root. It then spawns `ocx launcher exec "<pkg-root>" -- "cmake" <args…>` directly through `CreateProcessW` — never `cmd.exe`.

`ocx launcher exec` forces the self view internally — no flag needs to be baked into the launcher. The stable wire ABI is the `launcher exec` subcommand name pair and positional shape.

See the [Entry Points][entry-points] in-depth page for the full launcher generation pipeline, character rejection rules, and cross-platform launcher behavior.

## OCX Configuration Forwarding {#ocx-forwarding}

Two variables cross into every `ocx` descendant. [`__OCX_ENV_STATE`][env-ocx-env-state] is the ocx-only state: a versioned value with a plaintext header and a compressed payload. [`OCX_BINARY_PIN`][env-ocx-binary-pin] names the binary that child runs. Together they keep configuration coherent across a chain. One example is [`ocx package exec`][cmd-package-exec] running a tool that invokes a generated [entrypoint launcher][entry-points]. That launcher re-enters ocx.

| Carrier | Content | Purpose |
|---|---|---|
| [`OCX_BINARY_PIN`][env-ocx-binary-pin] | The stable install path when the running ocx is the installed one, else the running binary | Pins the inner ocx to a binary that survives an update of the one that installed the package |
| [`__OCX_ENV_STATE`][env-ocx-env-state] | Header: narrowing policy (`n=offline`, `n=frozen`, ...) and the home (`h=`). Payload: applied values, received policy, session selection | Child ocx stays offline or frozen if the outer was, and resolves the same home |

The root flags `--config`, `--remote`, `--offline`, `--frozen` and `--index` reach children through the state. `--no-consent` reaches them as a narrowing. Subcommand flags such as `--no-verify` never do.

The resolved `[mirrors]`, `[patches]`, `[managed]`, `[records]` and toolchain-root settings travel the same way. A launcher re-entry takes no flags of its own. It sees the same mirror map, companion overlay and records sink as the invocation that started it.

An unreadable state, whether from another major version or garbled, is never an error. Its header still narrows, so an offline invocation stays offline, and ocx prints one warning.

The running ocx's parsed flags are authoritative. They overwrite what the inherited state says, so a stale exported `OCX_OFFLINE=1` cannot override an outer `ocx` invoked without `--offline`. Under `--clean` the child environment starts empty and the state is written afresh from the outer ocx's parsed settings. No ambient shell export can bypass this.

Some settings have no command-line flag: [`OCX_DEFAULT_REGISTRY`][env-ocx-default-registry], [`OCX_INSECURE_REGISTRIES`][env-ocx-insecure-registries], [`OCX_ALLOW_YANKED`][env-ocx-allow-yanked], [`OCX_NO_PROJECT`][env-ocx-no-project], [`OCX_NO_CONFIG_REFRESH`][env-ocx-no-config-refresh] and [`OCX_NO_UPDATE_CHECK`][env-ocx-no-update-check]. The child reads them from the environment it inherits. Two of them also have a config counterpart: `OCX_DEFAULT_REGISTRY` overlays `[registry] default`, and `OCX_INSECURE_REGISTRIES` unions with `[registries.<name>] insecure`.

:::caution[Presentation flags do not propagate]
`--log-level`, `--format`, and `--color` are outer-presentation choices and never flow into a child ocx via env. This ensures that running `cmake --version` through a launcher produces only cmake's output, not ocx logs.
:::

Some variables are deliberately outside what travels. [`OCX_LAZY_MODE`][env-ocx-lazy-mode], [`OCX_LAZY_REPORT`][env-ocx-lazy-report] and the three toolchain settings [`OCX_TOOLCHAIN_ACTIVATE`][env-ocx-toolchain-activate], [`OCX_TOOLCHAIN_PINNED`][env-ocx-toolchain-pinned] and [`OCX_TOOLCHAIN_UPDATE`][env-ocx-toolchain-update] change *when* or *how* content reaches `PATH`. They never change *which* digest resolves, so a child reads its own environment. The same holds for [`OCX_SELF_UPDATE`][env-ocx-self-update], [`OCX_UPDATE_CHECK_INTERVAL`][env-ocx-update-check-interval], [`OCX_CEILING_PATH`][env-ocx-ceiling-path] and [`OCX_SIGSTORE_TRUSTED_ROOT`][env-ocx-sigstore-trusted-root]. [`OCX_PROJECT`][env-ocx-project] selects per invocation and is never forwarded. A tool started under `ocx --project <file> exec` discovers its own project, and can pass `--project` or `--global` to a nested ocx without a conflict.

Four credentials are scrubbed from every child, plugins (`ocx-<name>`) included: `OCX_IDENTITY_TOKEN`, `OCX_KEY_PASSWORD`, `OCX_SIGNING_KEY` and `OCX_ANNOUNCE_GIT_TOKEN`. The registry tokens `OCX_AUTH_<REGISTRY>_TOKEN` are not scrubbed. A child inherits them unchanged under the default and `--isolate` modes, and under `--clean` they are absent. Launcher children re-enter via `ocx launcher exec` using a local package root rather than a registry, so they never need credentials. The runner variables that `--ci` and `--ci-annotations` read are not forwarded either, because the CI sink files are runner-managed paths.

Execution records carry the composition mode of the invocation as `envMode`. [Execution records][execution-records] covers it.
