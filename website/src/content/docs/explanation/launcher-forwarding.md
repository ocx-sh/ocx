This page explains how a generated launcher embeds its package root and how a running `ocx` forwards its configuration to every `ocx` it spawns.

## Launcher Embedding \{#launcher-embedding\}

When `ocx package install` generates launchers for a package's declared [entrypoints][entry-points], each launcher delegates to the internal `ocx launcher exec` subcommand with the package-root path baked at install time.

Unix (POSIX sh):

```sh
#!/bin/sh
# Generated by ocx at install time. Do not edit.
exec "${OCX_BINARY_PIN:-ocx}" launcher exec '/home/alice/.ocx/packages/ocx.sh/sha256/ab/c123…' -- "${0##*/}" "$@"
```

Windows (native `.exe` shim + `.shim` sidecar):

```text
# entrypoints/cmake.shim — one UTF-8 line, the absolute package root
C:\Users\alice\.ocx\packages\ocx.sh\sha256\ab\c123…
```

The companion `cmake.exe` is a compiled shim. It derives its entry-point name from its own filename and reads `cmake.shim` for the package root. It then spawns `ocx launcher exec "<pkg-root>" -- "cmake" <args…>` directly through `CreateProcessW` — never `cmd.exe`.

`ocx launcher exec` forces the self view internally — no flag needs to be baked into the launcher. The stable wire ABI is the `launcher exec` subcommand name pair and positional shape.

See the [Entry Points][entry-points] in-depth page for the full launcher generation pipeline, character rejection rules, and cross-platform launcher behavior.

## OCX Configuration Forwarding \{#ocx-forwarding\}

Whenever ocx spawns a subprocess, it materializes the running ocx's resolution-affecting policy as `OCX_*` env vars on the child. The most common case is the child process under [`ocx package exec`][cmd-package-exec], which may itself invoke a generated [entrypoint launcher][entry-points] that re-shells back into ocx. This is the chokepoint that keeps configuration coherent across the chain.

| Variable | Source | Purpose |
|---|---|---|
| [`OCX_BINARY_PIN`][env-ocx-binary-pin] | Resolved path of the running ocx executable | Pins the inner ocx to the same binary that installed the package |
| [`OCX_HOME`][env-ocx-home] | `crate::home::default_ocx_root()` — the outer ocx's own resolved data root | Set-always, even under `--clean`: a child that strips ambient state still resolves the same object store, not `~/.ocx` from the passwd database |
| [`OCX_OFFLINE`][env-ocx-offline] | `--offline` flag on the outer invocation | Child ocx stays offline if outer was offline |
| [`OCX_FROZEN`][env-ocx-frozen] | `--frozen` flag on the outer invocation | Child ocx stays frozen if outer was frozen |
| [`OCX_REMOTE`][env-ocx-remote] | `--remote` flag on the outer invocation | Child ocx uses the remote index if outer did |
| [`OCX_CONFIG`][env-ocx-config] | `--config` flag on the outer invocation | Child ocx loads the same explicit config file |
| [`OCX_INDEX`][env-ocx-index] | `--index` flag on the outer invocation | Child ocx reads the same local index directory |
| [`OCX_GLOBAL`][env-ocx-global] | `--global` flag on the outer invocation | Child ocx selects the same tier |
| [`OCX_PROJECT`][env-ocx-project] | `--project` flag on the outer invocation | Child ocx loads the same project file |
| [`OCX_NO_CONFIG`][env-ocx-no-config] | Hermetic outer invocation | A hermetic parent's child does not re-read the full config chain |
| [`OCX_MIRRORS`][env-ocx-mirrors], [`OCX_PATCHES`][env-ocx-patches], [`OCX_PATCH_SNAPSHOT`][env-ocx-patch-snapshot] | The resolved `[mirrors]` and `[patches]` tiers, and the active snapshot | Child ocx sees the same mirror map, companion overlay and frozen companion digests |
| [`OCX_MANAGED_CONFIG`][env-ocx-managed-config] | The resolved `[managed]` source | Child ocx resolves the same managed tier |
| [`OCX_RECORDS_DIR`][env-ocx-records-dir], [`OCX_RECORDS_NAME`][env-ocx-records-name] | The resolved `[records]` sink | A launcher re-entry, which takes no flags of its own, writes to the same sink |
| [`OCX_TOOLCHAIN_DIR`][env-ocx-toolchain-dir] | The resolved toolchain root | Every composed path moves with it, so the child must agree; with no root, an inherited value is removed |
| [`OCX_NO_VERIFY`][env-ocx-no-verify], [`OCX_NO_CONSENT`][env-ocx-no-consent] | The flag or the ambient variable | A launcher-spawned child install keeps the CI-wide verification and stamp decisions, across `--clean` too |

Six more settings are read from the environment with no command-line flag behind them: [`OCX_DEFAULT_REGISTRY`][env-ocx-default-registry], [`OCX_INSECURE_REGISTRIES`][env-ocx-insecure-registries], [`OCX_ALLOW_YANKED`][env-ocx-allow-yanked], [`OCX_NO_PROJECT`][env-ocx-no-project], [`OCX_NO_CONFIG_REFRESH`][env-ocx-no-config-refresh] and [`OCX_NO_UPDATE_CHECK`][env-ocx-no-update-check]. Two of them also have a config counterpart: `OCX_DEFAULT_REGISTRY` overlays `[registry] default`, and `OCX_INSECURE_REGISTRIES` unions with `[registries.<name>] insecure`.

They are forwarded as the invocation itself read them. A `--clean` child starts from an empty environment, so this keeps it from falling back to defaults the parent overrode. An empty value clears an inherited setting rather than travelling onward. `OCX_NO_PROJECT` is withheld when the invocation also carries an explicit `--project`, because a child reads the prune before the path. [`OCX_ENV`][env-ocx-env] is always cleared first and then written from the composed project and group `[env]` entries plus any `--env` override; [`OCX_LAUNCH_IDENTITIES`][env-ocx-launch-identities] is covered under [execution records][execution-records].

The running ocx's parsed flags are authoritative. They overwrite any inherited value from the parent shell, so a stale exported `OCX_OFFLINE=1` cannot override an outer `ocx` invoked without `--offline`. The same rule holds under [`ocx package exec --clean`][cmd-package-exec]: the child env starts empty, then `OCX_*` keys are written explicitly from the outer ocx's parsed state. No ambient shell export can bypass this.

:::caution[Presentation flags do not propagate]
`--log-level`, `--format`, and `--color` are outer-presentation choices and never flow into a child ocx via env. This ensures that running `cmake --version` through a launcher produces only cmake's output, not ocx logs.
:::

Some variables are deliberately outside the forwarded set. [`OCX_LAZY_MODE`][env-ocx-lazy-mode], [`OCX_LAZY_REPORT`][env-ocx-lazy-report] and the three toolchain settings [`OCX_TOOLCHAIN_ACTIVATE`][env-ocx-toolchain-activate], [`OCX_TOOLCHAIN_PINNED`][env-ocx-toolchain-pinned] and [`OCX_TOOLCHAIN_UPDATE`][env-ocx-toolchain-update] change *when* or *how* content reaches `PATH`, never *which* digest resolves, so a child reads its own environment. The same holds for [`OCX_SELF_UPDATE`][env-ocx-self-update], [`OCX_UPDATE_CHECK_INTERVAL`][env-ocx-update-check-interval], [`OCX_CEILING_PATH`][env-ocx-ceiling-path] and [`OCX_SIGSTORE_TRUSTED_ROOT`][env-ocx-sigstore-trusted-root]. [`OCX_EXTRA_CA_CERTS`][env-ocx-extra-ca-certs] is not part of the set either, so a CA supplied only through it does not reach an `ocx exec --clean` child. The `extra_ca_certs` config form survives, because the child re-reads `config.toml` itself. Four credentials are stripped from every child, plugins (`ocx-<name>`) included: `OCX_IDENTITY_TOKEN`, `OCX_KEY_PASSWORD`, `OCX_SIGNING_KEY` and `OCX_ANNOUNCE_GIT_TOKEN`. The runner variables that `--ci` and `--ci-annotations` read are not forwarded either, because the CI sink files are runner-managed paths.

`OCX_AUTH_<REGISTRY>_*` is not part of the forwarded set. Launcher children re-enter via `ocx launcher exec` using a local package root rather than a registry, so they never need credentials. Future deliberate ocx-spawns-ocx call sites that *do* need auth will declare that forwarding rule at their own boundary.
