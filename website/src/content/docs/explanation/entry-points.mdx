This page explains how entry points work. It covers how launchers are generated and how they integrate with [env composition][env-composition]. It also covers how collisions are detected and how transitive dependencies contribute their launchers through the synth-PATH mechanism. For the field-level schema see the [metadata reference][metadata-entry-points]. For the flags that wrap launchers at runtime see [`ocx package exec`][cmd-exec] and [`ocx package select`][cmd-select].

Most installed packages end up driven through one or two commands, such as `pipx`, `python`, `node` or `go`. OCX's clean-env execution model normally routes every invocation through [`ocx package exec <package> -- <command>`][cmd-exec]. That is the right default for reproducibility. It adds friction when humans sit in front of a shell and want to type `pipx --version` without remembering which package owns `pipx`.

Entry points close that gap. A publisher declares named launchers in [`metadata.json`][metadata-ref]. OCX generates a small native launcher per name that re-enters the package through the internal `ocx launcher exec` subcommand. Users add one directory to `$PATH` and every declared name becomes a top-level command. It has the same clean-env guarantees as a direct `ocx package exec` call.

## Declaring Entry Points \{#declaring\}

Entry points live as a sibling object on the bundle metadata, keyed by the command name users will invoke. This is the `entrypoints` object of the [`pypa/pipx`][pipx] package:

```json
{
  "entrypoints": {
    "pipx": {
      "command": "python",
      "args": [
        "-c",
        "import importlib, sys\nsys.argv[0] = \"pipx\"\n_obj = importlib.import_module(\"pipx.__main__\")\n_obj = getattr(_obj, \"cli\")\nsys.exit(_obj())"
      ]
    },
    "python": {}
  }
}
```

`entrypoints` is a JSON object keyed by command name. The value object carries the optional `command` and `args` fields, and omitting both yields `{}` as the value. The map shape mirrors Cargo's `[dependencies.X]`, Compose's `services:`, and GitHub Actions's `jobs:`, so uniqueness within a package follows from JSON object key semantics.

At runtime the launcher resolves the entry's name against the composed `PATH` from the package's [`env`][metadata-env] block. The publisher therefore declares the binary's location once via `env`, and the launcher exec resolver picks it up from there. The complete field reference lives at [Entry Points in the metadata reference][metadata-entry-points]. The publisher guide covers [baked arguments][publish-args].

OCX writes the launchers for every declared name into a `launchers/<generation>/` directory inside the content-addressed [package directory][fs-packages]. The generation is a 16-hex key over the launcher program and its record format. A package gets its launchers when it is pulled, and again on first use when the running OCX has a new generation.

Every launcher is the same compiled program on Linux, macOS and Windows, a file `<name>` (`<name>.exe` on Windows) with a record `<name>.launch` beside it. The record is a small JSON document that names the package root. Publishers never fork metadata per host OS.

:::tip[Declare the commands users will actually type]
Only promote user-facing commands to entry points. Internal helpers, wrapper scripts, and build-time binaries belong in `${self.installPath}/bin` (discoverable through `ocx package exec` or explicit path lookup) rather than on `$PATH`. Every launcher consumes a global name across every package a user has selected, so be deliberate about the ones you spend.
:::

## Interface-Only Surface \{#interface-only\}

Entry points are **always on the interface surface**. They represent the commands a package exposes to consumers. A package's launchers appear on `PATH` only under the interface surface (default `ocx package exec`, `--self` off).

Under `--self`, the root's own launchers are **suppressed** from its `PATH` to prevent a launcher from finding itself on `PATH` and recursing infinitely. The private surface is for a package's internal runtime env (compilers, runtimes, shared libraries), not its own CLI commands.

Transitive dependency launchers that pass the [interface edge filter][edge-filter] do appear in both views via the synth-PATH mechanism described below.

## Name Rules and Collisions \{#collisions\}

Names are validated at metadata deserialization time. The regex is `^[a-z0-9][a-z0-9_-]*$`: a lowercase slug where digits, `-` and `_` are allowed and the first character must be alphanumeric. The name must be at most 64 characters. Capital letters, dots, slashes, leading separators, and names exceeding the limit are rejected with a descriptive error, so invalid metadata never reaches the registry.

Uniqueness is enforced at three layers:

- **Within a package:** the map shape gives intra-package uniqueness via JSON object key semantics. Duplicate keys in the on-wire JSON are rejected at deserialization rather than silently last-wins, which is the `serde_json` default. A bundle that lists `"pipx"` twice fails to parse and never reaches the registry.
- **Across the interface surface (install time):** [`ocx package install`][cmd-install] aborts when the package's own bundle plus its interface-visible transitive deps declare the same entry-point name twice. The abort happens before the temp-to-object-store atomic move and exits with `EntrypointCollision` (exit 65, `DataError`). The scope is one package's interface closure, installed with or without `--select`. See [Multi-Owner Collision Reporting](#multi-owner) below for the exact error shape.
- **Across roots (consumption time):** two different installed packages that both declare `python` coexist on disk. The conflict surfaces when `ocx env` or `ocx package exec` is given two or more roots. The compose-time check projects each root's interface surface (bundle entry points plus interface-visible entries). It reports the same `EntrypointCollision` error if two roots declare the same name. The per-package install gate cannot see such conflicts, for example two roots installed independently and combined only at exec time.

[`ocx package select`][cmd-select] performs no collision check. It flips `current` for a single package and never composes an environment.

A name that appears as an entry point in a `private`-edge dep is **not an install error**. Private-surface duplicates do not collide at install time. They resolve at runtime by topological PATH order, and the dep whose launcher directory appears first in the composed `PATH` wins the lookup. This is intentional: `private`-edge deps are invisible to consumers and their launchers never appear on the consumer's `PATH`. Launcher naming conflicts among private deps are the package's internal concern.

:::caution[Choose names carefully for binaries that other packages also ship]
Short, common names (`ls`, `gcc`, `tar`) create more cross-package collisions than they are worth. Where possible, mirror the upstream binary name exactly. Most registries have one canonical publisher per upstream project. Entry-point collisions at install or compose time are a clear signal that two packages compete for the same slot.
:::

## How Launchers Work at Runtime \{#runtime\}

A launcher is a copy of one native program, so it behaves the same on every platform. It reads its record `<name>.launch`, a JSON object whose `kind` key is `package`:

```json
{"kind":"package","schema_version":1,"package_root":"/home/alice/.ocx/packages/ocx.sh/sha256/ab/c123…"}
```

The launcher derives its entry-point name from the file it was loaded from, minus a final `.exe` on Windows. It then starts `ocx launcher exec <package_root> -- <name> <args…>`. On Unix the launcher replaces its own process. On Windows it spawns the child through the Win32 [`CreateProcessW`][createprocessw] API. It never routes through `cmd.exe`.

Only the absolute package-root path is stored, in the record. The `ocx launcher exec` subcommand (hidden from `ocx --help`) forces the [private surface][visibility-views] internally. Private, public and interface entries are all visible to the launched binary. Internal helpers (compilers, runtimes, shared libraries) are therefore available without any flag in the launcher.

`launcher exec` reads the entry-point name and composes the runtime env, including `PATH`. It uses the standard PATH search to locate the executable. The optional `command` field overrides the dispatch target when the binary name differs from the invocable name. When it is absent, the entry-point name is dispatched directly on the composed `PATH` from the package's [`env`][metadata-env] block.

The launcher finds `ocx` itself, in this order. A non-empty [`OCX_BINARY_PIN`][env-ocx-binary-pin] wins, and an empty one counts as unset. Otherwise the launcher walks `PATH`, skipping empty entries, relative entries, its own directory and any directory entry that is another launcher. It never searches the working directory. Every OCX process writes `OCX_BINARY_PIN` into its children's environment. The value is the stable install path when the running OCX is the installed one, else the running binary.

A user-level OCX upgrade that sets `OCX_BINARY_PIN` therefore takes effect for every launcher without touching the launchers on disk. An entry point named `ocx` starts the real `ocx`, never itself.

The stable wire ABI is the `launcher exec` subcommand name pair and the positional shape (`<pkg-root> -- <argv0> [args...]`). Both are frozen, so launchers written by an earlier release keep working after OCX is upgraded. A launcher counts its own hops in the private variable `__OCX_LAUNCHER_DEPTH` and exits 78 at 32, which ends a loop of launchers that start each other.

<details>
<summary>Why bake the package root instead of resolving current at runtime?</summary>

A launcher whose record expanded `current` on every invocation would drift the moment the user selected a different tag. Storing the resolved package root in the record means a candidate's launcher always points at the candidate's content, even while `current` floats. This matches the broader OCX model: [candidates][fs-symlinks] are immutable pins and `current` is mutable state. The entry-point name is read from the launcher's own filename. OCX therefore never stores a second path that could drift out of sync with the first.

</details>

:::caution[Package roots a record cannot hold]
A record holds the package root as a JSON string. The root must be an absolute path and must not contain a newline (`\n`) or a carriage return (`\r`). Quotes, backslashes, apostrophes and percent signs are ordinary JSON characters and need no escaping rules of their own.

Ordinary Windows paths (`C:\Users\…`) and folders containing `%` (e.g. `100%real`) work. The launcher reads the record as data and spawns with no `cmd.exe`, so neither `\` nor `%` carries special meaning.

The check fires when the record is written. A package installed into a path with a newline never gets a corrupt launcher, because the write fails loudly first.
:::

## Synth-PATH Mechanism \{#synth-path\}

Entry points from transitive interface-visible dependencies become available without each intermediate package manually re-exporting them. The [composer][env-composition] may encounter a dep whose effective visibility has the interface axis set ([`has_interface()`][edge-filter] is true) and that declares entry points. It then synthesizes a `PATH ⊳ <dep-pkg-root>/launchers/<generation>` entry.

The synth-PATH entry for a dep is emitted in the same position as that dep's other env contributions, in topological order before the root. The root's own synth-PATH entry (consumer surface only) is emitted last. That gives the root's launchers PATH priority over all transitive deps' launchers.

This mechanism lets a top-level package depend on a runtime that ships its own commands, such as a top-level package that depends publicly on `pypa/pipx`, which ships its own `pipx` and `python` launchers. Those commands surface automatically on the consumer's `$PATH` without redeclaring them.

## PATH Integration \{#path\}

Launchers are harmless files until something puts them on `$PATH`. OCX does that through the composed environment, which names each package's launcher directory:

- [`ocx package select <package>`][cmd-select] flips the per-repo `current` symlink to the selected package root. The anchor exposes content (`current/content`) and metadata (`current/metadata.json`) for that package.
- [`ocx package deselect <package>`][cmd-deselect] and [`ocx package uninstall <package>`][cmd-uninstall] remove `current` as part of their cleanup. Both operations are idempotent, so an already-absent symlink is not an error.
- [`ocx package env --shell=bash <package>`][cmd-package-env] emits eval-safe export lines for the named package. The output includes a `PATH` entry for the launcher directory of every selected package that declares entry points. The global form `eval "$(ocx --global env --shell=bash)"` activates the full toolchain when packages are managed via `ocx.toml`.

The typical shell wire-up adds one of these to a login dotfile:

<ShellSession>

\<\<\< @/_scripts/entry-points/path-integration.sh\{sh\}

</ShellSession>

From the user's perspective, once the shell is open, `pipx --version` resolves to your launcher, which resolves to your binary, all inside a clean environment.

:::note[Similar to SDKMAN and asdf shims]
[SDKMAN][sdkman] generates shim scripts at `~/.sdkman/candidates/{tool}/current/bin/` and relies on a fixed PATH entry per tool. [asdf][asdf] takes the same approach with a single `~/.asdf/shims/` directory. OCX uses the same idea: one PATH entry per package, anchored on the per-repo `current` symlink.
:::

## Multi-Owner Collision Reporting \{#multi-owner\}

When two or more packages in the interface surface declare the same entry point name, the error reports all of them. The collision surfaces on stderr as a single line in the standard `thiserror` `Display` form:

```text
error: entrypoint name collision: 'python' declared by 2 packages: ghcr.io/acme/pytool:1.0@sha256:aaa..., ocx.sh/pypa/pipx:1.18@sha256:bbb...; deselect one before selecting another
```

The line has three parts:

- `'python'`: the colliding entry-point name.
- `N packages: …`: every interface-visible owner, comma-separated, each printed as a fully-qualified pinned identifier (`registry/repository:tag@sha256:…`). All N owners are listed so the publisher knows exactly which packages in the dependency graph compete for the name.
- `deselect one before selecting another`: suggested action.

The error is not a structured JSON payload. The collision is reported like every other failure, and the process exits with code `65` (`DataError`).

## Cross-Platform Caveats \{#cross-platform\}

Launchers are the first OCX artifact whose correctness depends on the user's shell as well as their OS. A few platform-specific quirks are worth calling out.

### Unix shells \{#unix\}

The Unix launcher is the same native program as on every other platform, not a script. It needs no interpreter and no `sh` on the host. The launcher file is mode `0755`, so the write is complete with no follow-up `chmod` step.

The launcher passes the package root to `ocx launcher exec` as one argument, so a path with an apostrophe or a space reaches OCX unchanged.

### Windows \{#windows\}

The Windows launcher is `<name>.exe` with `<name>.launch` beside it. When a shell resolves `pipx` it finds `pipx.exe`. The `.EXE` extension is unconditionally in the default Windows `PATHEXT`, so no `PATHEXT` configuration is ever needed for launcher discovery. The launcher reads its record for the package root. It spawns `ocx launcher exec` through [`CreateProcessW`][createprocessw], passing caller arguments straight through with Win32 [`CommandLineToArgvW`][cmdlinetoargv]-compatible quoting. A Windows home holds no extensionless script.

Nothing re-parses the command line through `cmd.exe`, so arguments survive verbatim. Spaces, Unicode, shell metacharacters (`&`, `|`, `^`, `<`, `>`), and literal empty strings (`pipx "" --version`) all reach the binary exactly as written. This closes the `BatBadBut` / [CVE-2024-24576][batbadbut] `%*` argument-injection class for default resolution. Automation that interpolates untrusted strings (a CI branch name, a build label) into launcher arguments is not exposed through OCX's own launchers.

The launcher is transparent. It propagates the child's exit code unchanged (full 32-bit passthrough) and forwards stdin, stdout and stderr to the real console. It also uses a Win32 job object, so a force-killed launcher reaps its child tree rather than orphaning it. Errors before the child starts go to stderr as a single `ocx-shim:` line with a [sysexits][sysexits]-aligned exit code.

A missing record is recoverable. The next use of the package writes the launcher directory again.

When `ocx` cannot be resolved, the launcher exits 78 and the stderr line names what it tried. A launcher never starts a batch file, so an `OCX_BINARY_PIN` that names a `.bat` or `.cmd` file is refused.

The launcher's pre-child exit codes are stable and scriptable:

| Code | Meaning | Operator action |
|------|---------|-----------------|
| `64` | An argument is not valid Unicode, or cannot reach a batch-file program safely (a line break); the stderr line names the argument by position, never its text | Remove the line break from the argument, or pass the value to the program another way |
| `69` | The `ocx` the launcher resolved is no longer at its path when `CreateProcessW` starts it | Fix [`OCX_BINARY_PIN`][env-ocx-binary-pin] or reinstall `ocx`; the stderr line names the path |
| `74` | `CreateProcessW` failed, with the Win32 error code on the stderr line | Inspect the reported Win32 code; usually a corrupt binary or a transient OS condition. Retry, then re-run `ocx package install` |
| `77` | Permission denied (`ERROR_ACCESS_DENIED`) starting the child, or the package root in the record resolves outside the OCX home | For access denied, check execution policy / AppLocker / antivirus blocking the launcher and grant execute on the package root. For a root outside the OCX home, re-run [`ocx package install`][cmd-install] |
| `78` | No `ocx` found, a relative or batch-file `OCX_BINARY_PIN`, a missing or unreadable `<name>.launch`, or a launcher loop | Put `ocx` on `$PATH` or fix [`OCX_BINARY_PIN`][env-ocx-binary-pin]. A launcher found beside only an older sidecar names `<name>.launch` and needs a new launcher directory |

The child's own exit code passes through untouched on the success path. A non-zero value above is therefore unambiguously a launcher-stage failure, not the binary's.

### PowerShell \{#powershell\}

PowerShell resolves `pipx` to `pipx.exe` on `$PATH` and runs it directly. There is no intervening `cmd.exe`, so PowerShell's own `%VAR%`-in-double-quotes expansion quirk does not apply to OCX launchers. OCX does not generate a `.ps1` launcher. The native launcher already covers the entire PowerShell user base with no script-language argument-forwarding caveats.

The practical rule is that PowerShell users get this for free from the installer. The installer writes `$OCX_HOME/env.ps1` and adds a block to `$PROFILE` that sources it. On every session `env.ps1` runs `Invoke-Expression ((& ocx --global env --shell=pwsh) | Out-String)`, and the resulting `$PATH` entries pick up the `.exe` launchers automatically.

### Git Bash, MSYS2 and Cygwin \{#git-bash\}

On Windows, POSIX runtimes (Git Bash, MSYS2, Cygwin) resolve `pipx.exe` directly by its explicit extension. These shells do not consult `PATHEXT`, so the native `.exe` is exactly what they need with no extra `.sh` launcher. The same launcher runs identically from `cmd.exe`, PowerShell, and a Git Bash prompt because none of them route the call through `cmd.exe`.

:::caution[`ocx` must be resolvable]
Every launcher delegates to `ocx launcher exec`. If the launcher cannot find `ocx` it exits with code `78` and names what it tried: the pin, or the `PATH` entries it walked.

Installation flows that put OCX itself on `$PATH` must be in place *before* any launcher is invoked. Examples are an `ocx` package installed with `--select` or a system-level install. The [installation guide][install] covers the supported bootstrap paths.
:::

## End-to-End Example \{#example\}

The metadata of the [`pypa/pipx`][pipx] package, which ships two launchers, `pipx` and `python`, is the publisher side. The published document also sets `PYTHONPATH`; it is cut here to the parts this page discusses, and it spells the install path with the alias `${installPath}`:

```json
{
  "type": "bundle",
  "version": 1,
  "env": [
    { "key": "PATH", "type": "path", "required": false, "value": "${installPath}/bin", "visibility": "private" }
  ],
  "dependencies": [
    { "identifier": "ghcr.io/ocx-contrib/astral-sh/python-build-standalone:3.13.14@sha256:0dd5ac8eb7f146720e674624548fac05f1e589c1f91792fff5dc8fb73ef38c12", "visibility": "private" }
  ],
  "entrypoints": {
    "pipx": {
      "command": "python",
      "args": [
        "-c",
        "import importlib, sys\nsys.argv[0] = \"pipx\"\n_obj = importlib.import_module(\"pipx.__main__\")\n_obj = getattr(_obj, \"cli\")\nsys.exit(_obj())"
      ]
    },
    "python": {}
  }
}
```

And on the consumer side:

<ShellSession>

\<\<\< @/_scripts/entry-points/example-install.sh\{sh\}

</ShellSession>

Switching to a different version is a single `ocx package select`:

<ShellSession>

\<\<\< @/_scripts/entry-points/example-select.sh\{sh\}

</ShellSession>

No re-sourcing dotfiles. The `ocx package env --shell` output is stable. It emits exports for whichever packages are selected. The select re-points the `current` symlink at the new package root, and the next shell open picks up the updated env output automatically.
