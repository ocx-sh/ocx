Build a deterministic archive, attach metadata that declares its environment, and push both to any [OCI registry][oci-distribution].

## The publisher journey \{#journey\}

This section has a page for each step and for each decision around it. Follow the journey to the pages you need, or start with the first package at the end of this page. Most packages start as an upstream binary release on [GitHub][gh-releases] or a vendor's download page. The pages below take you from "I have a binary" to "consumers can install it", grouped by task.

### Prepare the package \{#journey-prepare\}

- [Bundle a release][authoring-bundle-anatomy]: what goes in the archive, whether to repack the upstream layout and which compression to pick.
- [Declare dependencies][authoring-dependencies]: when to depend on another package instead of bundling it, how to pin by digest and which edge visibility to use.
- [Declare the environment][authoring-env-surface]: which variables to declare and how to mark each as `private`, `public` or `interface`.
- [Add named launchers][authoring-entry-points]: when to ship launchers instead of exposing `bin/`, and how to pick names that do not collide.

### Check and push \{#journey-push\}

- [Test a package before you push it][authoring-testing]: run the install pipeline in a temporary directory, with no registry round trip and no new digest.
- [Write script tests for a package][authoring-script-tests]: assert on a package's behavior with a Starlark script.
- [Publish a package to a registry][authoring-building-pushing]: the first push, `--cascade` for rolling tags and layer reuse by digest.
- [Publish for several platforms][authoring-multi-platform]: push per platform under one tag and let OCX assemble the [OCI Image Index][oci-image-index].
- [Publish glibc and musl variants][authoring-libc-variants]: publish Linux builds that differ by C library.

### Make it resolvable \{#journey-announce\}

- [Announce a package][authoring-announcing]: claim the namespace once, then publish tags into the index on every release.
- [Announce from CI][authoring-announce-ci]: the credential postures for a GitHub or GitLab job, and who reviews what.

### Secure and maintain releases \{#journey-secure\}

- [Sign a release][authoring-sign]: keyless Sigstore signing from a laptop or CI, or a key pair instead.
- [Attestations][authoring-attest]: attach an SBOM or another attestation to a package.
- [Promote packages between environments][authoring-promote]: move a tested build from one registry to the next without rebuilding.
- [Snapshot tracks][authoring-snapshots]: publish nightly or per-change builds and delete them again.
- [Maintain patches][authoring-patches]: ship fixes on top of a published package.

### Wrap tools you do not own \{#journey-wrap\}

- [Repackage an upstream release][authoring-migration]: turn a GitHub Release, Homebrew bottle or vendor archive into an OCX package, by hand or with `ocx_mirror`.

## Publish your first package \{#tldr\}

You have a compiled binary, a Python script or any other executable, and you want consumers to run it after [`ocx package install`][cmd-install]. The path takes three steps, and [Publish a package to a registry][authoring-building-pushing] covers each one in detail.

First, lay out the working directory. The bundle contents live under `build/`, and the metadata sidecar sits next to it. The sidecar is not part of the archive. [`ocx package push`][cmd-package-push] uploads it as the [OCI manifest config blob][oci-manifest-config], and OCX restores it beside `content/` at install time.

      </Node>
    </Node>
    <Node name="metadata.json">
      <Description slot="description">OCI config sidecar, not part of the archive</Description>
    </Node>
  </Node>
</Tree>

Second, write `metadata.json` with one [public env entry][authoring-env-visibility] that prepends the package's `bin/` to `PATH`:

```json
{
  "$schema": "https://ocx.sh/schemas/metadata/v1.json",
  "type": "bundle",
  "version": 1,
  "env": [
    {
      "key": "PATH",
      "type": "path",
      "value": "${installPath}/bin",
      "visibility": "public"
    }
  ]
}
```

Third, bundle `build/` into a deterministic archive and push it to a registry you can authenticate against. The push attaches `metadata.json` as the manifest config blob.

```sh
ocx login ghcr.io
ocx package create build -p linux/amd64 -m metadata.json -o mytool-1.0.0.tar.xz
ocx package push -p linux/amd64 -m metadata.json \
  -i ghcr.io/me/mytool:1.0.0 mytool-1.0.0.tar.xz
```

<Terminal src="/casts/authoring/package-push.cast" title="Bundle and push mytool:1.0.0" collapsed />

Consumers reach the package with [`ocx package install ghcr.io/me/mytool:1.0.0`][cmd-install], and the binary lands on their `PATH` once they pass `--select` or run `ocx package select` later, which makes the package current.

:::tip[Scripted runtimes]
A Python script, a JAR or anything else that needs an interpreter should declare the runtime as a [dependency][authoring-dependencies]. Ship a [named launcher][authoring-entry-points] that resolves the interpreter from it. Pin the version your package expects and skip the ambient `python3` lookup.
:::
