## 1. Symbolic links inside directories as action inputs

**Tree artifacts, local replacement after a cache hit.** The closest match to the local finding is bazelbuild/bazel issue 25671, "Disk cache possibly turns symlinks in output directories into files" (open, P2, team-Performance, assigned to tjgq, opened 2025-03-22, last activity 2025-05-09, reported on Bazel 7.3.1; SUMMARY). Symlinks such as `libfoo.so -> libfoo.so.1.0.0` in a rules_foreign_cc output directory survived a build without the disk cache and became regular files on a cache hit. tjgq's diagnosis: under build-without-the-bytes, a cache hit creates an in-memory `TreeArtifactValue` that cannot tell a symlink from a regular file with the same digest, so it is materialised as a regular file; the problem shows only when the output is not marked for immediate download. `--remote_download_all`, or building the target directly, avoids it. He later generalised it: `TreeArtifactValue` cannot represent all relevant filesystem states, and "resolved symlinks" may need explicit support. It was closed as a duplicate of 15454 on 2025-05-08 and reopened the same day. No fix or timeline is stated.

**The tracking issue.** Issue 15454, "Allow unresolved symlinks inside a tree artifact" (opened 2022-05-10, last human comment 2024-05-06, closed as "not planned" by the stale bot on 2025-10-10; SUMMARY). lberki said in 2022 that the flag works only for regular artifacts, that remote execution and sandbox support were both missing, and that the problem was "highly non-trivial" and shelved. tjgq on 2024-05-06: it is "a feature request that we haven't yet decided to implement." So the long-running tracker is closed by a bot, not resolved, and 25671 is the live carrier of the same defect.

**Tree artifacts, remote execution.** Issue 16361, "Decide how to handle a symlink inside a remotely produced tree artifact" (opened 2022-09-30, closed "not planned" 2023-12-04; SUMMARY, OLD). A remote action can report a symlink in a tree; Bazel rejected absolute ones and dereferenced relative ones locally, which tjgq called non-hermetic. His closing comment says recent changes make remote symlinks in trees be handled "in the exact same manner as inside a locally produced one" and that a feature request (15454) would come as a flag, not by redefining tree artifacts. The linked commit a03ec7f returned 404 on GitHub, so its content is UNVERIFIED.

**Tree artifacts may contain resolved symlinks since 7.1.0.** Issue 20891 (closed 2024-02-21, in 7.1.0 RC1, last comment 2026-03-29; SUMMARY, OLD) removed the check that rejected relative symlinks pointing out of a tree. tjgq: "a tree artifact is defined to contain regular files, not symlinks"; dangling symlinks stay out of scope. justinhorvitz noted an internal Google remote execution service ignores TreeArtifact symlinks ("feel free to proceed but with caution").

**Related defects.** Issue 21171 (closed 2024-02-19, fix commit 4247c20 in 7.1.0 RC1; SUMMARY, OLD): a tree artifact containing a symlink to a directory failed with an IOException when fetched from cache under `--remote_download_outputs=toplevel`; the fix traverses symlinks to directories while collecting the `TreeArtifactValue`. Issue 31976, "Prefetch can hide files behind directory symlinks" (open, opened 2026-10-22, reproduced at commit b353e09 near 9.3.1; SUMMARY): prefetching a partially materialised tree replaces an on-disk directory symlink with a real directory so a recorded child becomes unreachable. Issue 32149 (open, opened 2026-10-27; SUMMARY): on Windows, relative directory symlinks are junctions that store absolute targets, so digests differ and actions re-run on every build with a disk or remote cache; the reporter cites about 6,700 reruns for rules_js `node_modules` links.

**Source files and external repositories.** Issue 23620, "Preserve symlink structure of remote execution inputs" (open, P3, no assignee, opened 2024-09-13, last activity 2026-02-01; SUMMARY). Source artifacts are always treated as file type, so a symlink among source files reaches the executor as a regular file. The reporter's case was a hermetic LLVM "busybox" toolchain where `bin/clang` links to `bin/llvm` and depends on argv[0]. tjgq said he is "not convinced that we can redefine the behavior for all source artifacts" and sketched an opt-in API, with issue 16712 as prerequisite. fmeum on 2026-02-01 liked a proposal to populate `declare_symlink` outputs via `symlink()`. Workarounds named: `declare_symlink` outputs and wrapper scripts using `exec -a`. Corroboration from a ruleset: toolchains_llvm pull request 914 (merged 2026-10-20; SUMMARY) states that Bazel dereferences repository symlinks in remote inputs, which relocates executables away from their `$ORIGIN`-relative libraries. A Jira ticket, MongoDB SERVER-87211 (created 2024-02-28, unresolved; SUMMARY, OLD), reports the same on EngFlow: `v4/bin/clang++` linking to `stow/llvm-v4/bin/clang-12` arrived as a copy of the binary. Whether that input was a source file or an output is not stated there. Bazel's own remote-execution guide (SUMMARY) says symlinks to host tools created by repository rules fail remotely and tells authors not to use `repository_ctx.symlink` to targets outside the repo.

**Plan or release.** None stated that would preserve links inside tree artifacts or source inputs. The only fixes found are the 7.1.0 changes above and the open items 25671, 23620, 31976, 32149.

## 2. Unresolved symlink artifacts (`ctx.actions.declare_symlink`)

**Carried as links.** The actions documentation (SUMMARY) says of `declare_symlink` that "Bazel will never dereference this symlink and will transfer it verbatim to sandboxes or remote executors," and also that "Symlinks inside tree artifacts are not currently supported." The Bazel source option text is the same (SRC, master and release 9.0.0): `allow_unresolved_symlinks`, old name `experimental_allow_unresolved_symlinks`, default `true`, "Unresolved symlinks inside tree artifacts are not currently supported." So no flag is required on 9.x; on 8.x the rename and default-true came from the 2022 stabilisation (issue 10298, closed 2022-10-13 with the flag enabled by default; SUMMARY, OLD). Remote execution support landed in commit ca95fecde (Meumertzheim, 2022-08-22, "Add RBE support for generated unresolved symlinks", touches the merkle tree builder and the remote worker; SUMMARY, OLD).

**Dereferencing reports.** A Buildbarn reproduction repository reports `declare_symlink` output arriving as the file, not a link (SEARCH, date UNVERIFIED, probably before the 2022 fix). lberki on 2022-10-07 said remote execution was "reported fine" (SUMMARY). I found no current per-service statement for BuildBuddy, Buildbarn, NativeLink or EngFlow that confirms keeping `SymlinkNode` entries from `declare_symlink` outputs. The only service-level reports found are: Google's internal service ignores TreeArtifact symlinks (issue 20891, OLD), and the EngFlow ticket above (inputs, not necessarily declared symlinks).

**Who relies on it.** aspect rules_js: `npm/private/utils.bzl` calls `ctx.actions.declare_symlink` plus `ctx.actions.symlink(target_path = <relative>)` for directory links, and on Bazel with `symlink_action_has_target_type` adds `target_type = "directory"` (SRC, main branch, fetched today). Its package store itself is a tree artifact per package, made by an unpack action (`npm_package_store.bzl`, SRC). So rules_js uses unresolved links between trees, never links inside a tree.

**Windows.** Issue 26701 (closed, reported 2025-08-04 on 8.3.1; SUMMARY): directory symlinks from `declare_symlink` were not created as directory links on Windows, which broke rules_js. Fix: a `target_type` argument on `ctx.actions.symlink`, merged 2026-02-05, in 8.6.0 RC1 and Bazel 9. Older: issue 10298 recorded that the Windows file system copies files and makes junctions instead of file symlinks (2019, OLD). macOS: a 2020 exception under remote caching, "symlinks should already have been resolved by Skyframe" (10298, SUMMARY, OLD); no current macOS limit found. `ctx.actions.symlink` with a target file creates absolute targets (fmeum, 23620).

## 3. Established rulesets

**Node (rules_nodejs, `nodejs/repositories.bzl`, SRC main).** Form (i): `download_and_extract` into `bin/nodejs`, then a `filegroup` of `glob(["bin/nodejs/**"])` (SUMMARY of the template; the generated wrapper text I read in SRC). The npm entry point is deliberately the file `lib/node_modules/npm/bin/npm-cli.js`, with the comment "so there are no symlink issues with `%s/bin/npm`"; the same for npx. On Windows it is `npm.cmd`. No remote-execution link documentation beyond that comment.

**Python (rules_python, `python_repository.bzl` and `hermetic_runtime_repo_setup.bzl`, SRC main).** Form (i): `download_and_extract` of python-build-standalone, a glob `filegroup` with excludes (tests, static libraries, `__pycache__`). It pre-creates `__pycache__` symlinks that point out of the repository and excludes them from the glob. It deletes `share/terminfo` because releases from 20240224 contain an infinite symlink loop on non-Linux hosts. I found no documented remote-execution link problem; rules_python issue 691 (SUMMARY) is about system-interpreter bootstrap and absolute paths, not links.

**Java (rules_java, `toolchains/remote_java_repository.bzl` and `jdk_build_file.bzl`, SRC master).** Form (i): `http_archive` plus a BUILD file of glob `filegroup`s (`bin/**`, `lib/**`, `conf/**`, `include/**`). No link workaround seen.

**LLVM (toolchains_llvm, SRC master and SUMMARY of pull request 914).** Form (i): glob filegroups in `BUILD.llvm_repo.tpl`. Under remote execution, links in dylib-linked LLVM were dereferenced, breaking `$ORIGIN` lookups; the workaround (merged 2026-10-20) declares LLVM, Clang and runtime libraries as tool inputs and shares path resolution through compiler wrapper scripts. dzbarsky suggested a statically linked multicall binary instead. The busybox case in 23620 is the same class.

**Foreign build (rules_foreign_cc; SUMMARY).** Form (ii): built libraries are directory outputs. Its generated `replace_symlink` step resolves each output link with `readlink -f`, deletes it and copies the real file in with `cp -a`, so the ruleset removes the links itself (issue 1579, open, opened 2026-08-11, fix pull request 1580 open). That issue reports `cp -a` failing on remote executors whose action directories sit on filesystems that refuse `chmod`; the reporter's worker details were promised but not seen. Pull request 1529 (draft, 2026-04) copies tool runtime closures into a short path on Windows and notes runfiles manifests from remote builds hold absolute cache paths.

**JavaScript packages (aspect rules_js, SRC main).** Form (ii) for packages (tree artifact per package from an unpack action) plus unresolved relative symlinks between them, and `node_modules/.bin` entries via `bins` (SEARCH on docs). Windows cost: issue 32149 above.

## 4. Per-action cost of large input sets

Measured: issue 10875 (closed 2021-10-27, OLD; SUMMARY): a node tool with about 10,000 runfiles over 15,000 actions cost about 200 ms per action to compute the cache key, about 50 CPU-minutes in total; `MerkleTree.build` averaged 11 ms per action in one run; with caching, the execution phase of one build fell from 50.24 s to 35.26 s (hashing 0.961 s versus 16.11 s for input mapping plus tree build). A bundled-script trick cut `MerkleTree.build` from 94 ms to 0.15 ms and a 40,000-action all-cached build from 138 s to 14 s (a user report on that issue; hardware not stated). Pull request 13879 (merged 2021-10-27, Bazel 5.0, OLD; SUMMARY): Merkle tree calculation 78 ms to 3 ms for 3,000 inputs; follow-up about 0.7 ms; the cache lives in client JVM memory; a later report says a TypeScript-heavy cached run went from about 1.5 to nearly 10 minutes with the flag on; coeuvre in 2022 was "not confident enough" to make it default, and the default size is 1000. Issue 17804 (closed 2024-12-13 as duplicate of 21379; SUMMARY, OLD): a report of actions with about 30k input files spending time in `MerkleTree.build` after moving from 6.4 to 7.0 (no timings); the tree for one spawn is built sequentially, many spawns do it concurrently; Bazel 6.1 limits concurrent builds. Issue 16899 (closed 2022-12-06, OLD; SUMMARY): a 100,001-file tree artifact was rejected by one executor service at 70,000 files; meisterT says Bazel cannot query that limit.

Sandbox: bazel-dev thread of 2022-02-28 by Ed Schouten (SUMMARY, OLD): large monolithic toolchains as inputs can make sandbox setup and teardown take "up to minutes"; this is anecdote, no numbers. Replies: `--experimental_reuse_sandbox_directories` still walks the tree but creates fewer links; tree artifacts could cut link count from files to trees but the risk is an action modifying a linked directory. Issue 5971 (closed 2018-09-03, OLD; SUMMARY): since 0.17 the sandbox expands tree artifacts into per-file symlinks, with a flag to restore directory links; whether that still holds on 9.x is UNVERIFIED. One forum anecdote reports a large speedup by placing sandbox links in `/dev/shm` with `--experimental_sandbox_base` (SEARCH, undated). The sandboxfs results (2018: 581 s none, 621 s symlinks, 612 s sandboxfs on a Mac; SEARCH, OLD) are measured but the project is abandoned.

Executor side: Buildbarn's design document (SUMMARY) says hardlinking from a worker file cache "does not introduce any overhead while executing" but "may be slow for large input roots, especially if only a fraction gets used"; its FUSE or NFSv4 mode loads lazily; a 2023 presentation reports workers spend under 1% of time fetching input files after lazy population (SEARCH, OLD). I found no first-hand BuildBuddy or EngFlow input-root timings. Path mapping: no cost numbers found.

## 5. Form (iii) in the wild

No ruleset found that hands an archive to every action and unpacks it there. Related evidence: Bazel's own remote-execution guide tells authors to pre-install tools in the executor environment or build them for the platform, not ship binaries (SUMMARY). Pants named caches (SEARCH of Pants docs and chat, undated): Remote Execution API has no append-only cache concept; an option `--remote-execution-append-only-caches-base-path` points at a writable path outside the sandbox area; users call it a workaround that works only with a single worker, and Buildfarm, Buildgrid and Buildbarn do not support named caches. BuildBuddy runner recycling (`recycle-runner`, docs page dated 2026-11-24; SUMMARY) keeps a runner between actions, and the docs warn it "reduces action hermeticity." rules_nixpkgs (Tweag post 2024-02-29, OLD; SEARCH): store paths realised on the client do not exist on executors; the tested fix was a read-only NFS mount of `/nix/store` on the executors, with no simple solution; alternatives in rules_nixpkgs issue 180 are executor images or a `remotable` flag. Buck2 `http_archive` (SUMMARY) is an archive-extraction rule fetched with `buck2 fetch` or during build; the page says nothing about symlinks or where extraction runs.

## 6. Source directories as inputs

Change tracking: in Bazel source (SRC), `TrackSourceDirectoriesFlag` reads the JVM property `BAZEL_TRACK_SOURCE_DIRECTORIES`. In 7.4.0 and 8.0.0 it is on only when the property equals "1" (default off); in 9.0.0 and master the default is true ("0" disables), and the class comment says Bazel and Blaze defaults once differed. A comment on `ArtifactFunction` says the traversal key is requested only when source directories are tracked. So on 9.x tracking is on by default; on 8.x it needs `--host_jvm_args=-DBAZEL_TRACK_SOURCE_DIRECTORIES=1` (my inference from the source comment that `--host_jvm_args` is how to set it). I did not find the 9.0 release note that announces the flip, and did not find the documentation wording that warns about directories. A mailing-list thread surfaced by search (SEARCH, undated) says Bazel warned that a directory dependency check is unsound, which matches the pre-9 default.

Remote execution: issue 32416 (open, P2, opened 2026-11-04, Bazel 9.3.1; SUMMARY) says that with `--experimental_remote_repo_contents_cache`, a reproducible repo injected from the remote cache is re-materialised for every local action with a source-directory input, and concurrent actions fail with "No such file or directory"; local source-directory inputs from that cache work since 9.3.0 (fix of issue 30217, not read). Issue 32346 (open, P2, opened 2026-11-02; SUMMARY): a repo that symlinks a file from another repo dangles after the target repo is re-fetched from the remote repo contents cache. Issue 11811 (closed 2024-08-21, SUMMARY, OLD) concerns tree artifacts that are not action inputs expanding to nothing; it does not cover source directories.

## 7. Local repo contents cache (Bazel 9)

SRC (release 9.0.0 `RepositoryOptions.java`, `LocalRepoContentsCache.java`, `RepositoryFetchFunction.java`): `--repo_contents_cache` defaults to `{--repository_cache}/contents`, and `--repository_cache` defaults to `{--output_user_root}/cache/repos/v1`; so it is on by default and sits under the user-wide output root, shared across workspaces. An empty string disables it; setting `--repository_cache=` also disables it unless the content cache path is set. Layout: one directory per "predeclared inputs hash", holding pairs `<UUID>` and `<UUID>.recorded_inputs`. On a hit the repo directory is linked to the cached directory (`setupOverride`), so an unpacked repo is shared, not copied (my reading of the code; I did not run it). Garbage collection: entries unused for 14 days (`--repo_contents_cache_gc_max_age`), run after 5 minutes idle. Eligibility: the fetch must return reproducible metadata and the rule must not be `local`. A rule that returns nothing or a dict is treated as non-reproducible (`default -> RepoMetadata.NONREPRODUCIBLE`); a rule opts in with `ctx.repo_metadata(reproducible = True)`. The stock `http_archive` does so when `sha256` or `integrity` is given (`http.bzl`, SRC).

`bazel vendor` (SRC, `VendorManager.java`, 9.0.0): the repo is moved or copied under the vendor directory, a symlink is left in the external directory, and symlinks whose target is under the external root are rewritten to relative paths through a `bazel-external` link in the vendor directory. Relative links inside the repo are kept as they are by the move or copy (my inference; the code only rewrites links whose target starts with the external root). Absolute links to other locations are skipped, with a source TODO to warn. Links pointing outside the repository but not under the external root are left untouched. Windows is special-cased to keep relative targets.
