## (a) Bazel's stance on network access inside actions

- Tags: `requires-network` "allows access to the external network from inside the sandbox" and "only has an effect if sandboxing is enabled". `block-network` "blocks access to the external network from inside the sandbox... only communication with localhost is allowed". `no-remote-exec` = never executed remotely, may be cached remotely. `local` = no remote cache, no remote exec, no sandbox. https://bazel.build/reference/be/common-definitions (current, undated).
- `--sandbox_default_allow_network`: `defaultValue = "true"`, help "Allow network access by default for actions; this may not work with all sandboxing implementations." https://raw.githubusercontent.com/bazelbuild/bazel/master/src/main/java/com/google/devtools/build/lib/sandbox/SandboxOptions.java (master, read 2026-11-23). Matches the earlier lane's claim from the command-line reference. Sandbox-only: actions run `local` or on platforms without sandbox support are unaffected (search summary only, UNVERIFIED primary).
- The sandboxing doc says network namespaces are one of the isolation mechanisms and that you can "prevent the action from accessing the network"; it does not name `requires-network`, does not state the default, and does not address darwin or Windows. https://bazel.build/docs/sandboxing (current).
- Hermeticity doc: hermetic builds "download copies of tools and manage their storage and use inside managed file trees"; it does not discuss action-time network access nor "repository rule vs action". It points to `--experimental_workspace_rules_log_file` for auditing non-hermetic repository-rule behaviour. https://bazel.build/basics/hermeticity (current).
- Remote-execution rules guide (WORKSPACE-era wording, partly OLD in form): "Executing compilation actions in `WORKSPACE` rules results in binaries that are incompatible"; "Actions that produce target-specific artifacts for external dependencies must execute during the build"; platform inspection and dependency enumeration, and downloading packages "that must be built", are "safe to execute locally via WORKSPACE rules". It makes no statement on network access. https://bazel.build/remote/rules (current). This is the closest Bazel-owned text on the split; it is about building artifacts, not about fetching prebuilt bytes.
- Maintainer statement "downloads belong in repository rules": none found. Bazel's own docs never state it. The nearest statements are third-party: Tweag, 2026-04-02: "it is advised to rely on MODULE.bazel or WORKSPACE mechanisms for accessing external dependencies"; Bazel "lacks support and features for downloads to take place within build actions"; downloader config "can only rewrite or block requests that Bazel is aware of"; `wget` in a genrule is not a structured fetch event in BEP. https://tweag.io/blog/2026-04-02-making-bazel-builds-more-reliable/ (author Alexey Tereshenkov, not a Bazel maintainer in the page).
- Security stance for RBE: James Marcus (jmmv), 2025-09: checksums are "not enough" for downloads run as remote actions; "the only thing you can and must do here is to disable network access in the remote worker"; checksummed downloads in repo rules are still acceptable. https://jmmv.dev/2025/09/bazel-remote-execution.html (personal blog).
- Proposal for a download action / fixed-output action: none found. `ctx.actions` has no download method (earlier lane, https://bazel.build/rules/lib/builtins/actions). The only Bazel-owned download-offload design is the 2020 Remote Asset proposal (status "Approved", last update 2020-01-20, OLD): it moves downloads that the build tool does "when calculating which actions to execute" to a remote service via `--experimental_remote_downloader`; it does not cover network access from within build actions. https://github.com/bazelbuild/proposals/blob/main/designs/2020-01-14-remote-downloads.md
- Practice: Android Kleaf has `--config=internet` / `--config=no_internet` to control downloads, stating `no_internet` "will be set by default" (planned, not current). https://android.googlesource.com/kernel/build/+/main/kleaf/docs/network.md (undated).

The only ruleset found that fetches registry bytes over the network inside an action is rules_img lazy mode (plus build-time pushes). Its auth doc: "Registry traffic from a build action needs **network access**, which makes the action non-hermetic"; "The connection is opened by the executor, not the machine running Bazel"; config files "must exist on the executor"; an optional gateway on a UNIX socket holds credentials; a cache hit skips execution so "rotating the credential alone does not rerun" the action; it does not mention `requires-network`, `no-sandbox` or `no-remote`. https://raw.githubusercontent.com/bazel-contrib/rules_img/main/docs/authenticating-build-actions.md (current). ## (d) What `fetch`, `vendor`, caches, downloader config and credential helpers cover

- `bazel fetch` pre-fetches repos; with `--nofetch` the build uses cached copies or fails. `--fetch` "serves to manage network access", default true. https://bazel.build/external/overview (current).
- `bazel vendor` vendors repos and registry files; excludes repository rules with `local` or `configure` true; nothing on build actions. "The build should work in a clean build environment without network access and repository cache." Absolute symlinks outside the external dir are not rewritten. https://bazel.build/external/vendor (current).
- Flags (9.2 command-line reference, current): `--repository_cache` (downloaded values while fetching external repos; default `{output_user_root}/cache/repos/v1`), `--repo_contents_cache` (fetched repo dirs, default `{repository_cache}/contents`), `--distdir` ("Additional places to search for archives before accessing the network"), `--credential_helper` ("repository fetching, remote caching and execution, and the build event service"), `--experimental_remote_downloader` (Remote Asset API endpoint, "remote download proxy"). https://bazel.build/versions/9.2.0/reference/command-line-reference
- `--experimental_downloader_config` is not a separate flag now: `RepositoryOptions.java` has `downloader_config` with `oldName = "experimental_downloader_config"`; directives `allow`, `block`, `rewrite`, `all_blocked_message`. https://raw.githubusercontent.com/bazelbuild/bazel/master/src/main/java/com/google/devtools/build/lib/bazel/repository/RepositoryOptions.java
- Reach into actions: none of these is documented to apply to actions. Tweag 2026-04-02 states downloader config cannot see ad hoc shell network calls (see (a)); the vendor page is silent; the credential-helper flag help lists no build-action coverage. A positive statement "none reach actions" has no primary source; the evidence is absence in the docs above plus the Tweag claim. rules_img confirms by construction: its actions run their own keychain, including a rules_img-specific credential helper env (`IMG_CREDENTIAL_HELPER`), because the Bazel client's helper is not passed in (https://raw.githubusercontent.com/bazel-contrib/rules_img/main/docs/authenticating-build-actions.md).

## (e) Cost of the repo-rule placement under remote execution

- Fetching is per workspace and on demand: "Normally, Bazel only fetches a repo when it needs something from the repo." https://bazel.build/external/overview. External dependencies are fetched on the client at build time; no primary source states what a warm remote action cache changes. A fresh client with a warm remote action cache still evaluates repository rules it needs for loading and analysis: this is the default behaviour implied by the overview page, and the remote repo contents cache exists to change it. Direct statement UNVERIFIED.
- Inputs: "Bazel stores an action's input files in the CAS" before execution. https://blog.engflow.com/2024/05/13/the-many-caches-of-bazel/ (2024-05, OLD). Repository contents reach the cluster only as action inputs uploaded by the client; no other path was found.
- Remote repo contents cache, Bazel 9.2 line:
  - Flag `--experimental_remote_repo_contents_cache`, default false: "If enabled, the remote cache will be used to store the results of reproducible repository rules." https://bazel.build/versions/9.2.0/reference/command-line-reference ; it is a startup option per https://blog.bazel.build/2026/01/20/bazel-9.html (2026-01-20: "an experimental remote repo contents cache"; local `--repo_contents_cache` is the stable part).
  - Experimental and tracked for stabilisation: bazelbuild/bazel#31456 (opened 2026-10-02, P1, open) "make ... a stable feature and (eventually) enable it by default". https://github.com/bazelbuild/bazel/issues/31456 . Children: #30218 does not recover from missing CAS blobs; #31434 `http_archive` `files` symlinks into the main repo silently keep the repo out of the cache; #31197 internal error with `--rewind_lost_inputs`; #31005 "unnecessarily materializes entire repos to local disk"; #31244 external tools cannot get source digests for in-memory repos; #30160 overlay FS for cross-FS symlinks.
  - Limits: repos with cross-repo symlinks are excluded since 9.2.0 (PR #30161); #30160 reopened 2026-10-02 as the tracking issue "for a better solution". https://github.com/bazelbuild/bazel/issues/30160 . The exclusion is silent today (#31456 open task "Warn when a repo is left out of the cache due to symlinks").
  - Hang: bazelbuild/bazel#30780 (opened 2026-08-18, closed 2026-09-08): Bazel 9.2.0 hangs after a remote-cache ByteStream read times out during repo loading through this cache; fixes backported to 9.3.0 and 8.8.0. https://github.com/bazelbuild/bazel/issues/30780 . EngFlow: "Only enable this startup option with Bazel 9.3.0 or later". https://docs.engflow.com/re/client/bazel-known-issues.html
  - Lazy behaviour: from Bazel's own test `remote_repo_contents_cache_test.py` (fetched raw): after `clean --expunge`, a cached repo is restored into an in-memory overlay and written to disk only when something needs it (a rule reading it via another repo, or a local action consuming an input); `rctx.path()` on a repo file triggers full materialisation; repos are refetched without a remote cache, when predeclared or recorded inputs change, for non-UTF-8 paths, with cross-repo symlinks, and with symlink chains into the main repo. https://raw.githubusercontent.com/bazelbuild/bazel/master/src/test/py/bazel/bzlmod/remote_repo_contents_cache_test.py . Test names, not docs; the summary says its fetch covered about 100k of 138k characters.
  - Applies only to rules declared reproducible (flag help above). Combined with the earlier lane's fact that digest-pinned rules_oci pulls set `reproducible` only for sha256 identifiers (https://raw.githubusercontent.com/bazel-contrib/rules_oci/main/oci/private/pull.bzl).
- Remote Asset downloader (`--experimental_remote_downloader`) offloads the HTTP fetch to the cluster but the result still lands in the client's repo (2020 proposal, OLD, https://github.com/bazelbuild/proposals/blob/main/designs/2020-01-14-remote-downloads.md). Backend support: Buildfarm supports `FetchBlob` with checksum and header qualifiers, `FetchDirectory` UNIMPLEMENTED (earlier lane, `research_reapi-backends-test-rig.md`).
- Older vendor-neutral workaround evidence: issue #6359 comments describe teams tarring the external dir for stateless CI (search summary, UNVERIFIED primary, OLD).

## (f) OCI registry blobs through Bazel's downloader

- Bazel downloader cannot sniff `WWW-Authenticate`: rules_oci `authn.bzl` comment "Unfortunately bazel downloader doesn't let us sniff the WWW-Authenticate header, therefore we need to keep a map of known registries that require us to acquire a temporary token"; others added via the experimental `www_authenticate_challenges`. https://raw.githubusercontent.com/bazel-contrib/rules_oci/main/oci/private/authn.bzl (main, read 2026-11-23).
- Auth flow in rules_oci: reads `$DOCKER_CONFIG/config.json` (or `containers/auth.json`, `REGISTRY_AUTH_FILE`); `credHelpers`, then `auths`, then `credsStore`; credential helper run via a temporary shim with `rctx.execute`; for bearer registries `_get_token` calls `rctx.download(..., auth={url: pattern})` to the token endpoint, reads `token`/`access_token`, and returns an `auth` pattern `"<challenge> <password>"` handed to the blob download. Digest-pinned pulls do not watch credentials ("Credentials only decide whether the registry serves the content"). OAuth2 refresh-token path needs `OCI_ENABLE_OAUTH2_SUPPORT` and runs curl/wget/PowerShell via `rctx.execute`, flagged "may change or abandon it without a notice". Same file. The `pull.bzl` file sets `Accept` and `Docker-Distribution-API-Version` headers, forwarded only on Bazel 7.1.0+.
- Redirects: `pull.bzl` has no redirect handling; blob GETs go through Bazel's downloader unchanged.
- Authorization-on-redirect: bazelbuild/bazel#29660, "Downloader forwards Authorization headers across cross-origin redirects and HTTPS to HTTP downgrades", opened 2026-05-27, Bazel 9.1.0, labels P3 / help wanted / team-ExternalDeps / bug, triaged 2026-06-03, open; no merged fix confirmed (a copybara commit titled "Update header propagation on cross-origin redirects in Bazel downloader" is linked 2026-07-27, merge status not visible); related #30013 is the opposite problem (netrc dropped on same-host redirects). https://github.com/bazelbuild/bazel/issues/29660 . Registry-side failure mode: S3 or GCS reject a signed-URL request that also carries `Authorization` (OPA issue and GitLab work item, https://gitlab.com/gitlab-org/ops/registry-conformance/-/work_items/55 ; search summaries). No Bazel- or rules_oci-specific report of that 400 was found; the link between #29660 and a failing registry blob fetch is an inference.
- rules_img: actions use their own keychain (Bazel credential helper, `IMG_REGISTRY_AUTH_HOST`, `IMG_DOCKER_CONFIG_INLINE`, Docker/Podman config, ADC, ECR); `docker_config_path` affects build-time blob downloads. https://raw.githubusercontent.com/bazel-contrib/rules_img/main/docs/authenticating-build-actions.md
- The `headers` and `auth` pattern parameters: https://aspect.build/blog/custom-download-headers (undated, OLD).

## (g) Analogues outside Bazel

- Nix fixed-output derivations: with `outputHash`, `outputHashAlgo`, `outputHashMode` the derivation is fixed-output; "Unlike a regular derivation, the builder executable of a derivation that produced fixed outputs has access to the network"; the output must match the declared hash or the build fails, so "regardless of what the builder does ... it cannot influence downstream builds in unanticipated ways". `impureEnvVars` is honoured only for fixed-output derivations. https://nix.dev/manual/nix/stable/store/derivation/outputs/content-address.html ; https://nix.dev/manual/nix/stable/language/advanced-attributes.html . Network is a property granted to the hash-pinned action class, not to ordinary actions. Whether the FOD sandbox restricts anything else: not stated on these pages.
- Buck2: `actions.download_file(output, url, sha1=None, sha256=None, size_bytes=None, is_executable=False, ...)` is an action API, digests optional in the signature; "The file at the URL must have the given sha1 or the command will fail". https://buck2.build/docs/api/build/AnalysisActions/ . `http_file` passes sha1/sha256 straight through and does no validation in the prelude; the unzip step is `local_only` when no sha1. https://raw.githubusercontent.com/facebook/buck2/main/prelude/http_file.bzl . Buck1-style docs: "Buck verifies this is correct and fails the fetch command if it doesn't match"; downloaded by `fetch` or as part of `build`. https://buck2.build/docs/prelude/rules/core/http_file/ . Where `download_file` executes (client vs RE) and how it interacts with deferred materialisation: UNVERIFIED. A search summary claiming the prelude passes `is_deferrable=True` is contradicted by the raw prelude file read here (no such argument).
- Pants: `DownloadFile(url, expected_digest: FileDigest)` is a native engine intrinsic in Rust; digest is required (docs heading "HTTP requests without digests are unsafe"); cached and never re-pings once cached; Digests are designed to move between local and remote execution environments. https://pantsbuild.org/dev/docs/writing-plugins/the-rules-api/file-system . Where the download runs relative to RE: not stated (UNVERIFIED).
