## The `ocx_shim` program

- Steps (`crates/ocx_shim/src/main.rs:136`): harden the DLL search path; read its own file name; strip one `.exe`; probe `<stem>.shim`, `.shimref`, `.exec` in that order (`core.rs:117`); check that a package root lies inside `OCX_HOME` (exit 77 if not); for `.exec` drop `OCX_GLOBAL` and `OCX_PROJECT`; pick the program (`OCX_BINARY_PIN`, then the `ocx` named in `.exec`, then bare `ocx`); build the command line; create a kill-on-close job; `CreateProcessW`; wait; return the child's exit code.
- Wire ABI (`core.rs:373-427`): one sidecar file beside the `.exe`, UTF-8, no BOM, lines ended by LF. No resource is read. The environment reads are `OCX_HOME` and `OCX_BINARY_PIN`.
- Exit codes: 78 missing or malformed sidecar, 77 containment or access denied, 74 I/O or spawn failure, 69 `ocx` not found (`main.rs:57-71`).
- Platforms: the runtime is `#[cfg(windows)]`; off Windows `run()` is `unimplemented!` (`main.rs:563`). Release blobs are built for `x86_64-pc-windows-gnullvm` and `aarch64-pc-windows-gnullvm` with cargo-zigbuild (`.github/workflows/build-windows-shims.yml:113-114,170-171`).
- Dependencies: std, `windows-sys`, `dunce`. No `ocx_*` crate, to stay inside the size budget of 512 KiB (`crates/ocx_store/src/shim.rs:15`).
- How the bytes reach the store: two committed blobs under `crates/ocx_store/src/shims/`, embedded with `include_bytes!` on Windows builds only (`shim.rs:19-27`), written once to `$OCX_HOME/.bin/ocx-shim/<digest>.exe`.
- The code states a rule for the blob: every `<name>.exe` must be a verbatim copy, because "any transform invalidates" an Authenticode signature (`crates/ocx_package_manager/src/launcher/generate.rs:479,533-534`, `shim_bin_store.rs:332-333`). No signing step for the shim was found in code or CI.

## What `ocx launcher exec` and `ocx launcher shim` do at run time

`launcher exec` (`crates/ocx_cli/src/command/launcher/exec.rs`), beyond composing an environment and starting the target:

- validates the package root: absolute, canonical, inside the packages root or a test scratch root (`:46-54`, `:367-407`);
- reads the parent's recorded launch identities and, under a `[patches]` tier, computes patch opt-outs (`:63-86`);
- replays the parent's `[env]` and `--env` and reconciles list separators (`:96-113`);
- reads `metadata.json` and maps argv0 through the entry-point table (`:117-124`), then interpolates the entry point's arguments (`:126-148`);
- applies the child environment with the binary pin (`:196-214`);
- writes an execution record (`:225-266`).

`launcher shim` (`crates/ocx_cli/src/command/launcher/shim.rs`) also checks that the package claims the name (`:64-70`), installs the package on first use (`:75-85`, `crates/ocx_package_manager/src/tasks/materialize_lazy.rs:91`), strips the shim directory from `PATH` (`:113-118`) and writes an execution record (`:128-155`).

Not found in either file: signature verification and consent.

## macOS code signing

- One step: `ocx_store::codesign::sign_extracted_content` (`crates/ocx_store/src/codesign.rs:13`), called from `crates/ocx_package_manager/src/tasks/pull.rs:861` and `pull_local.rs:397`.
- It covers Mach-O files under a layer's `content` whose signature does not verify. Per file, never per bundle.
- Mechanism: the `/usr/bin/codesign` subprocess. First `--verify --strict`; on failure `--sign - --force --preserve-metadata=entitlements` (`codesign.rs:219-228`). A fresh-inode workaround follows (`:267-285`), quarantine attributes are removed, and hardlink aliases are relinked.
- Gating: no-op off macOS (`codesign.rs:14`), when `OCX_NO_CODESIGN` is set, or when `codesign` is absent. Failures only warn.
- No generated launcher or shim is signed. On POSIX they are shell scripts.

## The macOS binaries of ocx are built on Linux, and the linker signs the arm64 one

Added on 2026-11-25. Basis: READ for the workflows, RUN for the bytes. The question was whether a native program for macOS can be built and signed without a macOS machine.

- The release binaries for all eight targets are built on `ubuntu-latest` (`.github/workflows/cross.yml:50,74`), through `task cross:build:release`, which is a Bazel build with the hermetic `@llvm` toolchain (`MODULE.bazel:56,96,98`).
- No step signs them. A search for `codesign`, `rcodesign`, `adhoc_codesign`, `ad-hoc` and `notariz` over `.github/workflows/*.yml`, `taskfiles/*.yml`, `taskfile.yml`, `.bazelrc`, `MODULE.bazel` and `BUILD.bazel` matches nothing. A search for `codesign` over `.github/actions`, `test/src` and `scripts` matches no file.
- Release readiness run [45277014613](https://github.com/ocx-sh/ocx/actions/runs/45277014613) (2026-11-23, head `1f6fff93`, success) shows the path of the binary:
  - `Cross-build (stamped) / Cross-build (aarch64-apple-darwin)` builds it on Linux.
  - `Release archives` packs it on Linux (`.github/actions/release-assets/action.yml:17-19` takes the `ocx-release-*` artifacts).
  - `Stage test/bin` unpacks `ocx-<target>.tar.gz` on the native runner and copies `ocx` (`.github/workflows/release-readiness.yml`).
  - `Acceptance (macOS arm64)` runs the suite with it on `macos-latest`, four shards, all green. Before the suite, the leg only sets the executable bit (`.github/workflows/acceptance.yml:247-250`).
  - `Acceptance (macOS x64)` does the same on `macos-15-intel`, green.
- The bytes of the two macOS binaries in that run's `release-dist` artifact, read with a Mach-O reader of 40 lines (Python standard library, nothing executed):

| Binary | Size (bytes) | `LC_CODE_SIGNATURE` | Blobs | Code directory flags |
|---|---|---|---|---|
| `ocx-aarch64-apple-darwin/ocx` | 25191744 | present, offset 24996320, size 195424 | 1 (code directory only) | `0x20002`: ad-hoc and linker-signed |
| `ocx-x86_64-apple-darwin/ocx` | 27974072 | absent | none | none |

What this shows:

- The linker signs an arm64 Mach-O binary ad hoc when it links on Linux. No macOS machine and no `codesign` call takes part.
- A binary signed that way on one machine starts on another: it was built on a Linux runner and ran on a macOS runner.
- The reader can report both results: one binary with a signature and one without.

What this does not show:

- That a signed program still starts after it is hardlinked or copied under another name, uploaded to a remote executor, vendored or archived. The suite does not use `ocx` that way.
- Anything about the `ocx_shim` crate on macOS. Its runtime is Windows-only, and the readiness run builds it natively with cargo.
- Gatekeeper, notarization and files that carry a quarantine attribute.
