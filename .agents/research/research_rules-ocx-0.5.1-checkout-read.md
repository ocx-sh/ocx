## 1. Eager package mode: files in the generated repository

The package repository rule runs three `ocx` commands and then writes files. It runs `ocx package install` (`package.bzl:187`), `ocx package which --lazy-mode never` (`package.bzl:207-215`) and `ocx package env --lazy-mode never` (`package.bzl:243-251`). For a platform that matches the host it also runs `ocx package inspect --closure` (`package.bzl:261-282`).

The generated repository then holds these entries:

- A symlink `content` that points at `<store root>/content` (`package.bzl:255`: `ctx.symlink(root + "/content", "content")`). `root` is the absolute path that `ocx package which` reports. The code fails unless it is absolute and the report says `kind` is `package` (`package.bzl:222-241`).
- A symlink `entrypoints` that points at `<store root>/entrypoints`, only if that directory exists (`package.bzl:256-257`).
- One file `launchers/<name>.sh` (`.bat` on Windows) per discovered tool, written by `write_launchers` (`package.bzl:283`, `repo_utils.bzl:1689-1706`). The file is marked executable.
- `env.bzl`, rendered by `render_env_bzl` (`package.bzl:284`, `repo_utils.bzl:1608`).
- `BUILD.bazel` (`package.bzl:285-297`, `repo_utils.bzl:1651-1686`).

The content is exposed as one `filegroup` named `content`, with `srcs = glob(["content/**"], allow_empty = True)` (`package.bzl:290-295`). `exports_files(["env.bzl"])` is in the same BUILD file (`package.bzl:289`). There is no directory label and no per-file target other than the launchers.

The content is a symlink to a path outside the repository, in the shared ocx store (`~/.ocx` by default, see section 9). It is neither a copy nor a hardlink made by this rule. The code comment says: "The store is content-addressed and digest-pinned: symlinks into it are stable for the lifetime of the pin" (`package.bzl:253-254`). The README and docs say the store itself is "hardlink-composed" (`README.md:78`, `docs/concepts/how-it-works.md:19`). That is a statement about the ocx store, not about code in this ruleset.

For a foreign platform (`runnable` false, `package.bzl:185`) the `content` symlink and `filegroup` still exist, but no launchers are written (`package.bzl:260-261`).

## 2. Eager package mode: dependencies

One repository exists per `ocx.package` tag, or one per platform plus a hub (section 7). Dependencies of a package do not get repositories of their own.

The rule symlinks only the root package's `content` and `entrypoints`. `ocx package which` is asked for the single reference `pkg` and the first row of its answer is used (`package.bzl:215`: `.values()[0]`). Dependencies reach the generated files in two ways:

- `ocx package env` composes the environment of the package including its dependencies (`package.bzl:243-251`). Its entries carry absolute store paths of every contributing package. These entries go into `env.bzl` and into the launchers (`package.bzl:283-284`).
- `ocx package inspect --closure` lists the closure's public surface. Every declared binary or entrypoint name in the closure becomes a target (`package.bzl:268-282`, `repo_utils.bzl:1033-1075`, `repo_utils.bzl:1153-1195`). A name is found by walking the composed PATH directories (`repo_utils.bzl:1111-1150`).

Dependency content is therefore reachable only through absolute paths inside launcher text and `env.bzl`. It is not in `//:content` and not in any runfiles. Two packages in the closure that declare the same entrypoint make `inspect --closure` exit 65, which the rule turns into a fetch failure with a hint (`package.bzl:264-267`).

## 3. Eager package mode: environment and launchers

### The generated POSIX launcher

The template is the POSIX branch of `render_launcher` (`repo_utils.bzl:1585-1606`):

```
#!/usr/bin/env bash
# Generated by rules_ocx — do not edit.
set -euo pipefail
export OCX_HOME=<sh_quote(home)>
export OCX_BINARY_PIN=<sh_quote(ocx binary path)>
export <KEY>=<sh_quote(value)>                      # one line per `constant` entry
export <KEY>=<sh_quote("v1:v2:...")>"${<KEY>:+:${<KEY>}}"   # one line per `path` key
if [ -n "${<KEY>:-}" ]; then export <KEY>="${<KEY>}"<sh_quote(sep)><sh_quote(folded)>; else export <KEY>=<sh_quote(folded)>; fi   # one line per `list` key
exec <sh_quote(target)> "$@"
```

The substitutions are:

- `home` is the resolved `OCX_HOME`. `make_ocx_env` returns it (`repo_utils.bzl:653-680`). It is `OCX_HOME` from the environment, else `$HOME/.ocx` (`$USERPROFILE\.ocx` on Windows), else `<repo>/.ocx_home` with `isolated_home`.
- `ocx` is `str(binary)`, the absolute path of the `ocx` file in the `@ocx_tool` repository inside Bazel's output base (`package.bzl:283`).
- `target` is the absolute path of the executable that was found on the composed PATH (`resolve_bins`, `repo_utils.bzl:1111-1150`). It points into the store, not into the repository's `content` symlink.

The substituted result for the unit-test entries (`ocx/tests/launcher_test.bzl:36-40`, `:672-713`) is:

```
#!/usr/bin/env bash
# Generated by rules_ocx — do not edit.
set -euo pipefail
export OCX_HOME='/home/u/.ocx'
export OCX_BINARY_PIN='/repo/ocx'
export JAVA_HOME='/store/cc/content'
export PATH='/store/bb/content:/store/aa/content/bin'"${PATH:+:${PATH}}"
exec '/store/aa/content/bin/tool' "$@"
```

The test file asserts each of these lines (`launcher_test.bzl:678-713`). A real `OCX_HOME` store path would have the form `/home/<user>/.ocx/...`. The exact store layout is not defined in this checkout, so the real digest paths are not shown.

### Where the paths come from, and prefix rewriting

Every path in an eager launcher is an absolute host path. The values of `path` entries, `constant` entries and `list` entries are copied from the `ocx env` report verbatim (`repo_utils.bzl:1531-1547`, `:1586-1604`). No code replaces or rewrites a path prefix. The only string edits are quoting (`sh_quote`, `repo_utils.bzl:333-345`), reversal of PATH entries with first-wins deduplication (`repo_utils.bzl:1545-1555`), and list folding (`fold_lists`, `repo_utils.bzl:1458-1483`). There are no runfiles lookups in an eager launcher. The launcher test asserts that a launcher does not mention `OCX_CONFIG` or `OCX_PATCH_SNAPSHOT` (`launcher_test.bzl:724-726`).

`OCX_HOME` and `OCX_BINARY_PIN` are exported "so ocx entrypoint launchers re-enter the pinned ocx against the right store" (`repo_utils.bzl:1493-1494`).

### Handling of an `ocx env` entry

`env_entries` decodes the report (`repo_utils.bzl:873-894`). It reads `items` (ocx 0.6.6 and later) or `entries`, and renames `kind` to `type`. Each row has `key`, `value` and `type`. In `render_launcher`:

- A key that fails `valid_env_key` is skipped (`repo_utils.bzl:1531-1533`).
- `path` entries are prepended to the invoking environment's value of the key (`"${KEY:+:${KEY}}"`).
- `constant` entries replace the value.
- `list` entries are appended behind the invoking value, with the `separator` from the entry.
- An unknown type calls `fail` (`repo_utils.bzl:1541`).

### The generated `env.bzl`

`render_env_bzl` writes a file (`repo_utils.bzl:1608-1648`) that defines `_DATA = json.decode(<encoded payload>)` and four exported names. `OCX_ENV` is the list of entry dicts as reported, with absolute paths. `OCX_HOME` is the resolved home path. `OCX_SCANNED_PACKAGES` lists packages that forced a PATH scan. `OCX_REJECTED_BINS` lists tool names that were dropped.

The BUILD file contains `exports_files(["env.bzl"])` (`package.bzl:289`) and the default visibility is public (`repo_utils.bzl:1665`). Any package that can name the label can `load()` it. The example loads it from a BUILD file: `load("@tools_arm64//:env.bzl", ARM64_ENV = "OCX_ENV")` (`examples/project/BUILD.bazel:5`). `env.bzl` does not exist in lazy mode (`README.md:292-293`).

## 4. Executable targets, rule kind, runfiles, action inputs

Every discovered tool gets one `native_binary` target named `<tool>`, from `load("@bazel_skylib//rules:native_binary.bzl", "native_binary")` (`repo_utils.bzl:1659-1686`). Its `src` is `launchers/<name>.sh`. On Windows it also sets `out = "<name>.bat"` (`repo_utils.bzl:1681-1682`). `data` is attached only when the caller passes it, and the eager rules pass none (`package.bzl:285-297`, `project.bzl:271-275`). The `content` target is a plain `filegroup`, not executable.

In eager mode the runfiles of a tool target are therefore as follows. This part is INFERRED, because the skylib source is not in the checkout: skylib's `native_binary` is expected to add its output file to the runfiles and add `data`. The rule code here decides only that `data` is empty. The launcher script is the only file. `content` is not in `data`. The store files the launcher executes are not declared anywhere.

If a `genrule` uses such a target in `tools =` or `$(location ...)`, as `examples/package/BUILD.bazel:6-12` does, the rule code decides this: the inputs are the launcher script (and, INFERRED, the symlink to it that `native_binary` makes) and nothing else. The tool bytes are read through absolute paths that are not Bazel inputs. A target that wants the content as inputs must list `@jq//:content` itself. The cross-platform example does that (`examples/cross_platform/BUILD.bazel:26`).

In lazy mode `data` is `[ocx binary label] + staged config files + @bazel_tools//tools/bash/runfiles` (`package.bzl:95-98`), and for the project tier also `:ocx.lock` and `:ocx.toml` (`project.bzl:148-150`). The lazy launcher is the only tool target whose runfiles include the `ocx` binary.

## 5. Project mode

Repository contents, in eager mode (`project.bzl:158-275`):

- `ocx.toml` and `ocx.lock` copies, read from the checkout (`project.bzl:215-216`). `ocx pull` runs against these copies, and the other `ocx` calls use the checkout's `--project` path (`project.bzl:174`, `:228-236`, `:243`).
- `launchers/<name>.sh` per tool, `env.bzl`, and `BUILD.bazel` with `exports_files(["env.bzl"])` (`project.bzl:269-275`).
- There is no `content` filegroup and no symlink into the store.

Composition into one environment: `ocx lock --check` (`project.bzl:176-190`), then `ocx pull [--platform P] --lazy-mode never [-g groups]` (`pull_args`, `project.bzl:35-49`), then `ocx --format json --project <toml> env --pinned [--platform P] --lazy-mode never [-g groups]` (`env_args`, `project.bzl:51-72`). One environment results from one `env` call over the chosen groups. Without `groups`, ocx's defaults apply: every group is pulled, but only the default `[tools]` table is composed into launchers (`project.bzl:294-297`).

Targets: one `native_binary` per name in the closure surface (`ocx inspect --closure`, `project.bzl:242-268`). Every launcher carries the same composed environment (`write_launchers(ctx, discovered.bins, entries, ...)`, `project.bzl:269`). So each launcher sets the PATH and variables of all packages in scope, not of its own package only.

Dependencies of a launcher: eager launchers have no Bazel dependencies, as in section 4. The lock file and all packages are baked in only as absolute paths. The lock file is read at fetch time only, via `ctx.watch` (`project.bzl:165-166`).

Lazy project launchers carry `:ocx.lock`, `:ocx.toml` and the `ocx` binary as runfiles (`project.bzl:148`). They call `ocx --project <runfiles toml> exec --pinned [-g groups] -- <name>` (`lazy_project_command`, `project.bzl:74-94`). So every lazy launcher depends on the whole lock file and all of `ocx.toml`, not only its own package.

## 6. Lazy mode

### Launcher text

The lazy launcher is `render_lazy_launcher` (`repo_utils.bzl:1325-1387`). POSIX form, for the package tier with a package `ocx.sh/jq@sha256:abc` and tool `jq` (command from `package.bzl:88-89`, preamble from `repo_utils.bzl:1300-1308`, pinned rows from `launcher_test.bzl:804-815`):

```
#!/usr/bin/env bash
# Generated by rules_ocx — do not edit.
# --- begin runfiles.bash initialization v3 ---
set -uo pipefail; set +e; f=bazel_tools/tools/bash/runfiles/runfiles.bash
source "${RUNFILES_DIR:-/dev/null}/$f" 2>/dev/null || \
  source "$(grep -sm1 "^$f " "${RUNFILES_MANIFEST_FILE:-/dev/null}" | cut -f2- -d' ')" 2>/dev/null || \
  source "$0.runfiles/$f" 2>/dev/null || \
  source "$(grep -sm1 "^$f " "$0.runfiles_manifest" | cut -f2- -d' ')" 2>/dev/null || \
  source "$(grep -sm1 "^$f " "$0.exe.runfiles_manifest" | cut -f2- -d' ')" 2>/dev/null || \
  { echo>&2 "ERROR: cannot find $f"; exit 1; }; f=; set -e
# --- end runfiles.bash initialization v3 ---
OCX_PROJECT=""
export OCX_PROJECT
OCX_GLOBAL="0"
export OCX_GLOBAL
OCX_NO_PROJECT="1"
export OCX_NO_PROJECT
OCX_NO_CONFIG_REFRESH="1"
export OCX_NO_CONFIG_REFRESH
OCX_NO_CONSENT="1"
export OCX_NO_CONSENT
OCX_TOOLCHAIN_DIR=""
export OCX_TOOLCHAIN_DIR
OCX_NO_VERIFY="0"
export OCX_NO_VERIFY
OCX_ALLOW_YANKED="0"
export OCX_ALLOW_YANKED
[ staged config rows with `$(rlocation <repo>/<file>)` plus the guard line, only if set ]
exec "$(rlocation <canonical ocx_tool repo>/ocx)" package exec 'ocx.sh/jq@sha256:abc' -- jq "$@"
```

`OCX_NO_CONFIG="1"` and blanked hermetic rows appear only with `no_config`. The order of the pinned rows is the table order in `OCX_ENV_CLASSES` (`repo_utils.bzl:45-99`) without `OCX_QUIET`. The guard line for a staged row is `[ -n "$KEY" ] || { echo "rules_ocx: KEY runfile missing" >&2; exit 74; }` (`repo_utils.bzl:1323`). The project tier differs in the last line: `exec "$(rlocation <ocx_tool>/ocx)" --project "$(rlocation <repo>/ocx.toml)" exec --pinned [-g '<groups>'] -- <name> "$@"` (`project.bzl:137-142`, `:94`). The package tier requires an `@sha256:` reference, from `pins` or the `package` string (`package.bzl:67-70`).

The Windows form (`repo_utils.bzl:1369-1376`) is:

```
@echo off
rem Generated by rules_ocx - do not edit.
set "OCX_PROJECT="
set "OCX_GLOBAL=0"
... (the same pinned rows, then staged rows with absolute paths)
"<absolute path of ocx.exe>" package exec "<ref>" -- <name> %*
```

It uses CRLF line ends. A value containing `"` is dropped silently from the `set` lines (`repo_utils.bzl:1372-1374`, `bat_value` returns None).

### Run-time needs

The launcher needs the Bash runfiles library (`@bazel_tools//tools/bash/runfiles`, added to `data`, `package.bzl:96-97`), `bash`, `grep` and `cut` for the manifest path, and the `ocx` binary through runfiles. `ocx package exec` or `ocx exec` installs missing content on first use (`package.bzl:55-58`). That needs network access to the registry (or a mirror), and a store at the executing machine's default `OCX_HOME`, because the launcher exports no `OCX_HOME` (`launcher_test.bzl:842`: `asserts.false(env, "OCX_HOME" in script)`). The lazy launcher does not export `OCX_HOME`. The rest of the environment is the executor's. A translucent row without an attr is deliberately not exported (`repo_utils.bzl:1250-1254`). Lazy mode refuses `isolated_home` (`package.bzl:61-63`), and for packages also `index` (`package.bzl:64-66`).

### Source of the `ocx` binary

Lazy POSIX launchers locate `ocx` through `$(rlocation <ocx_tool>/ocx)` (`package.bzl:88`, `repo_utils.bzl:1229-1238`). The label is `ctx.attr.ocx`, default `@ocx_tool//:ocx`, and it is in `data` (`package.bzl:95`). On Windows the launcher bakes the absolute path of the `ocx` file in the output base (`package.bzl:86`).

## 7. Platforms

Host platform: `host_info(ctx.os.name, ctx.os.arch)` gives `linux/amd64`, `linux/arm64`, `darwin/amd64`, `darwin/arm64`, `windows/amd64` or `windows/arm64` (`platforms.bzl:73-118`). It is read inside every repository rule (`package.bzl:157`, `project.bzl:159`). The repository rule runs on the machine that runs the Bazel server, so that is the "host" here. No code reads the execution platform or the target platform inside a repository rule.

What is passed to `ocx`:

- Package tier: `-p <real platform>` when `resolved_platform` or `platform` is set, else nothing, so ocx resolves the host (`package.bzl:178-179`, `install_args` at `:50`). `pins` apply per platform key via `pinned_ref` (`package.bzl:104-120`), and the pinned manifest digest then fixes the leaf.
- Project tier: `--platform <platform>` when set, else nothing (`project.bzl:200`). The same `ocx.lock` supplies the leaves.
- Lazy mode passes no platform flag. The platform is resolved by the executing machine's ocx at run time (`project.bzl:192-196`). `platform` and `bins` together fail on the project tier.

Installing for another platform is possible: set `platform` (project or package) or `platforms` (package). The result is a content-only or env-only repository with no launchers, since `runnable` is false (`package.bzl:185`, `:261`; `project.bzl:240`, `:242`). The runnable test compares only the `os/arch` prefix, and a musl repository on a glibc host reads as runnable (comment at `package.bzl:181-184`).

Bazel platform objects: there is no `toolchain()` declaration anywhere in `ocx/` (grep over `*.bzl` and `BUILD.bazel` found none, INFERRED from the files read). For `platforms = [...]` on `ocx.package` the extension creates one `ocx_package_repo` per platform named `<name>_<slug>` and a hub `ocx_package_hub` named `<name>` (`extensions.bzl:287-313`). The hub writes one `config_setting` per platform with `constraint_values` from `ocx_platform_constraints` (`package.bzl:382-390`, `platforms.bzl:44-71`) and one `alias` per target with `select({":<slug>": "@<repo>//:<target>"})` (`package.bzl:393-405`). The hub aliases `content` in eager mode and the named launchers in lazy mode (`package.bzl:393`). The `select()` keys on the target platform of the configuration the alias is analysed in. The example changes `--platforms` with a rule-level transition (`examples/cross_platform/transition.bzl`). In an eager hub the `alias` for a launcher name is not created, so only `//:content` can be selected (`docs/guides/cross-platform.md:26`: "The hub `@jq` aliases only `//:content`").

The constraint mapping knows only `linux`, `darwin`, `windows` and `amd64`, `arm64` (`platforms.bzl:13-21`). Anything else fails the hub.

## 8. The `ocx` binary

`@ocx_tool` is created by the `ocx_download` repository rule, always, from the `ocx` extension (`extensions.bzl:249-254`). The default version is `0.6.6` (`versions.bzl:15`), with floor `0.6.1` (`versions.bzl:18`). The rule reads the release row from `dist/dist.json` (or `OCX_INSTALL_DIST_URL`), downloads the archive with `ctx.download_and_extract(url, ..., sha256 = row["sha256"])` (`download.bzl:45`), and symlinks the extracted binary to `ocx` (`download.bzl:56`; plus `ocx.exe` on Windows, `:57-58`). The host triple selects the artifact (`download.bzl:33-34`, `platforms.bzl:97-117`). Linux uses a musl build. A mirrored manifest named `<sha256>.json` is verified, any other name is not (`download.bzl:36-38`, docs at `:71-76`).

The repository rules call that file through `ctx.execute` (`repo_utils.bzl:838`). It is not a `toolchain`. There is no use of an `ocx` on `PATH` anywhere.

An `ocx` binary becomes an input of a build action only in lazy mode. There the `ocx` label is in the `data` of every lazy `native_binary` (`package.bzl:95`, `project.bzl:148`), so it is a runfile of the launcher. Eager targets do not carry it. They bake only its absolute path as `OCX_BINARY_PIN` (`repo_utils.bzl:1586`).

## 9. Repository rule declarations

There is no `local`, `configure`, or `environ` argument on any `repository_rule` in the checkout. A grep for `local *=`, `configure *=`, `environ` and `repo_metadata` over `ocx/`, `docs/`, `examples/`, `e2e/`, `MODULE.bazel`, `.bazelrc` and `bazel/` matched nothing relevant. No rule returns `repo_metadata`. The extension returns `module_ctx.extension_metadata(reproducible = True)` (`extensions.bzl:331`), and its docstring says the extension "is marked reproducible and stays out of MODULE.bazel.lock" (`extensions.bzl:9-10`). That is the module extension, not a repository rule.

Host state read or written outside the repository directory:

- The `ocx` store. Default `OCX_HOME` is `$OCX_HOME`, else `$HOME/.ocx` (`$USERPROFILE\.ocx` on Windows) (`repo_utils.bzl:663-671`). It is passed in `env = {"OCX_HOME": home}` (`repo_utils.bzl:696`). `ocx package install` and `ocx pull` write the store there, and the eager launchers and symlinks point into it. With `isolated_home` it is `<repo>/.ocx_home` (`repo_utils.bzl:661-662`).
- Host config files, watched but not written: `/etc/ocx/config.toml`, the user config (`$XDG_CONFIG_HOME` or `~/.config/ocx/config.toml`, macOS `~/Library/Application Support/ocx/config.toml`, Windows `%APPDATA%\ocx\config.toml`), `$OCX_HOME/config.toml`, and `$OCX_HOME/state/managed-config/{snapshot.json,config.toml}` (`repo_utils.bzl:417-471`, watched at `:777-789`). Also `$OCX_HOME/sigstore/trusted-root.json` (`repo_utils.bzl:621-645`, watched at `:768-772`).
- The ambient environment, read with `ctx.getenv` for these rows: `OCX_MIRRORS`, `OCX_INSECURE_REGISTRIES`, `OCX_OFFLINE`, `OCX_FROZEN`, `OCX_REMOTE`, `OCX_JOBS`, `OCX_INDEX`, `OCX_DEFAULT_REGISTRY`, `OCX_MANAGED_CONFIG`, `OCX_PATCHES`, `OCX_EXTRA_CA_CERTS`, `OCX_CONFIG`, `OCX_PATCH_SNAPSHOT`, `OCX_SIGSTORE_TRUSTED_ROOT`, `OCX_NO_CONFIG` (`repo_utils.bzl:45-99`). `OCX_AUTH_<REGISTRY>_*` cannot be enumerated and is not tracked (`repo_utils.bzl:51-52`).
- The checkout (`ocx.toml` project directory) is read by `ocx` for `lock --check`, `env` and `inspect` (`project.bzl:174`). The writes of `pull` are redirected to the repository copies (`project.bzl:209-217`).
- One side process: `/bin/sh -c 'sleep ...'` for retries (`repo_utils.bzl:852-857`), and `/bin/sh` for the executable scan (`repo_utils.bzl:1018-1031`).

## 10. Remote execution mentions, and absolute host paths

Every mention found in the checkout (excluding vendored agent-rule folders, `node_modules` and lock files):

## 11. Windows

What differs (all from the code above):

- Launchers are `.bat` files with CRLF line ends, and `native_binary` gets `out = "<name>.bat"` (`repo_utils.bzl:1555-1583`, `:1682`). The eager Windows launcher sets `OCX_HOME`, `OCX_BINARY_PIN` and constants with `set "KEY=VALUE"`, prepends PATH-type values with `set "KEY=a;b;%KEY%"`, and folds list keys with an `if defined` line. It ends with `"<target>" %*`.
- A value with `"` is dropped (not rendered) from `set` lines, and a launcher target containing `"` fails (`repo_utils.bzl:347-364`, `:1557-1560`). `%` is doubled.
- The `ocx` binary also appears as `ocx.exe` (`download.bzl:57-58`), and `ocx_bin` prefers it (`repo_utils.bzl:792-810`).
- Windows lazy launchers have no runfiles library and bake absolute paths (section 6, `repo_utils.bzl:1357-1369`). `data` adds the runfiles library only for non-Windows (`package.bzl:96-97`).
- Absolute-path test accepts drive letter or UNC paths (`repo_utils.bzl:388-414`). `$USERPROFILE\.ocx` is the default home (`repo_utils.bzl:668-670`). `/etc/ocx/config.toml` is not watched (`repo_utils.bzl:437-444`, documented gap).
- Executable discovery uses extensions `.exe`, `.bat`, `.cmd` instead of the exec bit (`repo_utils.bzl:1012-1027`, `:1126`). `resolve_bins` joins with `/` even on Windows (`repo_utils.bzl:1130`).
- Symlinks: `ctx.symlink` is used for `content` and `entrypoints` as on POSIX. The ruleset's `.bazelrc` sets `startup --windows_enable_symlinks` and `common:windows --enable_runfiles` (`.bazelrc:6-8`) for its own `sh_test` data. Whether a consumer needs the same flags is not stated in the rule code.
- Retries do not sleep on Windows (`repo_utils.bzl:848-851`).
- `windows/arm64` is mapped by `host_info`, but the Bazel constraint table covers `windows` with `amd64`/`arm64` (`platforms.bzl:13-21`).
