- **Upstream SBOM carried.** Where an upstream publishes an SBOM, release mirroring fetches it and attests it with the signer the `sign:` block names. It is located through two interfaces (owner, 2026-11-25: "we need an interface in the dist json as well as the configuration then though to specify the sbom url right? in case it exists. with the common platform overwrite and default fields"): the url-index document that a generator or an inline `versions:` map supplies ("dist json" is read as that document, Claude's reading), and `mirror.yml` for a source that only lists release asset names, in the `default:` plus `platforms:` form that `metadata:` and `asset_type:` already use (`docs/reference/mirror-yml.md` in `ocx-sh/ocx-mirror`). The mirror SDK gains the interface that emits the url-index field. The exact shape of both is under Open questions.
- **SBOM command.** Where the upstream publishes none, a free-form command the spec names produces the SBOM (Decisions). It runs after the download, on the package content, in a job that holds no signing permission, and hands one CycloneDX JSON document to the push job, which validates and attests it (the contract is Claude's reading, confirmed with the restate of 2026-11-25). A command that fails or writes an invalid document fails the run (default under Open questions).
- **Minimal generator.** With no upstream SBOM and no command, a built-in generator writes the SBOM from what the mirror already knows; for PyPI that is every wheel of the resolved lock with its hashes. A generated SBOM says it was produced by the mirror, not by the upstream.
- **OCX dependencies in an SBOM.** A mirrored package's SBOM names each OCX dependency as a component by digest (a PyPI package depends on its pinned interpreter package) and does not embed the dependency's SBOM.
- **PyPI SBOM from a scanner.** The mirror SDK gains a syft helper that the SBOM command runs, promoted with `uvx`, and the PyPI mirror workflow uses it. On one PyPI package the loop measures whether the scanner's document lists the shared libraries bundled in the wheels and carries the wheel hashes the lock holds, and adds what is missing in the helper (Open questions).
- **One generated workflow per package, with SBOM and backfill.** The generated workflow gains the SBOM job, and backfill becomes a dispatch mode of the same file, so a package keeps one stable workflow file and one signer identity (default under Open questions). `ocx-mirror package pipeline sign` also backfills SBOMs for packages already mirrored.
- **Registry sync carries signatures and SBOM attestations, proven.** `registry sync` already copies referrers (`docs/reference/registry-yml.md` § Signatures and attestations in `ocx-sh/ocx-mirror`); the loop proves end to end that a client verifies the copied signatures, the SBOM attestations and the signatures of SBOMs against the upstream `publishers`. It generates no SBOM. It verifies the upstream index signature while syncing unless told not to.
- **Subsets.** `registry sync` selects packages (the `include:` and `exclude:` filters exist), tags and platforms. A platform subset writes a new OCI image index, and tag and package subsets copy each tag's image index byte for byte (default under Open questions).
- **Re-signing.** Opt-in, with copy-over as the default. With it on, the mirror verifies each upstream signature against the upstream `publishers` and fails the package otherwise, adds its own signature to the package and to its SBOM, and appends its signer to `publishers` in the mirror's index, where the upstream entries stay. The signer is a key file or keyless on a configurable Sigstore instance, in the shape of the existing `sign:` block.
- **The mirror's index is signed.** The mirror signs its resolution index with the index signature of the first loop. A subset sync with no index signer fails; one explicit setting publishes the index unsigned, also when the upstream's index was signed.
- **`ocx-sh/e2e-mirror`.** A new fixture repository beside `ocx-sh/e2e-package` and `ocx-sh/e2e-index`. Everything that needs a real certificate, a real registry or a served index runs there, dispatched: release mirroring with each SBOM source, backfill, registry sync with subsets, re-signing and a signed mirror index.
- **Existing specs keep working.** A `mirror.yml` or a `registry.yml` without the new blocks behaves as before and renders the same workflows. The one case in question is a filtered `registry.yml` against a signed upstream (Open questions).
- **Reference documentation.** *(Claude's addition.)* `docs/reference/mirror-yml.md`, `docs/reference/registry-yml.md` and `docs/reference/cli.md` in `ocx-sh/ocx-mirror`, and the SDK's documentation, describe every new key, command mode and helper.

## Decisions

Working positions taken with the owner on 2026-11-13, unless a bullet gives another date.

- **The mirror signs a package only after verifying it** (owner, 2026-11-25, chosen over "sign what was copied" and "re-sign the index only"): with re-signing on, the upstream signature is verified against the upstream `publishers` first, and a package that does not verify fails the sync. Counter-argument named once and not pursued: `.claude/artifacts/research_mirror_signature_practice.md` found no ecosystem in which a mirror re-signs individual packages, and a Sigstore keyless bundle verifies with no network call when the trusted root is supplied out of band, so package re-signing is a convenience for air-gapped clients (one key, no root rotation to track), not a necessity.
- **Two loops** (owner, 2026-11-25, chosen over three and one): index signing first (`ocx-sh/ocx`, `ocx-sh/index`, `ocx-sh/indexbot`), then all mirror work in one loop (`ocx-sh/ocx-mirror`, its SDK, `ocx-sh/e2e-mirror`).
- **Reversals of the ratified ocx-mirror decisions, confirmed in words** (owner, 2026-11-25): the mirror carries upstream SBOMs; `registry sync` gains package and tag subsets and platform subsets. Generating an SBOM where the upstream has none was not among the confirmed items; the next bullet settles it.
- **Two mirror use cases, two SBOM rules** (owner, 2026-11-25). A mirror of a registry (`registry sync`) generates no SBOM: "that is part of the package author"; it carries what the upstream published. A mirror of releases is the package author: it provides an SBOM, signs the package and the SBOM, supports backfill, and each package gets a stable workflow file for release and backfill (owner: "look that we get per package a stable workflow yml for backfill/release"). The SBOM source order below applies to release mirroring only.
- **The address-keyed Sigstore tables replace `[trust.sigstore]`, as a break, inside the index-signing loop** (owner, 2026-11-25). The shape is the ADR's item 4: `[sigstore."<host>"]`, `[registry] sigstore` and `[registries."<host>"] sigstore`, and the `sigstore` field of a publisher entry (the two registry-level keys were dropped later the same day, see the next bullet). Asked "Do you lift 'non-breaking' for `config.toml`, as a hard break with the old table refused by name?", the owner answered "yes in this case it is allowed to be breaking". Asked whether it runs as the first slice of the index-signing loop or as a loop of its own, the owner answered "no we splitted our second loop alreayd again into two - inline that into the next loop". So there is no second form and no window: a leftover `[trust.sigstore]` is refused with a message that names the new table, never ignored as an unknown key. Claude had leaned towards a loop of its own and named the risk once (reshape, index signing, the bot and the signing job failing together); inside the loop the reshape comes first *(Claude's ordering)*, because the keyless `ocx.sh` index signature cannot be verified on a host pinned to a private instance without it.
- **There is no registry-level `sigstore` key** (owner, 2026-11-25, chosen over keeping it as the default for entries without the field and over keeping it for signing only). The instance is named in one place, the `sigstore` field of a signer entry: an index `publishers` entry, an `index_publishers` entry, an operator `[[trust.policy]]` signer. Its value is the key of a `[sigstore."<host>"]` table. An entry without the field always means the public instance; an entry naming a host the client has no table for matches nobody. On the signing side the host of `--fulcio-url` selects the table. This departs from the ADR's item 4, which lists `[registry] sigstore` and `[registries."<host>"] sigstore`; the loop amends the ADR. Cost named once and accepted: an index written for a private instance under the single-table model adds the field to its entries, and keeps a twin without it while older clients read that index.
- **`ocx index sign` takes the signing flags of `ocx package sign`, for key and keyless alike** (owner, 2026-11-25: "for index sign the cli flags should align with the package sign parameters for both key and keyless signing"). Read in `crates/ocx_cli/src/command/package_sign.rs`: `--key`, `--rekor-upload` / `--no-rekor-upload`, `--fulcio-url`, `--rekor-url`, `--identity-token-file`, `--identity-token-stdin`, `--no-tty` and `--no-cache`, of which the key, Rekor-upload and signature-format flags are flattened option groups. *(Claude's reading: the same option groups are reused and not re-declared, so the two commands cannot drift; what addresses a package stays behind, that is `--platform`, the tag options and the package identifier, replaced by the index directory; whether the signature-format option applies to a signature served as a file beside `c/index.json` is the loop's design call.)* This settles the difference raised on resume, where the ADR gives only `ocx index sign --key <pem> <dir>`.
- **A mirror of the Sigstore TUF repository is configured under `[mirrors]`, keyed by the TUF host** (owner, 2026-11-25, chosen over a key of the instance table: "i would go for a and also make sure the environment variable is considered as well"). It is network policy, as `.claude/artifacts/adr_index_indirection.md` F5b draws it; the instance table keeps the path and inline trust roots. The environment variable is read as `OCX_MIRRORS` (Claude's reading), which carries the same per-host union and wins per host.
- **The TUF mirror's design is ratified and it is built later, as a follow-up outside the index-signing loop** (owner, 2026-11-25, chosen over building it in the loop and over handing off at once). The design: a third `[mirrors]` role named `trust_root` beside `registry` and `index`; a plain address covers every role and an object names the roles it rewrites; `OCX_MIRRORS` carries the same union; one `MirrorMap` in `ocx_oci` holds every role, with the registry role as a method of its own because it rewrites an OCI reference; the documentation says a caching proxy must not cache `timestamp.json`, that the mirror serves a proxied network, and that a network with no route out uses the inline root. The follow-up owns what was not checked: the change in the vendored `sigstore` fork, the address guard for a private target, and a test fixture for a TUF repository.
- **A signature check on the managed configuration is a follow-up, outside both loops** (owner, 2026-11-25): "signed managed config must be a follow up and kinda important it is not verified atm, this needs more brain work to establish a good scheme especially considering updating the signer of the managed config itself, leading into handshake and cross signing scenarious". Consequence for the index-signing loop *(Claude's reading, stated to the owner; carried under Open questions with this as the default)*: an index authority that arrives through a managed payload follows the rule `trusted_root_json` already follows, honoured only from a digest-pinned `[managed].source` or from a local tier. Cost named once: until the follow-up lands, every rotation of a signer or of the Sigstore root is a new pin on every host.
- **Index signing is in scope and `ocx.sh` rolls out to `warn`**, not `enforce`. Ordering constraint: the `ocx.sh` signing job must be deployed before a client with the `warn` default is released, otherwise every fresh fetch warns about an unsigned index.
- **The SBOM generator is a free-form command, and syft arrives as an SDK helper** (owner, 2026-11-25, chosen over a typed generator with a syft preset and over keeping the `syft` keyword; it reverses the next bullet's "syft as a first-class variant" and "No generic command hook"): "free-form command, similar to dist we should promot uvx which could itslef load the mirror-sdk with a new syft helper, we also have the ptyhon sdk for ocx which could bootstrap then - though that is currently a bit outdated". Read in `ocx-sh/ocx-mirror` at `0cb959a`: the shape already exists. `GeneratorConfig` in `crates/ocx_mirror_source/src/generator.rs` is a `command` list with `working_directory` and `timeout_seconds`, it has two callers, and the generated workflows install nothing for it beyond `setup-ocx`. That answers the second reason of 2026-11-13: the pin lives in the script and in ocx, not in the workflow. The first reason still decides where the command runs: it needs the package content, so it is a new point after the download, not the `url_index` generator. *(Claude's reading, confirmed with the restate of 2026-11-25: the command gets a fixed contract, the package directory in and one CycloneDX JSON document at a given path out, read back and validated, because the free-form shape in GoReleaser lets format and file name disagree; and it runs in a job that holds no signing permission, with the document passed to the push job, because `uvx` fetches code at run time.)*
- **The PyPI SBOM comes from a scanner over the package** (owner, 2026-11-25, chosen over carrying the documents wheels embed plus the lock list, over the lock list alone and over measuring first). It runs through the command above. Not measured: `.claude/artifacts/research_sbom_generator_contracts.md` found no source that shows syft listing the shared libraries bundled in a wheel. ## Open questions

Each default below was listed in the restate of 2026-11-25 and confirmed by the owner's yes as the working answer. The questions stay listed so the plan can overturn one with evidence, which it then reports.

- [NEEDS CLARIFICATION: What shape do the two upstream-SBOM interfaces take?]
  Recommended: in url-index, an optional `sbom` on a version (the default) and on an asset's object form (the override for that asset's platform), each an address or `{url, sha256}`, added to v1 the way the object form was; in `mirror.yml`, an `sbom:` block with `default:` and `platforms:`, each a regex list matched against the version's asset names as `assets:` does — url-index has no platform keys today and the spec's regexes assign platforms, so an asset-level field is per platform without adding any, and a dedicated field keeps SBOM addresses out of the list those regexes match, where a new entry could make an existing spec ambiguous. The format is read from the document, since ocx attests both CycloneDX and SPDX (`crates/ocx_sign/src/attest/predicate.rs`). Which interface wins when both name one is left to the plan.
- [NEEDS CLARIFICATION: Does the syft helper of the mirror SDK start syft by calling `ocx` directly, or through the Python SDK for ocx?]
  Recommended: by calling `ocx` directly — the runner already has it through `setup-ocx`, and the owner called the Python SDK for ocx "a bit outdated", so the other route adds its refresh to this loop.
- [NEEDS CLARIFICATION: Does a scanner's document for a PyPI package list the shared libraries bundled in its wheels, and does it carry the wheel hashes the lock holds?]
  Recommended: measure both in the loop on one `mirror-pypi` package before the PyPI workflows are switched over, and add what is missing in the SDK helper — no source read shows either, and the owner chose the scanner without a measurement.
- [NEEDS CLARIFICATION: How does a subset keep upstream signatures valid when the image index is rewritten?]
  Recommended: tag and package subsets copy each tag's OCI image index byte for byte; a platform subset writes a new image index, which carries no upstream index signature, and relies on the per-platform signatures that install verifies. The resolution index is a separate matter, see Threads.
- [NEEDS CLARIFICATION: Is append the only re-signing mode built now, with replace left as a later, separate opt-in?]
  Recommended: yes — it is the decision of 2026-11-13, the owner called append fine on 2026-11-25, and it meets the offline case; replace is additive later. Re-signing itself stays opt-in with copy-over as the default.
- [NEEDS CLARIFICATION: Is backfill for a mirrored package a mode of the package's one generated workflow (one signer identity) or a second generated workflow (two identities in `publishers`)?]
  Recommended: one file, backfill as a dispatch mode — a mirror signs after the upstream's build either way, so a second identity says nothing; the owner leaned the same way on 2026-11-25.
- [NEEDS CLARIFICATION: When the spec names an SBOM command and it fails or writes an invalid document, does the run fail or fall through to the minimal generator?]
  Recommended: the run fails — a silent step down to the lock list would hide a broken scanner behind a document that still attests.
- [NEEDS CLARIFICATION: An existing `registry.yml` with `include:` or `exclude:` is already a subset and names no index signer. Once the upstream index is signed, does its next sync fail, which breaks the non-breaking line for mirror specs?]
  Recommended: yes, it fails, as a named break of the ocx-mirror release — the operator's fix is one line (a signer or the explicit unsigned setting), and an unsigned index published silently from a signed source is the downgrade the rule exists to stop. It needed the owner's word, as the `[trust.sigstore]` break did; it was given with the restate of 2026-11-25, which listed this default and was answered with yes, and the separate question was not answered in words of its own. Not checked (found 2026-11-25 while listing the user-facing changes): whether the `c/index.json` that an unfiltered `registry sync` writes is byte-identical to the upstream's, which decides whether copy-over can carry the upstream index signature at all (`docs/reference/registry-yml.md` in `ocx-sh/ocx-mirror` does not say).
- [NEEDS CLARIFICATION: In which order do the pull requests of this loop land, and what does ocx-mirror pin while the first loop is unreleased?]
  Recommended: the loop starts once the first loop is merged on `ocx-sh/ocx` `main`; ocx-mirror's submodule pins that commit, the SDK follows, and the pin moves to the released ocx by a follow-up the owner triggers after releasing. ## Verification

Each check is shown red on the failing case and green on the passing one. Everything that needs a real certificate, a real registry or a served index runs in `ocx-sh/e2e-mirror`, dispatched, never per pull request.

- **Mirror SBOMs**: a mirrored package carries an SBOM from each source in turn (the upstream's, found once through the url-index field and once through the `sbom:` block of `mirror.yml`; the spec's command; the minimal generator), attested by the mirror's signer, and a generated one names the mirror as its producer; a platform override wins over the default; a command that writes no document, or one that is not valid CycloneDX JSON, fails the run (the default under Open questions); an already mirrored package gains one through backfill.
- **PyPI**: one `mirror-pypi` package gets its SBOM from the scanner through the command, and the run records whether the document lists the bundled shared libraries and the wheel hashes (the measurement under Open questions).
- **Registry sync**: a sync of a subset (some packages, some tags, some platforms) keeps every upstream signature and SBOM attestation verifiable against the upstream `publishers`; a package whose upstream signature does not verify fails a re-signing sync; with re-signing, a client configured only with the mirror's key verifies packages, SBOMs and the index with no Sigstore network access.
- **Subset index**: a subset sync with no index signer fails and publishes no index; with a signer it publishes an index the mirror signed, which a client that names that signer accepts under enforce; with the explicit setting it publishes the index unsigned, also when the upstream's index was signed.
- **Non-breaking**: an existing `mirror.yml` or `registry.yml` without the new blocks behaves as before and renders the same workflows; a filtered `registry.yml` against a signed upstream follows the answer under Open questions.
- **Loop phases**: as under Decisions › Loop shape.
