## Decisions

- **The first release fetches package bytes in a repository rule on the client, and nowhere else** (owner, 2026-11-23). A network-free build action extracts. The download inside a build action on the executor is deferred; it stays possible later because both routes fill the same blob directory. This reverses three lines of `.agents/discussions/bazel-hermetic-package-bundles.md`: "The fetch is an ordinary action", the requirement "under remote execution a build does no local work and sends no traffic from the client to the cluster", and the cache bar "zero registry bytes" as a default. The last two now hold only with `--experimental_remote_repo_contents_cache` on Bazel 9.3.0 or later. Lines that fall with the executor download: executors need registry or mirror access, credentials come from the executor, and the per-project dictionary of execution properties for network.
- **The repository rule downloads with the host `ocx`; a native download comes later** (owner, 2026-11-23). First release: the rule runs the host's `ocx package export` for one package and one platform into the repository. The Bazel ADR also specifies the data a native download needs, the blob list from `ocx package inspect` plus the physical blob URLs, so that `rctx.download` and the index-generated modules can be added without a redesign. Accepted cost for the first release: Bazel's downloader config, repository cache and `--distdir` do not apply, because `ocx` does the transfer. This narrows the earlier out-of-scope line "any design in which Bazel's downloader fetches package blobs" to "not in the first release".
- **Extraction is a build action by default, plus a repository-rule variant** (owner, 2026-11-23, confirming the 2026-11-18 "two materialisers" decision). The owner's reason: a tool cannot simply be forwarded to a remote runner, so the action is needed. The action runs on the tool's own platform, takes that platform's `ocx` as an input file through the toolchain, reads the repository's blob directory as input and uses no network. The repository-rule variant unpacks on the client, for per-file labels and for tools that other repository rules run.
- **One repository per package and platform, holding that platform's blobs only** (owner, 2026-11-23: "the export could just contain that platform ... this would spare a lot of network traffic"). The platform list is explicit: `ocx.lock` pins one leaf digest per platform and libc variant, and the module extension generates the repositories from it with no registry call. The rule passes the platform to `ocx package export`, whose own default is every platform. Bazel fetches a repository only when the build selects it. Working note, from Bazel's documented behaviour and not tested: `bazel fetch` and `bazel vendor` over everything still download every platform.
- **`bazel fetch` and `bazel vendor` cover ocx packages** (consequence of the entry above, 2026-11-23). The separate `bazel run` export target is no longer the only offline route.
- **Bazel modules generated from the ocx index get their own discussion later** (owner, 2026-11-23), once rules_ocx works under remote execution. The Bazel ADR records one requirement from the idea: rules_ocx works from digests and blob data handed over as plain attributes, with no `ocx.lock` in the root workspace and no registry call at analysis.

### As handed off on 2026-11-26 (read this first)

This block is the settled design in short. Requirements bind the run. The blocks "Ruled by the owner" hold the owner's own words. Everything else is the record of how the design was reached.

- **ocx gets one command in each tier.** `ocx vendor -o DIR [-g GROUP…] [NAME…]` takes a project's groups and binding names. `ocx package vendor -o DIR PACKAGE…` takes package identifiers. Each takes one platform and one output directory, and `-o` (`--output`) is required.
- **What a run writes.** The selected packages and their dependencies, each once, as plain files. A native launcher for every binary and entry point. `DIR/manifest.json`. The directory works at any path and needs no `ocx` to run a tool.
- **`--manifest-only`** writes `DIR/manifest.json` and nothing else, and downloads no layer. A field in the manifest says that the content is absent.
- **The manifest is the interface.** It lists the packages, the links, the tools by name and the environments. Every value is resolved, and paths are relative to the directory through one fixed token. It is a versioned specification, published like ocx's other JSON specifications, and it must not break. Nothing in it or in the directory is specific to Bazel. It never goes to stdout.
- **The launcher is one native program for every platform.** A new kind of launcher data starts the target directly. Launchers of installed homes keep starting `ocx`; moving them is [ocx-sh/ocx#679](https://github.com/ocx-sh/ocx/issues/679) and not this work.
- **rules_ocx runs the command in a repository rule, on the client.** One repository per declared set and platform. The hub is generated from facts in `MODULE.bazel.lock`, which come from the call with `--manifest-only`. Links are declared symlinks, and a directory with no link below it is one directory label. rules_ocx reads the manifest and nothing else of ocx.
- **Reversed by this hand-off:** three decisions of 2026-11-23, namely extraction in a build action, one repository per package, and the repository rule running `ocx package export`.
- **Words in the older text.** "The materialise command" is `ocx vendor`. "The document" is the manifest. "The no-files call" and "the describe call" are `--manifest-only`. Where older text speaks of a report root, of `--dry-run`, of a subcommand, of a default directory or of stdout, the rulings of 2026-11-26 win.
- **Left to the run's architecture step:** every entry under Open questions.
- **Grants.** The list under Intent, "Hand-off to a goal loop", says what the run needs. It grants nothing; a grant comes only from the owner's own invocation of `/hex-loop`.

### Track 2 as it stood on 2026-11-23 (history; three of its decisions are reversed, see the block above)

The Decisions of `.agents/discussions/bazel-hermetic-package-bundles.md` are the baseline. They stand unless this block says otherwise.

- **Declaration, unchanged.** `ocx.project(...)` in `MODULE.bazel`; the module extension reads `ocx.lock`; package metadata is kept as facts in `MODULE.bazel.lock`.
- **Download, changed.** A repository rule on the client runs the host `ocx package export` for one package and one platform. The repository is a blob directory in the shipped layout.
- **Extraction, changed in its input only.** A build action on the tool's platform turns the blob directory into one content tree per package digest. It needs no network. It needs the content-tree command that ocx still lacks.
- **Use, unchanged.** A provider with tree, environment and entry points, or the native launcher for generic executable labels.
- **Reversed.** "The fetch is an ordinary action"; "executors need network access to the registry or a mirror"; "private-registry credentials come from the executor"; "network for the fetch action is set on the extension"; the requirement "under remote execution a build sends no traffic from the client to the cluster"; the cache bar "zero registry bytes" as a default. The last two hold only with `--experimental_remote_repo_contents_cache` on Bazel 9.3.0 or later.
- **Credentials.** The host `ocx` in the repository rule uses the client's own ocx and registry configuration. Mirrors are the client's ocx configuration too.
- **Stale wording.** "bundle" means an export directory or a blob directory. `LayoutTransport` does not exist. The `bundle` attribute sketched for `ocx.project` becomes a blob-directory label.
- **Offline.** `bazel vendor`, or a blob-directory label that points at a checked-in or fetched export directory.
- **Test rig.** Executors without network are now the normal case, so Buildbarn's reference setup needs no special handling.
- **Still missing in ocx, unchanged from the earlier discussion.** The content-tree command; the environment report with symbolic roots; the unified launcher with its direct-exec and environment-wrapper modes; the verification gate on the lock write.
- **Order of work.** Spikes, then the Bazel ADR, then the ocx side, an ocx release, then rules_ocx with the repository rule and the extraction action, then this repository moves to it. Later, each on its own: the native download, the executor download as an opt-in, the index-generated modules.

### Proposed on 2026-11-25, ratified by the owner with the hand-off on 2026-11-26

The owner asked on 2026-11-25 to reconsider the whole discussion and allowed tests. Each line below names the decision it would change. The evidence is under Research, in the entries dated 2026-11-25. The owner ratified the block on 2026-11-26. Where a line below disagrees with "Ruled by the owner on 2026-11-26" or with the block "As handed off", those win.

- **Unpack in the repository rule, not in a build action.** Changes "Extraction is a build action by default" (2026-11-23) and the "two materialisers" decision of 2026-11-18. The rule runs the host `ocx` for the execution platform, and `ocx` writes the directory (see the interface entry below). The prototype reached the same files with today's commands: it pulled into a scratch home inside the repository, moved `content` out and deleted the home.
  - For: a tree built by an action loses its links for a remote consumer always, and for a local consumer after a cache hit (run, two backends). A repository on the client's disk does not have the second failure (run). rules_nodejs, rules_python, rules_java and toolchains_llvm unpack in the repository rule (read from source). Bazel's repo contents cache shares the result between output bases on one machine (run).
  - Against: rules_js extracts in an action into one tree per package (read from source). Its packages are linked to each other by declared symlinks outside the trees; links inside a tree are the case ocx packages have and npm packages mostly do not. The first upload is larger: 144 MB of files against a 59 MB archive for node (run).
  - The owner's reason for the action, "a tool cannot simply be forwarded to a remote runner", does not hold: Bazel uploads the files of an external repository as ordinary action inputs (run).
  - An action form that keeps links exists and is recorded for later: one unpack action that declares every file and every link as its own output (run on NativeLink, every situation, cache hits included). It needs the complete file list when the build is analysed, and an unpacker on the executor. On Buildbarn's reference configuration it failed: the action's result record for 4800 outputs is 941839 bytes and that configuration stores at most 581632. It is the form a later download on the executor would use.
- **Carry every link as a declared symlink in the launcher's runfiles.** Changes "Trees are never flattened" and the shipped backend conformance test (2026-11-18). `ocx` lists the links in its manifest and leaves them off the disk. A rule declares one unresolved symlink per link. The prototype listed and deleted them with `find`. The requirement on a backend becomes: it keeps symlink nodes in an input root. Buildbarn's hardlinking worker and NativeLink do (run). A link to a directory works the same way (run).
  - Limit: the files are repository files and the links are build outputs, so only a runfiles tree shows them as one directory. A rule that takes a package's file labels directly gets the files without the links. Copying every file to an output gives a complete tree as plain inputs, at one internal action per file (run).
  - Mode bits are not kept, in any form: on the executor every input file is executable, 4797 of 4797 for node where the package has 66 (run). No package is known to depend on a file not being executable.
- **Hand link-free directories over as directory labels.** New. A directory of a package that holds no link below it is one directory label; the remaining files are file labels; the links are declared symlinks. Fidelity is the same as with file labels only (run).   - **Materialise, new.** A command in two forms, because ocx's two command tiers are firm (read on main: a command that takes binding names and a command that takes package identifiers are two commands). The project form takes the selection of `ocx inspect` and `ocx exec`: groups and binding names. The `package` form takes package identifiers. Each takes one platform and one output directory. It writes the selected packages and their dependencies, each once, as plain files. It writes a native launcher for every binary and entry point the selection exposes. It writes one document that lists the packages, the links, the tools by name and the environments. The environments have the shape of the `ocx env` report, with every path relative to the directory. On request it leaves the links off the disk. The directory can be moved, and the output is the same on every machine. The command reads the registry or a blob directory, and it works for a platform that is not the host's.

The launcher comes from the same cross build, is hardlinked or copied verbatim, and its data sits beside it and never inside it. The code already states this rule for the Windows blob. A design that edits the launcher per tool would need `codesign`, which ocx runs on a macOS host only, so it could not materialise for macOS from Linux.

- There is no remote-execution lane. The only remote piece is a cache (`bazel/baseline.bazelrc:3`).
- There is no local registry. Every test and example pulls from the live public registry (`taskfile.yml:88`), so no test can count registry requests.
- The one offline check is `deep:offline` (`taskfile.yml:164`). It proves that a fetch against an empty store fails; it does not prove an offline build passes.
- The suite runs Bazel 8.7.0 and 9.x (`taskfile.yml:15`), and `MODULE.bazel` declares `bazel_compatibility >= 8.0.0`.
- All three examples and `e2e/bzlmod` (the BCR presubmit workspace) use `bins`, the lazy mode in `ocx/private/package.bzl:52`.
- The earlier discussion drops both Bazel 8 and `bins`. So the new rules_ocx is a breaking release that rewrites every example and the BCR workspace.

**Where the rig lives.** In the rules_ocx repository, as a new lane beside `e2e/bzlmod`. The conformance test ships with rules_ocx, so the rig and the test belong together.

**Parts.**

- A local OCI registry with an access log. zot is the candidate; the ocx acceptance suite already runs it. It is seeded with fixture packages: one with several platforms, one with a dependency, one with relative symlinks, one that needs a login.
- Buildbarn's reference compose setup (executor network off, no shell in the runner) and the second backend. The same setup serves as the generic REAPI cache.
- One fixed example workspace, used for every run.

**One compose file, one entry point** (owner, 2026-11-23). The whole rig is one docker-compose file. A single reverse proxy (nginx, if it proves workable) is the only published endpoint and reaches every service: the REAPI endpoint, the registry and Buildbarn's browser. The owner also wants cache hits asserted as acceptance tests for named scenarios.

Working positions on that, proposed here and not yet confirmed:

- The proxy routes by path. REAPI paths (`/build.bazel.remote.execution.v2.*`, `/google.bytestream.*`) and registry paths (`/v2/*`) do not collide. Whether one cleartext nginx port can serve gRPC and HTTP/1.1 together is recalled from the nginx 1.25.1 changes and is not verified; spike 1 proves it. The fallback is two ports on the same proxy.
- The proxy writes one JSON access log. It is the witness for registry requests and bytes, which only a server can report.
- A cache hit is asserted from Bazel's own output (the build event file and the execution log), not from the proxy log. Bazel reports a hit per action directly. The proxy log shows only gRPC calls, and a hit would have to be inferred from them.
- Only one check ships to users: the symlink conformance test (earlier discussion, owner, 2026-11-18), because backends differ on whether they keep relative symlinks. It reads Bazel's output only, since a user's cluster has no proxy. Every other check is rig-only and may read the proxy log. Corrected on 2026-11-23: an earlier version of this block wrongly treated the cache-hit checks as shipped too.
- Tests are isolated by a cache-silo key in the execution properties, one key per test. No reset endpoint and no volume wipe between tests. Whether Buildbarn's reference configuration accepts an arbitrary extra property is not verified.
- Executors keep `network_mode: none`. The proxy must not give them a route to the registry.
- The lane runs on Linux only, because the other CI hosts cannot run the compose file.

**For the loop (2026-11-25).** The run builds this rig. The block above is its specification, and the hand-off ratifies it.

- The `ocx` under test is the build of the ocx pull request and never a released one (Intent, "Order that the releases force"). The rig hands it to rules_ocx through the download source that rules_ocx already lets a caller set.
- The rig runs in two places: on the run's host, and in rules_ocx CI on Linux. The macOS and Windows legs of rules_ocx CI run the local-execution tests only.
- The rig uses a compose project name and ports of its own, because other sessions' containers run on the same host.
- The "Spikes before the ADR" below are the run's first work, before its architecture step fixes the design.

**How each result is observed.**

- Registry requests and bytes: the registry's access log.
- Action inputs, output digests and the number of extraction actions: Bazel's execution log.
- "Network blocked" on the client: a network namespace with no route, not a flag.

**Baseline first.** The same example is run with rules_ocx 0.5.1 on the rig before any change. The 17 checks are pass or fail only; the baseline is what makes "better" measurable. Numbers recorded for old and new:

- Wall time of a cold client fetch.
- Registry requests and bytes, per platform.
- On a second fresh client that shares the cache: registry requests and extraction actions run.
- Whether the build passes at all on executors without network.

**Spikes before the ADR, in this order.** Each one closes an open question above.

1. The rig stands up and the baseline is recorded.
2. Two machines export the same package; the directories are compared byte for byte.
3. A tree with relative symlinks is used as an action input on both backends.
4. A fresh client builds on 9.3.0 with the remote repo contents cache on, then off.
5. A build for one platform is checked for fetches of other platforms' repositories.
6. The launcher finds its trees inside an action, on Linux and on Windows.
7. Mach-O output is compared across two machines.
