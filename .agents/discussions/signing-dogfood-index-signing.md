## Intent

Owner, 2026-11-13, for the whole effort: "I want to target a loop, we need to dogfood the signing now, that is adopting the indexbot, catalog, ocx-mirror and ocx. This should be done in a none-breaking way."

Index signing was designed on 2026-11-13 (`.claude/artifacts/adr_publisher_trust_distribution.md` § Sequencing, item 4) and never built. The owner put it in scope with `ocx.sh` rolled out to `warn`, because a mirror cannot re-sign an index before index signing exists, and until then the index server can rewrite `publishers` for a fresh client.

Non-breaking, as this discussion uses it *(Claude's reading)*: no existing install, config file, published package or index entry stops working. New checks ship opt-in or as a warning. Flipping a default to refuse is a later owner step. One exception, granted by the owner on 2026-11-25: `config.toml` breaks where `[trust.sigstore]` is replaced by the address-keyed Sigstore tables.

Out of scope: the `ocx.sh` index signature at `enforce`; building the mirror of the Sigstore TUF repository, whose design is settled under Decisions (a follow-up); a signature check on the managed configuration payload and the rotation of its signer (a follow-up); Rekor v2 ([ocx-sh/ocx#107](https://github.com/ocx-sh/ocx/issues/107)); every mirror feature (the second loop); the index bot's rules for `publishers` and the catalog badges (the parked discussion above); adding `publishers` or a signature to the production index, cutting a release and merging (the owner's acts).

- **Sigstore instance tables.** `[sigstore."<host>"]` tables replace `[trust.sigstore]`; each carries `trusted_root` or `trusted_root_json` and, by the default under Open questions, `fulcio_url` and `rekor_url`. A leftover `[trust.sigstore]` is refused with a message that names the new table, never ignored as an unknown key. What follows the table moves with it: the six trust-root sources in `website/src/content/docs/explanation/signing.mdx`, the system lock, the managed-payload rules for `trusted_root_json`, `fulcio_url` and `rekor_url`, `ocx config push`, the generated schema, and the defaults of `ocx package sign`, `ocx package attest` and `ocx package push`, where the host of `--fulcio-url` selects the table.
- **Instance named on the signer entry.** The `sigstore` field of a keyless signer entry becomes usable in an index `publishers` entry, in an `index_publishers` entry and in an operator `[[trust.policy]]` signer. It selects a locally configured table and never defines one *(Claude's reading of the last clause)*. An entry without the field means the public instance, and an entry naming a host with no table matches nobody. There is no registry-level `sigstore` key.
- **`ocx index sign`.** One signature over the exact bytes of `c/index.json`, served beside it, with an `expires` date in the signed catalog. It signs with a key or keylessly, with the signing flags of `ocx package sign` (Decisions).
- **Client check.** On the remote-to-local write path the client checks the index signature against a signer list in the `publishers` vocabulary: built in for `ocx.sh`, replaced per registry by `index_publishers`. `index_signature` is `off`, `warn` or `enforce`, and `ocx.sh` defaults to `warn`. An expired catalog is treated as the mode says and `index_expiry = "ignore"` opts out; the package-file hash is checked against its catalog entry; `--no-verify` skips the check. An index authority that arrives through a managed payload is honoured only from a digest-pinned source or a local tier (default under Open questions).
- **Catalog schema and its readers.** `schema/c-index.schema.json` in `ocx-sh/index` admits the signature fields (it sets `additionalProperties: false` today). The index bot and the catalog renderer keep working on a signed catalog *(the renderer is Claude's addition; neither was read for this)*.
- **`ocx.sh` signing job and expiry alert.** The deploy workflow of `ocx-sh/index` signs the catalog keylessly on every change and weekly, with 30 days validity, and an alert that runs outside the index repository fires when `expires` is less than 21 days away. Both land by pull request and are proven in `ocx-sh/e2e-index`; the first production run is the owner's. The signing job must be deployed before a client with the `warn` default is released.
- **`ocx package sbom` and dependencies.** A flag pair, `--dependencies` / `--no-dependencies`, selects whether the SBOMs of the dependency closure are returned too; a package's SBOM never silently absorbs them. The default is under Open questions.
- **End-to-end proof in `ocx-sh/e2e-index`.** A served index signed with a key and one signed keylessly with a GitHub-issued certificate, an expired and a tampered one, a client at `warn` and at `enforce`, and the previous ocx release still installing from the signed index.
- **ocx-mirror lockstep.** ocx-mirror links `ocx_config`, `ocx_trust` and `ocx_sign`, so the configuration break is carried into `ocx-sh/ocx-mirror` in the same change series and `task satellite:verify` passes.
- **Reference documentation.** *(Claude's addition.)* The configuration reference, `website/src/content/docs/reference/environment.md`, the command-line reference and `website/src/content/docs/explanation/signing.mdx` describe the new tables, keys and command, and the ADR's item 4 is amended where Decisions depart from it. The break is announced by the commit subject and nowhere else.

## Open questions

Each default below was listed in the restate of 2026-11-25 and confirmed by the owner's yes as the working answer. The questions stay listed so the plan can overturn one with evidence, which it then reports.

- [NEEDS CLARIFICATION: What is the default of `ocx package sbom --dependencies` and what does it return?]
  Recommended: default `--no-dependencies`; with the flag, one document per package of the closure, each verified against its own `publishers`, never a merged document.
- [NEEDS CLARIFICATION: What does the `<host>` key of a `[sigstore."<host>"]` table denote?]
  Recommended: the Fulcio host — a publisher entry in an index is written by someone who cannot know an operator's local names, so the key has to be globally meaningful, and a keyless signer is a certificate from that Fulcio; Rekor, CT log and timestamp authorities are attributes of the instance.
- [NEEDS CLARIFICATION: Does an instance table keep `fulcio_url` and `rekor_url`, or take Sigstore's `SigningConfig` document beside the trusted root?]
  Recommended: keep the two keys in this loop and name nothing that blocks the document later — the client verifies Rekor v1 only ([ocx-sh/ocx#107](https://github.com/ocx-sh/ocx/issues/107)) and the document's gain is Rekor v2 and timestamp authorities, which arrive with that issue.
- [NEEDS CLARIFICATION: Until the managed configuration is signed, is an index authority from a managed payload honoured only from a digest-pinned source or a local tier?]
  Recommended: yes — it is the rule the Sigstore trust root already follows, and the same class of value.
- [NEEDS CLARIFICATION: With several Sigstore instances, which instance do `--sigstore-trusted-root`, `OCX_SIGSTORE_TRUSTED_ROOT`, `$OCX_HOME/sigstore/trusted-root.json` and the trust-root cache feed?]
  Recommended: the flag and the variable stay a one-run override for whichever instance the verification selects; the convention path and the cache become per instance, keyed by the table's host, with the public-good instance keeping today's paths.
- [NEEDS CLARIFICATION: In which order do the pull requests of this loop land?]
  Recommended: the schema in `ocx-sh/index` first (it only admits fields), then the signing job, then the client in `ocx-sh/ocx` with the lockstep change in `ocx-sh/ocx-mirror`; the loop opens them all, and the owner merges in that order and releases the client only after the signing job has run on `ocx.sh`.
- [NEEDS CLARIFICATION: Where does the expiry alert run, and whom does it tell?]
  Recommended: a scheduled workflow outside `ocx-sh/index` (in `ocx-sh/indexbot` unless the owner names another home) that fetches the served catalog and fails when `expires` is less than 21 days away, so the failed-run notification is the alert and no new credential is needed; proven against `ocx-sh/e2e-index`.

## Verification

Each check is shown red on the failing case and green on the passing one. Everything that needs a real certificate or a served index runs in `ocx-sh/e2e-index`, dispatched, never per pull request; a private Sigstore instance is exercised in the local acceptance suite (`test/sigstore/**`).

- **Index signing**: an index signed with a key and one signed keylessly verify; an expired or tampered one warns under warn and refuses under enforce; an unchanged client talking to an unsigned index behaves as before except for the `ocx.sh` warning.
- **Sigstore tables**: a keyless signature from a private instance verifies against an entry whose `sigstore` field names that instance's `[sigstore."<host>"]` table, and is refused against an entry without the field or one naming another instance; an entry naming an instance the client has no table for matches nobody; a signing command picks the table by the host of `--fulcio-url`; a `config.toml` that still carries `[trust.sigstore]` is refused with a message naming the new table; `ocx config push` and the ocx-mirror lockstep (`task satellite:verify`) pass on the new shape.
- **`ocx index sign`**: `--key` and the keyless flags behave as they do on `ocx package sign`; a keyless signature made with a GitHub-issued certificate in `ocx-sh/e2e-index` verifies under that workflow's identity and is refused under another.
- **Signing job and alert**: in `ocx-sh/e2e-index` a change and the weekly schedule each produce a fresh signature, and the alert is red against a catalog whose `expires` is under 21 days away and green otherwise.
- **`ocx package sbom`**: without the flag it returns one document; with `--dependencies` it returns one per package of the closure (as the default under Open questions has it).
- **Non-breaking**: the previous ocx release still installs from an index whose catalog is signed; a client that talks to an unsigned index other than `ocx.sh` behaves as before. The one granted exception is the `[trust.sigstore]` table (Intent).
- **Loop phases**: as under Decisions › Loop shape.
